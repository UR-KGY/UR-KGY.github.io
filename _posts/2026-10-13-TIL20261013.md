# 1부. DB 스키마 관리

## 1. Flyway 개념

> **Flyway**: DB 구조 변경을 **SQL 파일(마이그레이션)로 버전 관리**하고, 앱이 뜰 때 아직 적용되지 않은 파일만 순서대로 실행해 주는 도구

| 구성 요소 | 의미 | 비유 |
|---|---|---|
| 마이그레이션 파일 (`V1__init.sql`) | 스키마 변경 내용. **원본(Source of truth)** | 설계 변경 지시서 |
| `flyway_schema_history` 테이블 | 어떤 파일을 언제 적용했는지 기록 | 출석부 |
| 체크섬 | 적용된 파일 내용의 지문. 파일이 바뀌면 불일치로 기동 실패 | 봉인 스티커 |

**ddl-auto와 비교**

| 방식 | 하는 일 | 문제 |
|---|---|---|
| `update` | 엔티티 보고 **추가만** 함 | 컬럼 삭제·이름 변경·제약조건 정리 불가, 기록이 없음 |
| `validate` | 테이블·컬럼·타입이 **있는지만** 검사 | NOT NULL, 길이, 인덱스, enum 값은 검사 안 함 |
| **Flyway + validate** | Flyway가 구조를 만들고, validate가 엔티티와 맞는지 확인 | (현재 방식) |

**기동 순서**: Flyway 마이그레이션 → Hibernate validate → 앱 시작. 그래서 마이그레이션이 빠지면 validate에서 기동 실패한다.

**의존성 (build.gradle)**

```gradle
implementation 'org.springframework.boot:spring-boot-starter-flyway'
implementation 'org.flywaydb:flyway-mysql'
```

## 2. V1 마이그레이션 만들기

깨끗한 로컬 DB를 `ddl-auto=create`로 만든 뒤, 그 구조를 mysqldump로 뽑았다.

```bash
# MySQL이 Docker 컨테이너라서 docker exec로 실행
PW=1234
docker exec {mysql컨테이너} mysqldump -uroot -p"$PW" \
  --no-data --skip-comments --skip-add-drop-table swordmaster_clean \
  > src/main/resources/db/migration/V1__init.sql
```

| 결과 | 내용 |
|---|---|
| 테이블 8개 | `battle_histories`, `currency_histories`, `idempotency_keys`, `player_artifacts`, `player_currencies`, `players`, `shop_purchase_logs`, `users` |
| 엔진 / 정렬 | InnoDB / `utf8mb4_unicode_ci` |
| `FOREIGN_KEY_CHECKS=0` 헤더 유지 | mysqldump는 테이블을 **알파벳순**으로 출력 → 외래키 순서 문제 방지 |
| 자동 생성 제약조건 이름 (`UKr2bd…`, `FK3rfv…`) | 그대로 두기로 결정 |

- **파일 위치**: `src/main/resources/db/migration/` (Flyway 기본 경로)
- **파일 이름 규칙**: `V{버전}__{설명}.sql` (언더스코어 **2개**). 팀 규칙은 타임스탬프 버전 `V20261020_1530__add_xxx.sql`

## 3. 운영 RDS 초기화와 적용 확인

Flyway는 **테이블이 있는데 history 테이블이 없는 DB**에서는 실행을 거부한다. 기존 RDS는 `ddl-auto=update`로 만든 테이블이 있었으므로 비우고 시작했다.

| 단계 | 내용 |
|---|---|
| 1 | SSM으로 EC2 접속 → Docker MySQL 클라이언트로 RDS 접속 |
| 2 | `swordmaster` DB의 테이블 전부 삭제 (사용자 데이터 없음 확인) |
| 3 | deploy-test push → CI/CD → 인스턴스 새로 고침 |
| 4 | 새 서버 기동 시 Flyway가 V1 적용 |

**확인**

```sql
SELECT version, description, type, success FROM flyway_schema_history;
-- 1 | init | SQL | 1

SELECT COUNT(*) FROM users;
-- 0
```

- CloudWatch 로그에서 `flywaydb`로 검색하면 거의 안 나온다. 로거 이름이 `o.f.core…`로 **축약**되기 때문. `Migrating`, `migration`으로 검색한다.
- 예전 `update` 시절에 남아 있던 중복 UNIQUE(`uk_shop_purchase_user_request`)도 함께 사라졌다.

## 4. 앞으로의 마이그레이션 규칙

| 규칙 | 이유 |
|---|---|
| **적용된 파일은 절대 수정 금지** | 체크섬 불일치 → 모든 서버 기동 실패 |
| 변경은 **새 파일에 차이(delta)만** | V1을 복사해 고치는 것이 아님 |
| 롤백 = **되돌리는 새 마이그레이션** | Flyway 무료판에 undo 없음. 삭제된 데이터는 복구 불가 → 스냅샷 |
| 엔티티 변경 PR에는 마이그레이션 파일 필수 | 없으면 prod validate 실패 |
| `ENGINE=MyISAM` 금지 | RDS 자동 백업의 시점 복구는 InnoDB만 지원 |

**prod 설정**

```properties
spring.jpa.hibernate.ddl-auto=validate
spring.flyway.enabled=true
spring.flyway.baseline-on-migrate=false
```

## 5. deploy-test → develop PR

| PR 화면 표시 | 의미 |
|---|---|
| All checks have passed | **최신 커밋**의 워크플로가 성공 |
| 커밋 목록의 ✗ | 그 커밋 push 때의 Actions 실패 **기록**. 머지를 막지 않음 |
| No conflicts | 자동 병합 가능 |

- 워크플로 트리거가 `deploy-test` push라서 **develop에 머지해도 배포되지 않는다.**
- 실패했던 커밋: OIDC 신뢰 정책 불일치 2건, 컴파일 오류가 있는 상태로 커밋한 것 2건.
- 팀원 공지: 로컬에 `SPRING_FLYWAY_ENABLED=false`, 운영 DB 초기화로 재가입 필요, 엔티티 변경 시 마이그레이션 파일 필수.

**이후 develop → deploy-test 반영 흐름**

```bash
git checkout deploy-test
git fetch origin
git diff deploy-test origin/develop --stat -- src/main/resources/db/migration/   # 마이그레이션 추가 여부 확인
git merge origin/develop
# 로컬 기동 확인 후 push
```

## 6. 로컬 실행과 Flyway

로컬 DB에는 `update`로 만든 테이블이 이미 있어서, Flyway가 켜진 채로 기동하면 실패한다.

| 방법 | 내용 | 특징 |
|---|---|---|
| A. 로컬은 Flyway 끄기 (현재 임시) | IntelliJ 환경변수 `SPRING_FLYWAY_ENABLED=false` | 가장 빠름 |
| B. 로컬 DB 비우고 Flyway로 생성 | `DROP DATABASE` → 재생성 → 기동 | 가장 깨끗함 (팀 정책 A안) |
| C. baseline | `SPRING_FLYWAY_BASELINE_ON_MIGRATE=true` 1회 | V1을 실행 없이 "적용됨" 표시. 기존 차이가 남음. **prod 금지** |

- 환경변수 `SPRING_FLYWAY_ENABLED` → 프로퍼티 `spring.flyway.enabled` (relaxed binding: `_` → `.`, 대문자 → 소문자). 환경변수가 properties 파일보다 우선.

# 3부. 운영 안전장치

## 7. ASG 스케일링 정책 비활성화

**이유**: STOMP가 `SimpleBroker`(서버 메모리 안의 우체국)를 쓰기 때문에, 서버가 2대가 되면 **다른 서버에 붙은 사용자에게 채팅이 전달되지 않는다.**

```
[철수] ── 서버 A (SimpleBroker A) ──▶ A에 붙은 사람만 받음
[영희] ── 서버 B (SimpleBroker B)     ✗ 철수 메시지 못 받음
```

| 영향 | 이유 |
|---|---|
| 채팅, 공지가 일부에게만 감 | 브로커가 서버별로 나뉨 |
| 시트 데이터가 서버마다 다를 수 있음 | 각 서버가 기동 시점의 시트를 메모리에 보관 |
| REST API는 문제없음 | JWT는 무상태, 데이터는 RDS·Valkey에 공유 |

| 선택지 | 결정 |
|---|---|
| ASG max 2 → 1 | ✘ 최소 정상 100% 새로 고침과 충돌 가능 (새 서버 띄울 자리 없음) |
| **max 2 유지 + 스케일링 정책 비활성화** | ✔ 자동 확장만 막고, 배포 때는 잠깐 2대 허용 |

- 위치: EC2 → Auto Scaling 그룹 → `swordmaster-asg` → **자동 크기 조정** 탭 → 정책 선택 → 작업 → 비활성화
- 배포(인스턴스 새로 고침) 중 몇 분은 여전히 2대 → 테스트 중 배포는 팀에 공지
- sticky session으로는 해결 안 됨. 근본 해결은 Redis Pub/Sub 같은 외부 브로커

**시트 데이터 변경**: 서버가 **기동 시 1회** 시트를 읽어 메모리에 둔다 → 바꾸면 재시작 필요 → ASG에서는 인스턴스 새로 고침 (**Skip matching OFF** 필수, 시작 템플릿이 그대로이므로).

## 8. RDS 삭제 방지, 자동 백업, 스냅샷

### 개념

| 설정 | 막는 사고 | 비유 |
|---|---|---|
| **삭제 방지** | 콘솔에서 실수로 DB 삭제 | "철거 금지" 팻말 |
| **자동 백업** | 잘못된 마이그레이션, 실수한 DELETE → 보존 기간 내 **원하는 시점(초 단위)**으로 복구 | 매일 녹화되는 CCTV |
| **수동 스냅샷** | 위험 작업 전 기준점 보관 | 게임 세이브 파일 |

> **스냅샷 = 현 시점 DB 인스턴스 전체의 복제본.** 단, 바로 열어볼 수 없고 **새 RDS 인스턴스로 복구**해야 쓸 수 있다.

| | 자동 백업 | 수동 스냅샷 |
|---|---|---|
| 주체 | AWS가 매일 | 내가 직접 |
| 보관 | 보존 기간 후 자동 삭제 | **직접 지울 때까지** |
| DB 삭제 시 | 함께 삭제 | **남음** |
| 복구 시점 | 기간 내 아무 시점 | 찍은 순간만 |

**복구 흐름** (기존 DB를 덮어쓰지 않음)

```
스냅샷 ─복구─▶ 새 RDS (새 엔드포인트, SG rds-sg / 같은 서브넷 그룹 지정)
             ─▶ Parameter Store DB_HOST 변경 ─▶ 인스턴스 새로 고침 (Skip matching OFF)
             ─▶ 확인 후 기존 DB 삭제
```

### 실습 내용

| 항목 | 값 |
|---|---|
| 삭제 방지 | ✔ |
| 백업 보존 기간 | **1일** (7일 시도 → 프리 플랜 제한 오류) |
| 적용 | 즉시 적용 |

- 백업 0일 → 1일 이상으로 바꾸면 DB가 잠깐 재시작될 수 있다.
- 백업 저장소는 DB 크기만큼 무료. 초과분은 크레딧 차감.
- "자동 백업은 InnoDB만 지원" 안내는 경고가 아님 (MySQL 8 기본 엔진이 InnoDB).
- 1일 보존의 보완책: **위험 작업 직전 수동 스냅샷** (`before-{작업}-{날짜}`). 지금까지 찍은 수동 스냅샷은 없음.

```bash
aws rds create-db-snapshot \
  --db-instance-identifier {DB식별자} \
  --db-snapshot-identifier before-{작업}-{날짜}
```

| 스냅샷 찍을 때 | 예 |
|---|---|
| 컬럼·테이블 삭제/변경 마이그레이션 배포 직전 | `before-v20261020-1530` |
| 운영 DB 직접 DELETE/UPDATE 전 | `before-manual-fix-20261015` |
| 통합 테스트 종료 시 | `after-integration-test` |

- 단일 AZ RDS는 스냅샷 시작 시 수 초간 I/O가 멈출 수 있음 → 사용자 적은 시간에.

# 4부. 알림

## 9. CloudWatch 알람 + SNS

> 로그와 지표(CCTV)는 있었지만 **경비원이 없던** 상태. 알람은 이상을 감지하면 메일로 알려 주는 화재경보기.

| 구성 요소 | 역할 |
|---|---|
| CloudWatch 알람 | 지표를 감시하다 조건을 넘으면 ALARM (감지기) |
| SNS 토픽 | 알람 메시지를 구독자에게 전달 (방송실) |
| 이메일 구독 | 받는 사람. **Confirm subscription 필수** |

| 알람 상태 | 의미 |
|---|---|
| 정상 (OK) | 조건 미달 |
| 경보 (ALARM) | 조건 초과 |
| 데이터 부족 | 지표 없음 (생성 직후, 또는 원래 기록이 없는 지표) |

**SNS 설정**: SNS → 주제 → 생성 (표준, `swordmaster-alerts`) → 구독 생성 (이메일) → 메일에서 확인 → 상태 **확인됨**

## 10. 알람 3개 만들기

공통: 경보 상태 → `swordmaster-alerts`, **정상(OK) → `swordmaster-alerts`** (복구 메일도 받기)

| 알람 | 지표 | 통계 / 기간 | 조건 | 데이터 포인트 | 누락 데이터 |
|---|---|---|---|---|---|
| `swordmaster-no-healthy-host` | `HealthyHostCount` (AppELB별, TG별) | 최소 / 1분 | `< 1` | 2/2 | **위반** |
| `swordmaster-target-5xx` | `HTTPCode_Target_5XX_Count` (AppELB별, TG별) | 합계 / 5분 | `>= 5` | 1/1 | **정상** |
| `swordmaster-rds-low-storage` | `FreeStorageSpace` (데이터베이스별) | 최소 / 5분 | `< 2147483648` (2GB) | 2/2 | 무시 |

**설계 포인트**

| 포인트 | 이유 |
|---|---|
| Unhealthy 수가 아니라 **Healthy가 0대인지** 감시 | 서버가 아예 종료되면 Unhealthy도 0 → 알람이 안 울리는 빈틈 |
| AZ별이 아니라 **TG별** 지표 | 대상 그룹 전체 기준으로 판단 |
| Healthy 알람의 누락 = **위반** | 항상 기록되는 지표라 누락 자체가 이상 |
| 5xx 알람의 누락 = **정상** | 에러가 없으면 기록 자체가 없음. "위반"으로 두면 계속 울림 |
| Target 5xx (앱)만 감시 | ELB 5xx는 대부분 서버가 죽었을 때 → Healthy 알람이 잡음 |
| 4xx는 감시 안 함 | 401, 400은 정상 흐름이 많아 소음 |
| RDS 임계값은 **바이트** | `2`나 `2GB` 입력 시 영원히 안 울림 |

**지표가 목록에 없을 때** (5xx가 한 번도 없어서 기록 없음): HealthyHostCount 행 선택 → **소스** 탭 → `"HealthyHostCount"`를 `"HTTPCode_Target_5XX_Count"`로 바꾸고 업데이트. 네임스페이스와 차원(LoadBalancer, TargetGroup)이 같으니 이름만 바꾸면 된다.

**경보 생성 입구**: CloudWatch → 경보 → 모든 경보 → 경보 생성 → 지표 선택 → **찾아보기**. EC2/ASG 화면에서 들어가면 CPU 같은 그 리소스 지표만 보인다.

## 11. 알림 테스트

```bash
aws cloudwatch set-alarm-state \
  --alarm-name swordmaster-no-healthy-host \
  --state-value ALARM \
  --state-reason "알림 테스트"
```

| 시점 | 결과 |
|---|---|

| 1~2분 후 | 다음 평가에서 실제 지표로 덮어씀 → `OK` 메일 |

# 5부. 헬스체크

## 12. Actuator health 그룹

```json
{"groups":["liveness","readiness"],"status":"UP"}
```

| 필드 | 의미 |
|---|---|
| `status` | **전체 검사**(DB, Redis, 디스크 등 모두 합친 것)의 결과 |
| `groups` | 따로 조회할 수 있는 **하위 그룹 목록** (결과가 아님. 건물 안내판) |

| 경로 | 검사 내용 (기본) | DOWN이 되는 때 |
|---|---|---|
| `/actuator/health` | DB, Redis, 디스크, 앱 상태 전부 | 하나라도 DOWN |
| `/actuator/health/readiness` | `readinessState`만 | 기동 중 (`ApplicationReadyEvent` 전), 종료 시작 |
| `/actuator/health/liveness` | `livenessState`만 | 회복 불가 상태 (거의 없음) |

- 최신 Spring Boot는 두 그룹이 기본 활성화 (예전엔 `management.endpoint.health.probes.enabled=true` 필요).
- 상세 항목은 기본적으로 숨김. 확인용: `management.endpoint.health.show-components=always`

**두 개의 층을 구분**

| 층 | 질문 | 상태 (변경 전) |
|---|---|---|
| ① Actuator | readiness 주소가 **존재하나?** | ✅ (`groups`에 표시) |
| ② Spring Security | 인증 없이 **들어갈 수 있나?** | ❌ `/actuator/health`만 허용 → 401 |

```
요청 /actuator/health/readiness
   ↓
[② Security] 문을 먼저 통과해야
   ↓
[① Actuator] 방에 도착
```

## 13. readiness 전환

### Security 경로 패턴

```java
// 변경 전: 정확히 그 경로 하나만
.requestMatchers(HttpMethod.GET, "/actuator/health").permitAll()
// 변경 후: 자기 자신 + 모든 하위 경로
.requestMatchers(HttpMethod.GET, "/actuator/health/**").permitAll()
```

| 패턴 | `/actuator/health` | `/actuator/health/readiness` |
|---|---|---|
| `/actuator/health` | ✔ | ✘ |
| `/actuator/health/*` | ✘ | ✔ |
| **`/actuator/health/**`** | ✔ | ✔ |

- `/actuator/**`로 넓히지 않는다 (나중에 다른 엔드포인트를 노출하면 인증 없이 열림).

### 502 사고

```
대상 그룹 경로를 readiness로 먼저 변경 (Security는 아직 /actuator/health만 허용)
  → 401 → ALB: Unhealthy
  → ASG(ELB 헬스체크): 서버 종료 후 새로 생성
  → 새 서버 기동 중 요청 → 502
  → 새 서버도 401 → 교체 반복
```

**복구**: 대상 그룹 경로를 `/actuator/health`로 되돌림 → 새 서버 Healthy 대기 (2~3분)

### 올바른 순서

| 단계 | 내용 | 확인 |
|---|---|---|
| 1 | `FilterConfig`를 `/actuator/health/**`로 수정 | 기존 경로도 허용되므로 배포 안전 |
| 2 | deploy-test push → 인스턴스 새로 고침 완료 대기 | 새로 고침 탭 "성공" |
| 3 | `GET http://{ALB주소}/actuator/health/readiness` | **200 + `{"status":"UP"}`을 직접 확인** |
| 4 | 대상 그룹 → 상태 검사 → 경로 `/actuator/health/readiness` | 대상 탭 Healthy 유지 |

> **구성 변경의 원칙**: ① 새 설정이 동작할 조건을 먼저 갖추고 → ② 동작하는지 직접 확인한 뒤 → ③ 전환한다.

## 14. 헬스체크 설계 원칙

> ASG가 ELB 헬스체크를 쓰는 구조에서 **헬스체크 경로는 서버 생사를 결정하는 스위치**다.

| 상황 | `/actuator/health` (DB·Redis 포함) | `/actuator/health/readiness` |
|---|---|---|
| Redis 1분 끊김 | 모든 서버 DOWN → **멀쩡한 서버 교체 반복** | 서버 유지, 해당 API만 에러 → **5xx 알람** |
| Redis 복구 | 새 서버 뜰 때까지 추가 중단 | 즉시 정상 |
| 앱 기동 중 | DOWN | DOWN (트래픽 안 받음) |
| 앱 자체 고장 | DOWN → 교체 | DOWN → 교체 |

| 감지 대상 | 담당 | 결과 |
|---|---|---|
| 서버(앱) 자체 문제 | readiness 헬스체크 | 트래픽 제외 + ASG 교체 |
| 외부 의존성 (RDS, Valkey) | 5xx 알람, CloudWatch 로그 | 사람에게 메일 |

- 이런 문제를 **연쇄 장애(cascading failure)**라고 한다. "헬스체크에 외부 의존성을 넣지 말라"가 일반 원칙.
- readiness는 시트 검증, Flyway가 끝나기 전에는 UP이 되지 않으므로 기동 실패 서버가 트래픽을 받지 않는다.
