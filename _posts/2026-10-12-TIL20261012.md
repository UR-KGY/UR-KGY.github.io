## 0. 한눈에 보는 차이

| 구분 | 실습 | swordmaster 구축 |
|---|---|---|
| 목적 | 기능을 하나씩 익히기 | 클라이언트가 실제로 접속할 운영 구조 |
| 진행 방식 | 기능별로 만들고 지우기 반복 | 한 번 만든 뒤 **계속 유지** |
| 서버 위치 | 퍼블릭 → (NAT 실습에서) 프라이빗 | **처음부터 프라이빗** |
| NAT | 실습 후 **삭제** | **상시 유지** |
| EC2 접속 | SSH(22번) → Session Manager | **처음부터 Session Manager만** (키 페어 없음) |
| 설정·비밀값 | 이미지/서버에 직접 (Parameter Store는 TODO) | **Parameter Store** (SecureString) |
| 배포 단위 | 서버는 그대로, **컨테이너만 교체** (SSM send-command) | **서버 자체를 교체** (인스턴스 새로 고침) |
| 이미지 버전 지정 | `latest` 태그 | Parameter Store의 **`IMAGE_TAG`** |
| 로그 | CloudWatch **Agent** (파일 로그 + 메모리 지표) | Docker **awslogs 드라이버** (컨테이너 로그만) |
| 자동 확장 | 정책 없음 (TODO) | **CPU 60% 대상 추적** (1~2대) |
| 캐시 | ElastiCache (실습만) | **Valkey를 앱에 실제 연결** |

## 1. 전체 구성 비교

### 실습

```
사용자 ── IGW ── ALB (퍼블릭 2a·2b, :80)
                   │
                   ▼ 8081
                 EC2 (프라이빗 2a·2b) ← ASG
                   │ (나가는 요청: docker pull, SSM)
                   ▼
                 NAT (퍼블릭 2a) ── IGW ── ECR / SSM

GitHub push ─▶ Actions(OIDC) ─▶ ECR push ─▶ SSM send-command로 각 서버 컨테이너 교체
```

### swordmaster

```
사용자 ── IGW ── ALB (퍼블릭 2a·2c, :80, 유휴 타임아웃 300초)
                   │
                   ▼ 8080
                 EC2 (프라이빗 2a·2c) ← ASG (1~2대, CPU 60%)
                   │   └─ 부팅 시: Parameter Store에서 IMAGE_TAG·비밀값 읽고 실행
                   ├──▶ RDS MySQL 8.4 (validate)
                   ├──▶ ElastiCache Valkey (TLS, 클러스터 모드 샤드 1)
                   └──▶ NAT ── IGW ── ECR / SSM / Parameter Store / CloudWatch / Google Sheets

GitHub push(deploy-test) ─▶ Actions(OIDC) ─▶ ECR push ─▶ IMAGE_TAG 갱신 ─▶ ASG 인스턴스 새로 고침
```

## 2. 네트워크와 보안 그룹

### 2-1. 서브넷과 NAT

| 항목 | 실습 | swordmaster | 이유 |
|---|---|---|---|
| AZ | 2a, 2b | 2a, 2c | VPC 설계 차이 (기능상 차이 없음) |
| EC2 서브넷 | 처음엔 퍼블릭, NAT 실습에서 프라이빗으로 이동 | **처음부터 프라이빗** | 운영 구조를 바로 적용 |
| NAT | 실습 후 삭제 (비용) | **상시 유지** | 프라이빗 EC2가 ECR, Parameter Store, Google Sheets에 접근하려면 필수 |

### 2-2. 보안 그룹

| 역할 | 실습 | swordmaster |
|---|---|---|
| ALB | `webcraft-alb`: 80 ← `0.0.0.0/0` | `alb-sg`: 80 ← **내 IP로 시작** → 검증 후 `0.0.0.0/0` |
| EC2 | `webcraft-app`: 8081 ← ALB SG, **22 ← 내 IP** | `app-sg`: 8080 ← `alb-sg` (**22번 없음**) |
| DB | `webcraft-data`: 3306·6379 ← app (**RDS와 캐시가 하나의 SG**) | `rds-sg`: 3306 ← `app-sg` |
| 캐시 | (위와 공용) | `valkey-sg`: 6379 ← `app-sg` (**분리**) |

- **ALB를 내 IP로 시작한 이유**: health가 401이라 대상이 전부 Unhealthy인 상태에서 ALB를 붙였다. 이때 **fail-open**으로 모든 요청이 서버에 그대로 전달되므로, 외부 노출을 막으려고 내 IP만 허용했다.
- **DB와 캐시 SG를 나눈 이유**: 포트별로 출입문을 분리하면 한쪽 규칙을 바꿀 때 다른 쪽에 영향이 없다.
- **ElastiCache `default` SG**: 데모 구성으로 만들면 `default` SG가 붙어서 `valkey-sg`로 교체했다 (실습에는 없던 함정).

## 3. IAM 역할

### 3-1. EC2 역할

| 권한 | 실습 `webcraft-ec2-role` | swordmaster `sword-master-ec2-role` |
|---|---|---|
| Session Manager | `AmazonSSMManagedInstanceCore` | 같음 |
| ECR 읽기 | `AmazonEC2ContainerRegistryReadOnly` | 같음 |
| CloudWatch | `CloudWatchAgentServerPolicy` (**관리형, 범위 넓음**) | 인라인 `swordmaster-cloudwatch-logs` (**`/swordmaster/prod/*` 로그 그룹만**, `CreateLogGroup` 제외) |
| S3 | `ci-demo-deploy-read` (jar 배포용) | 없음 (jar 방식 안 씀) |
| **Parameter Store** | 없음 (TODO) | 인라인: **`/swordmaster/prod/*` 읽기** |

### 3-2. GitHub Actions 역할

| 항목 | 실습 `github-actions-ci-demo` | swordmaster `github-actions-swordmaster-deploy` |
|---|---|---|
| 허용 브랜치 | `ci-demo` 저장소 `main` | `upgrade-29/swordmaster-server` **`deploy-test`** |
| `sub` 형식 | **숫자 ID 포함** (`{아이디}@{숫자}/ci-demo@{숫자}`) | **숫자 ID 포함** (조직 설정) → **같은 오류를 두 번 겪음** |
| ECR | push | push (`swordmaster` 저장소만) |
| 서버에 명령 | `ssm:SendCommand` (`App=ci-demo` 태그 서버만) | **없음** |
| 배포 트리거 | ASG 서버 목록 조회 + SendCommand | `ssm:PutParameter` (**IMAGE_TAG 하나만**) + `autoscaling:StartInstanceRefresh` (`swordmaster-asg`만) |
| 비밀값 접근 | - | **불가** (JWT, DB 비밀번호는 읽을 수 없음) |

> **핵심 차이**: 실습은 GitHub가 **서버 안에서 명령을 실행**할 수 있었다. swordmaster는 GitHub가 **"버전 이름표를 바꾸고 교대를 지시"**만 할 수 있다. 서버 안에 들어갈 권한이 없어서 더 안전하다.

## 4. 설정값과 비밀값 관리

| 항목 | 실습 | swordmaster |
|---|---|---|
| DB 비밀번호, JWT 키 | 이미지나 서버에 직접 (Parameter Store 연동은 TODO) | **Parameter Store** (`/swordmaster/prod/*`, SecureString) |
| 전달 방식 | - | 부팅 스크립트가 읽어 `docker run -e`로 전달 |
| prod 설정 파일 | - | `application-prod.properties`에 **`${…}` 자리표시자만** → Git 관리 대상으로 전환 |
| 이미지 버전 | `latest` 태그 | **`IMAGE_TAG`** 파라미터 (검증된 날짜 태그만) |

- **`latest` 대신 `IMAGE_TAG`를 쓴 이유**: 오늘 enum 문제로 **기동에 실패하는 이미지**를 push한 적이 있다. `latest`를 썼다면 그 순간 이후 새로 뜨는 서버가 **모두 기동 실패**했을 것이다. `IMAGE_TAG`는 사람이(또는 CI가) 명시적으로 바꿀 때만 반영된다.

## 7. 배포 방식 (CI/CD)

| 항목 | 실습 C (ECR + SSM, ASG 단계) | swordmaster |
|---|---|---|
| 트리거 | `main` push | `deploy-test` push (+ 수동 실행 버튼) |
| 빌드 | QEMU + buildx `linux/arm64` | 같음 (`provenance/sbom: false`) |
| 태그 | `{sha}` + `latest` | `v{날짜-시각}-{sha 7자리}` (**한 개, 겹치지 않음**) |
| 반영 방법 | ASG 서버 목록 조회 → **SSM으로 각 서버의 컨테이너 교체** (롤링) | **IMAGE_TAG 갱신 → 인스턴스 새로 고침** (서버 교체) |
| 서버 | **그대로 유지** | **새 서버로 교체** |
| 동시 실행 방지 | - | `concurrency: deploy-prod` |
| 로그의 계정 ID | - | `mask-aws-account-id: true` |

### 두 방식의 장단점

| | 컨테이너만 교체 (실습) | 서버 교체 (swordmaster) |
|---|---|---|
| 속도 | 빠름 (1~2분) | 느림 (5~8분) |
| 서버 상태 | 오래 쓰면 서버마다 상태가 달라질 수 있음 | **항상 시작 템플릿과 같은 깨끗한 서버** |
| GitHub 권한 | 서버에 명령 실행 (넓음) | 이름표 변경 + 교대 지시 (좁음) |
| 시작 템플릿 변경 반영 | 별도로 서버 교체 필요 | **같은 과정으로 함께 반영** |

## 9. ElastiCache 연결 방식

| 항목 | 실습 노트 | swordmaster 현재 |
|---|---|---|
| 엔드포인트 | 구성 엔드포인트 (`clustercfg.`) | 같음 (데모 구성이 **클러스터 모드 활성화**) |
| Spring 설정 | **`spring.data.redis.cluster.nodes`** + `lettuce.cluster.refresh.adaptive=true` | **`spring.data.redis.host`** |
| TLS | `ssl.enabled=true` | 같음 |
| 평가 | 클러스터 모드에 맞는 정석 | 샤드 1·복제본 0이라 **지금은 동작** |

> **알려진 위험**: 샤드나 복제본을 추가하는 순간 `MOVED` 오류가 날 수 있다. 실습 노트에 이미 정답(`cluster.nodes`)이 있으니, 확장 전에 반드시 전환한다.

## 10. 헬스 체크

| 항목 | 실습 | swordmaster |
|---|---|---|
| 경로 | `/health` (직접 만든 엔드포인트) | `/actuator/health` |
| DB·캐시 검사 포함 | ✘ | **✔ (RDS + Valkey)** |
| 인증 | 필요 없음 | Spring Security에서 막혀 **401** → `permitAll` 추가로 해결 |
| 실습 노트의 권장 | ALB에는 **`/actuator/health/readiness`** | (아직 미적용) |

> **알려진 위험**: 지금은 ALB가 DB·Valkey까지 검사한다. RDS가 잠깐 느려지면 **모든 서버가 Unhealthy → ASG가 멀쩡한 서버를 전부 교체**하는 연쇄 장애가 생길 수 있다. 실습 노트대로 readiness로 바꾸는 것을 검토한다.

## 11. 같은 실패, 다른 실패

### 두 번 모두 겪은 실패

| 실패 | 실습 | swordmaster | 교훈 |
|---|---|---|---|
| ALB **fail-open** | 서버 1대 `docker stop` → 502 | health 401 상태에서 ALB 경유 요청이 앱까지 도달 | 대상이 전부 Unhealthy면 ALB는 그래도 보낸다 → 내 IP로 막고 실험 |
| OIDC `sub` 불일치 | 개인 계정 + 숫자 ID | **조직** + 숫자 ID | 신뢰 정책은 **토큰을 출력해 보고 그대로** 적는다 |
| `exec format error` 예방 | `platforms: linux/arm64` | 같음 | t4g는 ARM |

### swordmaster에서 새로 겪은 실패

| 실패 | 원인 | 해결 |
|---|---|---|
| health **401** | Spring Security가 actuator도 막음 | `GET /actuator/health` permitAll |
| 시트 검증 실패로 **기동 반복** | 다른 브랜치의 enum 수정이 빠짐 (코드-데이터 버전 불일치) | 수정 후 재배포 (**롤백이 아니라 roll forward**) |
| `invalid reference format` | `TAG` 변수가 비어 있음 | `echo "[$TAG]"`로 확인하는 습관 |
| 붙여 넣은 명령이 실행 안 됨 | `bash`와 다른 명령을 함께 붙여 넣음 | `bash`는 단독으로 먼저 |
| Postman STOMP 응답 없음 | 끝 문자(NULL)가 지워짐 | 실제 클라이언트로 확인 |
| 인스턴스 새로 고침 **자동 롤백 비활성** | ASG가 `Default` 버전 사용 | 최소 정상 100%로 대체 |
| CI/CD 빌드에서 prod 설정 누락 위험 | `application-prod.properties`가 `.gitignore` | 비밀값이 없음을 확인하고 Git 관리 대상으로 전환 |

| ALB 유휴 타임아웃 | ✅ 300초 |
| webcraft를 ASG로 이전 (Pet → Cattle) | ✅ swordmaster를 처음부터 Cattle로 구성 |

## 13. 아직 남은 것 (실습 노트 기준으로 다시 정리)

| 항목 | 이유 | 우선순위 |
|---|---|---|
| **WebSocket + Redis Pub/Sub** | 현재 STOMP는 `SimpleBroker`(서버 메모리). ASG가 **2대로 늘면 다른 서버에 접속한 유저에게 채팅이 전달되지 않는다** | 높음 (확장 정책이 이미 최대 2대) |

| Budgets 알림 | 크레딧 소진 시점 파악 | 바로 |

# 부록 A. Hibernate `ddl-auto=validate`는 무엇을 검사하나

> **기준은 엔티티(`@Entity`)**다. Hibernate가 엔티티를 보고 "DB에 이런 테이블과 컬럼이 있어야 한다"는 목록을 만든 뒤 실제 DB와 비교한다.
> 비유: 엔티티는 **설계도**, DB는 **건물**. 검수원은 "설계도에 있는 방과 문이 건물에 있는가"만 확인하고, 설계도에 없는 방이 더 있는 것은 문제 삼지 않는다.

## A-1. 검사하는 것

| 검사 항목 | 엔티티 쪽 기준 | 실패 메시지 예 |
|---|---|---|
| 테이블 존재 | `@Entity`, `@Table(name=…)` | `Schema-validation: missing table [player]` |
| 컬럼 존재 | 필드, `@Column(name=…)`, `@JoinColumn` | `missing column [nickname] in table [player]` |
| 컬럼 타입 호환 | 필드의 Java 타입 | `wrong column type encountered in column [level]; found [varchar], but expecting [integer]` |
| ID 생성용 테이블·시퀀스 | `@GeneratedValue`가 `TABLE`/`SEQUENCE` 전략일 때 | `missing table [hibernate_sequences]` |

## A-2. 검사하지 않는 것

| 항목 | 예 | 결과 |
|---|---|---|
| DB에만 있는 테이블·컬럼 | 엔티티에서 지운 컬럼이 DB에 남음 | 통과 |
| `NOT NULL` 여부 | `nullable=false`인데 DB는 NULL 허용 | 통과 |
| 문자열 길이 | `length=30`인데 DB는 `VARCHAR(255)` | 통과 |
| 인덱스, UNIQUE, 외래 키, 기본값 | | 통과 |
| enum 값 목록 | Java enum에 값을 추가했는데 DB `ENUM('A','B')`에는 없음 | **통과 → 저장할 때 오류** |

> validate는 **"엔티티가 쓰려는 것이 DB에 있는가"**만 본다. 통과해도 **실행 중 오류**가 날 수 있으니 마지막 안전장치로 생각한다.

## A-3. 운영에서의 의미

| 상황 | 결과 |
|---|---|
| DB에 컬럼을 **먼저** 추가 → 앱 배포 | ✅ 안전 (기존 앱은 새 컬럼을 몰라도 통과) |
| 엔티티에 필드 추가, DB는 그대로 배포 | ❌ 기동 실패 (`missing column`) |
| 엔티티에서 필드 삭제, DB 컬럼은 그대로 | ✅ 통과 (단, 그 컬럼이 `NOT NULL`이면 INSERT 오류) |
| enum 값 추가 | ✅ 기동 통과, 컬럼이 MySQL `ENUM`이면 저장할 때 오류 |

**→ 원칙: "DB 먼저, 앱 나중"**

# 부록 B. 테이블 생성·변경은 어떻게 반영하나

## B-1. 지금 CI/CD로는 반영되지 않는다

지금 CI/CD는 **앱을 빌드해서 서버를 교체**할 뿐이고, 서버는 validate 모드라 **테이블을 만들거나 바꾸지 않는다.**

| 상황 | CI/CD로 배포하면 |
|---|---|
| 새 엔티티 (테이블 없음) | `missing table`로 기동 실패 |
| 필드 추가 (컬럼 없음) | `missing column`으로 기동 실패 |
| 필드 타입 변경 | `wrong column type`으로 기동 실패 |

```
push → 빌드 → 새 서버 → validate 실패 → Unhealthy
                      → 인스턴스 새로 고침이 옛 서버를 종료하지 않음 (최소 정상 100%)
                      → 서비스는 옛 버전으로 유지, 배포만 실패
```

## B-2. 방법 1: Flyway (자동, 추천)

- **AWS 서비스가 아니라 Spring 앱에 넣는 라이브러리**다.
- 개발자가 작성한 **번호 붙은 SQL 파일**을 앱이 시작할 때 **validate보다 먼저** 실행하고, 실행 기록을 RDS의 `flyway_schema_history` 테이블에 남긴다.
- 방향: **코드에 적은 변경 → RDS에 반영** (RDS 변경을 감지하는 도구가 아님)

```
src/main/resources/db/migration/
 ├─ V1__init.sql                 ← 현재 테이블 구조 (기존 DB는 baseline으로 건너뜀)
 └─ V2__add_player_nickname.sql  ← 다음 변경
```

```
push → 빌드 → 새 서버 → Flyway: 미적용 SQL 실행 → validate 통과 → 기동 성공
```

| 항목 | 내용 |
|---|---|
| CI/CD 수정 | **필요 없음** (SQL 파일이 jar에 들어감) |
| 서버 여러 대 동시 기동 | DB 잠금으로 **한 대만** 실행 |
| 기존 RDS에 처음 적용 | `spring.flyway.baseline-on-migrate=true`, `baseline-version=1` |
| 규칙 | 적용된 SQL 파일은 **절대 수정 금지** (체크섬 불일치로 기동 실패) → 새 버전 파일 추가 |
| 주의 | MySQL DDL은 롤백되지 않음 → 파일 하나에 변경을 작게 |

## B-3. 방법 2: 수동 SQL (Flyway가 없을 때)

사람이 직접 RDS에 SQL을 실행한다. RDS는 private이라 **통로**가 필요하다.

```
① 통로 열기 → ② RDS에 CREATE/ALTER 실행 → ③ 그다음 push (순서가 바뀌면 기동 실패)
```

| 주의 | 이유 |
|---|---|
| 실행한 SQL을 기록 (`docs/db-changes.md` 등) | 운영 DB가 언제, 왜 바뀌었는지 남지 않음 |
| 로컬 DB와 어긋남 | 로컬은 `update`, 운영은 수동 |
| `DROP`, 컬럼 삭제는 재확인 | 되돌리기 어려움 |
| `update` 모드로 잠깐 배포하는 방법은 쓰지 않기 | 서버 여러 대가 동시에 테이블을 고칠 수 있고 기록이 없음 |

## B-4. 비교

| | Flyway | 수동 SQL |
|---|---|---|
| 변경 방법 | SQL 파일을 코드에 추가 → push | 통로로 직접 실행 → push |
| 통로 필요 | 없음 | **필요** |
| 기록 | Git에 자동 | 사람이 따로 |
| 적합 | 변경이 잦을 때 | 변경이 가끔일 때 |

# 부록 C. Bastion, 포트 포워딩, GUI 접속

## C-1. 누가 접근하느냐에 따라 다르다

| 접근하는 쪽 | private RDS·Valkey 접근 | 이유 |
|---|---|---|
| **EC2 (앱)** | ✅ 가능 (health `UP`이 증거) | 같은 VPC + 보안그룹이 `app-sg` 허용 |
| **내 PC** | ❌ 불가 | private 서브넷이라 인터넷에서 닿지 않음 (의도한 설계) |

> "private이라 접근이 안 된다"는 것은 **내 PC에서**의 이야기다. 앱 동작을 위해 할 일은 없다.
- 이게 정말 환각없는 사실이라면 flyway 나 bastion 을 통한 내 pc 에서의 접근을 말씀하신 것. 
- 둘중 어떤 것이 난이도가 쉬운지는 모르나 이후 테이블을 수정하거나 새로 추가해야하는 상황이 온다면 필요한 기능이 맞다.

## C-2. 용어

| 용어 | 의미 | 비유 |
|---|---|---|
| **Bastion 호스트** | public 서브넷에 두는 중간 다리 서버. 외부 → Bastion → private 리소스 | 보안 구역 앞 경비 초소 |
| **포트 포워딩** | 내 PC의 포트(`localhost:3307`)를 터널로 RDS 3306에 연결 | 초소를 거쳐 금고까지 이은 전용 통로 |
| **GUI 도구** | 터널을 통해 데이터를 화면으로 보여 줌 | 금고 안을 보는 모니터 |

> Bastion은 **통로**이고, 화면은 **내 PC의 GUI 도구**가 보여 준다. 둘을 함께 써야 한다.

## C-3. 지금 구성에서는 Bastion 서버가 필요 없다 (일단 AI 판단임)

| | 전통적인 Bastion | **Session Manager 포트 포워딩** |
|---|---|---|
| 중간 서버 | public 서브넷에 새로 만듦 | **기존 private EC2 사용** |
| 22번 포트 / 키 페어 | 필요 | **불필요** (IAM으로 접속) |
| 추가 비용 | EC2 + 퍼블릭 IP | 없음 |
| 접속 기록 | 직접 관리 | CloudTrail 자동 기록 |

```
내 PC [GUI] ── localhost:3307 ── Session Manager 터널 ── EC2 (private, ASG) ── RDS:3306
```

- 필요한 것: 내 PC에 **Session Manager 플러그인**, AWS CLI, GUI 도구
- ASG가 서버를 교체하면 **인스턴스 ID가 바뀌고 터널이 끊긴다** → 다시 연결

## C-4. GUI 도구와 난이도

| 대상 | 도구 | 난이도 |
|---|---|---|
| RDS (MySQL) | IntelliJ Database, DBeaver, MySQL Workbench | **쉬움** (`localhost:3307` + DB 계정) |
| Valkey | Redis Insight, Another Redis Desktop Manager | **까다로움** |

**Valkey가 까다로운 이유**

1. **TLS 인증서 이름 불일치**: 인증서는 `clustercfg.…` 이름, 접속은 `localhost` → GUI에서 인증서 검증 끄기 필요
2. **클러스터 모드**: 클러스터 모드로 연결하면 내부 주소로 이동하라는 안내를 받는데 내 PC는 닿지 않음 → **Standalone 모드**로 연결 (샤드 1개라 모든 키 조회 가능)
3. 간단한 확인은 EC2에서 `valkey-cli --tls`가 더 쉽다

> **주의**: 운영 데이터를 직접 보는 것이므로 조회 위주로 쓴다. RDS 테이블 구조를 바꾸면 validate 때문에 다음 서버 교체 때 기동이 실패할 수 있다.
