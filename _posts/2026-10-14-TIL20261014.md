- 바스티온은 강의 과정에서 했던 것 처럼 ssh + 펨 키 인증의 ec2 를 하나 두고 rds 와 elasticashe 에 접근하는 용도로만 사용하였다.

내 PC의 ssh가 bastion EC2의 22번 포트로 접속한다.
bastion EC2는 VPC 안에서 RDS(3306)와 ElastiCache Valkey(6379)에 접근할 수 있다.

[Valkey] 내 PC에 포트를 열지 않고, bastion에 SSH로 들어가서
bastion 안에서 valkey-cli로 Valkey 6379에 접속한다.

## 1. 바스티온 vs SSM

| | 바스티온 (Bastion) | SSM Session Manager |
|---|---|---|
| 정체 | 퍼블릭 서브넷에 둔 **중간 다리 서버** | AWS가 제공하는 **원격 접속 서비스** |
| 들어가는 문 | SSH **22번을 열어 둠** | **열린 포트 없음** (서버의 에이전트가 AWS로 먼저 연결) |
| 인증 | 키 페어 (`.pem`) | IAM (콘솔 로그인 사용자 권한) |
| 기록 | 직접 설정 | CloudTrail에 접속 기록 |
| 비용 | EC2 1대 + 퍼블릭 IPv4 | 무료 |
| swordmaster 용도 | **RDS·Valkey를 GUI로 보기** | **앱 서버** 로그·컨테이너 확인 |

> 바스티온은 **보안 구역 앞 경비 초소**(바깥에 문이 있고 출입증 필요), SSM은 **건물 안에서 미리 걸어 둔 직통 전화**(바깥에 문이 없고 사원증으로 확인).

- **둘 다 함께 쓸 수 있다.** 서로 충돌하지 않는다.
- 바스티온은 **RDS·Valkey만** 연결한다. 앱 서버는 이미 SSM으로 접속되므로 22번을 새로 열지 않는다.
- 대안: 프라이빗 서브넷에 두고 **SSM으로만 접속하는 고정 접속 서버** (열린 포트·키 없음, 인스턴스 ID 고정). GUI를 자주 쓰면 이쪽이 더 안전하다.

### 다른 사람이 접근하려면 넘어야 하는 3겹

| 순서 | 관문 | 막히는 경우 |
|---|---|---|
| ① | `bastion-sg` 22번 **내 IP만** | 다른 네트워크에서 접속 → 타임아웃 |
| ② | **키 페어** | 키 파일 없음 → `Permission denied (publickey)` |
| ③ | **DB 계정·비밀번호** | 바스티온까지 와도 RDS 로그인 불가 |

> 같은 와이파이(같은 공인 IP)를 쓰는 사람은 ①을 통과할 수 있다 → **`.pem`과 DB 비밀번호 관리가 실질적인 방어선**.

## 2. 전체 구조

```
                         인터넷                       VPC
내 PC ─────SSH:22 (내 IP만)─────▶ 바스티온 (퍼블릭 서브넷, bastion-sg)
                                    ├──3306──▶ RDS     (rds-sg가 bastion-sg 허용)
                                    └──6379──▶ Valkey  (valkey-sg가 bastion-sg 허용)
```

| 보안 그룹 | 변경 |
|---|---|
| `bastion-sg` | **새로 생성**: 22 ← 내 IP |
| `rds-sg` | **규칙 추가**: 3306 ← `bastion-sg` (기존 `app-sg` 규칙 유지) |
| `valkey-sg` | **규칙 추가**: 6379 ← `bastion-sg` (기존 `app-sg` 규칙 유지) |
| `app-sg` | **변경 없음** |

## 3. 구축 단계

### 1단계: 보안 그룹 `bastion-sg`

EC2 → 보안 그룹 → 생성

| 항목 | 값 |
|---|---|
| 이름 / 설명 | `bastion-sg` / `SSH bastion - my IP only` |
| VPC | **swordmaster VPC** (`app-sg`와 같은 VPC) |
| 인바운드 | SSH 22 ← **내 IP** |
| 아웃바운드 | 기본값 (모두 허용) |

- `0.0.0.0/0` 금지. 몇 분 안에 무작위 SSH 시도가 들어온다.
- 네트워크를 옮기면 IP가 바뀐다 → 규칙 소스를 다시 "내 IP"로.

### 2단계: 키 페어

EC2 → 키 페어 → 생성: `swordmaster-bastion-key`, **ED25519**, **.pem**

| 구성 | 위치 | 역할 |
|---|---|---|
| 공개 키 | AWS → 바스티온에 자동 설치 | 자물쇠 |
| 개인 키 `.pem` | **내 PC에만** (다운로드 1회) | 열쇠 |

**보관 위치**: `C:\Users\{사용자}\.ssh\` (Git Bash에서 `~/.ssh/`). 드래그로 옮겨도 된다. 다운로드 폴더에 사본이 남지 않게 확인.

| Git Bash | Windows |
|---|---|
| `~` | `C:\Users\{사용자}` |
| `~/.ssh` | `C:\Users\{사용자}\.ssh` |

**권한 잠그기 (Git Bash)**

```bash
chmod 400 ~/.ssh/swordmaster-bastion-key.pem
ls -l ~/.ssh/swordmaster-bastion-key.pem
```

`UNPROTECTED PRIVATE KEY FILE`이 나오면 Windows 권한으로 잠근다.

```bash
KEY_WIN=$(cygpath -w ~/.ssh/swordmaster-bastion-key.pem)
MSYS_NO_PATHCONV=1 icacls "$KEY_WIN" /inheritance:r
MSYS_NO_PATHCONV=1 icacls "$KEY_WIN" /grant:r "$USERNAME:(R)"
```

- `MSYS_NO_PATHCONV=1`: Git Bash가 `/inheritance:r`를 경로로 바꾸지 못하게 막음
- `.pem`은 **Git, 채팅, 공유 금지**. 잃어버리면 재발급 불가 (키 페어와 바스티온을 다시 만들어야 함)

**`.ssh` 폴더에 원래 있던 파일들** (지우지 않는다)

| 파일 | 정체 |
|---|---|
| `known_hosts` | 접속했던 서버들의 신분증 목록. 바스티온 첫 접속 때 한 줄 추가됨 |
| `known_hosts.old` | 위 파일의 자동 백업 |
| `id_rsa`, `id_ed25519` (+`.pub`) | GitHub SSH 등 다른 용도의 개인 키 |

### 3단계: 바스티온 EC2

| 항목 | 값 |
|---|---|
| 이름 | `swordmaster-bastion` |
| AMI / 아키텍처 | Amazon Linux 2023 / **Arm** |
| 유형 | t4g.nano (없으면 t4g.micro) |
| 키 페어 | `swordmaster-bastion-key` |
| VPC / 서브넷 | swordmaster VPC / **퍼블릭 서브넷** |
| 퍼블릭 IP 자동 할당 | **활성화** |
| 보안 그룹 | 기존 `bastion-sg` |
| IAM 인스턴스 프로파일 | **비워 둠** (뚫려도 넘어갈 권한이 없게) |

- 퍼블릭 서브넷 구분: 라우팅 테이블의 `0.0.0.0/0`이 `igw-…`면 퍼블릭, `nat-…`면 프라이빗
- 인스턴스를 중지했다 켜면 **퍼블릭 IP가 바뀐다**

### 4단계: `rds-sg`, `valkey-sg`에 규칙 추가

| 보안 그룹 | 추가 규칙 |
|---|---|
| `rds-sg` | MYSQL/Aurora 3306 ← **사용자 지정** `bastion-sg` |
| `valkey-sg` | 사용자 지정 TCP 6379 ← `bastion-sg` |

- **"규칙 추가"로 새 줄을 만든다.** 기존 `app-sg` 규칙을 수정·삭제하면 앱이 DB에 못 붙어 5xx 알람이 울린다
- 소스를 IP가 아닌 **보안 그룹**으로 지정 → 바스티온을 다시 만들어 IP가 바뀌어도 규칙 수정 불필요
- 즉시 적용, 서비스 중단 없음

### 5단계: SSH 접속 확인 (Git Bash)

```bash
ssh -i ~/.ssh/swordmaster-bastion-key.pem ec2-user@{바스티온공인IP}
```

| 부분 | 의미 |
|---|---|
| `-i` | 사용할 개인 키 |
| `ec2-user` | Amazon Linux 기본 사용자 |

- 첫 접속 시 `Are you sure you want to continue connecting?` → `yes` (known_hosts에 기록)
- 프롬프트가 `[ec2-user@ip-10-0-x-x ~]$`로 바뀌면 성공 → `exit`

### 6단계: 바스티온 → RDS 경로 확인 (바스티온 안에서)

```bash
timeout 3 bash -c '</dev/tcp/{RDS엔드포인트}/3306' && echo "3306 OK" || echo "3306 FAIL"
timeout 3 bash -c '</dev/tcp/{Valkey구성엔드포인트}/6379' && echo "6379 OK" || echo "6379 FAIL"
```

- `/dev/tcp/주소/포트`: bash 기능으로 해당 포트에 연결 시도. **포트를 빠뜨리면 파일로 해석**되어 `No such file or directory`
- `OK`면 4단계 규칙 정상

### 7단계: SSH 터널 열기 (내 PC의 Git Bash)

```bash
ssh -i ~/.ssh/swordmaster-bastion-key.pem -N -L 3307:{RDS엔드포인트}:3306 ec2-user@{바스티온공인IP}
```

| 부분 | 의미 |
|---|---|
| `-N` | 명령 실행 없이 터널만 유지 |
| `-L 3307:{RDS엔드포인트}:3306` | 내 PC 3307 → 바스티온 경유 → RDS 3306 |

- **출력 없이 멈춘 것처럼 보이면 정상.** 창을 닫지 않는다. 종료는 Ctrl+C
- **내 PC에서** 실행해야 한다. 바스티온 안에서 실행하면 바스티온에 3307이 열린다
- 끊김 방지: `-o ServerAliveInterval=60`

### 8단계: GUI 접속

| 항목 | 값 |
|---|---|
| 호스트 | **`127.0.0.1`** (RDS 엔드포인트 아님) |
| 포트 | **`3307`** |
| 네트워크 유형 (HeidiSQL) | MariaDB or MySQL (TCP/IP) |
| 데이터베이스 | `swordmaster` |
| 사용자 / 암호 | `DB_USERNAME` / `DB_PASSWORD` |

```sql
SELECT version, description, success FROM flyway_schema_history;
```

> **10/14 GUI 접속 성공** (`127.0.0.1:3307`)

**GUI 도구** = DB 서버(MySQL, MariaDB)에 접속해 화면으로 보여주는 **클라이언트**: DBeaver, HeidiSQL, MySQL Workbench, IntelliJ Database 탭(Ultimate).

**GUI 없이 (Docker MySQL 클라이언트, 두 번째 Git Bash 창에서)**

```bash
docker run -it --rm mysql:8 mysql -h host.docker.internal -P 3307 -u {DB사용자} -p swordmaster
```

- `host.docker.internal`: 컨테이너 안에서 **내 PC**를 가리키는 주소
- Git Bash에서 `not a TTY` 오류 시 앞에 `winpty`

## 4. SSH 터널의 원리

### localhost로 접속하는데 어떻게 RDS에 닿나

**내 PC의 3307번을 받고 있는 프로그램이 MySQL이 아니라 `ssh`이기 때문이다.**

```
① GUI ──"SELECT ..."──▶ 127.0.0.1:3307        (받는 프로그램 = 내 PC의 ssh)
② ssh가 암호화 ──인터넷 22번──▶ 바스티온의 sshd
③ sshd가 RDS:3306으로 새 연결을 열고 전달
④ 응답은 역순: RDS ──▶ sshd ──(암호화)──▶ ssh ──▶ GUI
```

| 구간 | 담당 |
|---|---|
| GUI ↔ `127.0.0.1:3307` | 내 PC의 **ssh 클라이언트** |
| 내 PC ↔ 바스티온 | SSH 암호화 연결 (22번) |
| 바스티온 ↔ RDS | 바스티온의 **sshd**가 대신 접속 (3306번) |

> **착신 전환 전화기** 비유: GUI는 내 방 전화기(`127.0.0.1:3307`)로 걸지만, 그 전화기를 ssh가 받아 경비 초소(바스티온)로 돌리고, 초소가 금고실 내선(RDS 3306)으로 연결한다.

- GUI는 SSH나 바스티온의 존재를 모른다. "localhost에 있는 MySQL"이라고 생각하고 평소처럼 대화한다
- RDS 입장에서는 **바스티온의 사설 IP**가 접속한 것으로 보인다 (`SHOW PROCESSLIST;`로 확인 가능)
- **내 PC가 바스티온이 된 것이 아니다.** 내 PC는 터널 **입구**만 가진 클라이언트이고, 중계는 바스티온 EC2가 한다

### localhost와 내 IP의 차이

| 주소 | 의미 | 누가 쓸 수 있나 |
|---|---|---|
| **`127.0.0.1` (localhost)** | **이 컴퓨터 자신**. 밖으로 나가지 않는 내부 주소 | 내 PC 안의 프로그램끼리만 |
| 공인 IP | 인터넷에서 나를 찾는 주소 | `bastion-sg`에 등록한 그 IP |
| 사설 IP (`192.168.x.x`) | 공유기 안에서의 주소 | 같은 공유기의 기기 |

→ 터널 입구(3307)는 `127.0.0.1`에만 열리므로 **다른 사람이 인터넷에서 내 PC의 3307로 접속할 수 없다.**

### 왜 3307인가

**내 PC의 3306은 로컬 Docker MySQL이 이미 쓰고 있기 때문.** 3307은 "3306 다음 번호"라 고른 것일 뿐 의미는 없다 (안 쓰는 포트면 무엇이든 가능).

```
내 PC
 ├─ 127.0.0.1:3306 ──▶ 로컬 Docker MySQL (개발용)
 └─ 127.0.0.1:3307 ──SSH 터널──▶ 바스티온 ──▶ RDS:3306 (운영)
```

| 3306으로 터널을 열면 | 결과 |
|---|---|
| 로컬 MySQL이 사용 중 | `bind: Address already in use`로 실패 |
| 둘 다 연결된 것처럼 보이는 경우 | 운영 DB를 보는 줄 알았는데 **로컬 DB**를 보고 있는 사고 |

`-L 3307:{RDS}:3306`에서 **앞의 3307은 내 PC 쪽 입구, 뒤의 3306은 RDS 쪽 포트**. RDS는 계속 3306에서 받는다.

### 직접 확인

```bash
netstat -ano | grep ":3307"          # LISTENING + PID
tasklist //FI "PID eq {PID}"         # ssh.exe 가 나오면 3307을 ssh가 받고 있다는 증거
```

터널 창을 Ctrl+C로 닫으면 `LISTENING`이 사라지고 GUI 접속도 끊긴다.

## 4-1. ElastiCache(Valkey) 접속 (10/14 성공)

### 방법 비교

| 방법 | 경로 | 판단 |
|---|---|---|
| **A. 바스티온에서 `valkey-cli`** | 내 PC → SSH → 바스티온 → Valkey | ✅ **사용 중 (성공)** |
| B. SSM으로 앱 서버에서 Docker `valkey-cli` | SSM → 앱 EC2 → Valkey | ⚠️ `valkey/valkey` 이미지에 CA 목록이 없어 `certificate verify failed` → `--cacert` 필요 |
| C. SSH 터널 + GUI (Redis Insight 등) | 내 PC → 터널 → Valkey | ❌ 권장 안 함 |

**GUI 터널이 어려운 이유**

| 특징 | 문제 |
|---|---|
| TLS 필수 | 인증서 이름은 `clustercfg.…amazonaws.com`인데 터널 주소는 `127.0.0.1` → 이름 불일치 |
| 클러스터 모드 | 서버가 "다른 노드(`10.0.x.x`)로 가라"(MOVED)고 안내 → 내 PC는 사설 주소로 갈 수 없음 |

> RDS는 **창구가 하나인 은행**이라 터널 하나로 충분하지만, Valkey 클러스터는 **"3번 창구로 가세요"라고 안내하는 은행**이라 1번 창구에만 연결된 터널로는 따라갈 수 없다.

### 방법 A 절차

**전제**: `valkey-sg`에 6379 ← `bastion-sg` 규칙 (3장 4단계)

```bash
# 1. 바스티온 접속 (내 PC Git Bash)
ssh -i ~/.ssh/swordmaster-bastion-key.pem ec2-user@{바스티온공인IP}

# 2. 경로 확인 (보안 그룹)
timeout 3 bash -c '</dev/tcp/{구성엔드포인트}/6379' && echo "6379 OK" || echo "6379 FAIL"

# 3. 클라이언트 설치 (최초 1회) - AL2023은 valkey 패키지로 설치됨
sudo dnf install -y valkey || sudo dnf install -y redis6
which valkey-cli

# 4. 접속
valkey-cli --tls -c -h {구성엔드포인트} -p 6379
```

| 옵션 | 의미 |
|---|---|
| `--tls` | 암호화 연결 (빠지면 에러 없이 멈춤) |
| `-c` | 클러스터 모드: MOVED 안내를 자동으로 따라감 |
| `-h` / `-p` | **주소만** / 포트 (주소에 `:6379`나 `{ }`를 넣지 않는다) |

- `{구성엔드포인트}`: ElastiCache → 클러스터 → `clustercfg.`로 시작하는 주소 (포트 제외)
- `dnf`로 설치한 클라이언트는 Amazon Linux의 CA 목록을 써서 TLS 검증이 통과한다
- `which` 결과의 `no redis6-cli in …`은 에러가 아니라 "그 프로그램은 없음" 안내

### 방법 B (참고): SSM + Docker

```bash
sudo docker run --rm -it \
  -v /etc/pki/tls/certs/ca-bundle.crt:/ca.crt:ro \
  valkey/valkey:8 valkey-cli --tls --cacert /ca.crt -c -h {구성엔드포인트} -p 6379
```

- `-v …:/ca.crt:ro`: 앱 서버의 CA 목록을 컨테이너에 읽기 전용으로 빌려줌
- 빠른 확인만 할 때는 `--insecure` (암호화는 하되 상대 신원 확인 생략). 운영 앱 설정에서는 절대 사용 금지

### 확인 결과 (10/14)

```
> PING            → PONG
> DBSIZE          → (integer) 0
> INFO keyspace   → # Keyspace (내용 없음)
> SCAN 0 COUNT 20 → 1) "0"  2) (empty array)
```

- **키 0개는 정상.** Valkey에는 전투 진행 데이터, 캐시처럼 **TTL로 사라지는 데이터**만 있고, 진행 중인 전투가 없으며 DB도 초기화된 상태
- 키를 보고 싶으면: 전투 시작 API 호출 직후 `SCAN 0 COUNT 20` → `TTL {키}`
- 프롬프트가 두 번 찍히는 것은 Git Bash 화면 표시 문제 (동작 무관)

### 자주 쓰는 명령과 금지 명령

| 명령 | 용도 |
|---|---|
| `PING` | 연결 확인 |
| `DBSIZE`, `INFO keyspace` | 키 개수 |
| `SCAN 0 MATCH {접두어}:* COUNT 100` | 키 목록을 조금씩 (첫 줄 숫자가 0이 될 때까지 그 숫자로 반복) |
| `TYPE` / `GET` / `HGETALL` / `TTL` | 값 종류 / 값 / 해시 값 / 남은 만료 시간 (`-1` 만료 없음, `-2` 없음) |

**금지**: `KEYS *` (키가 많으면 Valkey가 멈춤), `FLUSHALL`, `FLUSHDB`, `DEL` (진행 중인 전투 데이터 삭제)

### 연결 단계별 실패 위치

```
① DNS (주소 찾기)       → 실패: Name or service not known      ← 주소에 { } 나 :6379 포함
② TCP (보안 그룹)        → 실패: 응답 없이 멈춤 / timed out
③ TLS (인증서 확인)      → 실패: certificate verify failed      ← 클라이언트의 CA 목록 문제
④ 명령                  → PING → PONG
```

`certificate verify failed`가 나왔다는 것은 **②(보안 그룹)는 통과했다**는 증거다. 앱(Java)은 자체 CA 목록이 있어 문제없고, 차이는 **클라이언트 프로그램**에 있다.

### 프롬프트로 현재 위치 구분

| 프롬프트 | 위치 | 입력할 것 |
|---|---|---|
| `[ec2-user@ip-…]$` / `[ssm-user@ip-…]$` | 리눅스 셸 | `valkey-cli`, `docker` 같은 명령 |
| `clustercfg…:6379>` | valkey-cli (접속됨) | `PING`, `SCAN` 같은 Valkey 명령 |
| `not connected>` | valkey-cli (접속 실패) | **`exit`로 나간 뒤** 셸에서 다시 실행 |

### RDS 터널과 동시에 쓰기

3307 터널을 닫을 필요 없다. 바스티온으로 가는 **SSH 연결을 하나 더** 열면 된다.

```
창 1: 127.0.0.1:3307 ═══SSH 연결 A═══▶ 바스티온 ──▶ RDS:3306        (-N -L, 멈춘 채 유지)
창 2: 터미널        ═══SSH 연결 B═══▶ 바스티온 ──▶ valkey-cli ──▶ Valkey:6379
```

- Valkey 방식은 **내 PC에 포트를 열지 않으므로** 3307과 충돌하지 않는다
- 한 창에서 하려면 터널 명령에서 `-N`을 빼면 터널 + 셸을 함께 쓸 수 있다 (단, `exit`하면 터널도 닫힘)

## 5. 관련 개념: RDS 서브넷 그룹과 AZ 장애

### DB 서브넷 그룹

**"RDS를 이 서브넷들 중에서만 만들어라"라는 후보 서브넷 목록.**

| 역할 | 설명 |
|---|---|
| 위치 지정 | RDS의 네트워크 카드(ENI)를 둘 서브넷 결정 |
| 프라이빗 유지 | 프라이빗 서브넷만 넣으면 퍼블릭에 생길 일이 없음 |
| 장애 대비 | **AZ 2개 이상** 필수. Multi-AZ 대기 DB 위치 |
| 복구 위치 | 스냅샷 복구, 사양 변경 시 이 목록 안에서 위치 선택 |

| | 서브넷 그룹 | 보안 그룹 |
|---|---|---|
| 정하는 것 | **어디에** 둘지 | **누가** 들어올지 |
| 바스티온 작업 | 변경 없음 | `rds-sg`에 규칙 추가 |

- VPC 안의 서브넷끼리는 `local` 경로로 항상 통신 가능 → 퍼블릭 서브넷의 바스티온도 프라이빗 RDS에 닿는다
- **현재 swordmaster RDS**: **기본 서브넷 그룹(`default-vpc-…`)** 사용, 퍼블릭 액세스 **`False`** (확인 완료) → 지금은 안전. 기본 그룹은 퍼블릭 서브넷이 섞일 수 있어 **출시 전 프라이빗 전용 서브넷 그룹으로 정리** (스냅샷 → 새 그룹으로 복구 → `DB_HOST` 변경 → 인스턴스 새로 고침)

```bash
aws rds describe-db-instances --db-instance-identifier swordmaster-db \
  --query 'DBInstances[0].{Public:PubliclyAccessible,AZ:AvailabilityZone,SubnetGroup:DBSubnetGroup.DBSubnetGroupName}' \
  --output table
```

### AZ 하나가 장애 나면 데이터가 사라지나

**대부분 사라지지 않는다. 서비스는 멈춘다.**

| 데이터 | 범위 | AZ 장애 시 |
|---|---|---|
| RDS 디스크 (EBS) | 그 AZ 안에서 복제 | AZ 복구 시 그대로 돌아옴 |
| **자동 백업 / 스냅샷** | **S3, 리전 전체** | 안전. 다른 AZ에 새 DB로 복구 가능 |

| | 단일 AZ (현재) | Multi-AZ |
|---|---|---|
| 장애 시 | 복구까지 중단 또는 수동 복구 (최근 몇 분치 손실 가능) | 1~2분 내 자동 전환, 엔드포인트 동일 |
| 비용 | 1배 | 약 2배 |

→ 통합 테스트 단계는 **단일 AZ + 자동 백업(1일)**으로 충분. 실사용자가 생기면 Multi-AZ 검토.

## 6. 트러블슈팅

| 증상 / 로그 | 원인 | 해결 |
|---|---|---|
| `Connection timed out` (SSH) | 22번이 막힘 | `bastion-sg` 내 IP가 현재 IP인지, 퍼블릭 서브넷인지, 공인 IP가 있는지 |
| `UNPROTECTED PRIVATE KEY FILE` | 키 권한이 너무 열림 | `chmod 400`, 안 되면 `icacls` (Git Bash 버전) |
| `Permission denied (publickey)` | 키 또는 사용자 이름 틀림 | `swordmaster-bastion-key`, `ec2-user` 확인 |
| `/dev/tcp/…: No such file or directory` | 경로에 **포트(`/3306`) 누락** | `/dev/tcp/{엔드포인트}/3306` |
| `3306 FAIL` (3초 후) | `rds-sg`에 `bastion-sg` 규칙 없음 | 4단계 확인 |
| `bash: -i: command not found` | 명령 앞의 **`ssh`가 빠짐** (복사 누락, 두 줄로 붙여넣기) | 한 줄 전체를 다시 붙여넣기, 맨 앞이 `ssh`인지 확인 |
| 터널을 바스티온 안에서 실행 | 프롬프트가 `[ec2-user@…]` | `exit` 후 내 PC Git Bash에서 실행 |
| `bind [127.0.0.1]:3307: Address already in use` | 3307 사용 중 | 다른 포트(3308) |
| **GUI `Can't connect to server on '{RDS엔드포인트}' (10060)`** | GUI 호스트에 **RDS 엔드포인트를 직접** 입력 → 프라이빗이라 닿지 않음 (10060 = 시간 초과) | 호스트 **`127.0.0.1`**, 포트 **`3307`** (터널 열린 상태) |
| Valkey `Could not connect … at {clustercfg…:6379}:6379: Name or service not known` | `-h`에 **중괄호와 `:6379`까지** 넣음 | `-h clustercfg…amazonaws.com -p 6379` (주소만) |
| `not connected>` 상태에서 `sudo docker run …` 입력 | valkey-cli **안에서** 셸 명령 입력 → Valkey 명령으로 해석 | `exit`로 나간 뒤 셸에서 실행 |
| Valkey `SSL_connect failed: certificate verify failed` | Docker `valkey/valkey` 이미지에 **CA 목록 없음** (보안 그룹은 통과한 상태) | 바스티온에서 `dnf` 설치 클라이언트 사용, 또는 `-v …ca-bundle.crt:/ca.crt:ro --cacert /ca.crt` |
| Valkey 접속 후 멈춤 | `--tls` 누락 | Ctrl+C 후 `--tls` 추가 |
| GUI `(10061)` | 터널이 안 열린 상태 (연결 거부) | 7단계 터널 먼저 |
| 터널 창에 `channel 2: open failed: connect failed` | 바스티온 → RDS 경로 실패 | 6단계 `3306 OK` 확인 |
| DBeaver `Public Key Retrieval is not allowed` | MySQL 8 인증 방식 | Driver properties `allowPublicKeyRetrieval=true` |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | 바스티온을 다시 만들었는데 같은 IP | `ssh-keygen -R {IP}` |

## 7. 주의사항

- **운영 DB다.** 조회는 괜찮지만 `UPDATE`, `DELETE`, `DROP` 전에는 **RDS 수동 스냅샷**
- GUI 연결 이름을 `swordmaster-PROD (3307)`처럼 눈에 띄게, 가능하면 빨간색 (DBeaver "Production" 유형은 위험 쿼리 확인 창 제공)
- Valkey는 GUI 터널 대신 **바스티온 안에서 `valkey-cli`** (4-1장)
- **비용과 운영 방식**

  | 방식 | 월 비용 (대략) | 다시 쓸 때 |
  |---|---|---|
  | 켜 둠 | 약 $7 (t4g.nano + 퍼블릭 IPv4 + EBS) | 바로 사용 |
  | **중지 (권장)** | EBS만 약 $0.7 | 시작 → **새 공인 IP** 확인 → 명령의 IP만 교체 |
  | 종료 + 정리 | 0 | 3단계부터 재생성 (8장 참고) |

  보안 그룹 규칙·키 페어·설정은 중지해도 그대로 남는다. 네트워크를 옮기면 `bastion-sg`의 내 IP도 다시 설정.

## 8. 정리 (실습 종료 시, 순서 중요)

| 순서 | 작업 | 이유 |
|---|---|---|
| 1 | `rds-sg`에서 `bastion-sg` 3306 규칙 **삭제** | 다른 보안 그룹이 참조 중이면 `bastion-sg` 삭제가 거부됨 |
| 2 | `valkey-sg`에서 `bastion-sg` 6379 규칙 **삭제** | 위와 같음 |
| 3 | `swordmaster-bastion` EC2 **종료(terminate)** | 과금 중단 (EC2 + 공인 IP + EBS) |
| 4 | `bastion-sg` 삭제 | 종료된 인스턴스와 참조 규칙이 모두 없어야 가능 |
| 5 | 키 페어 `swordmaster-bastion-key` 삭제 (선택) | AWS 쪽 공개 키 |
| 6 | 내 PC `~/.ssh/swordmaster-bastion-key.pem` 삭제 (선택) | 개인 키 |

- **기존 `app-sg` 규칙은 절대 지우지 않는다.**
- 다시 쓸 계획이면 1~4만 하고 키 페어는 남겨도 된다.
