# 이력서 작성 요령 (개발자 기준)

> 이력서는 "나를 다 보여주는 문서"가 아니라, **10~60초 안에 핵심이 보이도록 설계한 요약 문서**입니다.
> 핵심 원칙은 세 가지예요: **구조화 · 간결함 · 객관적 사실**

---

## 1. 이력서의 용도: 왜 이렇게 써야 하나

### 입사지원 서류는 목적이 각각 다릅니다

| 구분 | 이력서 | 자기소개서 | 포트폴리오 |
|---|---|---|---|
| **목적** | 경력 요약과 핵심 정보 제공 | 가치관, 직무·조직 적합성 표현 | 강점 어필, 프로젝트 과정·성과 시각화 |
| **내용** | 인적 사항, 학력·경력, 자격증·어학, 기술/역량 요약 | 지원 동기, 입사 후 포부, 문제 해결 경험, 성격의 장단점 | 경력 요약, 주요 프로젝트 과정·성과, 이미지·차트 |
| **구성 포인트** | 간결하고 직관적인 구성, 전체 흐름 강조 | 스토리텔링, 가치관·태도, 회사·직무 이해도 | 비주얼 중심, 프로젝트 깊이와 시각화 |

**정리하면:** 이력서에 자기소개서식 서술(지원 동기, 포부)이나 포트폴리오급 트러블슈팅 전문을 넣으면 역할이 섞입니다. 이력서는 **요약**, 나머지는 각 서류로 보냅니다.

### 검토자는 이력서를 얼마나 볼까?

- **10초 ~ 60초 이내**
- 전체를 읽지 않고 **About Me → Skills → 경력/프로젝트 핵심 bullet**만 훑어봄
- **핵심이 안 보이면 그냥 넘어갑니다**

## 2. 아쉬운 이력서 vs 합격하는 이력서

| 아쉬운 이력서 | 합격하는 이력서 |
|---|---|
| ❌ **구조화가 안 됨** — 프로젝트/기능을 전부 같은 비중으로 나열 → 대표 경험이 안 보임 | ✅ **구조화** — 대표 프로젝트 중심, 프로젝트마다 같은 틀 |
| ❌ **간결하지 않음** — 기술 나열 + 긴 트러블슈팅에 핵심이 묻힘 | ✅ **간결하게** — 짧은 문장, 명사형 종결, 불릿 |
| ❌ **객관적 사실이 아님** — 내 역할·근거 없이 "개선했다"만 있음 | ✅ **객관적 사실** — 역할·기여 명시, 측정된 수치 |

### 아쉬운 예시에서 자주 보이는 패턴

- 한 프로젝트 안에 `문제 발생 → 실패한 시도 → 최종 해결 → 결과`를 **문단 단위로** 길게 서술 (트러블슈팅 블로그를 그대로 붙인 형태)
- 기술 스택을 수십 개 태그로 나열 (Java, JS, MyBatis, Oracle, React, Jenkins, Kubernetes …)
- 이력서 안에 자기소개서(지원 동기, 입사 후 포부)를 통째로 포함
- "꺼지지 않는 열정, 제가 보여드리겠습니다" 같은 **근거 없는 슬로건**형 헤드라인
- 볼드·색상·밑줄을 과하게 써서 오히려 강조가 사라짐

### 합격 예시에서 보이는 공통점

- 상단 **About Me**에 강점 3개를 카드/한 줄로 요약 (예: 실시간 통신 구조 설계 / 성능 병목 분석 / 캐싱 조회 최적화)
- Tech Stack을 **분류별(Backend / Database / DevOps / Tools)** 로 정리
- 프로젝트마다 `한 줄 소개 → 주요 구현 기능(2열 카드) → 사용 기술 태그` 동일한 틀
- 성과는 짧게: `Virtual Thread 도입 (OS 스레드 84% ↓)`, `JMeter 부하 테스트 (동접 1,500)`

## 3. 작성 포인트 1 — 구조화

### 사용법: 무엇을 앞에 둘지

- **직무와 가장 맞닿은 경험부터.** 전부 넣지 말고 **대표 프로젝트 중심**
- **신입 추천 순서:** `프로젝트 → 교육 → 학력·자격`

### 사용법: 어떻게 정리할지

- 프로젝트마다 **같은 틀**: `개요 → 담당 → 주요 구현 → 문제 해결`
- 기본 기능(로그인, CRUD 등)은 **1줄로 압축**, 직접 설계·개선한 기능부터

### 예시 (템플릿)

```markdown
### 프로젝트명 | 2025.04 ~ 2025.06 | 인원 BE 3명 / FE 2명 | 담당: 채팅·알림 서버
AI 기반 여행 코스 추천 서비스

**주요 구현** (핵심 2~3줄)
- STOMP 기반 실시간 채팅 구조 설계 (JWT 인증 연동)
- Redis Sorted Set 기반 인기 코스 랭킹 조회 구현

**문제 해결** (상황 → 행동 → 결과 각 1줄)
- 상황: 목록 조회 시 N+1 쿼리로 평균 응답 6.1s
- 행동: fetch join 적용 + 복합 인덱스 추가
- 결과: 평균 응답 6.1s → 0.9s (JMeter, 동시 사용자 100명)

`Spring Boot` `WebSocket` `Redis` `MySQL` · [GitHub](https://github.com/...)
```

### 주의 사항

- 모든 프로젝트를 같은 분량으로 쓰면 **아무것도 대표가 아니게 됩니다.** 대표 1~2개는 자세히, 나머지는 2~3줄
- 틀이 프로젝트마다 다르면 검토자가 매번 다시 "읽는 법"을 익혀야 합니다

## 4. 작성 포인트 2 — 간결함

### 사용법: 무엇을 앞에 둘지

- **짧은 문장, 명사형 종결**: `구현했습니다` → `구현`
- **수식어·부사 X, 줄글 X → 불릿**

### 사용법: 어떻게 정리할지

- 기술은 **주력만 분류**해서 기재
- 긴 트러블슈팅은 **블로그·포트폴리오로 분리**
- 링크는 풀 URL 대신 **앵커 텍스트**: `[GitHub]`, `[Blog]`, `[배포]`

### 예시

```markdown
❌ 사용자 경험을 크게 향상시키기 위해 열심히 노력하여 매우 효율적인 캐싱 구조를 성공적으로 구현했습니다.
✅ Redis 캐싱 적용으로 상품 상세 조회 응답 320ms → 45ms

❌ 블로그: https://velog.io/@username/series/troubleshooting-2025-redis-cache
✅ [트러블슈팅 기록](https://velog.io/@username/...)
```

### 선택: 보유 기술 한 줄 더하기

주력 기술 **2~3개만** `수준 | 사용처`를 한 줄로.

```markdown
- Spring Boot | 즉시 활용 | REST API 설계, 글로벌 예외 처리
- Redis       | 응용 가능 | 인증 코드 만료(TTL) 관리
```

### 주의 사항

- 기술 태그 20개 나열은 "다 조금씩 써봤다"로 읽힙니다. **주력이 무엇인지** 보이게
- 간결함 ≠ 정보 삭제. 숫자·역할·기술명 같은 **핵심 정보는 남기고 수식어만** 덜어냅니다

## 5. 작성 포인트 3 — 객관적 사실

### 사용법: 역할·기여가 명확한가

- **팀 인원 / 내 담당 범위 / 기여도** 명시
- "구조 설계 주도" 같은 표현은 **실제로 한 일로 뒷받침**

### 사용법: 결과는 측정한 값으로

- **측정 도구·조건과 함께** 기재 (포장된 수치 X)
- 수치가 없으면 **정성 결과**: `QA 오류 0건 통과`, `배포 자동화 적용`

### 예시

```markdown
❌ 서버 응답 속도를 대폭 개선
✅ N+1 해결·인덱스 추가로 목록 조회 평균 응답 6.1s → 0.9s (JMeter 측정)

❌ 팀 프로젝트에서 백엔드 구조 설계를 주도
✅ BE 3명 중 도메인 모델·패키지 구조 설계 담당, ERD 12개 테이블 설계

❌ 배포 과정을 개선
✅ GitHub Actions + Docker로 배포 자동화 (수동 배포 약 20분 → 푸시 시 자동)
```

### 주의 사항

- 근거 없는 큰 숫자(예: "성능 1000% 향상")는 **면접에서 반드시 검증**당합니다. 재현 가능한 측정만
- 팀 성과를 내 성과처럼 쓰지 말 것. "팀은 무엇을, 나는 무엇을"을 구분

## 6. 추가 포인트

### 한 줄 요약 (About Me)

- **무슨 직무 / 어떤 강점(경험)** 이 있는지 요약
- 뒷받침하는 **경험·근거 한 줄** + **앞으로의 방향성**

```markdown
## About Me
실시간 통신과 성능 개선에 강한 백엔드 개발자 홍길동입니다.
- 실시간 통신 구조 설계: WebSocket/STOMP 기반 다중 채팅 서버 구현
- 성능 병목 분석·개선: Virtual Thread 도입으로 OS 스레드 84% 감소
- 캐싱 기반 조회 최적화: Redis Sorted Set 랭킹 조회 O(log N)
```

### GitHub 정리

- 대표 레포 **README에 개요 / 아키텍처 / 실행 방법**
- 이력서 링크는 **프로필이 아니라 대표 레포로 바로** 연결

### 기록 (블로그)

- 트러블슈팅·학습 블로그는 **대표 글 2~3개만** 링크
- "글 N개 작성"보다 **어떤 문제를 기록했는지**가 중요

---

## 7. 제출 전 체크리스트

- [ ] 상단 About Me만 읽어도 직무·강점 3가지가 보이는가
- [ ] 대표 프로젝트가 맨 앞에 있고, 다른 프로젝트보다 비중이 큰가
- [ ] 모든 프로젝트가 `개요 → 담당 → 주요 구현 → 문제 해결` 같은 틀인가
- [ ] 각 프로젝트에 **기간 · 인원 · 내 담당**이 적혀 있는가
- [ ] 문장이 명사형으로 끝나고, 줄글 문단이 없는가
- [ ] 성과에 **측정값 + 측정 도구/조건**이 있는가 (없으면 정성 결과)
- [ ] 긴 트러블슈팅은 블로그/포트폴리오 링크로 뺐는가
- [ ] 링크가 앵커 텍스트이고, 대표 레포·대표 글로 바로 가는가
- [ ] 자기소개서 내용(지원 동기·포부)이 이력서에 섞여 있지 않은가

## 부록: 세부 정리

### A. 신입 이력서 권장 섹션 순서

1. 이름 / 직무 타이틀 / 연락처 / GitHub·Blog 링크
2. About Me (한 줄 요약 + 강점 3개)
3. Tech Stack (분류별, 주력 위주)
4. Projects (대표 프로젝트 → 나머지)
5. 교육 (부트캠프 등)
6. 학력 · 자격증 · 활동

### B. 문제 해결 1줄 공식 (STAR 축약)

| 단계 | 쓰는 내용 | 예시 |
|---|---|---|
| 상황 | 어떤 문제가, 어떤 수치로 | 로그인 API 평균 응답 504ms |
| 행동 | 원인 분석 + 적용한 기술 | BCrypt cost 조정, 인스턴스 스케일업 |
| 결과 | 측정값 + 도구/조건 | 504ms → 75ms (JMeter, 동시 100명) |

### C. 자주 쓰는 명사형 종결 변환

| 서술형 | 명사형 |
|---|---|
| ~를 구현했습니다 | ~ 구현 |
| ~를 도입하여 개선했습니다 | ~ 도입으로 개선 |
| ~를 담당하였습니다 | ~ 담당 |
| ~를 통해 자동화하였습니다 | ~ 기반 자동화 |

### D. 측정 도구 예시 (백엔드)

- 부하 테스트: JMeter, nGrinder, k6
- 모니터링: Prometheus + Grafana, Actuator, Micrometer
- 쿼리 분석: `EXPLAIN`, Slow Query Log
- 프론트 성능(참고): Lighthouse (LCP, FCP, TTFB)
