## 1. 웹의 기본 뼈대: 클라이언트 - 네트워크 - 서버

**개념**: 웹 통신은 클라이언트 → 네트워크 → 서버 → (다시) 네트워크 → 클라이언트 순서로 이루어집니다.

| 구성요소 | 정의 | 예시 | 역할 |
|---|---|---|---|
| 클라이언트 | 서비스를 요청하는 사용자 기기/소프트웨어 | 브라우저(크롬, 사파리), 서버→서버 요청도 포함 | "이 작업 처리해줘"라고 요청 전송 |
| 네트워크 | 클라이언트-서버를 연결하는 통로 | 인터넷 | 요청/응답 전달 (주로 HTTP 프로토콜 사용) |
| 서버 | 요청을 처리하고 결과를 돌려주는 시스템 | 네이버 서버, 게임 서버 | 24시간 대기, 요청 처리 후 응답 |

**핵심 전제**: 클라이언트와 서버는 서로의 위치(IP 주소)를 알아야 요청/응답을 주고받을 수 있습니다.

**용도**: 이후 배우는 EC2, 보안그룹, VPC 개념은 전부 이 요청-응답 구조를 이해해야 납득이 됩니다.

## 2. 온프레미스 vs 클라우드, IaaS/PaaS/SaaS

### 온프레미스 (On-Premise)
회사가 직접 서버를 구매해 자체 서버실에서 운영하는 방식.
- 서버 컴퓨터 직접 구매/설치/관리
- 전기·냉방 비용 발생
- 네트워크 구축·관리 직접 수행

### 클라우드 (Cloud)
AWS, GCP, Azure 같은 업체의 서버를 빌려 쓰는 방식.
- 수만~수십만 대 서버가 이미 준비되어 있어 초기 비용 없음
- 클릭 몇 번으로 서버 할당/반납 가능

### 서비스 모델: IaaS / PaaS / SaaS

| 모델 | 빌리는 범위 | AWS가 제공 | 내가 해야 하는 것 | 예시 |
|---|---|---|---|---|
| **IaaS** | 인프라만 (서버, 네트워크, 스토리지) | 하드웨어, 네트워크 | OS부터 애플리케이션까지 전부 | EC2 (지금 배우는 방식) |
| **PaaS** | 플랫폼까지 (런타임, 미들웨어 포함) | 서버/네트워크, OS, 런타임, 오토스케일링, 로드밸런싱 | 애플리케이션 코드 작성/배포 | Elastic Beanstalk |
| **SaaS** | 소프트웨어까지 (완성된 서비스) | 모든 것 | 툴 사용만 | - |

> ⚠️ **주의**: 관리 범위가 SaaS 쪽으로 갈수록 내 책임/자유도는 줄어듭니다. IaaS를 쓴다는 건 거의 모든 책임이 나에게 있다는 뜻입니다.

## 3. AWS 계정 구조: Account - Region - AZ

**AWS**: 아마존이 제공하는 클라우드 서비스. 전 세계에 분산된 데이터센터 보유.

| 단위 | 정의 | 비고 |
|---|---|---|
| **Account** | AWS 서비스 사용의 기본 단위 | 결제·보안·리소스 관리의 경계. 1인 1계정 또는 회사당 여러 계정 |
| **Region** | 지리적 영역 (서울, 버지니아 등) | 리전마다 독립적 — 서울에서 만든 EC2는 버지니아에서 안 보임. 서울 = `ap-northeast-2` |
| **AZ (Availability Zone)** | 리전 안의 개별 데이터센터 | 실제 위치는 보안상 비공개. 여러 AZ 운영 이유 = 고가용성 확보 |

**가용성**이란 서비스가 정상적으로 사용 가능한 상태를 뜻합니다.
- 가용성 낮음: 자주 다운, 접속 불가 시간 많음 → 이용자 불편
- 가용성 높음: 24시간 접속 가능, 장애 거의 없음 → 이용자 편리

**AWS 서비스 예시**
- 서버가 필요할 때 → **EC2**
- 데이터베이스가 필요할 때 → **RDS**
- 이미지/파일 저장이 필요할 때 → **S3**

## 4. 공동 책임 모델 (Shared Responsibility)

클라우드 사용 중 보안 사고에 대한 책임은 AWS와 사용자가 나눠서 집니다.

| 구분 | 책임 범위 | 예시 |
|---|---|---|
| **고객 책임** (Security IN the Cloud) | 클라우드 "안에서" 내가 만든 것의 보안 | 데이터 암호화/보호, IAM 사용자/권한 관리, 보안그룹 설정, OS 패치, 애플리케이션 보안 |
| **AWS 책임** (Security OF the Cloud) | 클라우드 "자체" 인프라의 보안 | 물리적 보안(데이터센터), 네트워크 인프라, 관리형 서비스 기본 보안 |

**서비스 유형별 책임 범위 요약**
- IaaS: 인프라만 빌림 → 내가 거의 모두 관리 (책임 대부분 사용자)
- PaaS: 플랫폼까지 빌림 → IaaS보다 AWS 관리 범위 많음
- SaaS: 소프트웨어까지 빌림 → 거의 다 AWS가 관리

> 관리 범위가 늘어날수록 사용자의 책임 범위는 줄어듭니다.

## 5. Budget 설정

**용도**: 클라우드 사용 중 실수로 비싼 리소스를 설정하는 등의 상황을 막는 안전장치. 예산 기준 초과 시 실시간 알림.

**사용법**
```
AWS 콘솔 → Billing → Budgets
→ "Create a budget" 클릭
→ "Cost budget" 선택
→ 월 예산 설정 (예: $30, 필요 시 조정 가능)
→ 알림 임계값: 80%, 100%
→ 이메일 주소 입력 (알림 수신용)
→ 생성 완료
```

> ⚠️ **주의**: 요금 폭탄을 맞지 않으려면 실습 시작 전 무조건 설정할 것.

## 6. IAM: User / Role / Policy

**정의**: AWS에서 누가(Who) 어떤 AWS 리소스에 무엇을(What) 할 수 있는지(Can)를 정하고 통제하는 접근 제어 시스템.

### ① User — "사람"용 계정
- 개발자가 콘솔 로그인 / 관리자가 CLI로 관리하는 등 사람이 직접 AWS를 조작하는 모든 경우
- 핵심 특징: **영구적인 자격증명(Credential)** 보유
  - 비밀번호: 콘솔(웹사이트) 로그인용
  - Access Key: API/CLI 접근용 (Access Key ID = 아이디, Secret Access Key = 비밀번호)
- 특징: 한 번 생성하면 삭제 전까지 유효(만료 없음), 1인 1계정 원칙 권장

> ⚠️ **User Access Key 문제점**: 영구적으로 유효하므로 유출 시 큰 사고로 이어지고 관리도 어려움 → 서버/자동화에는 User 대신 **Role 사용 권장**

### ② Role — "서버/서비스"용 임시 권한
- EC2가 S3에 업로드할 때, GitHub Actions가 배포할 때 등 서버·자동화 시스템이 AWS를 쓰는 모든 경우
- 핵심 특징: **임시로 빌려 쓰는 권한 세트**

### ③ Policy — 허용/거부 규칙 정의
- Policy를 User나 Role에 "연결"하는 형태로 사용
- 예: S3 읽기 Policy를 `kim-dev` User에 연결 → `kim-dev`가 S3 읽기 가능

**예시 코드 (Policy JSON)**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}
```
- `"Effect": "Allow"` → 허용 (거부는 `"Deny"`)
- `"Action": "s3:GetObject"` → S3에서 Object 가져오기
- `"Resource": "arn:aws:s3:::my-bucket/*"` → S3의 `my-bucket/*` 대상

**ARN (Amazon Resource Name)**: AWS 리소스의 고유 주소 (사람의 주민등록번호에 비유). 형식: `arn:aws:{서비스}:…`

> AWS에서 자주 쓰이는 Policy는 미리 만들어져 있어 암기할 필요 없음.

**IAM 3요소 요약**: User 또는 Role에 Policy를 연결하여 사용한다.

### 보안 원칙

**1. 최소 권한 원칙**: 작업에 꼭 필요한 권한만 부여, 그 외 모두 거부.
- `AdministratorAccess` 같은 광범위한 Policy 부여 지양
- 초기엔 무권한 → 필요 시 하나씩 추가
- IAM Access Analyzer로 미사용 과도한 권한 식별·제거

**2. 루트 사용자 보호**
- Access Key 삭제: 루트 사용자 Access Key는 사용하지 않는 편이 좋음
- 일상 업무 사용 금지: 계정 생성, 결제 정보 수정 등 특수 상황 외엔 절대 사용 금지

## 7. 네트워크: 보안그룹과 VPC

### 보안그룹 (Security Group)
**정의**: AWS 리소스에 대한 네트워크 트래픽을 제어하는 가상 방화벽.

| 특성 | 내용 |
|---|---|
| 규칙 방식 | **Whitelist 방식** — 허용(Allow)만 가능, 차단(Deny) 규칙 없음. 규칙에 없는 트래픽은 자동 차단 |
| Stateful | 인바운드로 허락받은 트래픽은 아웃바운드에서 재검사 없이 통과 |
| 인바운드 기본값 | 모두 차단 |
| 아웃바운드 기본값 | 모두 허용 |

> "보안그룹 = EC2 앞의 방화벽" — 규칙에 없으면 트래픽 차단됨.

### VPC (Virtual Private Cloud)
**정의**: AWS 클라우드 내에 만드는 사설 네트워크. 다른 AWS 계정의 네트워크와 완벽히 격리.

**IP 주소 범위 설정**
- 사설 IP 대역 사용 (주로 `10.x.x.x`)
- 실습용 표준값: `10.0.0.0/16` → 약 65,000개의 IP 사용 가능

### VPC 하위 요소

**① Subnet**
- 거대한 VPC를 관리하기 쉽게 작게 쪼갠 구역. 하나의 VPC에 여러 서브넷 생성 가능
- 필수 규칙: **서브넷 = 1개 AZ** (여러 AZ에 걸칠 수 없음, 가용성 확보 목적)
- VPC 전체 IP를 서브넷들이 나눠 가짐 (예: 서브넷당 약 250개씩)

**② Route Table (라우팅 테이블)**
- 트래픽이 "어디로 가야 하는지" 알려주는 표지판. 모든 서브넷은 반드시 하나의 라우팅 테이블과 연결
- **Local (내부 통신)**: 도착지가 VPC 내부(`10.0.x.x`)면 VPC 안에서 처리 — 삭제 불가, 별도 설정 없이 통신 가능
- **External (외부 통신)**: 도착지가 알 수 없는 주소(`0.0.0.0/0`, 인터넷)면 인터넷 게이트웨이로 전달 — 이 규칙 유무가 Public/Private 결정

**③ Internet Gateway (IGW)**
- VPC와 외부 인터넷을 연결하는 유일한 관문 (VPC당 오직 1개)
- IGW가 없으면 VPC 내부에서 인터넷 접속 불가

**④ Public Subnet vs Private Subnet**

> ⚠️ AWS에는 "Private Subnet 만들기" 버튼이 따로 없습니다. **오직 라우팅 테이블 설정 차이**로만 구분됩니다.

| 구분 | 조건 | 라우팅 규칙 |
|---|---|---|
| Public Subnet 🌐 | 라우팅 테이블에 IGW로 향하는 경로 있음 | `172.31.0.0/16 → local` (자동 생성, VPC 내부 통신) |
| Private Subnet 🔒 | 라우팅 테이블에 IGW로 향하는 경로 없음 | `172.31.0.0/16 → local` (VPC 내부 통신만 가능) |

## 8. EC2 개념

**EC2 (Elastic Compute Cloud)**: AWS에서 제공하는 클라우드 컴퓨팅 서비스. 마음대로 세팅해볼 수 있는 AWS 컴퓨터.

- 로컬에서 코드를 짜고 실행하던 환경을 아마존 데이터센터의 원격 컴퓨터로 옮길 수 있음
- EC2 인스턴스는 실제 컴퓨터 1대가 아니라, 물리적 서버 1대를 여러 개의 가상 서버로 나눈 것 (**가상화**)
- 인스턴스 = 가상 서버 한 대. EC2뿐 아니라 AWS의 모든 서비스가 실제 물리 하드웨어 1개가 아님

### AMI (Amazon Machine Image)
EC2를 시작할 때 사용하는 설치 이미지. 포함 내용:
- 운영체제 (Linux, Windows 등)
- 기본 패키지/도구 (AWS CLI 등)
- 초기 설정 (보안 설정 등)

### 인스턴스 유형 표기법 (예: `t4g.small`)

| 요소 | 의미 |
|---|---|
| family (`t`) | 용도 (딥하게 알 필요 없음) |
| generation (`4`) | 세대 — 대체로 높을수록 좋음 |
| additional capability (`g`) | `g` 있음 = Graviton 프로세서(Arm/`arm64`) / `g` 없음 = 보통 x86(`x86_64`) |
| instance size (`.small`) | 사양: nano < micro < small < medium < large < … |

> Arm과 x86: 애플 M1 이상 맥 시리즈 = Arm 아키텍처 / Intel·AMD CPU = x86 아키텍처. 강의에서는 주로 `g`가 붙은 Graviton 인스턴스 사용.
>
> 동급 인스턴스 기준 Arm이 x86보다 성능·가성비 면에서 좋음 (태생이 모바일용이라 가벼움).
>
> **`t4g.small`은 2026년 12월 31일까지 무료** (월 750시간).
>
> 스프링은 다른 프레임워크보다 무거우므로 micro는 버거운 편, small 이상 권장.

### 인스턴스 상태

| 상태 | 설명 | EC2 비용 | 퍼블릭 IP | 데이터 |
|---|---|---|---|---|
| Pending | 시작 중 | - | - | 유지 |
| Running | 실행 중 | 과금 | 과금 | 유지 |
| Stopped | 중지됨 (재시작 가능) | 무료 | 해제 (재시작 시 새 IP 할당) | 유지 |
| Terminated | 삭제됨 (복구 불가) | 무료 | 해제 | 삭제 |

> ⚠️ 재시작 시 퍼블릭 IP가 바뀝니다. 실습 후 종료하지 않으면 계속 과금되니, 필요 없으면 반드시 종료(Stop) 또는 삭제(Terminate)하세요.

### EC2 인스턴스의 IP 주소

| 종류 | 용도 | 특징 |
|---|---|---|
| Private IP | VPC 내부 통신용 | 인스턴스 생성 시 자동 할당, 중지/시작해도 유지, 인터넷에서 접근 불가 |
| Public IP | 인터넷 통신용 | 인스턴스 시작 시 자동 할당(설정에 따라 미할당 가능) |
| Elastic IP (EIP) | 고정된 Public IP | 현재는 Public IP와 요금 정책 동일. 고정 Public IP = Elastic IP로 봐도 무방. 다른 EC2로 이동 가능 |

## 9. EC2 생성 실습 (7단계)

### 사전 준비 순서
```
Region 설정 → Budget 설정 → VPC 생성 → EC2 생성
```
Region을 먼저 정해야 이후 리소스가 그 지역에 묶이고, Budget은 EC2보다 먼저 걸어야 과금 사고를 막을 수 있으며, VPC는 EC2가 들어갈 네트워크 공간이므로 EC2보다 먼저 존재해야 합니다. (EC2는 "이미 준비된 집(VPC)에 입주하는 세입자")

### 1단계: 이름 및 태그
- EC2 이름 설정 — 인스턴스가 늘어났을 때 구분하기 위한 이름표 (예: `my-web-server`)

### 2단계: AMI 선택
- Quick Start에서 **Amazon Linux 2023** AMI 선택
- **64비트** 확인 (대부분의 애플리케이션·인스턴스 유형은 64비트 전제)

### 3단계: 인스턴스 유형
- **t4g.small** 선택 (2026년 12월까지 무료, Arm 기반이라 가성비 좋음)

### 4단계: 키 페어
- '새 키 페어 생성' 클릭
  - 키 페어 이름 설정
  - 키 페어 유형: **RSA**
  - 프라이빗 키 파일 형식: **.pem**

```
⚠️ 키 페어는 생성 시점에만 다운로드 가능
   분실 시 재발급 불가 → 새 키 페어를 만들어 인스턴스에 재연결해야 함
```

### 5단계: 네트워크 설정
- VPC 설정: 사전에 만든 VPC 선택
- Subnet: **퍼블릭 서브넷** 선택 *(실습 중 설정값, 이후 변경 가능)*
- Public IP 자동 할당: **활성화**
- Security Group 설정: 방화벽 규칙(포트 등) 지정

> 실무에서는 DB처럼 외부 노출이 안 되어야 하는 리소스는 프라이빗 서브넷에 두는 것이 원칙입니다.

### 6단계: 스토리지 구성
- 기본값 그대로 사용 (**8 GiB, gp3**) — 범용 SSD로 실습·소규모 서비스에 충분

### 7단계: 검토 및 시작
- 전체 설정 확인 후 **[인스턴스 시작]** 클릭 → 상태가 `Pending → Running`으로 전환되면 완료

### 단계별 핵심 요약표

| 단계 | 설정 항목 | 선택값 | 의미 |
|---|---|---|---|
| 1 | 이름/태그 | 자유 지정 | 식별용 |
| 2 | AMI | Amazon Linux 2023, 64bit | OS + 기본 패키지 |
| 3 | 인스턴스 유형 | t4g.small | Arm, 무료 티어(~2026.12) |
| 4 | 키 페어 | RSA, .pem | SSH 접속 키 (1회만 다운로드) |
| 5 | 네트워크 | 퍼블릭 서브넷 + Public IP 활성화 + 보안그룹 | 외부 접근 경로 |
| 6 | 스토리지 | 8GiB gp3 | 기본 디스크 |
| 7 | 시작 | - | Pending → Running |

## 10. EC2 접속 및 장애 체험 실습

### 키 파일 권한 설정
```bash
chmod 400 ~/{pem키경로}
```
- **`chmod 400`이란?** 소유자만 읽기 가능, 쓰기/실행 금지. SSH가 키 파일에 요구하는 보안 설정 — 이 권한이 없으면 SSH 접속 시 에러 발생.

### SSH 접속
```bash
ssh -i {pem파일경로} ec2-user@{public-ip주소}
```
- 최초 접속 시 핑거프린트 확인 메시지 → `yes` 입력
- IAM Role 연결 여부도 함께 확인

### 서버 상태 확인 명령어
```bash
free -h   # 메모리 사용량
df -h     # 디스크 사용량
top       # CPU/메모리 실시간 모니터링 (q로 종료)
```

### HTTP 장애 체험 실습

1. **보안그룹에서 HTTP(80) 규칙 삭제**
   - AWS 콘솔 → EC2 → 보안 그룹 → `my-ec2-sg`
   - 인바운드 규칙 편집 → HTTP(80) 규칙 삭제 → 저장
2. **브라우저 새로고침** → ❌ 접속 불가 (로딩 중... 타임아웃, "Connection timed out")
   → 이 증상은 **보안그룹 문제일 가능성이 높음**
3. **HTTP(80) 규칙 다시 추가**
   - 인바운드 규칙 편집 → 규칙 추가 → 유형: HTTP, 포트: 80, 소스: Anywhere (`0.0.0.0/0`) → 저장
4. **브라우저 새로고침** → ✅ 페이지 다시 보임

> "보안그룹 = EC2 앞의 방화벽" — 규칙에 없으면 트래픽 차단! `Connection timed out` 에러가 뜨면 가장 먼저 보안그룹 인바운드 규칙을 확인하세요.

## 11. 하단 세부 정리 (빠른 참조표)

**용어 한 줄 사전**

| 용어 | 의미 |
|---|---|
| ARN | AWS 리소스의 고유 주소 |
| 가용성 | 서비스가 정상적으로 사용 가능한 상태의 정도 |
| Stateful | 들어올 때 허용된 트래픽은 나갈 때 재검사 안 함 |
| Region (서울) | `ap-northeast-2` |
| 무료 인스턴스 | `t4g.small`, 2026년 12월 31일까지, 월 750시간 |

**전체 흐름 한눈에 보기**

```
[사전 준비]
Region 설정 → Budget 설정 → VPC 생성
   └─ VPC(10.0.0.0/16) → Subnet(AZ별) → Route Table → IGW → Public/Private 구분

[EC2 생성]
이름/태그 → AMI(Amazon Linux 2023) → 인스턴스 유형(t4g.small)
   → 키 페어(.pem) → 네트워크(퍼블릭 서브넷+Public IP+보안그룹)
   → 스토리지(8GiB gp3) → 시작(Pending→Running)

[접속 및 운영]
chmod 400 → ssh 접속 → 상태 확인(free/df/top)
   → 보안그룹으로 HTTP(80)/SSH(22) 포트 오픈 여부 점검
   → 실습 후 반드시 Stop 또는 Terminate로 정리 (과금 방지)
```

**실수하기 쉬운 포인트 체크리스트**
- [ ] Budget을 EC2 생성보다 먼저 설정했는가
- [ ] AMI는 64비트로 선택했는가
- [ ] 키 페어(.pem)를 안전한 곳에 백업했는가 (재다운로드 불가)
- [ ] 보안그룹에 HTTP(80)/SSH(22) 인바운드 규칙이 열려 있는가
- [ ] 실습 종료 후 인스턴스를 Stop/Terminate 했는가
