## 01. JWT 

JWT (JSON WEB TOKEN)
정의는 정보를 JSON으로 표현하여 전달하는 토큰 형식이다. 

세션이 서버가 클라이언트의 정보를 들고있는 것이었다면 
JWT는 클라이언트가 인증에 필요한 정보를 들고 있다가 서버에게 요청할 때 
같이 제출하는 형태이다.

### 핵심

| 부분 | 내용 |
|---|---|
| `Header` | 서명 알고리즘 등 토큰 처리에 필요한 정보 |
| `Payload` | 회원 ID, 역할 등 전달하려는 데이터 (각 항목 = 클레임) |
| `Signature` | Header + Payload 와 Key 를 이용하여 만든 검증용 값 |

### 설명 · 예시

JWT는 Header, Payload, Signature 세 부분으로 이루어져 있으며, 각 부분은 점(`.`)으로 구분되어 하나의 문자열로 이어진다.

- **Header**: 서명 알고리즘 등 토큰을 처리하는 데 필요한 정보가 담긴다.
- **Payload**: 회원 ID, 역할 등 실제로 전달하고자 하는 데이터가 담긴다. Payload 내 각 항목을 **클레임**이라고 부른다.
- **Signature**: Header + Payload 와 Key를 이용하여 만든 검증용 값이다. 이 값이 있어야 토큰이 위·변조되지 않았음을 확인할 수 있다.

실제 발급된 JWT 하나를 세 부분으로 쪼개보면:

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInJvbGUiOiJBRE1JTiIsImlhdCI6MTc1ODAwMDAwMCwiZXhwIjoxNzU4MDAzNjAwfQ.4f8a3c9e1b7d2c6f0a5e8b3d9c1a7f4e2d6b8c0a3f5e7d9b1c4a6e8f0d2b4c6a
└──────────── Header ────────────┘└──────────────────── Payload ────────────────────┘└──────────────── Signature ────────────────┘
```

각 부분을 Base64Url **디코딩**하면 아래처럼 사람이 읽을 수 있는 JSON이 나온다 (jwt.io 같은 사이트에 붙여넣으면 바로 확인 가능).

```json
// Header
{ "alg": "HS256" }

// Payload
{ "sub": "42", "role": "ADMIN", "iat": 1758000000, "exp": 1758003600 }
```

## 02. 클레임 (Payload) 과 만료 시각

### 핵심

| 클레임 | 역할 |
|---|---|
| `sub` | 회원 ID (토큰의 주체) |
| `iat` | 발급 시각 |
| `exp` | 만료 시각 |
| `role` | 애플리케이션이 정한 사용자 역할 — 표준 등록 클레임 아님 |
| 그 외 | 필요한 데이터 key : value 를 자유롭게 추가 가능 |

### 설명 · 예시

JWT에 담는 정보의 각 항목을 클레임이라고 부른다. (Payload의 데이터 항목)

- `sub` : 회원 ID가 주로 담긴다. (토큰의 주체)
- `iat` : 발급 시각
- `exp` : 만료 시각
- `role` : 어플리케이션이 정한 사용자 역할. 표준 등록 클레임이 아닌 사용자 정의 항목
- 이 외의 필요한 데이터 key : 이 외의 필요한 데이터 value 를 추가할 수 있다.

클레임이 실제 시간과 어떻게 대응되는지:

```
iat = 1758000000  →  2026-01-16 09:20:00 UTC (발급 시각)
exp = 1758003600  →  2026-01-16 10:20:00 UTC (발급 + 1시간 후 만료)
```

## 03. Session 과 JWT 비교

### 핵심

| | Session | JWT |
|---|---|---|
| 상태 | Stateful (서버가 데이터를 가짐) | Stateless (서버가 가지고 있지 않음) |
| Key/Token 값 | 의미 없는 쓰레기 값 | 로그인에 필요한 모든 정보가 담김 |

### 설명 · 예시

Session에서 만드는 Session Key는 아무 의미없는 쓰레기 값이지만, JWT의 토큰에는 모든 로그인에 필요한 정보들이 담긴다.

따라서 JWT는 서버에서 JWT를 저장하지 않고, 발급받은 클라이언트가 JWT를 인증함으로써 서버는 유저 식별이 가능하다.

즉 Session은 **Stateful** (서버가 데이터를 가짐) 이라면, JWT는 **Stateless** (서버가 가지고 있지 않음) 이다.

같은 로그인 결과를 각 방식이 어떻게 표현하는지 비교하면:

```
[Session 방식]
클라이언트가 받는 값: "JSESSIONID=A1B2C3D4E5F6..."  ← 의미 없는 랜덤 문자열
서버가 들고 있는 값 : sessionStore["A1B2C3D4E5F6"] = { userId: 42, role: "ADMIN" }

[JWT 방식]
클라이언트가 받는 값: "eyJhbGci...eyJzdWIiOiI0MiIs...4f8a3c9e..."  ← 그 자체가 정보
서버가 들고 있는 값 : (없음)
```

## 04. JWT 서명과 검증

### 핵심

```
Signature = {암호화알고리즘}(Base64Url(Header) + "." + Base64Url(Payload), SecretKey)
```

Base64Url을 쓰는 이유: Base64의 `/ = +`가 URL에서 문제가 되는 문자라서, URL에 안전한 문자로 치환.

### 설명 · 예시

서명(Signature)의 생성 방법:

```
Signature = {암호화알고리즘}(Base64Url(Header) + "." + Base64Url(Payload), SecretKey)
```

Base64Url은 인터넷에 검색하기만 해도 다시 JSON으로 데이터를 되돌릴 수 있다. 따라서 민감한 데이터(개인정보 등)는 JWT에 넣으면 안 되고, 로그인에 필요한 사항(email 등)만 넣어야 한다.

Base64는 `/ = +` 등 url에 문제가 될 수 있는 부분들을 처리하지 못하기 때문에 Base64Url을 사용한다.

Base64Url이 왜 필요한지 일반 Base64와 비교한 예시:

```
원본 바이트를 Base64로 인코딩 →  "PDw/Pz8+Pg==" 처럼 +, /, = 문자가 섞여 나올 수 있음
                                   → URL 경로나 쿼리에 그대로 못 씀 (경로 구분자 / 와 충돌 등)

Base64Url 인코딩 규칙:
  +  →  -
  /  →  _
  =  →  제거(padding 생략)

→ "PDw_Pz8-Pg" 처럼 URL에 안전하게 그대로 쓸 수 있는 문자열이 됨
```

## 05. 비밀번호 암호화

### 핵심

| 메서드 | 역할 |
|---|---|
| `encode()` | 비밀번호를 암호화 |
| `matches()` | 암호화된 비밀번호와 다른 문자열을 대조하여 일치하는지 확인 |

### 설명 · 예시

`AuthenticationConfig`는 비밀번호 암호화를 하기 위한 객체를 빈으로 등록하기 위해 만든 config 클래스이다. (`@EnableMethodSecurity`는 일단 제외)

반환되는 빈인 `PasswordEncoder`의 메서드만 살펴보면, `encode()`는 비밀번호를 암호화하고, `matches()`는 암호화된 비밀번호와 다른 문자열을 대조하여 일치하는지 확인하는 메서드이다.

```java
@Configuration
@EnableMethodSecurity
public class AuthenticationConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
```

회원가입 요청과 DB에 저장되는 값의 차이:

```json
// 클라이언트가 보낸 SignupRequest
{
  "email": "kgy@example.com",
  "password": "myPassword123!"
}
```

```
// passwordEncoder.encode("myPassword123!") 결과 (DB users 테이블 password 컬럼)
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
```

```java
// 로그인 시 대조
passwordEncoder.matches("myPassword123!", "$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy")
// → true (같은 원문이어도 매번 다른 해시가 나오지만, matches()는 내부 salt를 읽어 정확히 비교함)
```

## 06. JwtProvider — 발급과 검증

JWT를 활용하기 위한 의존성 추가:

```gradle
implementation 'io.jsonwebtoken:jjwt-api:0.12.6'
runtimeOnly 'io.jsonwebtoken:jjwt-impl:0.12.6'
runtimeOnly 'io.jsonwebtoken:jjwt-gson:0.12.6'
```

`JwtProvider`는 JWT 발급과 검증을 **모두 담당하는 하나의 클래스**이다. 발급 메서드와 검증 메서드가 같은 `secretKey`를 공유한다는 게 흐름을 이해하는 핵심이라, 클래스 전체를 잘라내지 않고 그대로 옮겨둔다.

```java
@Component
public class JwtProvider {
    private final SecretKey secretKey; //서명에 만들 때 쓸 secret 키
    private final long accessTtlSeconds; //JWT의 만료시간

    public JwtProvider(
            @Value("${jwt.secret}") String secret,
            @Value("${jwt.access-ttl-seconds}") long accessTtlSeconds
    ) {
        this.secretKey = Keys.hmacShaKeyFor(Decoders.BASE64.decode(secret));
        this.accessTtlSeconds = accessTtlSeconds;
    }

    public String createAccessToken(
            User user        //user 테이블
    ) {
        Instant now = Instant.now();
        Instant expiresAt = now.plusSeconds(accessTtlSeconds);
        // 회원 정보와 만료 시각을 담아 JWT 발급
        return Jwts.builder()
                .subject(user.getId().toString()) //subejct 엔 userId
                .claim("role", user.getRole().name()) //"role" 키에 user의 roleName
                .issuedAt(Date.from(now))  //만들어진 시간
                .expiration(Date.from(expiresAt))
                .signWith(secretKey, Jwts.SIG.HS256)  //
                .compact();
    }

    public AuthUser parseToken(
            String token
    ) {
        try {
            // JWT 서명과 만료 검증
            Jws<Claims> signedClaims = Jwts.parser().verifyWith(secretKey).build().parseSignedClaims(token);
            Claims claims = signedClaims.getPayload();
            String subject = claims.getSubject();
            long userId = Long.parseLong(subject);
            Role role = Role.valueOf(claims.get("role", String.class));
            // 검증한 회원 정보로 인증 객체 생성
            return new AuthUser(userId, role);
        } catch (JwtException | IllegalArgumentException | NullPointerException exception) {
            throw new ResponseStatusException(HttpStatus.UNAUTHORIZED);
        }
    }
}
```

### 핵심 — JWT를 만드는 메서드 (`createAccessToken`)

`Jwts`라는 클래스의 빌더 패턴으로 JWT를 만들어 낸다. 호출 순서는 `.compact()`(조립 메서드)가 가장 뒤에 오기만 하면 상관없으나, `.signWith()`는 서명이 가장 뒤로 오는 게 순서에 맞아 `.compact()` 바로 앞에 위치한다.

| 메서드 | 설명 |
|---|---|
| `.subject(String)` | payload의 등록 클레임 `sub`에 값을 넣습니다. "이 토큰이 누구에 대한 것인가"를 나타내는 자리라, 보통 userId를 문자열로 변환해 넣습니다. |
| `.claim(String, Object)` | 표준에 없는 커스텀 클레임을 자유롭게 추가합니다. 여기선 `"role"`이라는 키에 사용자의 권한 문자열을 담고 있습니다. |
| `.issuedAt(Date)` | 등록 클레임 `iat`. 토큰이 "언제 발급되었는지" 기록합니다. |
| `.expiration(Date)` | 등록 클레임 `exp`. 토큰의 "만료 시각"을 지정하며, 검증 시 이 값이 지났으면 `ExpiredJwtException`이 발생합니다. |
| `.signWith(Key, SignatureAlgorithm)` | header에 알고리즘 정보(`alg`)를 기록하고, header+payload를 secretKey로 서명해 signature 부분을 생성합니다. 이 서명이 있어야 위조 여부를 검증할 수 있습니다. |
| `.compact()` | 지금까지 쌓은 header/payload를 Base64Url로 인코딩하고 서명까지 붙여 `xxx.yyy.zzz` 형태의 최종 문자열을 만들어 반환합니다. |

이 메서드가 참조하는 설정값 (`application.yml`):

```yaml
jwt:
  secret: bXlzdXBlcnNlY3JldGtleWZvcmp3dHNpZ25pbmcxMjM0NTY3ODkw   # Base64 인코딩된 256bit 이상 키
  access-ttl-seconds: 3600   # 1시간
```

입력(User)과 출력(JWT 문자열):

```
입력: User(id=42, email="kgy@example.com", role=Role.ADMIN)

출력: "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInJvbGUiOiJBRE1JTiIsImlhdCI6MTc1ODAwMDAwMCwiZXhwIjoxNzU4MDAzNjAwfQ.4f8a3c9e..."
```

### 핵심 — JWT를 검증하는 메서드 (`parseToken`)

생성과 마찬가지로 `Jwts`라는 클래스의 `parser()` 빌더 패턴을 통해 검증 도구를 만든다. 빌더로 만들어진 객체는 `Jws<Claims>` 타입이다. 이후 `Claims` 객체에서 userId, role을 가져와서 `AuthUser`라는 객체를 반환하고 있다.

| 메서드 | 설명 |
|---|---|
| `Jwts.parser()` | 파서를 만들기 위한 빌더를 시작합니다. (발급 때 `Jwts.builder()`와 짝을 이룹니다) |
| `.verifyWith(secretKey)` | "이 키로 서명을 검증하겠다"고 지정합니다. 발급 시 `.signWith(secretKey, ...)`에 쓴 것과 동일한 키가 들어가야 합니다. |
| `.build()` | 지금까지 설정을 바탕으로 실제 파서 객체를 완성합니다. |
| `.parseSignedClaims(token)` | 토큰 문자열을 실제로 분해·검증하는 지점입니다. 서명이 맞는지, 만료(`exp`)되지 않았는지를 이 한 줄에서 전부 확인하고, 문제가 있으면 예외를 던집니다. |
| `signedClaims.getPayload()` | 검증이 끝난 결과에서 payload(클레임 모음)만 꺼냅니다. |
| `claims.getSubject()` / `claims.get("role", String.class)` | payload 안의 등록 클레임(`sub`)과 커스텀 클레임(`role`)을 각각 꺼냅니다. |
| `new AuthUser(userId, role)` | 꺼낸 값으로 애플리케이션에서 쓸 인증 객체를 만들어 반환합니다. |

어떤 입력이 어떤 예외로 이어지는지:

| 상황 | 발생 예외 | 결과 |
|---|---|---|
| 정상 토큰 | 없음 | `AuthUser(userId=42, role=ADMIN)` 반환 |
| `exp` 시각이 지난 토큰 | `ExpiredJwtException` | 401 Unauthorized |
| secretKey가 달라 서명 불일치 | `SignatureException` | 401 Unauthorized |
| 토큰 형식 자체가 깨짐 (`.`이 2개가 아님 등) | `MalformedJwtException` | 401 Unauthorized |
| `role` 클레임 값이 `Role` enum에 없는 문자열 | `IllegalArgumentException` | 401 Unauthorized |
| `role` 클레임이 아예 없음 | `NullPointerException` | 401 Unauthorized |

## 07. Service 부분

### 핵심

| 클래스 | 역할 |
|---|---|
| `UserService` | 회원가입 — 비밀번호 암호화 후 저장 |
| `CredentialService` | 로그인 인증 — 이메일 조회 + 비밀번호 대조 |
| `JwtAuthService` | 로그인 — 인증 위임 후 토큰 발급 |

### 설명 · 예시

**UserService 부분의 회원가입 메서드**

여기서 중요한 것은 dto에서 받아온 password를 `passwordEncoder.encode()`를 통해 암호화를 시키는 것이다.

```java
@Service
@RequiredArgsConstructor
public class UserService {
    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;

    @Transactional
    public UserResponse signup(
            SignupRequest request
    ) {
        String password = request.getPassword();
        String encodedPassword = passwordEncoder.encode(password);
        User user = new User(request.getEmail(), encodedPassword, Role.USER);
        User savedUser = userRepository.save(user);
        return new UserResponse(savedUser.getId(), savedUser.getEmail(), savedUser.getRole());
    }

    @Transactional
    public UserResponse signupAdmin(
            SignupRequest request
    ) {
        String password = request.getPassword();
        String encodedPassword = passwordEncoder.encode(password);
        User user = new User(request.getEmail(), encodedPassword, Role.ADMIN);
        User savedUser = userRepository.save(user);
        return new UserResponse(savedUser.getId(), savedUser.getEmail(), savedUser.getRole());
    }
}
```

**CredentialService 부분**

UserService 부분에서 회원가입을 하며 db에는 암호화된 비밀번호가 저장되었다. 로그인을 하기 위해 인증할 때는 `if (!passwordEncoder.matches(password, encodedPassword))`처럼 `matches()` 메서드를 통해 요청으로 받은 비밀번호와 db의 암호화된 비밀번호가 일치하는지 확인한다.

```java
@Service
@RequiredArgsConstructor
public class CredentialService {
    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;

    @Transactional(readOnly = true)
    public User authenticate(
            LoginRequest request
    ) {
        User user = userRepository.findByEmail(request.getEmail())
                .orElseThrow(() -> new ResponseStatusException(HttpStatus.UNAUTHORIZED));
        String password = request.getPassword();
        String encodedPassword = user.getPassword();
        if (!passwordEncoder.matches(password, encodedPassword)) {
            throw new ResponseStatusException(HttpStatus.UNAUTHORIZED);
        }
        return user;
    }
}
```

**JwtAuthService 부분**

CredentialService에서 로그인 메서드의 유저를 찾으며 인증을 해준다. (서비스 → 서비스 요청) accessToken은 jwtProvider의 JWT를 만드는 메서드로 가져오며 응답 DTO에 담는다.

```java
@Service
@RequiredArgsConstructor
public class JwtAuthService {
    private final CredentialService credentialService;
    private final JwtProvider jwtProvider;

    @Transactional(readOnly = true)
    public AccessTokenResponse login(
            LoginRequest request
    ) {
        User user = credentialService.authenticate(request);
        String accessToken = jwtProvider.createAccessToken(user);
        return new AccessTokenResponse(accessToken);
    }
}
```

로그인 요청/응답 DTO 실제 값:

```json

{

  "password": "myPassword123!"
}
```

```json

{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsInJvbGUiOiJBRE1JTiIsImlhdCI6MTc1ODAwMDAwMCwiZXhwIjoxNzU4MDAzNjAwfQ.4f8a3c9e..."
}
```

## 08. Controller 부분

### 핵심

| 엔드포인트 | 호출 | 비고 |
|---|---|---|
| `POST /auth/signup` | `userService.signup()` | 201 Created + `UserResponse` |
| `POST /auth/login` | `jwtAuthService.login()` | 200 OK + `AccessTokenResponse`(지금은 문자열만 반환하는 dto) |

### 설명 · 예시

위의 회원가입, 로그인 부분을 HTTP 요청으로 받아오는 메서드이다.

```java
@RestController
@RequiredArgsConstructor
public class AuthController {
    private final JwtAuthService jwtAuthService;
    private final UserService userService;

    @PostMapping("/auth/signup")
    public ResponseEntity<UserResponse> signup(
            @RequestBody SignupRequest request
    ) {
        UserResponse user = userService.signup(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(user);
    }

    @PostMapping("/auth/login")
    public ResponseEntity<AccessTokenResponse> login(
            @RequestBody LoginRequest request
    ) {
        return ResponseEntity.ok(jwtAuthService.login(request)); //지금은 문자열만 반환하는 dto
    }
}
```

> 서버는 발급한 토큰을 **어디에도 저장하지 않는다.** 매 요청마다 서명만 재계산해 대조하는 stateless 구조.

## 09. JWT 와 Spring Security

### 핵심

Spring Security(2003) → JWT 도입(2018) → 그 이전 버전 호환을 위해 기본값 다수가 세션 기준.

### 설명 · 예시

Spring Security는 2003년에 개발되었으나 JWT를 도입하게 된 것은 2018년이다. 2018 이전까지는 세션을 자주 사용하였으니, 기본값으로 세션 관련 옵션이 설정되어 있는 것이 많다.
