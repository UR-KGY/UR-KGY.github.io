```
                       ┌────────────────────── VPC 10.0.0.0/16 ──────────────────────┐
사용자 ── IGW ────────▶ │ ALB (퍼블릭 2a·2b, :80)                                      │
                       │   │ local (사설 IP)                                          │
                       │   ▼                                                          │
                       │ EC2 (프라이빗 2a·2b, :8081, 공인 IP 없음) ← ASG가 대수 유지    │
                       │   │ 나가는 요청만 (docker pull, SSM)                          │
                       │   ▼                                                          │
                       │ NAT (퍼블릭 2a, EIP) ── IGW ──▶ ECR / SSM / 인터넷           │
                       │                                                              │
                       │ RDS (MySQL), ElastiCache (Valkey/Redis) ← local로 접근        │
                       └──────────────────────────────────────────────────────────────┘

GitHub push ─▶ Actions (OIDC로 Role 빌림) ─▶ 이미지 빌드 ─▶ ECR
                                            └▶ SSM으로 ASG 서버 전부에 롤링 배포
```

# 1부. 기초 개념

## 1. 계정, 리전, AZ

| 용어 | 의미 |
|---|---|
| **Account** | 리소스와 결제를 담는 **공간** (12자리 계정 ID). 로그인하는 사람이 아님 |
| 루트 사용자 | 계정의 주인 (가입 이메일). 일상 작업에 쓰지 않고 MFA 설정 |
| **Region** | 지리적 영역 (서울 `ap-northeast-2`). 리전마다 독립 → 콘솔에서 리소스가 안 보이면 리전부터 확인 |
| **AZ** | 리전 안의 분리된 데이터 센터 묶음 (2a, 2b …). 한 곳이 장애여도 다른 곳으로 서비스 유지 |

**공동 책임 모델**: AWS는 클라우드 **자체**(데이터 센터, 하드웨어)를, 사용자는 클라우드 **안에서** 만든 것(보안 그룹, IAM, OS 패치, 앱, 데이터)을 책임진다. RDS가 자동으로 만든 ENI와 공인 IP도 **내 계정의 과금과 보안 책임**이다.

## 2. IAM (User, Role, Policy)

| | User | Role |
|---|---|---|
| 대상 | 사람 | **서버, 서비스, 자동화** |
| 자격 증명 | 영구 (비밀번호, Access Key `AKIA…`) | 없음. 필요할 때 **임시 발급** (`ASIA…`, 자동 만료) |
| 비유 | 집 열쇠 | 호텔 카드키 |
| 실습 사용 | 콘솔 로그인 | `webcraft-ec2-role`(EC2), `github-actions-ci-demo`(GitHub 러너) |

- **원칙**: 서버와 자동화에는 Access Key 대신 Role. EC2에는 Role을 **하나만** 붙일 수 있으므로 정책을 추가해서 쓴다.
- **SDK 자격 증명 탐색 순서**: properties → 환경 변수 → `~/.aws/credentials` → **EC2 Role**. 그래서 로컬은 Access Key, EC2는 Role이 표준이다.

**Policy 구조**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::my-bucket/deploy/*",
      "Condition": { "...": "..." } }
  ]
}
```

| 항목 | 의미 |
|---|---|
| Effect | Allow / Deny (Deny가 우선) |
| Action | API 작업 이름 (`s3:PutObject`) |
| Resource | 대상 ARN |
| Condition | 조건 (예: `ssm:resourceTag/App = ci-demo` → 태그가 붙은 서버에만) |

| 정책 종류 | 특징 |
|---|---|
| AWS 관리형 | 재사용 (`AmazonSSMManagedInstanceCore` 등) |
| 인라인 | Role 안에 직접 작성. 실습 전용 권한에 사용 |

- **ARN**: `arn:aws:서비스:리전:계정ID:리소스`. S3는 이름이 전 세계 유일이라 리전과 계정을 비운다(`arn:aws:s3:::버킷/*`).
- 최소 권한: 필요한 Action과 Resource만. 처음엔 아무것도 주지 않고 필요할 때 추가.

## 3. VPC 네트워크

### 3-1. 구성 요소

| 구성 요소 | 역할 |
|---|---|
| **VPC** | 내 계정 전용으로 격리된 가상 네트워크. IP 대역(`10.0.0.0/16`)을 직접 설계 |
| **서브넷** | VPC를 나눈 구역. **AZ 하나에만** 속함. CIDR이 겹치면 안 되고, AWS가 5개 IP 예약 |
| **라우팅 테이블** | 서브넷의 **길 안내판** (목적지 → 타깃). 장치가 아니라 VPC 라우터가 참고하는 규칙표 |
| **IGW** | VPC와 인터넷을 잇는 **양방향** 출입문. 공인 IP ↔ 사설 IP 1:1 변환. VPC당 1개, 무료 |
| **NAT 게이트웨이** | 프라이빗 서버의 **나가기 전용** 출구. 여러 서버를 EIP 하나로 변환(N:1). 시간당 과금 |
| **VPC 엔드포인트** | NAT 없이 AWS 서비스에 직접 연결하는 통로 (S3 게이트웨이형은 무료) |

### 3-2. 퍼블릭 vs 프라이빗

**기준은 서브넷 이름이 아니라 라우팅 테이블에 `0.0.0.0/0 → IGW`가 있는지**이다.

| 라우팅 테이블 | `10.0.0.0/16` | `0.0.0.0/0` | 결과 |
|---|---|---|---|
| 퍼블릭 (`My-rtb-public`) | local | **igw-…** | 인터넷과 양방향 |
| 프라이빗 (`My-rtb-private1/2`) | local | 없음 → (NAT 실습 시) **nat-…** | VPC 안에서만 / 나가기만 |

- 인터넷 통신 조건: ① VPC에 IGW 연결 ② 라우팅 `0.0.0.0/0 → IGW` ③ 리소스에 공인 IP. **셋 다** 필요하다.
- **`local` 경로**는 자동으로 있고 삭제할 수 없다 → 같은 VPC 안의 서브넷끼리는 항상 길이 있다 (허용은 보안 그룹이 결정).
- **최장 접두사 일치**: 더 구체적인 경로가 우선 (`/16 local` > `/0`). 그래서 VPC 내부 통신은 항상 local로 간다.

### 3-3. 실습 VPC 구조

| 서브넷 | AZ | CIDR | 라우팅 테이블 |
|---|---|---|---|
| public1 `subnet-0611c55a…` | 2a | 10.0.0.0/20 | My-rtb-public (IGW) |
| public2 `subnet-056ea8fa…` | 2b | 10.0.16.0/20 | My-rtb-public (IGW) |
| private1 `subnet-0303ea07…` | 2a | 10.0.128.0/20 | `rtb-02fb2d14…` (local + S3 엔드포인트) |
| private2 `subnet-0996f54d…` | 2b | 10.0.144.0/20 | `rtb-0d431b5d…` (local + S3 엔드포인트) |
| - | - | - | `rtb-0f4c4ba0…` (main, 연결된 서브넷 없음) |

- 프라이빗 테이블에는 VPC 생성 때 만들어진 **S3 게이트웨이 엔드포인트(`My-vpce-s3`)**가 연결되어 있다 → 프라이빗 서버도 NAT 없이 S3 접근 가능.

### 3-4. 두 가지 트래픽 흐름 (가장 중요)

| | 들어오는 흐름 (사용자 요청) | 나가는 흐름 (서버가 먼저 시작) |
|---|---|---|
| 예시 | API 호출 | `docker pull`, SSM 통신, `dnf install` |
| 경로 | 사용자 → IGW → **ALB(퍼블릭)** → local → EC2(프라이빗) | EC2(프라이빗) → **NAT** → IGW → 인터넷 |
| 응답 | 같은 길로 ALB를 거쳐 돌아감 (NAT 안 거침) | NAT가 기억했다가 EC2로 돌려줌 |

> 프라이빗 EC2는 공인 IP가 없어서 인터넷이 직접 찾아올 수 없다. **받는 것은 ALB를 통해, 서버가 먼저 나가는 것만 NAT로.**

### 3-5. AWS 서비스와 EC2의 통신

데이터를 먼저 요청하는 쪽은 대부분 **EC2(앱)**이고, 서비스는 그 연결로 응답한다.

| 구분 | 서비스 | 경로 | 접근 제어 |
|---|---|---|---|
| **VPC 안** | RDS, ElastiCache, ALB | **local** (서브넷 안에 ENI, 사설 IP) | **보안 그룹** |
| **VPC 밖** | S3, ECR, SSM, CloudWatch | NAT/IGW 또는 **VPC 엔드포인트** | **IAM 역할** |

> 원칙: **VPC 안이면 보안 그룹, VPC 밖이면 IAM**. RDS 접속이 안 되면 SG를, S3 접근이 안 되면 IAM을 먼저 본다.
> 서비스가 먼저 보내는 경우(S3 업로드 이벤트 등)는 Lambda, SQS, SNS를 거친다.

### 3-6. 서브넷 그룹

- RDS, ElastiCache처럼 **AWS가 배치하는 서비스**가 쓸 서브넷 목록. **서로 다른 AZ 2개 이상** 필요.
- 목적: 고가용성(Multi-AZ 예비 자리), 보안(**프라이빗 서브넷만** 넣기). ElastiCache는 퍼블릭 접근 자체를 지원하지 않는다.

## 4. 보안 그룹

| 특징 | 의미 |
|---|---|
| 리소스별 가상 방화벽 | EC2, RDS, ALB 각각에 붙임. **요청을 받는 쪽**에 붙인다 |
| Whitelist | 규칙이 없으면 전부 차단 |
| Stateful | 허용된 요청의 **응답은 자동으로** 나감 → 인바운드만 엄격하게, 아웃바운드는 모두 허용 유지 |
| 소스로 **다른 SG** 지정 | IP가 바뀌어도 규칙 유지 (ALB 노드 IP, EC2 IP는 계속 바뀜) |

**실습 최종 구성**

| SG | 붙인 곳 | 인바운드 |
|---|---|---|
| `webcraft-alb` | ALB | 80 ← `0.0.0.0/0` |
| `webcraft-app` | EC2 (ASG 서버 포함) | **8081 ← `webcraft-alb` SG** / 22 ← 내 IP (또는 삭제) |
| `webcraft-data` | RDS, ElastiCache | 3306 ← `webcraft-app` / 6379 ← `webcraft-app` |

| CIDR | 의미 |
|---|---|
| `x.x.x.x/32` | IP 1개 |
| `10.0.0.0/16` | VPC 내부 전체 |
| `0.0.0.0/0` | 모든 IPv4 |

## 5. EC2

### 5-1. 접속 방법

| 방법 | 키 | 22번 포트 | 로그인 사용자 |
|---|---|---|---|
| SSH + 키 페어 | 필요 | 필요 | `ec2-user` |
| EC2 Instance Connect | 불필요 (임시 키) | 필요 | `ec2-user` |
| **Session Manager (SSM)** | 불필요 | **불필요** | `ssm-user` |

- Session Manager 조건: Role에 `AmazonSSMManagedInstanceCore`, SSM Agent 실행 중, EC2가 SSM 서비스로 나갈 수 있음(퍼블릭 IP 또는 NAT/엔드포인트).
- **키 페어**: 공개키(자물쇠)는 EC2 `~/.ssh/authorized_keys`, 개인키 `.pem`(열쇠)은 내 PC. 생성할 때 한 번만 다운로드. 다른 PC로 옮기면 `chmod 400` 필요.

### 5-2. 리눅스 사용자

| 사용자 / 명령 | 의미 |
|---|---|
| `root` | 최고 관리자. **SSM Run Command(배포 스크립트)와 User data는 root로 실행** |
| `ec2-user` | 기본 일반 사용자 (앱 파일 위치) |
| `ssm-user` | Session Manager 접속 사용자 → `sudo su - ec2-user`로 전환 |
| `sudo 명령` | root 권한으로 명령 하나 실행 |

### 5-3. 명령을 어디서 실행하나

| 작업 | 위치 | 이유 |
|---|---|---|
| AWS 리소스 생성, 조회, 변경 | **CloudShell** | 내 계정 권한 |
| 서버 안의 앱 확인 (`docker ps`, `curl localhost`) | EC2 (Session Manager) 또는 CloudShell에서 **SSM send-command** | 서버 안에서 실행해야 함 |

> EC2 Role에는 리소스 조회 권한(`ec2:Describe*` 등)이 없다. 최소 권한이라 **의도된 것**이다.

## 7. CloudWatch

### 개념

**AWS 리소스와 앱의 상태(지표, 로그)를 모아 보여 주고, 이상이 생기면 알려 주는 모니터링 서비스**

| 구성 요소 | 의미 | 실습 예 |
|---|---|---|
| Logs (그룹 / 스트림) | 그룹 = 앱 단위, 스트림 = 서버 단위 | `webcraft-app` / `i-0abc…` |
| Metrics | 시간에 따른 숫자 값 | `CPUUtilization`, `mem_used_percent` |
| Namespace | 지표 묶음 | `AWS/EC2`(기본), `CWAgent`(Agent가 보낸 것) |
| Alarm | 조건을 넘으면 동작 (SNS 알림, ASG 확장 등) | CPU 80% 이상 5분 |
| Agent | 서버 안에서 로그, 지표를 보내는 프로그램 | `amazon-cloudwatch-agent` |

- CPU는 Agent 없이도 수집된다. Agent가 필요한 것은 **메모리, 디스크, 앱 로그**.
- Agent는 **파일에 새로 추가되는 줄**을 읽어 보낸다 → 앱 로그가 파일로 있어야 한다 (`> ~/app.log 2>&1`).

### 실습 내용

1. **IAM Role**: `webcraft-ec2-role` 생성, `CloudWatchAgentServerPolicy` + `AmazonSSMManagedInstanceCore` → EC2에 연결
2. **Agent 설치, 설정, 시작**
   ```bash
   sudo dnf install -y amazon-cloudwatch-agent
   # /opt/aws/amazon-cloudwatch-agent/etc/config.json 작성 (mem_used_percent, disk used_percent, 로그 파일 /home/ec2-user/app.log → webcraft-app, 보관 7일)
   sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
     -a fetch-config -m ec2 -s -c file:/opt/aws/amazon-cloudwatch-agent/etc/config.json
   ```
3. **확인**: 로그 그룹 `webcraft-app`, 지표 **탐색기** → `CWAgent` → `mem_used_percent`
4. **경보**: `webcraft-cpu-high`(CPU > 80), `webcraft-mem-high`(메모리 > 90) → SNS 주제 `webcraft-alerts` 이메일 (**구독 확인 필수**)
   ```bash
   aws cloudwatch set-alarm-state --alarm-name webcraft-cpu-high --state-value ALARM --state-reason "테스트"
   ```

### 요금

| 항목 | 월 무료 |
|---|---|
| 기본 지표 | 항상 무료 |
| 커스텀 지표 | 10개 |
| 로그 수집 + 저장 | 5 GB |
| 경보 | 10개 |
| SNS 이메일 | 1,000건 |

> ASG로 서버가 늘면 커스텀 지표가 **인스턴스별로** 늘어난다.

## 9. 실습 A: SSH 방식

```
push → 러너: 빌드 → scp로 jar 전송 → ssh로 이전 버전 종료 → 교체 → nohup 실행 → curl /health
```

| 항목 | 내용 |
|---|---|
| 프로젝트 | `ci-demo` (Spring Boot 3.5.6, `GET /`, `GET /health`, 포트 8081, `--app.version=${{ github.sha }}`) |
| Secrets | `EC2_HOST`, `EC2_KEY` (.pem 전체) |
| 보안 그룹 | 22번 `0.0.0.0/0` (러너 IP가 매번 바뀜, **실습 중에만**) |

| 설계 포인트 | 이유 |
|---|---|
| `.jar.new`로 올린 뒤 교체 | 실행 중인 jar 덮어쓰기 방지 |
| PID 파일로 종료 | `pkill -f`는 스크립트 셸 자신도 종료할 수 있음 |
| `> log 2>&1 < /dev/null &` | SSH 세션이 앱을 기다리지 않게 |

- 키 관리: **CI 전용 키**(`ssh-keygen -t ed25519`)를 만들어 공개키만 EC2에 등록. 키는 이메일, 메신저, Git으로 옮기지 않는다.

## 10. 실습 B: S3 + JAR + SSM (OIDC)

### 개념

| 구성 요소 | 역할 | 비유 |
|---|---|---|
| S3 | jar 중간 보관소 | 택배 보관함 |
| SSM Run Command | 러너 → EC2 명령 전달 (22번 불필요) | 관리 사무소를 통한 지시 |
| **OIDC** | 러너가 GitHub 토큰으로 Role의 **임시 권한**을 받음 | 신분증 → 호텔 카드키 |
| ID 제공업체 | AWS가 GitHub 토큰을 믿도록 등록 (계정당 1번) | 인정하는 신분증 목록 |
| 신뢰 정책 | 어떤 저장소, 브랜치의 토큰만 받을지 | "이 사람에게만 발급" |

### 실습 내용

1. S3 `ci-demo-deploy-kgy` (퍼블릭 차단 유지)
2. EC2 Role 인라인 `ci-demo-deploy-read`: `s3:GetObject` on `deploy/*`
3. ID 제공업체: `https://token.actions.githubusercontent.com`, 대상 `sts.amazonaws.com`
4. GitHub Role `github-actions-ci-demo` (웹 자격 증명) + 인라인 `ci-demo-deploy` (S3 PutObject, 특정 EC2에 SendCommand, 결과 조회)
5. 신뢰 정책 `sub`: **숫자 ID 포함 형식** (트러블슈팅 6-4)
   ```
   repo:{GitHub아이디}@{계정숫자ID}/ci-demo@{저장소숫자ID}:ref:refs/heads/main
   ```
6. Secrets: `AWS_ROLE_ARN`, `EC2_INSTANCE_ID`, `DEPLOY_BUCKET`, `EC2_HOST`
7. 워크플로: `permissions: id-token: write` → `configure-aws-credentials@v4` → `s3 cp` → `remote.sh` 작성 → `jq`로 JSON 변환 → `ssm send-command` → 결과 확인
8. 성공 후 22번 닫고 재배포 → **22번 없이 배포** 확인, `EC2_KEY` 삭제

| 스크립트 요소 | 의미 |
|---|---|
| `\$(...)` | 러너가 아니라 **EC2에서** 해석 |
| `sudo -u ec2-user bash -lc '...'` | SSM은 root로 실행 → 앱은 ec2-user로 |
| `jq -n --rawfile s remote.sh '{commands: [$s]}'` | SSM 파라미터 형식으로 변환 |

## 11. 실습 C: ECR + Docker + SSM

### 개념

| 용어 | 의미 | 비유 |
|---|---|---|
| 이미지 | 앱 + Java + OS 환경 꾸러미 | 도시락 키트 |
| 컨테이너 | 이미지를 실행한 프로세스 | 데운 도시락 |
| Dockerfile | 이미지 레시피 | 조리법 |
| ECR | 이미지 저장소 | 도시락 창고 |
| **태그** | 이미지에 붙이는 **이름표**. 실체는 다이제스트(`sha256:…`) | 라벨 |

- **SSM과 ECR은 대체 관계가 아니다**: ECR(S3)은 **결과물 보관소**, SSM(SSH)은 **명령 전달 통로**.
- **Dockerfile은 "어떻게" 만들지, 워크플로는 "언제, 어디로", `docker run -e`는 "어떤 설정으로"** 실행할지를 정한다. Dockerfile에 프로필(`prod`)을 넣지 않는다.

### 실습 내용

1. EC2에 Docker 설치 (`dnf install docker`, `systemctl enable --now docker`, `usermod -aG docker ec2-user`)
2. ECR `ci-demo` (Private, namespace 비움, **Mutable**, 수명 주기 정책 5개 유지)
3. EC2 Role: `AmazonEC2ContainerRegistryReadOnly` / GitHub Role: 인라인 `ci-demo-ecr-push`
4. Dockerfile
   ```dockerfile
   FROM eclipse-temurin:21-jre
   WORKDIR /app
   COPY build/libs/ci-demo.jar app.jar
   EXPOSE 8081
   ENTRYPOINT ["java", "-Xmx256m", "-jar", "app.jar"]
   ```
5. 워크플로: 빌드 → ECR 로그인 → **QEMU + buildx로 `linux/arm64`** 빌드(t4g = ARM) → push → SSM으로 `docker pull` + `docker run -d --name ci-demo --restart unless-stopped -p 8081:8081`
6. 되돌리기: 이전 **SHA 태그**로 `docker run` → 1분 안에 복구

### 태그 전략 (ASG 실습에서 추가)

```yaml
tags: |
  {registry}/ci-demo:${{ github.sha }}   # 고정: 롤백용
  {registry}/ci-demo:latest              # 이동: ASG 새 서버가 받을 이미지
```

- `latest`는 이름에 특별한 기능이 있는 게 아니라, **push할 때마다 새 이미지로 옮겨 붙기 때문에** 최신을 가리킨다 (Mutable 저장소).
- 확인: `aws ecr describe-images --repository-name ci-demo --image-ids imageTag=latest --query "imageDetails[0].imageTags"` → `latest  {SHA}`

# 4부. 고가용성 구성

## 13. ALB (Application Load Balancer)

### 개념

> **로드 밸런싱**: 하나의 입구(DNS)로 들어온 요청을 **여러 서버 중 healthy인 서버 하나에** 나눠 보내서, 부하를 분산하고 장애 서버를 자동으로 제외하는 것

| 구성 요소 | 역할 |
|---|---|
| **ALB** | L7(HTTP) 로드 밸런서. **퍼블릭 서브넷, AZ 2개 이상**에 노드 생성 |
| **리스너** | 들어온 요청을 어디로 보낼지 정하는 규칙 (HTTP:80 → 대상 그룹) |
| **대상 그룹** | 보낼 서버 목록 + 포트(8081) + 헬스 체크 경로 |
| **헬스 체크** | 주기적으로 `/health` 호출. **상태 코드(200)**만 확인 |

```
사용자 ──80──▶ ALB      : 리스너 포트 (ALB SG가 허용)
ALB    ──8081──▶ EC2    : 대상 그룹 포트 (EC2 SG가 ALB SG만 허용)
```

| 질문 | 답 |
|---|---|
| ALB 노드는 하나만 활성? | 아니다. **AZ마다 노드가 있고 모두 동시에 동작** (Active-Active). DNS가 IP 여러 개를 돌려줌 → 항상 **DNS 이름**으로 접속 |
| 요청이 두 서버에 동시에 가나? | 아니다. **요청 1개 → 서버 1대**. 요청이 많으면 여러 서버로 나뉨 (기본 라운드 로빈) |
| 다른 AZ 서버로만 보내나? | 아니다. **healthy인 서버 전부**에 보냄 (Cross-zone 기본 ON) |
| ALB가 서버를 고치나? | 아니다. ALB는 **감지 + 라우팅**만. 복구는 ASG |
| 게이트웨이와 차이? | IGW/NAT는 네트워크 출입구, LB는 요청을 서버에 나눠 주는 장치 |
| 클라이언트 요청 방법이 달라지나? | 아니다. 주소(base URL)만 바뀜. 서버는 사용자 IP를 `X-Forwarded-For`로 받음 |

### 실습 내용

| 단계 | 내용 | 확인 |
|---|---|---|
| 1 | ALB SG `webcraft-alb`: 80 ← `0.0.0.0/0` | |
| 2 | 대상 그룹 `ci-demo-tg`: HTTP 8081, `/health`, 간격 10초, 임계값 2 | |
| 3 | ALB `webcraft-alb`: 인터넷 경계, 퍼블릭 2a·2b, 리스너 HTTP:80 → `ci-demo-tg` | 상태 활성 |
| 4 | `curl http://$ALB_DNS/` | 처음 503 → healthy 후 JSON |
| 5 | `webcraft-app` 8081 소스 → **`webcraft-alb` SG** | ALB OK, `EC2_IP:8081` 타임아웃 |
| 6 | 워크플로 Health check → `secrets.ALB_DNS` | Actions 성공 |
| 7 | 장애 테스트 `docker stop` → `docker start` | unhealthy → healthy 자동 전환 |

**7단계 결과 (서버 1대)**

```
대상상태=unhealthy  ALB응답=502   ← Fail-open: 전부 unhealthy면 ALB는 그래도 전부에게 보냄
대상상태=unhealthy  ALB응답=200   ← 앱이 살아나 응답 (판정은 아직 unhealthy)
대상상태=healthy    ALB응답=200   ← 헬스 체크 2회 성공 → 정상 복귀
```

| 상태 코드 | 의미 |
|---|---|
| 502 | 보냈는데 연결 거부, 응답 이상 |
| 503 | 보낼 대상이 없음 (등록 전, 대상 0개) |
| 504 | 응답 시간 초과 (주로 SG) |

## 14. ASG (Auto Scaling Group)

### 개념

> **ASG**: "서버를 항상 N대 유지하라"고 정해 두면, AWS가 **시작 템플릿**대로 서버를 만들고, 고장 나면 교체하고, 필요하면 늘리고 줄이는 기능

**ASG = 시작 템플릿(무엇을) + 규칙(몇 대, 어디에, 언제 교체)**

| 구성 | 정하는 것 | 실습 값 |
|---|---|---|
| 시작 템플릿 | 무엇을 만들지 | AL2023 Arm, t4g, SG `webcraft-app`, Role `webcraft-ec2-role`, User data |
| 용량 | 몇 대 | 원하는 2 / 최소 2 / 최대 2 → 이후 1/1/1 |
| 서브넷 | 어디에 | 2a, 2b (NAT 실습에서 프라이빗으로) |
| 대상 그룹 연결 | 누구에게 알릴지 | `ci-demo-tg`에 **자동 등록, 해제** |
| 헬스 체크 | 언제 교체할지 | **ELB 기준**, 유예 300초 |

**작동 원리**: "원하는 용량"과 "실제 healthy 서버 수"를 계속 비교해서 맞춘다 (생성, 종료, 교체).

| 고장 판단 정보원 | 보는 것 |
|---|---|
| EC2 상태 검사 (기본) | 하드웨어, OS가 살아 있는가 |
| **ELB 상태 확인 (선택)** | 앱이 `/health`에 응답하는가 → 켜야 앱 장애에도 교체됨 |
| 사용자 지정 | `set-instance-health` API |

| 역할 분담 | 감지 | 라우팅 | 복구 |
|---|---|---|---|
| ALB | ✔ | ✔ | ✘ |
| ASG | ✔ (ALB 판정 공유) | ✘ | ✔ |

**운영 방식**

| | Active-Active (웹 서버 표준) | Active-Standby |
|---|---|---|
| 평소 | 여러 AZ 서버가 모두 처리 | 한 대만 처리 |
| 장애 시 | 즉시, 무중단 | 수십 초~수 분 중단 |
| 주 사용처 | EC2 + ALB + ASG | DB (RDS Multi-AZ) |

### 실습 내용

| 단계 | 내용 | 이유 |
|---|---|---|
| 1 | 이미지에 `latest` 태그 추가 | 새 서버의 부팅 스크립트는 SHA를 모름 |
| 2 | 서브넷 퍼블릭 IP 자동 할당 확인 | NAT 없이 ECR, SSM에 나가려면 필요 |
| 3 | 시작 템플릿 `ci-demo-lt` | ASG의 설계도 |
| 4 | ASG `ci-demo-asg` (2a·2b, `ci-demo-tg`, ELB 헬스 체크, 태그 `App=ci-demo`) | 서버 자동 생성 + 대상 그룹 자동 등록 |
| 5 | 기존 EC2를 대상 그룹에서 해제 | ALB 뒤를 ASG 서버만으로 |
| 6 | 장애 테스트 | 무중단 + 자동 교체 확인 |
| 7 | 배포 워크플로를 ASG 전체로 | 서버 ID가 바뀌어도 배포 |

**User data** (첫 부팅 때 1번, root로 실행)

```bash
#!/bin/bash
set -e
REGION=ap-northeast-2
REGISTRY={계정ID}.dkr.ecr.$REGION.amazonaws.com
dnf install -y docker
systemctl enable --now docker
TOKEN=$(curl -sX PUT http://169.254.169.254/latest/api/token -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
IID=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-id)
aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin $REGISTRY
docker pull $REGISTRY/ci-demo:latest
docker run -d --name ci-demo --restart unless-stopped -p 8081:8081 \
  $REGISTRY/ci-demo:latest --app.version=latest-$IID
```

**6단계 결과 (서버 2대)**

```
03:37:22  응답=200  서버=i-051ad  ASG=[i-051ad Healthy, i-0ff36 InService Unhealthy]   ← 감지
03:37:27  응답=200  서버=i-051ad  ASG=[..., i-0fc5d Pending, i-0ff36 Terminating]      ← 교체 시작
03:38:40  응답=200  서버=i-051ad  ASG=[i-051ad, i-0fc5d]                               ← 다시 2대
```

- 장애 동안 응답이 **계속 200** (ALB 실습에서는 502가 계속됨) → 이중화 효과
- **사람 개입 없이** 교체. `docker stop`(앱만 죽음)인데 교체된 것은 **ELB 헬스 체크** 덕분
- ASG `InService` ≠ 대상 그룹 `healthy`. 새 서버는 앱이 뜬 뒤에 응답에 섞임

**7단계: 배포를 ASG 전체로**

```bash
# 배포할 때마다 ASG에 현재 서버 목록을 물어봄
IDS=$(aws autoscaling describe-auto-scaling-groups --auto-scaling-group-names ci-demo-asg \
  --query "AutoScalingGroups[0].Instances[?LifecycleState=='InService'].InstanceId" --output text)

# 롤링 배포: 한 대씩, 1대라도 실패하면 중단
aws ssm send-command --instance-ids $IDS --max-concurrency 1 --max-errors 0 ...
# 각 서버 스크립트 끝에서 localhost:8081/health가 OK일 때까지 대기 → 다음 서버로
```

- IAM: `ssm:SendCommand`를 `instance/*` + 조건 `ssm:resourceTag/App = ci-demo` → 태그 없는 webcraft 서버는 차단
- 추가 권한: `autoscaling:DescribeAutoScalingGroups`, `ssm:ListCommands`
- push해도 서버는 교체되지 않는다. **서버는 그대로, 컨테이너만** 교체 (서버까지 교체하려면 인스턴스 새로 고침)

## 15. NAT 게이트웨이

### 개념

> **NAT 게이트웨이**: 프라이빗 서브넷 서버가 **밖으로 나가는 것만** 허용하는 출구. 밖에서 먼저 들어오는 연결은 막는다.

| | IGW | NAT |
|---|---|---|
| 방향 | 양방향 | 나가기만 (응답은 돌아옴) |
| 위치 | VPC에 1개 | **퍼블릭 서브넷 안** (NAT 자신도 IGW로 나가야 하므로) |
| 주소 변환 | 1:1 | 여러 서버 → EIP 하나 (N:1) |
| 요금 | 무료 | **시간당 + GB당** |

### 실습 내용 (전부 CloudShell)

| 단계 | 명령 | 하는 일 |
|---|---|---|
| 2 | `allocate-address` → `create-nat-gateway --subnet-id {public1}` → `wait nat-gateway-available` | EIP 할당 + 퍼블릭 2a에 NAT |
| 3 | `create-route --route-table-id {private1/2} --destination-cidr-block 0.0.0.0/0 --nat-gateway-id $NAT` | 프라이빗에 "밖으로는 NAT로" 길 안내 |
| 4 | `update-auto-scaling-group --vpc-zone-identifier "{private1},{private2}"` → `terminate-instance-in-auto-scaling-group --no-should-decrement-desired-capacity` | ASG 위치 변경 + 기존 서버 교체 |
| 5 | 확인 (아래) | |
| 6 | 정리 (17장) | |

**5단계 결과**

```
subnet-0996f54dd707089cb  10.0.145.150  None   ← 프라이빗, 공인 IP 없음
Online                                         ← NAT 경유 SSM 연결
i-0931acb35599107db  healthy                   ← ALB → 프라이빗 EC2 (local)
{"message":"Hello ASG!", ...}                  ← NAT 경유 docker pull 성공
NAT의 EIP:       52.78.174.99
서버가 본 내 IP: 52.78.174.99                   ← 나가는 트래픽이 EIP로 변환됨
```

| 확인 | 증명 |
|---|---|
| 공인 IP `None` | 서버가 인터넷에 직접 노출되지 않음 |
| SSM `Online` | 공인 IP 없이도 NAT로 나감 |
| healthy + JSON | 들어오는 길(ALB)과 나가는 길(NAT)이 분리되어 모두 동작 |
| IP 일치 | NAT가 주소를 변환함 |

# 5부. 운영 원칙과 비용

## 16. 설계 원칙

### 서버 안에는 아무것도 남기지 않는다 (ASG의 전제)

| 남는 곳 | 무엇 |
|---|---|
| 시작 템플릿 | 서버를 어떻게 만들지 |
| 이미지 (ECR) | 무엇을 실행할지 |
| Parameter Store / Secrets Manager | 앱 설정, 비밀번호 |
| RDS / ElastiCache / S3 | 데이터, 세션, 파일 |
| CloudWatch | 로그, 지표 |
| ~~서버 디스크~~ | 교체되면 **사라짐** (SSH로 고친 설정, 로컬 파일, 로컬 로그) |

- **Pets vs Cattle**: 수동 관리 서버(webcraft EC2)는 Pet, ASG 서버는 Cattle(아프면 교체). 운영 웹 서버는 Cattle이 표준.
- 디버깅을 위해 접속하는 것은 괜찮지만, 고친 내용은 **반드시 템플릿이나 이미지에 반영**한다.

### Build once, deploy anywhere

- 이미지는 한 번만 빌드하고, 환경 차이는 **실행할 때** 주입한다.
- Spring 프로필은 파일에 적지 않고 `docker run -e SPRING_PROFILES_ACTIVE=prod`로 지정한다. 배포 스크립트와 User data **양쪽에 같은 값**.
- prod 설정에는 DB 기본값을 두지 않는다 → 환경 변수를 빠뜨리면 **기동 실패**(잘못된 DB 접속 방지).

### 헬스 체크 경로

| 경로 | DB 포함 | 용도 |
|---|---|---|
| `/actuator/health` | ✔ | 사람, 모니터링 |
| `/actuator/health/liveness` | ✘ | 프로세스 생존 |
| `/actuator/health/readiness` | ✘ | **ALB 대상 그룹** (기동 중, 종료 중에는 503) |

> ALB 헬스 체크에 DB를 넣으면, DB가 잠깐 느려질 때 **모든 서버가 unhealthy** → ASG가 멀쩡한 서버를 전부 교체하는 연쇄 장애가 생긴다.

## 17. 과금 기준과 정리 순서

### 과금 단위

| 리소스 | 과금 | 10분만 써도 |
|---|---|---|
| **NAT 게이트웨이** | 시간(**일부도 1시간**) + GB | 1시간 요금 |
| **ALB** | 시간(**일부도 1시간**) + LCU | 1시간 요금 |
| EC2 (Linux) | **초 단위** (최소 60초) | 10분 요금 |
| 퍼블릭 IPv4 / EIP | 시간당 (**연결 여부와 무관**) | 1시간 요금 |
| SNS 이메일 | 월 1,000건 무료 | - |
| ASG, 시작 템플릿, 대상 그룹, SG, IGW | 무료 | - |

- 만들고 지우기를 반복하면 생성할 때마다 새 1시간이 시작된다 → **한 번에 끝내기**
- 대략: NAT 시간당 약 $0.06, ALB 약 $0.02대, IPv4 약 $0.005 (정확한 값은 요금 페이지, Billing에서 확인)

### NAT 실습 정리 순서 (순서가 중요)

```bash
# ① 서버 먼저 0대 (NAT를 먼저 지우면 새 서버가 docker pull 실패 → 교체 루프)
aws autoscaling update-auto-scaling-group --auto-scaling-group-name ci-demo-asg --min-size 0 --desired-capacity 0
# ② 프라이빗 테이블의 NAT 경로 삭제 (blackhole 방지)
aws ec2 delete-route --route-table-id {private RT} --destination-cidr-block 0.0.0.0/0
# ③ NAT 삭제 → 완전히 삭제될 때까지 대기
aws ec2 delete-nat-gateway --nat-gateway-id $NAT && aws ec2 wait nat-gateway-deleted --nat-gateway-ids $NAT
# ④ EIP 릴리스 (NAT가 지워진 뒤에만 가능)
aws ec2 release-address --allocation-id $ALLOC
# ⑤ ALB 삭제
aws elbv2 delete-load-balancer --load-balancer-arn $ALB_ARN
```

### 고아 리소스 점검 습관

**EC2 → 탄력적 IP**, **VPC → NAT 게이트웨이**, **EC2 → 로드 밸런서**, **EC2 → 볼륨(사용 가능 상태)**, **Billing → 청구서**

# 6부. 트러블슈팅

## 6-1. SSH, EC2 접속

| 증상 / 로그 | 원인 | 해결 |
|---|---|---|
| `Connection timed out` | 보안 그룹 22번 소스, **프라이빗 서브넷**에 있는 EC2, 바뀐 퍼블릭 IP | SG(내 IP), 서브넷 라우팅(IGW), 현재 IP 확인 |
| `UNPROTECTED PRIVATE KEY FILE` | 키 권한이 너무 열림 | `chmod 400` (Windows는 `icacls`) |
| `Permission denied (publickey)` | 키 또는 사용자명 틀림 | 키 페어, `ec2-user` 확인 |
| Session Manager 연결 버튼 비활성 | Role에 SSM 정책 없음, Agent 오프라인 | 정책 확인, 5분 대기, `systemctl restart amazon-ssm-agent` |
| `ConnectionLost` | EC2가 SSM으로 나가지 못함 | 퍼블릭 IP 또는 NAT/엔드포인트 |
| 접속 후 `~`에 파일이 없음 | `ssm-user`로 접속 | `sudo su - ec2-user` |
| 실수로 SSM Agent 중지 + 22번 닫힘 | 접속 통로 없음 | 콘솔에서 EC2 재부팅 |
| EC2 터미널에서 `UnauthorizedOperation ... ec2:DescribeInstances` | 리소스 조회 명령을 **EC2 안에서** 실행 (EC2 Role은 최소 권한) | **CloudShell**에서 실행 |

## 6-2. 앱 실행, RDS, ElastiCache

| 증상 / 로그 | 원인 | 해결 |
|---|---|---|
| `Access denied ... to database 'mysql'` | 초기 DB를 안 만들어 시스템 DB에 접속 | `CREATE DATABASE webcraft ...` 후 URL 변경 |
| `Unknown database 'xxx'` | DB가 없음, 또는 **다른 MySQL에 접속** (로컬 MySQL과 포트 충돌) | `CREATE DATABASE`, 포트 확인 |
| `Communications link failure` | 네트워크 (SG, 엔드포인트), DB가 아직 기동 중 | SG 3306 소스, 엔드포인트 |
| `Host has a port: ...:6379` | Redis 호스트 값에 포트 포함 | 호스트만 입력 |
| Redis 연결이 멈춤 | 전송 중 암호화 필수인데 TLS 미설정 | `spring.data.redis.ssl.enabled=true`, 클러스터면 구성 엔드포인트 |
| `Another server is already running` | `Ctrl+Z`로 멈춘 이전 프로세스가 DB 잠금 보유 | `kill -9 {PID}` |
| `Port 8080 was already in use` | 이전 앱 실행 중 | `pgrep -af java` 후 종료 |
| `no main manifest attribute` | `-plain.jar` 실행 | `jar { enabled = false }` |
| `Exit 143` / `Exit 137` | kill 종료 / kill -9 또는 메모리 부족 | 143은 정상, 137이면 `-Xmx` 확인 |
| `You reached the maximum number of instances` | 무료 플랜 인스턴스 수 제한 | 안 쓰는 인스턴스 종료, 다른 리전 확인 |

| push `rejected (fetch first)` | 저장소 생성 시 README 체크 | 저장소 재생성, 또는 pull 후 push |
| Actions가 실행 안 됨 | 브랜치 `master` | `git branch -M main` |
| `Permission denied: ./gradlew` | 실행 권한 | `chmod +x gradlew` |
| SSH 단계 `i/o timeout` | 22번이 러너를 막음 | 실습 중 22번 `0.0.0.0/0` |
| SSH 스크립트가 중간에 끊김 | `pkill -f`가 자기 셸 종료 | PID 파일 방식 |
| `Credentials could not be loaded` | `permissions: id-token: write` 누락, Secret 이름 오타 | 워크플로, Secret 확인 |
| **`Request ARN is invalid`** | `AWS_ROLE_ARN`에 Role ARN이 아닌 값 | `aws iam get-role --role-name github-actions-ci-demo --query Role.Arn --output text` 결과로 재등록 |
| **`Not authorized to perform sts:AssumeRoleWithWebIdentity`** | 신뢰 정책 `sub`와 토큰 값 불일치. 실제 토큰은 **숫자 ID 포함** (`repo:{아이디}@{숫자}/ci-demo@{숫자}:ref:refs/heads/main`) | Debug 단계로 토큰의 `iss`, `aud`, `sub`를 출력해 **그대로** 신뢰 정책에 반영 (`update-assume-role-policy`). 숫자 ID는 고정값, 저장소를 다시 만들면 바뀜 |
| S3 `AccessDenied` | GitHub Role의 버킷, 경로 | 정책 확인 |
| SSM `AccessDeniedException` | 정책의 계정, 인스턴스 ID, 리전 / ASG 이후에는 **서버에 `App=ci-demo` 태그 없음** | 정책, ASG 태그 "새 인스턴스에 태그 지정" 확인 |
| `AccessDenied ... autoscaling:DescribeAutoScalingGroups` | IAM 정책 수정 전에 push | 정책 수정 후 **Re-run jobs** |
| `InService 인스턴스 없음` | ASG 원하는 용량 0 | 용량 1 이상 |
| ECR `not authorized ... GetAuthorizationToken` | GitHub Role에 ECR 정책 없음 | `ci-demo-ecr-push` |
| `COPY failed: build/libs/... not found` | jar 빌드 실패, 이름 불일치, `.dockerignore`에 `build` | 빌드 순서, `archiveFileName` |
| EC2 `no basic auth credentials` | EC2 Role에 ECR 읽기 없음 | `AmazonEC2ContainerRegistryReadOnly` |
| 컨테이너 `exec format error` | 이미지 아키텍처 불일치 | `platforms: linux/arm64` (t4g), AMI도 Arm |
| `port is already allocated` | 8081 사용 중 (이전 jar 방식) | PID 파일로 이전 jar 종료 |

## 6-5. ALB

| 증상 / 로그 | 원인 | 해결 |
|---|---|---|
| `503 Service Temporarily Unavailable` | healthy 대상이 없음 (등록 전, 헬스 체크 미통과) | `describe-target-health`, 서버에서 `curl localhost:8081/health`, SG 8081 |
| unhealthy인데 503이 아니라 **502** | **Fail-open**: 대상이 전부 unhealthy면 ALB는 그래도 전부에게 보냄 | 오류 아님. 서버 2대 이상이면 healthy로만 보냄 |
| 타임아웃 | `https://`로 접속(443 리스너 없음), ALB SG 80 미허용 | `http://`, SG 확인 |
| `/health`가 "not ok"인데 healthy | 헬스 체크는 **상태 코드만** 확인 | 오류 아님 |
| 5단계 이후 Actions Health check 실패 | 러너도 8081 직접 접근 불가 | `ALB_DNS`로 변경 |

## 6-6. ASG

| 증상 / 로그 | 원인 | 해결 |
|---|---|---|
| 대상 그룹 `Target.FailedHealthChecks`인데 ASG는 `Healthy` | **유예 기간** 중이라 ASG가 ELB 판정을 무시. t4g에서 Docker 설치 → pull → JVM 기동이 느림 | 기다리기, 유예 기간 **300초** |
| 생성과 종료가 반복됨 | 앱이 유예 기간 안에 뜨지 못하는 **교체 루프** | `suspend-processes --scaling-processes ReplaceUnhealthy` → 원인 수정 → `resume-processes` |
| 원인 찾는 순서 | - | ① `TargetHealth.Reason` ② 공인 IP / IAM 프로파일 / arm64 / SSM Online ③ `/var/log/cloud-init-output.log` ④ `docker ps -a` ⑤ `curl localhost:8081/health` |
| `Target.Timeout` | 연결 자체가 안 됨 | **보안 그룹** |
| 템플릿을 고쳤는데 기존 서버가 그대로 | 템플릿은 **새 서버부터** 적용 | 서버 교체 또는 인스턴스 새로 고침 |
| 축소 시 원하지 않는 서버가 종료됨 | 기본 종료 정책 (AZ 균형 → 오래된 템플릿 → …) | 필요하면 축소 보호 |

## 6-7. NAT, CloudShell

| 증상 / 로그 | 원인 | 해결 |
|---|---|---|
| CLI 출력이 `:`에서 멈춤 | AWS CLI v2의 **less 페이저** | `q`, 이후 `export AWS_PAGER=""` |
| 감시 루프가 Ctrl+C로 안 멈춤 | Ctrl+C가 그 순간의 명령만 종료 / 텍스트 선택 시 복사로 처리 | 화면 클릭 후 연타, Ctrl+Z → `kill %1`. 예방: `trap 'break' INT` + 횟수 제한 루프 |
| `wait` 중에 붙여 넣은 명령이 쌓임 | 앞 명령이 끝나지 않아 입력 버퍼에 대기 | 기다리면 순서대로 실행. **앞 명령이 실패해도 뒤 명령이 실행**되니 결과 확인 |
| `--max-items` 출력 끝의 `None` | 다음 페이지 토큰 | 오류 아님 |
| `release-address`에서 `InvalidIPAddress.InUse` | NAT가 아직 완전히 삭제되지 않음 | 1분 후 재시도 |
| 정리 후에도 EIP가 남아 있음 (`52.78.165.238`) | ENI 주인이 **RDS** (`RDSNetworkInterface`, 퍼블릭 액세스 = 예) | RDS 수정 → 퍼블릭 액세스 **아니요** → 즉시 적용 (TODO) |
