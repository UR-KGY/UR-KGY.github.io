# API와 RESTful API 정리

## API란

API(Application Programming Interface)는 서로 다른 소프트웨어가 상호작용할 수 있도록 정의된 규칙이다. "이런 형식으로 요청을 보내면 이런 결과를 반환한다"는 일종의 약속이다.

API는 웹에서만 쓰이는 개념이 아니다. 프로그래밍 언어의 라이브러리 함수, 운영체제가 제공하는 기능 역시 API에 해당한다. 다만 서버 개발 맥락에서는 보통 클라이언트(브라우저, 앱)가 서버에 데이터나 기능을 요청하는 창구, 즉 웹 API를 의미하는 경우가 많다.

## RESTful API란

RESTful API는 API를 설계하는 여러 방식 중 하나다. REST(Representational State Transfer)라는 아키텍처 원칙을 따르는 웹 API를 RESTful API라고 부른다. 모든 API가 REST 방식인 것은 아니며, REST 외에도 SOAP, GraphQL, gRPC 등 다른 설계 스타일이 존재한다.

### REST의 핵심 원칙

- **자원(Resource)을 URI로 표현한다.** `/users/1`처럼 명사형 주소로 자원을 나타낸다. `/getUser1`과 같은 동사형 URL은 REST 스타일에 맞지 않는다.
- **행위는 HTTP 메서드로 구분한다.** 같은 URI라도 HTTP 메서드에 따라 의미가 달라진다. GET은 조회, POST는 생성, PUT/PATCH는 수정, DELETE는 삭제를 뜻하며, 이는 CRUD와 HTTP 메서드의 매칭이다.
- **Stateless(무상태)다.** 서버는 이전 요청의 상태를 기억하지 않는다. 매 요청마다 필요한 정보(인증 토큰 등)를 요청 자체에 포함해야 한다.
- **응답은 자원의 상태를 표현한다.** 보통 JSON(또는 XML) 형식으로 반환된다.

### 예시

| HTTP 메서드 | URI | 의미 |
|---|---|---|
| GET | `/api/users/1` | 1번 유저 조회 |
| POST | `/api/users` | 유저 생성 |
| PUT | `/api/users/1` | 1번 유저 전체 수정 |
| DELETE | `/api/users/1` | 1번 유저 삭제 |

### 참고: "완벽한 REST"와 실무의 차이

Roy Fielding이 처음 정의한 REST는 HATEOAS(응답에 다음 가능한 행동 링크를 포함하는 것)를 포함한 더 엄격한 규칙을 갖는다. 하지만 실무에서 "REST API"라 불리는 것 대부분은 이 원칙을 전부 지키지는 않는다. 일반적으로는 "URI로 자원을 표현하고, HTTP 메서드로 행위를 구분하며, JSON으로 응답하는 API"를 통칭해 RESTful API라고 부른다.

## 웹 서버와 WAS

- **HTTP**는 정적 콘텐츠가 아니라, 클라이언트-서버 간 통신 규약(프로토콜)이다. 웹 서버와 WAS 모두 이 위에서 동작한다.
- **웹 서버(Web Server)**: 정적 자원(HTML, CSS, JS, 이미지)을 그대로 찾아 응답한다. 예: Apache, Nginx.
- **WAS(Web Application Server)**: 요청마다 서버 로직을 실행해 동적으로 결과를 생성한다. 예: Tomcat, JBoss, WildFly.
- **병행 사용 이유**:
  - 정적 파일 처리는 웹 서버가 더 가볍고 빠르다.
  - 웹 서버가 여러 WAS로 요청을 분산(로드 밸런싱)한다.
  - 웹 서버가 앞단에서 요청을 필터링해 WAS를 외부에 직접 노출하지 않는다(보안).
  - HTTPS 처리(SSL termination)를 웹 서버가 전담해 WAS 부담을 줄인다.
  - 여러 서비스/경로를 하나의 창구에서 라우팅할 수 있다.

## HTTP와 HTTPS

- **HTTPS = HTTP + Secure(보안).** 통신 내용을 암호화(SSL/TLS)한다는 점이 유일한 차이다.
- HTTP는 평문으로 데이터를 주고받아 중간에서 도청·변조가 가능하다.
- HTTPS는 암호화를 거치므로 로그인 정보, 개인정보 등을 안전하게 전송할 수 있다.
- 기본 포트: HTTP는 80번, HTTPS는 443번.

## Tomcat

- 자바 서블릿을 실행하는 서블릿 컨테이너(WAS의 일종).
- 원래는 별도 설치 후 war 파일을 배포하는 방식이 전통적이었다.
- 스프링 부트는 Tomcat을 내장(embedded)하고 있어, 별도 설치·배포 없이 `main` 실행만으로 서버가 뜬다.
- 기본 포트는 **8080**번이다(HTTP 표준 포트 80과 겹치지 않도록 관례적으로 사용). `application.properties`에서 `server.port` 값으로 변경 가능하다.

## HTTP 상태 코드

응답 코드의 첫 자리 숫자로 5가지 범주로 나뉜다.

| 범주 | 의미 | 대표 코드 |
|---|---|---|
| 1xx | 정보성 — 요청을 받았고 처리 중, 최종 응답 아님 | 100 Continue, 101 Switching Protocols |
| 2xx | 성공 — 요청이 정상 처리됨 | 200 OK, 201 Created, 204 No Content |
| 3xx | 리다이렉션 — 완료하려면 다른 URL로 추가 요청 필요 | 301 Moved Permanently, 302 Found, 304 Not Modified |
| 4xx | 클라이언트 오류 — 요청 자체에 문제가 있음 | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found |
| 5xx | 서버 오류 — 요청은 정상이나 서버 처리 중 오류 발생 | 500 Internal Server Error, 503 Service Unavailable |

## Postman

- HTTP 요청(GET, POST, PUT, DELETE 등)을 GUI로 손쉽게 구성하고 보내는 도구.
- 브라우저 주소창은 GET만 간편하게 지원하지만, Postman은 헤더·JSON 본문까지 자유롭게 설정 가능하다.
- 프론트엔드 없이도 백엔드 API 동작을 먼저 검증할 수 있다.

## 크롬 개발자도구 — Network 탭

브라우저가 서버로 보낸 모든 HTTP 요청/응답을 실시간으로 확인하는 탭. 백엔드 개발 시 가장 자주 쓰게 된다. 요청 목록에서 하나를 클릭하면 아래 하위 탭들로 상세 정보를 볼 수 있다.

- **Headers**: 요청 URL, HTTP 메서드, 상태 코드를 한눈에 보여준다. `Request Headers`(브라우저가 보낸 헤더: 쿠키, 인증 토큰 등)와 `Response Headers`(서버가 돌려준 헤더: Content-Type 등)로 나뉜다.
- **Payload / Request**: 요청 시 함께 보낸 데이터(JSON body, 쿼리 파라미터 등)를 보여준다.
- **Response**: 서버가 실제로 반환한 응답 본문(raw)을 그대로 보여준다.
- **Preview**: Response와 같은 내용이지만, JSON이면 트리 구조로 보기 좋게 파싱해서 보여준다.
- **Timing**: 요청부터 응답까지 걸린 시간을 단계별로 보여준다.

앞으로는 Headers에서 상태 코드·요청 방식을 먼저 확인하고, Response(또는 Preview)에서 실제 데이터가 의도대로 왔는지 확인하는 흐름을 자주 쓰게 된다.

## HTTP 요청/응답 구조: Headers vs Payload

> 참고: HTML(마크업 언어, 페이지 구조)과 HTTP(통신 프로토콜, 요청/응답 형식)는 다른 개념이다. 아래 내용은 HTTP 메시지의 구조다.

Network 탭의 **Headers**는 실제로 세 부분을 묶어 보여준다.

- **General**: Request URL(요청 대상), Request Method(GET/POST 등), Status Code(성공/실패 여부). 엄밀히는 헤더가 아니라 요청/응답의 첫 줄(요청 라인·상태 라인)이지만 편의상 Headers 탭에 함께 표시된다.
- **Request Headers**: 브라우저가 보내는 부가 정보(User-Agent, Accept, Cookie 등).
- **Response Headers**: 서버가 응답하며 보내는 부가 정보(Content-Type, Content-Length 등).

**Payload(요청 본문)**는 메서드 목적에 따라 쓰임이 다르다.

- **GET**: 데이터 "조회"가 목적이라 조건을 URL 쿼리스트링(`?id=1`)으로 전달한다. 별도 Payload가 거의 없다.
- **POST / PUT / PATCH**: 데이터 "생성·수정"이 목적이라, URL만으로 전달하기 부족한 실제 데이터(예: 회원 이름·이메일)를 JSON 형태로 Payload에 담아 보낸다.

즉 Headers는 "요청/응답에 대한 메타데이터", Payload는 "서버에 넘기는 실제 데이터"라는 차이가 있다.

## 한 줄 정리

- API는 소프트웨어 간 상호작용을 위한 규칙이다.
- RESTful API는 자원과 URI, HTTP 메서드를 활용해 설계하는 API의 한 방식이다.
- 웹 서버는 정적 자원을, WAS는 동적 로직을 처리하며 함께 쓰면 성능·보안·확장성 면에서 유리하다.
- HTTPS는 HTTP에 암호화(보안)가 추가된 것이며, 기본 포트는 각각 80번·443번이다.
- Tomcat은 스프링 부트에 내장된 WAS이며 기본 포트는 8080번이고, Postman은 API 테스트용 도구다.
- HTTP 상태 코드는 1xx(정보성), 2xx(성공), 3xx(리다이렉션), 4xx(클라이언트 오류), 5xx(서버 오류)로 구분된다.
- 크롬 개발자도구의 Network 탭에서 Headers(요청/응답 헤더, 상태 코드)와 Response(응답 본문)를 확인하며 API 동작을 디버깅할 수 있다.
- Headers는 요청/응답의 메타데이터이고, Payload는 실제 데이터다. GET은 URL 쿼리로 조회하고, POST/PUT/PATCH는 Payload에 실제 데이터를 담아 보낸다.
