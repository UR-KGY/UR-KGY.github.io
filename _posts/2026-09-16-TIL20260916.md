# 개인 프로젝트 시작 전 강의 개념 정리

어제 다 못한 내용정리를 수행하였다.
내일부터 개인프로젝트를 시작할 생각이고 시작전에 다시 정리 내용과 강의를 한번씩 정독해본다.
시간이 빠듯할테니 부족한 부분은 직접 써보면서 채운다.
(특히 웹소켓,JWT 부분이 제일 걱정이긴한데 모르면 물어봐서라도 알아야한다)

## 1. JWT 인증 흐름

### 발급 순서
```
회원가입 → DB에 유저 정보 저장
로그인 → 입력 정보와 DB 유저 정보 비교 → 검증 성공 시 액세스 토큰(JWT) 발급
이후 요청마다 → 클라이언트가 Authorization 헤더에 토큰을 담아 전송 → 서버가 매 요청마다 검증
```

서버는 응답 바디에 문자열을 실어 보내는 것까지만 책임진다. 토큰 문자열을 DTO에 담아 응답하면 그 값을 저장할지, 어디에 저장할지(localStorage, 메모리 변수, 모바일 시큐어 스토리지 등)는 전적으로 클라이언트 코드가 결정한다. 쿠키(`Set-Cookie`)와 달리 JSON 바디로 전달된 토큰은 브라우저가 자동으로 저장해주지 않는다. 클라이언트가 명시적으로 저장 코드를 작성해야만 이후 요청에 재사용할 수 있다.

### JwtProvider

| 필드/메서드 | 설명 |
|---|---|
| `secretKey` | 서명(signature)을 만들 때 쓰는 키 |
| `accessTTLSeconds` | 토큰 만료 시간(초) |
| `createAccessToken(User user)` | 유저 정보로 JWT 문자열을 생성. 유저의 `Role`(일반/관리자 구분 enum)도 포함 |
| `parseToken(String token)` | 서명·만료시간 검증 → 성공 시 `AuthUser` DTO(검증된 유저 정보) 반환, 실패 시 예외 발생 |

## 2. JwtAuthenticationFilter

`OncePerRequestFilter`를 상속. DispatcherServlet 도달 전(전처리)과 Controller 처리 후(후처리) 로직을 수행하는 필터의 전체 클래스는 다음과 같습니다.

```java
@RequiredArgsConstructor
public class JwtAuthenticationFilter extends OncePerRequestFilter {
    private final JwtProvider jwtProvider;

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain filterChain
    ) throws ServletException, IOException {
        String authorization = request.getHeader(HttpHeaders.AUTHORIZATION);
        if (authorization == null || !authorization.regionMatches(true, 0, "Bearer ", 0, 7)) {
            filterChain.doFilter(request, response);
            return;
        }
        AuthUser authUser;
        try {
            String token = authorization.substring(7);
            authUser = jwtProvider.parseToken(token);
        } catch (ResponseStatusException exception) {
            SecurityContextHolder.clearContext();
            response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            return;
        }
        SimpleGrantedAuthority authority = new SimpleGrantedAuthority("ROLE_" + authUser.getRole().name());
        List<SimpleGrantedAuthority> authorities = List.of(authority);
        Authentication authentication = new JwtAuthenticationToken(authUser, authorities);
        SecurityContext context = SecurityContextHolder.createEmptyContext();
        context.setAuthentication(authentication);
        SecurityContextHolder.setContext(context);
        try {
            filterChain.doFilter(request, response);
        } finally {
            SecurityContextHolder.clearContext();
        }
    }
}
```

### 매개변수
| 매개변수 | 역할 |
|---|---|
| `HttpServletRequest` | 요청 정보 조회. Controller에서는 `HandlerMethodArgumentResolver`가 필요한 부분만 추출해주지만, Filter는 그런 장치가 없어 객체 자체를 받아야 함 |
| `HttpServletResponse` | 응답 생성. 인증 실패 시 `response.setStatus(401)`처럼 직접 상태코드를 설정 |
| `FilterChain` | 다음 대상(다음 필터 또는 DispatcherServlet)으로 넘기는 통로. `doFilter()` 호출 시 다음으로 진행 |

### 처리 단계 설명

**1) Authorization 헤더 형식 확인** (`if (authorization == null || !authorization.regionMatches(...))`)
`regionMatches(true, 0, "Bearer ", 0, 7)`은 앞 7글자가 대소문자 무시하고 `"Bearer "`와 일치하는지 확인. 토큰이 없거나 Bearer 방식이 아니면 이 필터는 관여하지 않고 그대로 통과시킴

**2) 토큰 검증** (`try { ... authUser = jwtProvider.parseToken(token); } catch (ResponseStatusException ...)`)
"토큰 없음"(1단계, 통과)과 "토큰은 있는데 무효함"(이 단계, 즉시 401 후 종료)은 의미가 다르게 처리됨. `SecurityContextHolder.clearContext()`는 방어적 정리.

**3) 검증 성공 후 인증 정보 등록** (나머지 전체)
- `"ROLE_"` 접두어가 있어야 `hasRole("ADMIN")` 계열 검사가 동작함(Spring Security 관례).
- `SecurityContextHolder`는 ThreadLocal 기반 — 스레드 풀 재사용 시 인증정보가 다음 요청으로 새는 것을 막기 위해 `finally`로 반드시 정리.
- `try/finally`인 이유: `doFilter()` 내부(다음 필터~Controller)에서 예외가 나도 정리 로직은 반드시 실행되어야 하므로.

## 3. JwtSecurityConfig — 필터를 빈으로 등록

```java
@Configuration
public class JwtSecurityConfig {
    @Bean
    public SecurityFilterChain jwtSecurityFilterChain(
            HttpSecurity http,
            JwtProvider jwtProvider
    ) throws Exception {
        http
                .csrf(AbstractHttpConfigurer::disable) // 쿠키 인증 없이 Bearer 헤더를 쓰므로 CSRF 보호 끄기
                .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS)) // 요청마다 JWT를 검증하므로 인증용 세션 사용 안 함
                .requestCache(AbstractHttpConfigurer::disable) // 로그인 후 이동할 페이지가 없어 요청 저장 끄기
                .formLogin(AbstractHttpConfigurer::disable) // JSON 로그인 API를 쓰므로 기본 로그인 폼 끄기
                .httpBasic(AbstractHttpConfigurer::disable) // JWT로 요청을 인증하므로 HTTP Basic 인증 끄기
                .logout(AbstractHttpConfigurer::disable) // JWT 인증을 사용하므로 세션 기반 로그아웃 끄기
                .authorizeHttpRequests(authorize -> authorize
                        .dispatcherTypeMatchers(DispatcherType.ERROR).permitAll()
                        .requestMatchers(HttpMethod.GET, "/posts").permitAll()
                        .requestMatchers(HttpMethod.POST, "/auth/signup", "/auth/login", "/admin/signup").permitAll()
                        .requestMatchers("/admin/**").hasRole("ADMIN")
                        .anyRequest().authenticated())
                .exceptionHandling(exceptions -> exceptions
                        .authenticationEntryPoint((request, response, exception) ->
                                response.setStatus(HttpServletResponse.SC_UNAUTHORIZED))
                        .accessDeniedHandler((request, response, exception) ->
                                response.setStatus(HttpServletResponse.SC_FORBIDDEN)))
                .addFilterBefore(new JwtAuthenticationFilter(jwtProvider), AuthorizationFilter.class);
        return http.build();
    }
}
```

| authorizeHttpRequests 규칙 | 의미 |
|---|---|
| `dispatcherTypeMatchers(ERROR).permitAll()` | 에러 포워딩 요청은 인증 없이 허용 |
| `GET "/posts" → permitAll()` | 공개 조회 |
| `POST "/auth/signup", "/auth/login" 등 → permitAll()` | 로그인 전에 접근해야 하는 API |
| `"/admin/**" → hasRole("ADMIN")` | 관리자 전용 |
| `anyRequest().authenticated()` | 나머지는 로그인 필수 |

결국 `addFilterBefore(필터, AuthorizationFilter.class)`로 필터를 추가시켜준다는 것을 알아두고 나머지 설정들은 사용해보면서 알도록 하자.

## 4. 인증 정보를 이용한 접근 제어

### @AuthenticationPrincipal

```java
@RestController
@RequiredArgsConstructor
public class UserController {
    private final UserService userService;

    @GetMapping("/me")
    public ResponseEntity<UserResponse> me(
            @AuthenticationPrincipal AuthUser authUser
    ) {
        return ResponseEntity.ok(userService.findMe(authUser.getUserId()));
    }
}
```

위에서  `context.setAuthentication(authentication);`,
        `SecurityContextHolder.setContext(context);`
        에서  SecurityContext 에 Authentication을 넣어주었다. 그것을 꺼내쓰는 매개변수다. 
`SecurityContext`에 들어있는 `Authentication`(필터가 만든 `JwtAuthenticationToken`)의 `getPrincipal()`이 반환하는 객체를 그대로 꺼내주는 어노테이션. `JwtAuthenticationToken.getPrincipal()`이 `authUser`를 반환하도록 구현되어 있어서 동작한다.

### @EnableMethodSecurity + @PreAuthorize

```java
@Configuration
@EnableMethodSecurity
public class AuthenticationConfig {
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
```

```java
@PreAuthorize("hasRole('ADMIN')")
@GetMapping("/users")
public ResponseEntity<List<UserResponse>> users() {
    return ResponseEntity.ok(userService.findAll());
}
```

| 검사 표현 | 비교하는 실제 문자열 |
|---|---|
| `hasRole("ADMIN")` | `ROLE_ADMIN` (접두어 자동 부착) |
| `hasAuthority("ROLE_ADMIN")` | `ROLE_ADMIN` (그대로 비교) |

`authorizeHttpRequests`(URL 단위, Controller 진입 전 검사)와 `@PreAuthorize`(메서드 단위, 호출 시점 검사)는 검사 위치만 다를 뿐, 둘 다 같은 `SecurityContext`의 권한 정보를 사용한다. 
`@PreAuthorize()` 는 말 그대로 괄호안의 권한이 있을 때만 수행된다.

### 본인 확인 (IDOR 방지)

클라이언트가 `@RequestBody`나 `@PathVariable`로 "이 유저 ID로 처리해줘"라고 직접 넘기게 하면, 다른 사람 ID를 넣어 도용할 수 있다. 그래서 반드시 `@AuthenticationPrincipal`로 받은 **서버가 검증한 본인 정보**로 처리해야 한다.

```java
@RestController
@RequiredArgsConstructor
public class PostController {
    private final PostService postService;

    @PostMapping("/posts")
    public ResponseEntity<PostResponse> create(
            @AuthenticationPrincipal AuthUser authUser
    ) {
        PostResponse post = postService.create(authUser.getUserId());
        return ResponseEntity.status(HttpStatus.CREATED).body(post);
    }

    @GetMapping("/posts")
    public ResponseEntity<List<PostResponse>> posts() {
        return ResponseEntity.ok(postService.findAll());
    }

    @DeleteMapping("/posts/{id}")
    public ResponseEntity<Void> delete(
            @PathVariable long id,
            @AuthenticationPrincipal AuthUser authUser
    ) {
        postService.delete(id, authUser.getUserId());
        return ResponseEntity.noContent().build();
    }
}
```

```java
@Service
@RequiredArgsConstructor
public class PostService {
    private final PostRepository postRepository;
    private final UserRepository userRepository;

    @Transactional
    public PostResponse create(
            long authenticatedUserId
    ) {
        User user = userRepository.findById(authenticatedUserId)
                .orElseThrow(() -> new ResponseStatusException(HttpStatus.UNAUTHORIZED));
        Post post = new Post(user);
        Post savedPost = postRepository.save(post);
        return new PostResponse(savedPost.getId(), savedPost.getUser().getId());
    }

    @Transactional(readOnly = true)
    public List<PostResponse> findAll() {
        List<Post> posts = postRepository.findAll();
        return posts.stream()
                .map(post -> new PostResponse(post.getId(), post.getUser().getId()))
                .toList();
    }

    @Transactional
    public void delete(
            long postId,
            long authenticatedUserId
    ) {
        Post post = postRepository.findById(postId)
                .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
        if (post.getUser().getId() != authenticatedUserId) {
            throw new ResponseStatusException(HttpStatus.FORBIDDEN);
        }
        postRepository.delete(post);
    }
}
```

`PostController`는 `create`/`delete`에서 클라이언트가 넘긴 값이 아니라 `@AuthenticationPrincipal`로 받은 `authUser.getUserId()`를 사용합니다. `PostService.delete()`는 게시글 작성자와 요청자가 같은지(`post.getUser().getId() != authenticatedUserId`) 한 번 더 검증해 다른 사람의 글을 삭제하지 못하게 막습니다.

## 5. JPA N+1 문제

목록 조회 1번 + 각 항목의 연관 데이터 조회 N번 = 총 N+1번 쿼리가 발생하는 현상.

@ManyToOne(fetch = FetchType.LAZY)를 사용하며 생기는 문제다. (FetchType.EAGER을 사용하더라도 완전한 해결이 아니다.)

```java
List<Team> teams = teamRepository.findAll(); // 1번
for (Team team : teams) {
    team.getMembers().size(); // 팀마다 추가 쿼리
}
```
```sql
SELECT * FROM team;
SELECT * FROM member WHERE team_id = 1;
SELECT * FROM member WHERE team_id = 2;
...
```

**해결 방법**
1. **Fetch Join**: `@Query("SELECT t FROM Team t JOIN FETCH t.members")` — 쿼리 1번으로 해결.
2. **DTO 프로젝션**: 필요한 필드만 뽑아 애초에 N+1이 발생할 여지를 없앰.
   ```java
   @Query("SELECT new com.example.TeamDto(t.id, t.name, COUNT(m)) FROM Team t LEFT JOIN t.members m GROUP BY t.id")
   List<TeamDto> findTeamSummaries();
   ```

## 6. 페이징

```
GET /posts?page=0&size=10  → 0번째 페이지, 10개씩
```
```java
@GetMapping("/posts")
public ResponseEntity<List<String>> posts(
        @RequestParam int page,
        @RequestParam int size
) {
    return ResponseEntity.ok(postService.page(page, size));
}
```
```java
@Transactional(readOnly = true)
public List<String> page(
        int page,
        int size
) {
    Pageable pageable = PageRequest.of(page, size); // 페이지 번호는 0부터 시작
    Page<Post> found = postRepository.findAll(pageable);
    return found.getContent().stream()
            .map(Post::getTitle)
            .toList();
}
```

- `@RequestParam(defaultValue = "1")`처럼 기본값을 줄 수 있음. 클라이언트는 보통 1페이지부터 센다고 생각하므로, 기본값을 1로 주는 게 자연스러움 — **단, 실제 쿼리 시에는 `PageRequest.of(page - 1, size)`처럼 0-based로 보정해야 함.** (클라이언트 표시용 번호와 Spring Data 내부 인덱스가 다르다는 점이 핵심.)
- 정렬: `PageRequest.of(2, 10, Sort.by("createdAt").descending())`
- id가 아닌 다른 기준으로 페이징하려면 `Page<Member> findByName(String name, Pageable pageable)`처럼 쿼리 메서드에 `Pageable`을 추가 매개변수로 받으면 됨.

## 7. Redis 개요

- 메모리(RAM) 기반 Key-Value 저장소. 디스크 기반 RDB보다 훨씬 빠름. 주로 캐시 용도.
- **인메모리**: 서버 재시작 시 데이터 소실 가능(영속화 옵션은 있으나 잘 안 씀).
- **싱글 스레드 처리**: 명령 하나가 끝날 때까지 다른 명령이 끼어들지 않아 안전하지만, 느린 명령 하나가 뒤의 모든 명령을 지연시킬 수 있음.
- **다양한 자료구조**: String, Hash, List, Set, Sorted Set.
- **TTL**: 저장 시 항상 만료시간을 함께 설정하는 것이 관례.
- 기본 포트: `6379`

**Key 네이밍 컨벤션**: `product:1:name`처럼 `대상:식별자:속성`을 콜론으로 구분. Redis 엔진이 강제하는 규칙이 아니라 순수 관례이며, `redis-cli` 등 도구가 트리 구조로 보여주기 위해 널리 쓰임.

# Redis 자료구조별 사용법 정리 (Spring Data Redis)

Redis는 String, Hash, List, Set, Sorted Set 다섯 가지 자료구조를 제공합니다.
Spring Data Redis에서는 `StringRedisTemplate`이 자료구조별로 `opsForXxx()`라는 전용 인터페이스를 제공합니다.

> **주의**: 한 개의 물리적인 키는 오직 하나의 자료구조 타입만 가질 수 있습니다.
> 같은 키에 String으로 `set()`을 해놓고 나중에 `opsForHash().put()`을 호출하면
> `WRONGTYPE` 예외가 발생합니다.

---

## 1. String — `opsForValue()`

**용도**: 키 하나에 값 하나. 단순 캐싱, 카운터, 플래그, 세션 토큰 저장.

```java
@Service
@RequiredArgsConstructor
public class RedisStringService {
    private static final Duration TTL = Duration.ofMinutes(5);
    private final StringRedisTemplate redisTemplate;

    public void set(
            String key,
            String value
    ) {
        redisTemplate.opsForValue().set(key, value, TTL);
    }

    public String get(
            String key
    ) {
        return redisTemplate.opsForValue().get(key);
    }

    public Long increment(
            String key
    ) {
        Long count = redisTemplate.opsForValue().increment(key);
        redisTemplate.expire(key, TTL);
        return count;
    }
}
```

### 실습해보기

| 동작 | 요청 | 응답 |
|---|---|---|
| 저장 | `POST /redis/strings?key=product:1:name&value=keyboard` | - |
| 조회 | `GET /redis/strings?key=product:1:name` | `keyboard` |
| 수정 | `POST /redis/strings?key=product:1:name&value=mouse` | - |
| 수정 후 조회 | `GET /redis/strings?key=product:1:name` | `mouse` |
| 삭제 | `DELETE /redis/strings?key=product:1:name` | `true` |
| 삭제 후 조회 | `GET /redis/strings?key=product:1:name` | 본문 없음 |
| 숫자 올리기 | `POST /redis/strings/increment?key=product:1:views` | `1` |
| 숫자 올리기 | `POST /redis/strings/increment?key=product:1:views` | `2` |

### 메서드 설명
- `set()`: 값을 저장하면서 TTL을 5분으로 정합니다. 같은 key에 다시 저장하면 값이 바뀝니다.
- `get()`: 값을 읽습니다. key가 없으면 응답 본문이 비어 있습니다.
- `delete()`: key를 지우고, 지웠으면 `true`, 없는 key면 `false`를 돌려줍니다. `redisTemplate.delete()`는 자료구조와 상관없이 key 자체를 지웁니다.
- `increment()`: 숫자를 1 올리고 `expire()`로 TTL을 다시 5분으로 정한 뒤 올린 값을 돌려줍니다. 여러 요청이 동시에 올려도 Redis가 명령 하나씩 처리하므로 값이 어긋나지 않습니다.

## 2. Hash — `opsForHash()`

**용도**: key 하나 안에 필드와 값의 쌍을 여러 개 저장하는 자료구조. key 하나가 작은 Map 하나입니다.
→ 자바의 `Map<String, String> maps = new HashMap<>();`하고 같습니다.

```java
@Service
@RequiredArgsConstructor
public class RedisHashService {
    private static final Duration TTL = Duration.ofMinutes(5);
    private final StringRedisTemplate redisTemplate;

    public void put(
            String key,
            String field,
            String value
    ) {
        redisTemplate.opsForHash().put(key, field, value);
        redisTemplate.expire(key, TTL);
    }

    public Object get(
            String key,
            String field
    ) {
        return redisTemplate.opsForHash().get(key, field);
    }

    public Map<Object, Object> entries(
            String key
    ) {
        return redisTemplate.opsForHash().entries(key);
    }

    public Long delete(
            String key,
            String field
    ) {
        return redisTemplate.opsForHash().delete(key, field);
    }
}
```

### 실습해보기

| 동작 | 요청 | 응답 |
|---|---|---|
| 저장 | `POST /redis/hashes?key=user:1:profile&field=nickname&value=alice` | - |
| 저장 | `POST /redis/hashes?key=user:1:profile&field=grade&value=gold` | - |
| 전체 조회 | `GET /redis/hashes?key=user:1:profile` | `{"nickname":"alice","grade":"gold"}` |
| 필드 조회 | `GET /redis/hashes/field?key=user:1:profile&field=grade` | `gold` |
| 수정 | `POST /redis/hashes?key=user:1:profile&field=grade&value=vip` | - |
| 수정 후 조회 | `GET /redis/hashes?key=user:1:profile` | `{"nickname":"alice","grade":"vip"}` |
| 삭제 | `DELETE /redis/hashes?key=user:1:profile&field=grade` | `1` |
| 삭제 후 조회 | `GET /redis/hashes?key=user:1:profile` | `{"nickname":"alice"}` |

### 메서드 설명
- `put()`: 필드 하나를 저장하거나 바꾸고, `expire()`로 key의 TTL을 5분으로 정합니다. TTL은 필드마다가 아니라 key에 붙습니다. `grade`만 바꿔도 `nickname`은 그대로 남습니다.
- `get()`: 필드 하나의 값을 읽습니다.
- `entries()`: 모든 필드를 Map으로 돌려줍니다.
- `delete()`: 필드 하나만 지우고 지운 필드 수를 돌려줍니다. 없는 필드를 지우면 0입니다.

## 3. List — `opsForList()`

**용도**: 값을 넣은 순서대로 저장하는 자료구조.

```java
@Service
@RequiredArgsConstructor
public class RedisListService {
    private static final Duration TTL = Duration.ofMinutes(5);
    private final StringRedisTemplate redisTemplate;

    public Long leftPush(
            String key,
            String value
    ) {
        Long size = redisTemplate.opsForList().leftPush(key, value);
        redisTemplate.expire(key, TTL);
        return size;
    }

    public Long rightPush(
            String key,
            String value
    ) {
        Long size = redisTemplate.opsForList().rightPush(key, value);
        redisTemplate.expire(key, TTL);
        return size;
    }

    public List<String> range(
            String key
    ) {
        return redisTemplate.opsForList().range(key, 0, -1);
    }

    public void set(
            String key,
            long index,
            String value
    ) {
        redisTemplate.opsForList().set(key, index, value);
        redisTemplate.expire(key, TTL);
    }

    public String leftPop(
            String key
    ) {
        return redisTemplate.opsForList().leftPop(key);
    }

    public Long remove(
            String key,
            String value
    ) {
        return redisTemplate.opsForList().remove(key, 1, value);
    }
}
```

### 실습해보기

| 동작 | 요청 | 응답 |
|---|---|---|
| 뒤에 저장 | `POST /redis/lists/right-push?key=order:queue&value=order-1` | `1` |
| 뒤에 저장 | `POST /redis/lists/right-push?key=order:queue&value=order-2` | `2` |
| 앞에 저장 | `POST /redis/lists/left-push?key=order:queue&value=order-vip` | `3` |
| 조회 | `GET /redis/lists?key=order:queue` | `["order-vip","order-1","order-2"]` |
| 수정 | `PUT /redis/lists?key=order:queue&index=1&value=order-1-paid` | - |
| 수정 후 조회 | `GET /redis/lists?key=order:queue` | `["order-vip","order-1-paid","order-2"]` |
| 앞에서 꺼내기 | `POST /redis/lists/left-pop?key=order:queue` | `order-vip` |
| 삭제 | `DELETE /redis/lists?key=order:queue&value=order-2` | `1` |
| 삭제 후 조회 | `GET /redis/lists?key=order:queue` | `["order-1-paid"]` |

### 메서드 설명
- `rightPush()`: 값을 맨 뒤에 넣고 List의 길이를 돌려줍니다. 들어온 순서대로 줄을 세울 때 씁니다.
- `leftPush()`: 값을 맨 앞에 넣고 List의 길이를 돌려줍니다. 급한 주문 `order-vip`처럼 먼저 처리할 값을 끼워 넣을 때 씁니다.
- `range(key, 0, -1)`: 처음부터 끝까지 읽습니다. `-1`은 마지막 위치입니다.
- `set(key, index, value)`: 해당 위치의 값을 바꿉니다. 위치는 0부터 셉니다.
- `leftPop()`: 맨 앞의 값을 꺼내 돌려주고 List에서 지웁니다. List가 비어 있으면 응답 본문이 비어 있습니다.
- `remove(key, 1, value)`: 같은 값 중 앞에서부터 1개를 지우고 지운 개수를 돌려줍니다.
- 값을 쓸 때마다 `expire()`로 TTL을 5분으로 정합니다.

## 4. Set — `opsForSet()`

**용도**: 중복 없이 값을 모으는 자료구조. 값 사이에 순서는 없다.

```java
@Service
@RequiredArgsConstructor
public class RedisSetService {
    private static final Duration TTL = Duration.ofMinutes(5);
    private final StringRedisTemplate redisTemplate;

    public Long add(
            String key,
            String value
    ) {
        Long added = redisTemplate.opsForSet().add(key, value);
        redisTemplate.expire(key, TTL);
        return added;
    }

    public Set<String> members(
            String key
    ) {
        return redisTemplate.opsForSet().members(key);
    }

    public Boolean contains(
            String key,
            String value
    ) {
        return redisTemplate.opsForSet().isMember(key, value);
    }

    public Long remove(
            String key,
            String value
    ) {
        return redisTemplate.opsForSet().remove(key, value);
    }
}
```

### 실습해보기

| 동작 | 요청 | 응답 |
|---|---|---|
| 저장 | `POST /redis/sets?key=event:1:participants&value=alice` | `1` |
| 저장 | `POST /redis/sets?key=event:1:participants&value=bob` | `1` |
| 중복 저장 | `POST /redis/sets?key=event:1:participants&value=alice` | `0` |
| 전체 조회 | `GET /redis/sets?key=event:1:participants` | `["alice","bob"]` |
| 포함 여부 | `GET /redis/sets/contains?key=event:1:participants&value=bob` | `true` |
| 삭제 | `DELETE /redis/sets?key=event:1:participants&value=bob` | `1` |
| 삭제 후 조회 | `GET /redis/sets?key=event:1:participants` | `["alice"]` |

### 메서드 설명
- `add(key, value)`: Set에 값을 넣고, 새로 들어간 값의 개수를 돌려줍니다. 이미 있는 값은 다시 넣지 않으므로 0을 돌려줍니다.
- `members(key)`: Set의 모든 값을 돌려줍니다. 값 사이에 순서는 정해져 있지 않습니다.
- `isMember(key, value)`: 값이 Set에 들어 있으면 `true`, 없으면 `false`를 돌려줍니다.
- `remove(key, value)`: 값을 지우고 지운 개수를 돌려줍니다. 없는 값이면 0입니다.
- **수정**: Set의 값에는 위치나 이름이 없어 바꾸는 명령이 없습니다. 지우고 새로 넣습니다.
- **TTL**: `redisTemplate.expire(key, 시간)`으로 key 전체에 유효기간을 정합니다.

## 5. Sorted Set (ZSet) — `opsForZSet()`

**용도**: 값마다 점수(score)를 붙여, 점수 순서로 정렬해 두는 Set. 값은 중복되지 않는다.

```java
@Service
@RequiredArgsConstructor
public class RedisSortedSetService {
    private static final Duration TTL = Duration.ofMinutes(5);
    private final StringRedisTemplate redisTemplate;

    public Boolean add(
            String key,
            String member,
            double score
    ) {
        Boolean added = redisTemplate.opsForZSet().add(key, member, score);
        redisTemplate.expire(key, TTL);
        return added;
    }

    public Set<String> ranking(
            String key
    ) {
        return redisTemplate.opsForZSet().reverseRange(key, 0, -1);
    }

    public Double score(
            String key,
            String member
    ) {
        return redisTemplate.opsForZSet().score(key, member);
    }

    public Long remove(
            String key,
            String member
    ) {
        return redisTemplate.opsForZSet().remove(key, member);
    }
}
```

### 실습해보기

| 동작 | 요청 | 응답 |
|---|---|---|
| 저장 | `POST /redis/sorted-sets?key=game:ranking&member=alice&score=1200` | `true` |
| 저장 | `POST /redis/sorted-sets?key=game:ranking&member=bob&score=3400` | `true` |
| 저장 | `POST /redis/sorted-sets?key=game:ranking&member=carol&score=2500` | `true` |
| 순위 조회 | `GET /redis/sorted-sets?key=game:ranking` | `["bob","carol","alice"]` |
| 점수 조회 | `GET /redis/sorted-sets/score?key=game:ranking&member=alice` | `1200.0` |
| 수정 | `POST /redis/sorted-sets?key=game:ranking&member=alice&score=5000` | `false` |
| 수정 후 조회 | `GET /redis/sorted-sets?key=game:ranking` | `["alice","bob","carol"]` |
| 삭제 | `DELETE /redis/sorted-sets?key=game:ranking&member=carol` | `1` |
| 삭제 후 조회 | `GET /redis/sorted-sets?key=game:ranking` | `["alice","bob"]` |

### 메서드 설명
- `add(key, value, score)`: 값과 점수를 넣습니다. 새 값이면 `true`, 이미 있는 값이면 점수만 바꾸고 `false`를 돌려줍니다. 점수 수정도 `add()`로 합니다.
- `reverseRange(key, 시작, 끝)`: 점수가 높은 순서로 정렬했을 때 시작~끝 위치의 값을 읽습니다. `(0, -1)`은 전체, `(0, 2)`는 상위 3개입니다. 점수가 낮은 순서로 읽을 때는 `range()`를 씁니다(List의 `range`와 동일).
- `score(key, value)`: 값의 점수를 돌려줍니다. 점수는 소수점이 있는 숫자(`Double`)라서 `1200`이 아니라 `1200.0`으로 나옵니다.
- `remove(key, value)`: 값을 지우고 지운 개수를 돌려줍니다. 없는 값이면 0입니다.
- **TTL**: `redisTemplate.expire(key, 시간)`으로 key 전체에 유효기간을 정합니다.

## 8. Redis Pub/Sub
채널에 메시지를 보내면 구독 중인 모두에게 전달하는 기능이다.
발행자(Publisher)는 구독자(Subscriber)를 몰라도 된다. 

**발행**
```java
@Service
@RequiredArgsConstructor
public class MessagePublishService {
    private final StringRedisTemplate redisTemplate;

    public void publish(
            String category,
            String message
    ) {
        String channel = "news:" + category;
        redisTemplate.convertAndSend(channel, message);
    }
}
```
`MessagePublishService`는 분야 앞에 `news:`를 붙인 이름으로 `convertAndSend(채널, 메시지)`를 호출해 발행한다. 메시지를 바이트로 바꿔(convert) 보낸다(send)는 뜻이다.

**구독 (SSE와 연동)**
```java
@Service
@RequiredArgsConstructor
public class MessageSubscribeService {
    private final RedisMessageListenerContainer container;

    public synchronized SseEmitter subscribe(
            String category
    ) {
        SseEmitter emitter = new SseEmitter(0L);
        MessageSubscriber subscriber = new MessageSubscriber(emitter);
        ChannelTopic topic = new ChannelTopic("news:" + category);
        // 연결이 열리면 이 연결의 리스너로 news:{category} 채널을 구독
        container.addMessageListener(subscriber, topic);
        // 연결이 끊기면 구독 해제
        emitter.onCompletion(() -> container.removeMessageListener(subscriber, topic));
        return emitter;
    }
}
```
- `SseEmitter`: 브라우저와의 SSE 연결 하나. `send()`로 데이터 전송. `0L`은 시간 제한 없음(생략 시 30초 뒤 끊김).
- `RedisMessageListenerContainer`: Spring Boot가 자동으로 만들어 줌. 구독 관리 및 메시지 도착 시 리스너 실행.
- `ChannelTopic("news:" + category)`: 구독할 채널. `category`가 `sports`면 `news:sports`만 받음.
- `addMessageListener(리스너, 채널)`: 구독 등록.
- `onCompletion()`: 연결이 끝나면 `removeMessageListener()`로 구독 해제.
- `synchronized`: 여러 연결이 동시에 와도 구독을 하나씩 등록. 동시에 등록하면 메시지가 두 번 오는 문제가 생길 수 있음.

**리스너**
```java
@Slf4j
@RequiredArgsConstructor
public class MessageSubscriber implements MessageListener {
    private final SseEmitter emitter;

    @Override
    public void onMessage(
            Message message,
            byte[] pattern
    ) {
        String channel = new String(message.getChannel(), StandardCharsets.UTF_8);
        String body = new String(message.getBody(), StandardCharsets.UTF_8);
        log.info("수신: channel={} message={}", channel, body);
        try {
            emitter.send(new ReceivedMessage(channel, body));
        } catch (IOException | IllegalStateException closed) {
            emitter.complete();
        }
    }
}
```
- `onMessage()`: 메시지가 도착할 때마다 실행. `MessageListener` 인터페이스가 정한 메서드.
- `new String(..., StandardCharsets.UTF_8)`: Redis는 채널과 본문을 바이트(`byte[]`)로 주므로 문자열로 변환.
- `pattern`: 인터페이스가 정한 인자. `news:*`처럼 여러 채널을 한 번에 구독하는 패턴 구독에서만 값이 있어서, 여기서는 읽지 않음.
- `emitter.send()`: 받은 메시지를 JSON으로 브라우저에 전송. 브라우저가 떠나 실패하면 `complete()`로 연결 종료(구독도 함께 해제됨).

## 9. WebSocket 기초

- HTTP로 연결을 시작해 WebSocket 프로토콜(ws/wss)로 전환 후 계속 유지하는 **양방향** 통신. 채팅, 실시간 협업에 적합.
- 전환 과정을 **프로토콜 업그레이드**, 연결을 여는 절차를 **핸드셰이크**라고 부름.
- **SSE**: WebSocket이 아닌 HTTP 연결 유지 방식. 서버 → 클라이언트 **단방향**. 실시간 로그, 진행 상태 전달에 적합.
- **Polling**: 클라이언트가 주기적으로 HTTP 요청을 보내 새 데이터 유무를 확인하는 방식(WebSocket/SSE보다 비효율적).

### 등록Config WebSocketConfigurer
웹 소켓을 활용하기 위해선 webSocketConfigurer 인터페이스를 구현해야 한다.

registerWebSocketHandler() 

매개변수로 받아온 registry에 핸들러를 추가함으로서 사용준비를 마친다.

@EnableWebSocket이 있어야 웹소켓이 활성화된다.


```java
@Configuration
@EnableWebSocket
@RequiredArgsConstructor
public class WebSocketConfig implements WebSocketConfigurer {
    private final WebSocketHandler webSocketHandler;

    @Override
    public void registerWebSocketHandlers(
            WebSocketHandlerRegistry registry
    ) {
        registry.addHandler(webSocketHandler, "/ws");
    }
}
```

### 핸들러 (Controller에 해당하는 진입점)
```java
@Slf4j
@Component
public class WebSocketHandler extends TextWebSocketHandler {
    @Override
    public void afterConnectionEstablished(
            WebSocketSession session
    ) {
        log.info("연결됨: id={}", session.getId());
    }

    @Override
    protected void handleTextMessage(
            WebSocketSession session,
            TextMessage message
    ) throws Exception {
        log.info("받음: {}", message.getPayload());
        session.sendMessage(message);
    }

    @Override
    public void afterConnectionClosed(
            WebSocketSession session,
            CloseStatus status
    ) {
        log.info("끊김: id={} code={}", session.getId(), status.getCode());
    }
}
```
`WebSocketSession`은 Spring이 제공하는 **표준 인터페이스**(연결 하나를 표현). 개발자가 만드는 게 아니라 연결이 맺어질 때 프레임워크가 생성해 콜백 매개변수로 넘겨줌.

## 10. HandshakeInterceptor

WebSocket 연결을 허용하기 전, HTTP 요청 단계에서 필요한 정보를 검사/추출하는 인터페이스. `beforeHandshake()`가 `false`를 반환하면 연결이 거부됨.

```java
@Component
public class NicknameHandshakeInterceptor implements HandshakeInterceptor {
    public static final String ATTR_NICKNAME = "nickname";
    private static final Pattern NICKNAME = Pattern.compile("^[A-Za-z]{2,12}$");

    @Override
    public boolean beforeHandshake(
            ServerHttpRequest request,
            ServerHttpResponse response,
            WebSocketHandler handler,
            Map<String, Object> attributes
    ) {
        String query = request.getURI().getQuery();
        String nickname = (query != null && query.startsWith("nickname="))
                ? query.substring("nickname=".length()) : null;

        if (nickname == null || !NICKNAME.matcher(nickname).matches()) {
            response.setStatusCode(HttpStatus.BAD_REQUEST);
            return false;
        }

        attributes.put(ATTR_NICKNAME, nickname);
        return true;
    }

    @Override
    public void afterHandshake(
            ServerHttpRequest request,
            ServerHttpResponse response,
            WebSocketHandler handler,
            Exception exception
    ) {
    }
}
```

**동작 원리**: `beforeHandshake`에서 채운 `attributes` 맵의 내용은, 핸드셰이크가 성공하면 그대로 새로 생성되는 `WebSocketSession`의 속성으로 복사됨. 그래서 이후 핸들러에서 `session.getAttributes().get(ATTR_NICKNAME)`으로 꺼낼 수 있음.

**등록**
```java
@Configuration
@EnableWebSocket
@RequiredArgsConstructor
public class WebSocketConfig implements WebSocketConfigurer {
    private final WebSocketHandler webSocketHandler;
    private final NicknameHandshakeInterceptor nicknameHandshakeInterceptor;

    @Override
    public void registerWebSocketHandlers(
            WebSocketHandlerRegistry registry
    ) {
        registry.addHandler(webSocketHandler, "/ws")
                .addInterceptors(nicknameHandshakeInterceptor);
    }
}
```

## 11. 세션 레지스트리 & 브로드캐스트

### RoomSessionRegistry — 방 번호별로 (닉네임, 연결) 관리
```java
@Component
public class RoomSessionRegistry {
    private final Map<Long, Map<String, WebSocketSession>> rooms = new ConcurrentHashMap<>();

    public boolean register(
            Long roomId,
            String nickname,
            WebSocketSession session
    ) {
        Map<String, WebSocketSession> sessionsByNickname = rooms.computeIfAbsent(roomId, id -> new ConcurrentHashMap<>());
        return sessionsByNickname.putIfAbsent(nickname, session) == null;
    }

    public Collection<WebSocketSession> sessions(
            Long roomId
    ) {
        Map<String, WebSocketSession> sessionsByNickname = rooms.get(roomId);
        return sessionsByNickname == null ? List.of() : sessionsByNickname.values();
    }

    public boolean remove(
            Long roomId,
            String nickname,
            WebSocketSession session
    ) {
        Map<String, WebSocketSession> sessionsByNickname = rooms.get(roomId);
        return sessionsByNickname.remove(nickname, session);
    }
}
```
- `WebSocketSession`(프레임워크 제공, 연결 하나)과 `RoomSessionRegistry`(개발자 제작, 방별 명부)는 역할이 다름. 전자는 "실제 전송 창구", 후자는 "누구에게 보낼지 찾아주는 조회 담당".
- `@Component`로 등록된 싱글턴 빈이므로, `WebSocketHandler`에 DI로 주입해서 사용. 애플리케이션 전체가 같은 인스턴스를 공유해야 하므로 스코프를 프로토타입으로 바꾸면 안 됨.

### RoomBroadcaster — 실제 전송 담당
```java
@Slf4j
@Component
@RequiredArgsConstructor
public class RoomBroadcaster {
    private final RoomSessionRegistry registry;
    private final ObjectMapper objectMapper;

    public void broadcastJson(
            Long roomId,
            String jsonMessage
    ) {
        for (WebSocketSession session : registry.sessions(roomId)) {
            sendJson(session, jsonMessage);
        }
    }

    public void sendTo(
            WebSocketSession session,
            Object message
    ) {
        String jsonMessage = objectMapper.writeValueAsString(message);
        sendJson(session, jsonMessage);
    }

    private void sendJson(
            WebSocketSession session,
            String jsonMessage
    ) {
        try {
            synchronized (session) {
                if (session.isOpen()) {
                    TextMessage message = new TextMessage(jsonMessage);
                    session.sendMessage(message);
                }
            }
        } catch (Exception sendFailed) {
            log.warn("전송 실패: id={}", session.getId());
        }
    }
}
```
- `broadcastJson`은 이미 직렬화된 문자열을 받음(N명에게 보낼 것을 한 번만 직렬화하기 위함). `sendTo`는 객체를 받아 그 자리에서 직렬화(수신자가 1명뿐이므로).
- `synchronized(session)`: 같은 세션에 동시 전송 시 프레임 손상 방지.
- `try/catch`로 개별 전송 실패를 흡수 — 한 명 실패해도 나머지 브로드캐스트는 계속되어야 하므로.

## 12. 메시지 라우팅

한 WebSocket 연결로 여러 종류의 요청(`ping`, `chat` 등)을 처리하기 위해, 메시지에 `type` 필드를 넣고 그 값으로 라우팅.

### WsMessageHandler 인터페이스 (전략 패턴)
```java
public interface WsMessageHandler {
    String type();

    void handle(
            WebSocketSession session,
            Long roomId,
            String nickname,
            JsonNode message
    );
}
```

### PingWsHandler 예시 (하트비트)
```java
@Component
@RequiredArgsConstructor
public class PingWsHandler implements WsMessageHandler {
    private final RoomBroadcaster broadcaster;

    @Override
    public String type() {
        return "ping";
    }

    @Override
    public void handle(
            WebSocketSession session,
            Long roomId,
            String nickname,
            JsonNode message
    ) {
        PongResponse pong = new PongResponse();
        broadcaster.sendTo(session, pong);
    }
}
```
하트비트는 연결이 살아있는지 주기적으로 확인하는 용도. 이 예시에서는 클라이언트가 일정 간격(예: 30초)마다 ping을 보내는 방식으로 구현(서버 주도 방식도 가능).

### WsMessageRouter — type에 맞는 핸들러 탐색
```java
@Component
@RequiredArgsConstructor
public class WsMessageRouter {
    private final List<WsMessageHandler> handlers;

    public WsMessageHandler find(
            JsonNode message
    ) {
        String type = message.path("type").asString("");
        return handlers.stream()
                .filter(handler -> handler.type().equals(type))
                .findFirst()
                .orElse(null);
    }
}
```

`List<WsMessageHandler> handlers`가 핵심: Spring이 해당 인터페이스를 구현한 모든 `@Component`를 자동으로 리스트에 모아 주입해줌. 새 메시지 타입을 추가해도 이 라우터 클래스는 수정할 필요 없음(개방-폐쇄 원칙).

### ChatWebSocketHandler — 수신을 담당하는 핸들러
```java
@Slf4j
@Component
@RequiredArgsConstructor
public class ChatWebSocketHandler extends TextWebSocketHandler {
    private final RoomSessionRegistry registry;
    private final WsMessageRouter router;
    private final ObjectMapper objectMapper;

    @Override
    public void afterConnectionEstablished(
            WebSocketSession session
    ) throws Exception {
        // 연결 전에 Interceptor가 세션 attribute에 저장한 방 번호와 닉네임을 꺼냅니다.
        Long roomId = (Long) session.getAttributes().get(NicknameHandshakeInterceptor.ATTR_ROOM_ID);
        String nickname = (String) session.getAttributes().get(NicknameHandshakeInterceptor.ATTR_NICKNAME);
        // 같은 방에 닉네임이 이미 있으면 기존 연결을 유지하고 새 연결을 종료합니다.
        if (!registry.register(roomId, nickname, session)) {
            // 4002는 이 예제에서 닉네임 중복을 나타내도록 정한 종료 코드입니다.
            CloseStatus status = new CloseStatus(4002);
            session.close(status);
            return;
        }
        log.info("입장: room={} nickname={}", roomId, nickname);
    }

    @Override
    protected void handleTextMessage(
            WebSocketSession session,
            TextMessage message
    ) {
        Long roomId = (Long) session.getAttributes().get(NicknameHandshakeInterceptor.ATTR_ROOM_ID);
        String nickname = (String) session.getAttributes().get(NicknameHandshakeInterceptor.ATTR_NICKNAME);
        JsonNode parsedMessage;
        try {
            parsedMessage = objectMapper.readTree(message.getPayload());
        } catch (Exception notJson) {
            // JSON으로 읽을 수 없는 메시지는 처리하지 않습니다.
            return;
        }
        WsMessageHandler handler = router.find(parsedMessage);
        // type에 해당하는 핸들러가 없으면 이 메시지는 무시합니다.
        if (handler == null) {
            return;
        }
        handler.handle(session, roomId, nickname, parsedMessage);
    }

    @Override
    public void afterConnectionClosed(
            WebSocketSession session,
            CloseStatus status
    ) {
        Long roomId = (Long) session.getAttributes().get(NicknameHandshakeInterceptor.ATTR_ROOM_ID);
        String nickname = (String) session.getAttributes().get(NicknameHandshakeInterceptor.ATTR_NICKNAME);
        // 식별 정보가 없는 연결은 레지스트리에서 제거할 대상을 찾을 수 없습니다.
        if (roomId == null || nickname == null) {
            return;
        }
        // 현재 종료된 세션이 등록된 세션과 같을 때만 제거합니다.
        // 중복 닉네임으로 거절된 새 연결이 기존 연결을 지우는 것을 막습니다.
        if (!registry.remove(roomId, nickname, session)) {
            return;
        }
        log.info("퇴장: room={} nickname={} code={}", roomId, nickname, status.getCode());
    }
}
```

| 콜백 | 역할 |
|---|---|
| 연결 — `afterConnectionEstablished()` | `RoomSessionRegistry`에 연결을 등록. 같은 방에 닉네임이 중복되면 새 연결을 종료 |
| 수신 — `handleTextMessage()` | `getPayload()`로 받은 문자열을 꺼내고 `readTree()`로 `JsonNode`로 변환. `router.find()`로 담당 핸들러를 찾아 `handle()` 호출. JSON을 읽을 수 없거나 담당 핸들러가 없으면 `return` |
| 종료 — `afterConnectionClosed()` | `RoomSessionRegistry`에서 연결 제거 |

## 13. 데이터 저장 + 여러 서버로 메시지 전파 (Redis Pub/Sub 활용)

HTTP Controller에서 서비스 메서드를 호출하듯, WebSocket 핸들러도 메시지에서 필요한 값을 읽어 서비스에 전달합니다.

```java
@Component
@RequiredArgsConstructor
public class ChatWsHandler implements WsMessageHandler {
    private final ChatService chatService;
    private final ChatRelay chatRelay;
    private final ObjectMapper objectMapper;

    @Override
    public String type() {
        return "chat";
    }

    @Override
    public void handle(
            WebSocketSession session,
            Long roomId,
            String nickname,
            JsonNode message
    ) {
        if (!message.path("content").isString()) {
            return;
        }
        String content = message.path("content").asString("");
        if (content.isBlank() || content.length() > 200) {
            return;
        }
        ChatResponse savedChat = chatService.save(roomId, nickname, content);
        String jsonMessage = objectMapper.writeValueAsString(savedChat);
        chatRelay.publish(roomId, jsonMessage);
    }
}
```
- `ChatService.save()`: 채팅을 DB에 저장.
- `objectMapper.writeValueAsString(savedChat)`: `savedChat`을 JSON 문자열인 `jsonMessage`로 변환.
- `chatRelay.publish(roomId, jsonMessage)`: `jsonMessage`를 Redis에 publish하여 같은 방의 연결에 전달.

**왜 Redis를 거치는가**: 같은 채팅방 참여자가 서로 다른 서버에 연결되어 있을 수 있습니다. Redis Pub/Sub을 사용하면 각 서버가 채팅 메시지를 받아 자신에게 연결된 같은 방의 참여자에게 전달할 수 있습니다. `ChatRelay`가 Redis에 채팅을 발행하고, 구독한 메시지를 받아 WebSocket 전송으로 이어 줍니다.

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class ChatRelay implements MessageListener {
    private static final String CHANNEL_PREFIX = "chat:room:";
    private final StringRedisTemplate redisTemplate;
    private final RoomBroadcaster broadcaster;

    public void publish(
            Long roomId,
            String jsonMessage
    ) {
        redisTemplate.convertAndSend(CHANNEL_PREFIX + roomId, jsonMessage);
        log.info("발행: room={} {}", roomId, jsonMessage);
    }

    @Override
    public void onMessage(
            Message message,
            byte[] pattern
    ) {
        String channelName = new String(message.getChannel(), StandardCharsets.UTF_8);
        String jsonMessage = new String(message.getBody(), StandardCharsets.UTF_8);
        Long roomId = Long.valueOf(channelName.substring(CHANNEL_PREFIX.length()));
        log.info("수신: room={} {}", roomId, jsonMessage);
        broadcaster.broadcastJson(roomId, jsonMessage);
    }
}
```
- 발행 `publish()`: `convertAndSend()`로 채팅 JSON을 방별 Redis 채널에 전송. 방 번호가 1이면 채널 이름은 `chat:room:1`.
- 수신과 전송 `onMessage()`: 수신한 채널 이름과 JSON을 문자열로 읽음. 채널의 `chat:room:`을 제외한 부분에서 방 번호를 얻고, `broadcastJson()`으로 현재 서버의 같은 방 연결에 전송.

## 14. Lua Script와 원자성

Redis는 명령 하나는 원자적으로 실행하지만, "조회 후 판단 후 수정" 같은 여러 명령의 조합은 원자적이지 않습니다(RDB의 `@Transactional`처럼 여러 명령을 하나로 묶어주는 기능이 없음).

**문제가 되는 코드 (원자성 없음)**
```java
@Service
@RequiredArgsConstructor
public class UnsafeStockService {
    private final StringRedisTemplate redisTemplate;

    public boolean decrease(
            Long productId
    ) {
        String key = "stock:" + productId;
        String value = redisTemplate.opsForValue().get(key);
        int stock = Integer.parseInt(value);
        if (stock <= 0) {
            return false;
        }
        // 조회 이후 다른 요청이 재고를 차감했어도, 읽어 둔 stock 값은 그대로입니다.
        redisTemplate.opsForValue().decrement(key);
        return true;
    }
}
```

**Lua Script로 원자성 확보**
```java
@Service
@RequiredArgsConstructor
public class StockService {
    // 재고를 확인한 뒤 차감하는 과정을 Redis 안에서 한 번에 실행합니다.
    private static final DefaultRedisScript<Long> DECREASE_SCRIPT = new DefaultRedisScript<>("""
            local stock = tonumber(redis.call('GET', KEYS[1]))
            if stock <= 0 then
                return 0
            end
            redis.call('DECR', KEYS[1])
            return 1
            """, Long.class);
    private final StringRedisTemplate redisTemplate;

    public boolean decrease(
            Long productId
    ) {
        String key = "stock:" + productId;
        // key는 스크립트의 KEYS[1]로 전달됩니다.
        Long result = redisTemplate.execute(DECREASE_SCRIPT, List.of(key));
        // 스크립트가 반환한 1은 차감 성공, 0은 재고 부족입니다.
        return result == 1L;
    }
}
```
Redis는 내부적으로 Lua를 지원하며, 스크립트 전체가 **하나의 명령처럼 원자적으로** 실행됩니다(싱글 스레드 특성과 결합해 중간에 다른 명령이 끼어들 수 없음). "조회 → 조건 판단 → 수정"을 한 번에 원자적으로 처리해야 하는 경우(재고 차감, 선착순 쿠폰 등)에 사용합니다.

## 15. 동시성과 락


### 동시성 문제

여러 스레드/서버가 같은 데이터를 동시에 읽고 쓰면서 서로의 변경을 감지하지 못하고 덮어써버리는 현상을 말한다.
예를 들어 인터넷에서 한정판 상품이 1개 남았을 때 2명이 동시에 구매 버튼을 눌러서, 재고 체크를 둘 다 동시에 통과해버리는 상황을 생각해보자.

**예시**

| 시점 | Thread A | Thread B |
|---|---|---|
| 1 | 재고 조회 → 1 | |
| 2 | | 재고 조회 → 1 |
| 3 | 1 - 1 = 0 으로 저장 | |
| 4 | | 1 - 1 = 0 으로 저장 (A가 이미 처리한 걸 모른 채) |

→ 재고는 1개였는데 실제로는 2건이 판매됨.

### 락

이런 문제를 해결하기 위해 락이라고 부르는 수단을 사용한다.
락은 동시 접근을 막아 한 번에 하나의 트랜잭션만 그 데이터를 건드릴 수 있게 만드는 장치이다.

**코드상의 락 예시 (Java synchronized)**

​```java
public synchronized void decrease(int quantity) {
    if (this.stock < quantity) {
        throw new IllegalStateException("재고가 부족합니다.");
    }
    this.stock -= quantity;
}
​```
→ 같은 인스턴스를 공유하는 스레드끼리만 한 번에 하나씩 진입한다. 서버가 여러 대라 인스턴스가 각자 따로 떠 있으면 이 락은 무력해진다는 한계가 있다.

**DB 락 예시 (비관적 락, SELECT ... FOR UPDATE)**

​```java
public interface ProductRepository extends JpaRepository<Product, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT p FROM Product p WHERE p.id = :id")
    Optional<Product> findByIdForUpdate(@Param("id") Long id);
}
​```
→ 이 쿼리가 실행되는 순간 해당 row가 잠기고, 다른 트랜잭션은 이 트랜잭션이 끝날 때까지 대기한다. 여러 서버 인스턴스여도 결국 같은 DB row를 보고 있으므로, 위의 코드 락과 달리 확실하게 막아준다.

### 데드락

다만 이렇게 여러 개의 락을 동시에 걸어야 하는 경우, 데드락이라고 부르는 현상이 발생할 수 있다.

**데드락 예시**

​```
트랜잭션 A: 상품1 락 획득 → 상품2 락 요청 (대기)
트랜잭션 B: 상품2 락 획득 → 상품1 락 요청 (대기)
​```
→ A는 B가 쥔 상품2를, B는 A가 쥔 상품1을 서로 기다리며 둘 다 영원히 멈춘다 (순환 대기).
→ 예방법: 락을 걸 때 항상 같은 순서로(예: id 오름차순) 걸어서 순환이 생길 여지 자체를 없앤다.

### 낙관적 락

비관적 락은 이런 데드락 위험과 대기 비용을 안고 있다. 낙관적 락은 애초에 락(대기)을 걸지 않는 방식으로 이 부담 자체를 피하고, 그 결과로 데드락도 발생하지 않는다.
평소엔 락 없이 처리하다가 커밋 시점에 버전을 비교해서(@Version), 값이 바뀌었으면 예외를 발생시키고 재시도시킨다.

**예시**

​```java
@Entity
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private int stock;

    @Version
    private Long version;
}
​```

​```java
@Transactional
public void decrease(
        Long productId,
        int quantity
) {
    Product product = productRepository.findById(productId)
            .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
    product.decreaseStock(quantity);
    // 커밋 시점에 UPDATE ... WHERE id=? AND version=? 로 나감
    // 그 사이 다른 트랜잭션이 먼저 커밋해 version이 바뀌었으면
    // 0행이 수정되어 ObjectOptimisticLockingFailureException 발생 → 재시도
}
​```

| 계층 | 핵심 객체 | 역할 |
|---|---|---|
