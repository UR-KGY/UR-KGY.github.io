## 1. 자바 기초 함정

### 1-1. 배열 인덱스를 잘못 재사용해서 생기는 NullPointerException

`indexOf()`는 항상 **첫 등장 인덱스**를 반환한다. 중복 문자가 있는 문자열을 순회하면서 매번 `s.indexOf(str)`로 저장 위치를 다시 찾으면, 같은 위치만 계속 덮어쓰고 정작 각 글자의 실제 위치(반복문의 인덱스 `i`)는 채워지지 않는다. 그 결과 `Integer[]` 배열에 `null`이 남고, `Comparator.reverseOrder()`로 정렬할 때 `null.compareTo(...)`가 호출되며 `NullPointerException`이 발생한다.

- **교훈**: 반복문에서 이미 위치(인덱스)를 알고 있다면, 그 값을 다시 검색으로 찾지 말고 직접 사용한다.

### 1-2. 람다 안에서 checked exception 처리

`Predicate<T>.test(T t)`처럼 함수형 인터페이스의 추상 메서드가 `throws` 선언이 없으면, 그 메서드를 구현하는 람다 안에서 checked exception이 발생하는 코드를 쓸 경우 **반드시 그 안에서 try-catch로 처리**하거나 별도 헬퍼로 감싸야 한다. 람다 자체는 일반 코드 블록이라 try-catch를 쓰는 데 아무 제약이 없다 — 문제는 "함수형 인터페이스의 시그니처가 그 예외를 던지도록 허용하는가"이다.

### 1-3. IDE의 "AutoCloseable used without try-with-resources" 경고

`WebSocketSession`처럼 `Closeable`을 구현한 타입을 다룰 때 IntelliJ가 이 경고를 띄운다. 하지만 이 경고는 **내가 새로 연(open) 자원**에만 의미가 있다. 레지스트리 등에서 이미 관리 중인, 다른 곳에서 열고 닫는 "빌려온 자원"의 상태만 읽는 경우엔 오탐(false positive)이며, 억지로 `try-with-resources`를 붙이면 오히려 정상 연결을 강제로 끊어버리는 부작용이 생긴다. `@SuppressWarnings("resource")`로 명시적으로 억제하는 것이 맞다.

### 1-4. `Duration`의 단위 변환 메서드

`Duration`은 시간 길이를 표현하는 객체이고, `.toMillis()`, `.toSeconds()`, `.toNanos()` 등은 그 길이를 특정 단위의 순수 숫자(`long`)로 뽑아내는 변환 메서드다. `Duration` 객체를 직접 받지 않고 `long` 밀리초를 요구하는 저수준 API(예: `Thread.sleep`)에 값을 넘길 때 필요하다.

## 2. 동시성 & 컬렉션

### 2-1. `ConcurrentHashMap` vs `HashMap`

- `HashMap`은 순회 중 다른 스레드가 수정하면 `ConcurrentModificationException`을 던진다 (fail-fast).
- `ConcurrentHashMap`은 "weakly consistent iterator"를 제공해 순회 중 수정이 있어도 예외를 던지지 않는다. 대신 순회 결과가 그 순간의 완벽한 스냅샷이라는 보장은 하지 않는다.

### 2-2. `Stream.toList()`의 스냅샷 특성

`sessions.values().stream().filter(...).toList()`는 호출 시점의 상태를 복사한 **불변 스냅샷**을 만든다. 이후 원본 맵이 바뀌어도 이 리스트엔 영향이 없다. 다만 "확인한 시점"과 "그 결과를 실제로 사용하는 시점" 사이에는 여전히 시간차(TOCTOU)가 존재하므로, 그 사이 상태가 바뀔 수 있다는 점은 별개로 인지해야 한다.

## 3. JPA / Hibernate

### 3-1. `UnknownEntityTypeException`의 원인

`entityManager.getReference(X.class, id)` 호출 시 이 예외가 나면 원인은 보통 셋 중 하나다.

1. `X`가 `@Entity`가 아니다 (인터페이스, DTO, `@MappedSuperclass`만 붙은 클래스 등)
2. `X`가 Spring Boot의 컴포넌트/엔티티 스캔 범위 밖의 패키지에 있다
3. 멀티 모듈 구조에서 `@EntityScan` 설정이 빠져 있다

### 3-2. `@Version`을 이용한 낙관적 락

`@Version` 필드는 개발자가 직접 값을 읽거나 증가시키지 않아도 Hibernate가 UPDATE SQL을 생성할 때 자동으로 관리한다.

```sql
UPDATE table SET revision = 6, ... WHERE id = ? AND revision = 5
```

내가 읽었던 버전을 WHERE 조건에 걸고, 실제로 영향받은 row가 0개면(다른 트랜잭션이 먼저 커밋해서 버전이 이미 바뀐 경우) `OptimisticLockException`을 던진다.

### 3-3. `@Transactional`의 원자성(All-or-Nothing)

트랜잭션 메서드 안에서 `repository.save()`가 먼저 성공적으로 실행됐더라도, 같은 메서드 안의 **이후 코드**에서 unchecked exception이 발생하면 트랜잭션 전체가 롤백된다. 즉 "코드가 실행됐다"와 "DB에 실제로 커밋됐다"는 별개다. 이 특성 때문에, 여러 row를 한 트랜잭션에서 저장할 때 그중 하나만 버전 충돌이 나도 나머지 row 변경까지 전부 취소된다.

### 3-4. 동시성(낙관적 락 충돌) 테스트 설계 기법

두 트랜잭션이 정확히 같은 버전을 읽은 상황을 안정적으로 재현하려면 타이밍에 의존하면 안 된다. `CountDownLatch` 두 개로 "읽기 완료 → 상대방 커밋 → 재개해서 flush 시도" 순서를 강제로 동기화시키고, 기존에 있던 콜백 파라미터(예: `RewardMutation`)를 "flush 직전에 멈추는 훅"으로 재활용하면 결정적으로 충돌을 재현할 수 있다.

### 3-5. Jackson 직렬화 필드 순서

`@JsonPropertyOrder`가 없으면 JSON 필드 순서는 소스 코드 선언 순서를 보장하지 않는다 (리플렉션 메서드 순서가 원래 보장되지 않기 때문). 다만 JSON 스펙상 **객체(object)의 키 순서는 의미가 없으며**, `ObjectNode.equals()`도 순서를 무시한다. 순서가 중요한 건 **배열(array)**뿐이다.

## 4. 페이지네이션 (Offset vs Cursor)

### 4-1. Offset 방식의 한계

`LIMIT n OFFSET m`은 "몇 번째부터"라는 위치 기반 조건이라, 페이지를 넘기는 사이 데이터가 추가/삭제되면 위치 자체가 밀려서 중복이나 누락이 생긴다. 또한 `OFFSET`이 커질수록 그만큼 훑고 버려야 할 행이 늘어 성능도 떨어진다(deep pagination 문제).

### 4-2. 커서 방식의 원리

커서는 "몇 번째"가 아니라 **"어떤 값 이후/이전"**이라는 조건으로 다음 데이터를 지정한다.

```sql
WHERE id < :cursor ORDER BY id DESC LIMIT n
```

커서 자체는 SQL 조건이 아니라, 그 조건에 쓰이는 **값**(예: 마지막으로 받은 항목의 id)이다. 서버가 응답에 "다음 커서" 값을 실어주면, 클라이언트는 다음 요청에 그 값을 그대로 돌려보내기만 하면 된다.

### 4-3. 복합 커서(tie-breaker)가 필요한 이유

정렬 기준(`createdAt`)이 유일하지 않을 수 있으면(같은 시각에 여러 row 발생), 단일 컬럼 커서로는 순서가 애매해진다. 그래서 `(createdAt, id)`처럼 **유일성이 보장되는 컬럼을 추가로 묶어** 완전한 순서를 만든다.

```sql
message.createdAt < :beforeCreatedAt
  or (message.createdAt = :beforeCreatedAt and message.id < :beforeId)
```

### 4-4. `Pageable`과 커서를 함께 쓸 때의 역할 분리

`Pageable`은 원래 offset 기반(`page * size`)이지만, 커서 조건(WHERE)이 이미 "어디서부터"를 담당하므로 `page`는 항상 `0`으로 고정하고, `Pageable`은 순수하게 **"몇 개까지"(size)** 지정 용도로만 재활용한다.

### 4-5. `hasNext` 판별을 위한 `limit + 1` 트릭

```java
PageRequest.of(0, limit + 1)
boolean hasNext = found.size() > limit;
List<T> items = found.stream().limit(limit)...
```

요청한 개수보다 1개 더 많이 조회해서, 그 초과분이 실제로 왔는지(`size() > limit`)로 "더 있는지"를 판별한다. 초과분은 응답에는 포함시키지 않고 버린다. 이렇게 하면 별도의 `COUNT` 쿼리 없이 다음 페이지 존재 여부를 알 수 있다.

### 4-6. `(A == null) != (B == null)` — 짝을 이루는 파라미터 검증

불리언 두 개를 `!=`로 비교하면 XOR(배타적 논리합)이 된다. "둘 중 하나만 null"인 비정상 케이스를 감지해서 예외를 던지는 가드 클로즈 패턴이며, "둘 다 없거나 둘 다 있어야 한다"는 불변조건을 강제하는 데 쓰인다.

## 5. Redis

### 5-1. 키가 저장되는 원리

Redis는 DB마다 내부적으로 거대한 해시테이블 하나를 갖고 있고, `SET`/`HSET`/`SADD` 등 값을 쓰는 명령 자체가 곧 키를 그 해시테이블에 등록하는 행위다. "키 목록에 별도로 추가"하는 단계는 없다.

### 5-2. 키 조회 방법 비교

| 명령 | 용도 | 복잡도 |
|---|---|---|
| `EXISTS` (`hasKey`) | 특정 키 하나의 존재 여부 | O(1) |
| `GET` | 특정 키의 값 조회 (String 전용) | O(1) |
| `KEYS pattern` | 패턴에 맞는 키 전체를 한 번에 | O(N), 블로킹 — 운영 환경 지양 |
| `SCAN` | 패턴에 맞는 키를 커서로 나눠서 안전하게 순회 | O(N)이지만 비블로킹 |

`hasKey()`로 먼저 존재를 확인하고 `get()`을 또 호출하는 건 Redis에 **두 번 왕복**하는 것이라 손해다. `get()` 자체가 이미 "없으면 null"을 반환하므로 한 번의 호출로 충분하다.

### 5-3. Spring Data Redis API

Redis 데이터 타입별로 `opsForXxx()` 진입점이 나뉜다.

```java
redisTemplate.opsForValue().set(key, value);   // String
redisTemplate.opsForHash().put(key, field, value);  // Hash
redisTemplate.opsForSet().add(key, values...); // Set
```

`opsForValue()`는 String 타입 전용이라, 실제로 다른 타입으로 저장된 키에 쓰면 `null`이 아니라 **`WRONGTYPE` 예외**가 발생한다.

### 5-4. TTL 설정과 `KEEPTTL` 함정

```java
redisTemplate.opsForValue().set(key, value, Duration.ofSeconds(5)); // 값+TTL 원자적 처리
redisTemplate.expire(key, Duration.ofSeconds(5)); // 이미 있는 키의 TTL만 갱신
```

TTL이 걸려있는 키를 TTL 옵션 없이 다시 `SET`하면 **기존 TTL이 사라지고 영구 키가 된다.** 값과 TTL을 함께 갱신할 땐 결합형(`set(key, value, Duration)`)을 쓰는 것이, 별도로 `expire()`를 호출하는 것보다 안전하다 — 값만 쓰고 TTL을 아직 못 건 찰나의 틈(장애 시 영구 키로 남는 위험)이 없기 때문이다.

### 5-5. 캐시는 보조 저장소라는 설계 원칙

캐시(Redis)는 DB(진짜 데이터)의 조회 속도만 개선하는 보조 장치이므로, 캐시 저장/삭제가 실패해도 핵심 기능(DB 조회 결과 응답)에 영향을 주면 안 된다.

- 캐시 쓰기 실패 → 그냥 무시, DB 조회 결과는 그대로 응답
- 캐시 무효화(삭제) 실패 → TTL이 어차피 짧게(5초) 걸려있으므로 최악의 경우 그 시간 안에 자연 만료됨

이런 이유로 catch 블록이 의도적으로 비어있을 수 있으며, 이는 실수가 아니라 "실패해도 정합성이 깨지지 않는다"는 근거가 있는 설계 판단이다.
