## 3. 네트워크와 보안 그룹

| 서브넷 | 용도 |
|---|---|
| 퍼블릭 | ALB, (NAT), 바스티온 |
| 프라이빗 2a·2c | EC2 (공인 IP 없음) |
| DB 서브넷 그룹 | RDS — **기본 서브넷 그룹(`default-vpc-…`) 사용 중**, 퍼블릭 액세스 `False` 확인 (13장) |
| 캐시 서브넷 그룹 | Valkey |

| 보안 그룹 | 인바운드 | 의미 |
|---|---|---|
| `alb-sg` | 80 ← `0.0.0.0/0` | 사용자 → ALB |
| `app-sg` | 8080 ← `alb-sg` | ALB → EC2만 허용 (**22번 없음**) |
| `rds-sg` | 3306 ← `app-sg`, **3306 ← `bastion-sg`** | EC2, 바스티온 → RDS |
| `valkey-sg` | 6379 ← `app-sg`, **6379 ← `bastion-sg`** | EC2, 바스티온 → Valkey |
| `bastion-sg` (설계서 외) | 22 ← **내 IP만** | 내 PC → 바스티온 SSH |

- 보안 그룹은 **상태 저장(stateful)**: 들어온 요청의 응답은 아웃바운드 규칙과 상관없이 나간다.
- 내 PC에서 RDS·Valkey로 직접 접속할 수 없다 (의도한 설계). 접속은 **SSM**(앱 서버) 또는 **바스티온**(RDS·Valkey)을 거친다 (10-5).
- 네트워크를 옮기면 `bastion-sg`의 "내 IP"를 다시 설정해야 한다.
- 바스티온을 없앨 때는 `rds-sg`·`valkey-sg`의 `bastion-sg` 규칙을 **먼저** 지워야 `bastion-sg`를 삭제할 수 있다 (`bastion-ssh-tunnel.md` 8장).
- HTTPS 적용 시 `alb-sg`에 443 추가 필요.

## 4. IAM

### EC2 역할 `sword-master-ec2-role`

| 권한 | 용도 |
|---|---|
| `AmazonSSMManagedInstanceCore` | Session Manager 접속 |
| ECR 읽기 | 이미지 pull |
| Parameter Store 읽기 (`/swordmaster/prod/*`) | 부팅 시 설정·비밀값 읽기 |
| 인라인 `swordmaster-cloudwatch-logs` | `/swordmaster/prod/*` 로그 그룹에 스트림 생성, 로그 전송 |

### GitHub Actions 역할 `github-actions-swordmaster-deploy`

| 항목 | 값 |
|---|---|
| 신뢰 | GitHub OIDC (`token.actions.githubusercontent.com`) |
| `sub` 조건 | 조직·저장소 **숫자 ID가 포함된** 실제 토큰 값, `ref:refs/heads/deploy-test` |
| 인라인 `swordmaster-deploy` | ECR `swordmaster` push, `ssm:PutParameter`/`GetParameter` (`/swordmaster/prod/IMAGE_TAG`만), `autoscaling:StartInstanceRefresh` (`swordmaster-asg`만), `DescribeInstanceRefreshes` |
| GitHub Secret | `AWS_DEPLOY_ROLE_ARN` |

- GitHub는 **서버 안에서 명령을 실행할 권한이 없다.** 버전 이름표(IMAGE_TAG)를 바꾸고 교대(새로 고침)를 지시할 수만 있다.
- 배포 브랜치를 바꾸면 **워크플로와 신뢰 정책 `sub`를 함께** 바꿔야 한다.

## 5. 설정과 비밀값 (Parameter Store)

| 이름 | 타입 | 용도 |
|---|---|---|
| `/swordmaster/prod/IMAGE_TAG` | String | 실행할 이미지 태그 (CI/CD가 갱신) |
| `/swordmaster/prod/JWT_SECRET` | SecureString | JWT 서명 키 |
| `/swordmaster/prod/DB_HOST` | String/SecureString | RDS 엔드포인트 |
| `/swordmaster/prod/DB_USERNAME` | SecureString | DB 사용자 |
| `/swordmaster/prod/DB_PASSWORD` | SecureString | DB 비밀번호 |
| `/swordmaster/prod/REDIS_HOST` | String | Valkey 구성 엔드포인트 (`clustercfg.…`) |

**`application-prod.properties`** (Git에 포함, 비밀값은 모두 환경변수)

```properties
spring.datasource.url=jdbc:mysql://${DB_HOST}:3306/swordmaster?createDatabaseIfNotExist=true
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}
spring.data.redis.host=${REDIS_HOST}
spring.data.redis.port=6379
spring.data.redis.ssl.enabled=true
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false
jwt.secret=${JWT_SECRET}
```

- 값을 바꿔도 **실행 중인 서버에는 반영되지 않는다.** 부팅 때 한 번 읽으므로 인스턴스 새로 고침이 필요하다 (10장).
- SecureString 값은 확인할 때도 **길이만** 본다. 화면이나 로그에 출력하지 않는다.

## 6. 서버 실행 구조

### 시작 템플릿 v3 (사용자 데이터 요약)

| 순서 | 동작 |
|---|---|
| 1 | `set -euo pipefail`, 로그 `/var/log/swordmaster-init.log` (`set -x` 금지) |
| 2 | Docker 설치 (`dnf`) |
| 3 | Parameter Store에서 6개 값 읽기 (실패 시 10초 × 5회 재시도, 로그에는 **길이만**) |
| 4 | ECR 로그인 → `swordmaster:{IMAGE_TAG}` pull |
| 5 | IMDSv2로 인스턴스 ID 조회 |
| 6 | `docker run -p 8080:8080 --restart unless-stopped --log-driver awslogs …` + `SPRING_PROFILES_ACTIVE=prod` + 비밀값 환경변수 |

- EC2는 **ARM(t4g)** → 이미지는 `linux/arm64`로 빌드해야 한다 (`exec format error` 방지).
- 템플릿을 고치면 **새 버전 생성 → 기본 버전 변경 → 인스턴스 새로 고침** 순서. ASG가 `$Default`를 쓰므로 기본 버전만 바꾸면 된다.

### ASG `swordmaster-asg`

| 항목 | 값 |
|---|---|
| 용량 | 1 / 1 / 2 |
| 스케일링 정책 | CPU 60% 대상 추적 — **비활성** (통합 테스트 중 서버 1대 고정) |
| 헬스 체크 | **ELB**, 유예 180초 |
| 인스턴스 새로 고침 | 최소 정상 100%, 최대 정상 200%, 워밍업 180초 (먼저 띄우고 나중에 종료) |
| 자동 롤백 | 사용 불가 (`$Default` 버전 사용 때문) |

### ALB / 대상 그룹

| 항목 | 값 | 이유 |
|---|---|---|
| idle timeout | 300초 | WebSocket 연결 유지 |
| 헬스체크 경로 | `/actuator/health/readiness` | DB·Redis 장애로 서버 교체가 반복되는 것을 막음 |
| 등록 해제 지연 | 30초 | 배포 시간 단축 (WebSocket은 어차피 끊고 재연결) |

- `FilterConfig`에서 `/actuator/health/**`를 `permitAll`로 열어 두었다. 이 경로를 막으면 **모든 서버가 Unhealthy → 교체 반복**.

## 7. CI/CD

**파일**: `.github/workflows/deploy.yml` / **트리거**: `deploy-test` push, 수동 실행

| 순서 | 단계 |
|---|---|
| 1 | Java 21 → `./gradlew clean bootJar -x test` |
| 2 | OIDC로 `github-actions-swordmaster-deploy` 역할 획득 |
| 3 | ECR 로그인, QEMU + Buildx |
| 4 | 태그 생성 `v{KST 날짜-시각}-{커밋 7자리}` |
| 5 | `linux/arm64` 이미지 빌드·push (`provenance: false`, `sbom: false`) |
| 6 | `/swordmaster/prod/IMAGE_TAG` 갱신 |
| 7 | `start-instance-refresh` (최소 정상 100%, 최대 200%, 워밍업 180초) |

- `concurrency: deploy-prod`로 배포가 겹치지 않게 했다.
- **develop/main에 push해도 배포되지 않는다.**
- 7단계에서 실패해도 **6단계의 IMAGE_TAG는 이미 바뀐 상태**다. 다음 서버 교체 때 그 이미지가 쓰인다.
- 소요 시간: Actions 3~5분 + 새로 고침 5~8분.

## 8. DB 스키마 관리 (Flyway)

| 항목 | 값 |
|---|---|
| 위치 | `src/main/resources/db/migration/` |
| 적용 현황 (prod) | `V1__init.sql` (테이블 8개), `V20261014_1200__add_version_to_player_artifacts.sql` |
| 기동 순서 | Flyway 마이그레이션 → Hibernate `validate` → 앱 시작 |
| 기록 테이블 | `flyway_schema_history` |
| 상세 규칙 | `flyway-team-guide.md` |

**절대 규칙**
- 적용된 마이그레이션 파일은 **수정 금지** (체크섬 불일치 → 모든 서버 기동 실패)
- 엔티티를 바꾸면 **같은 PR에** 마이그레이션 파일 추가
- 롤백은 **되돌리는 새 마이그레이션**. 삭제된 데이터는 복구 불가 → 위험한 변경 전 **RDS 스냅샷**
- 파일 이름: `V{yyyyMMdd_HHmm}__{설명}.sql` (언더스코어 2개)
- 로컬은 현재 `SPRING_FLYWAY_ENABLED=false`로 실행 (팀 정책 미정) → **로컬에서 마이그레이션 누락을 발견하지 못하므로** 배포 전 Flyway를 켠 빈 DB로 기동 확인

## 9. 모니터링과 알림

### 로그

- CloudWatch → 로그 그룹 `/swordmaster/prod/app` → 스트림 = 인스턴스 ID
- 유용한 검색어: `ERROR`, `Exception`, `APPLICATION FAILED`, `Started`, `Migrating`
- Flyway 로그는 `o.f.core…`로 축약되어 `flywaydb`로는 거의 검색되지 않는다.

### 알람 (모두 → SNS `swordmaster-alerts`, ALARM과 OK 둘 다 알림)

| 알람 | 지표 | 조건 | 누락 데이터 | 의미 |
|---|---|---|---|---|
| `swordmaster-no-healthy-host` | `HealthyHostCount` (TG별), 최소, 1분 | `< 1`, 2/2 | 위반 | 서비스 중단 |
| `swordmaster-target-5xx` | `HTTPCode_Target_5XX_Count` (TG별), 합계, 5분 | `>= 5`, 1/1 | 정상 | 앱이 에러를 냄 (DB·Redis 장애 포함) |
| `swordmaster-rds-low-storage` | `FreeStorageSpace`, 최소, 5분 | `< 2147483648` (2GB), 2/2 | 무시 | 디스크 부족 임박 |

- 테스트: `aws cloudwatch set-alarm-state --alarm-name {이름} --state-value ALARM --state-reason "테스트"` (서비스 영향 없음)
- 팀원 추가: SNS 토픽에 이메일 구독 추가 → 본인이 메일에서 **Confirm subscription**

## 10. 운영 절차 (Runbook)

### 10-1. 코드 배포

```bash
git checkout deploy-test
git fetch origin
git diff deploy-test origin/develop --stat -- src/main/resources/db/migration/   # 마이그레이션 확인
git merge origin/develop
git push origin deploy-test
```

확인 순서: Actions ✅ → ASG **인스턴스 새로 고침** 탭 `성공` → 대상 그룹 새 인스턴스 Healthy (ID가 바뀌었는지) → 로그 `Started`

### 10-2. 이전 버전으로 롤백

```bash
aws ecr describe-images --repository-name swordmaster \
  --query 'sort_by(imageDetails,&imagePushedAt)[-10:].[imageTags[0],imagePushedAt]' --output table
aws ssm put-parameter --name /swordmaster/prod/IMAGE_TAG --value {이전태그} --type String --overwrite
aws autoscaling start-instance-refresh --auto-scaling-group-name swordmaster-asg \
  --preferences '{"MinHealthyPercentage":100,"MaxHealthyPercentage":200,"InstanceWarmup":180,"SkipMatching":false}'
```

- ECR에는 **최근 10개**만 남는다.
- 이전 버전이 **새 마이그레이션을 모르는 상태**면 Flyway는 통과하지만 validate가 실패할 수 있다 (컬럼 추가는 대체로 괜찮고, 삭제·이름 변경은 위험).

### 10-3. 설정·비밀값 변경 (JWT 키 교체 등)

1. Parameter Store 값 변경
2. 인스턴스 새로 고침, **Skip matching OFF** (시작 템플릿이 그대로라 ON이면 아무 서버도 교체되지 않음)
3. 새로 고침 중 잠깐 서버 2대가 서로 다른 키를 가짐 → JWT 교체 시 기존 토큰은 무효 (재로그인)

### 10-4. 구글 시트 데이터 변경

서버가 **기동 시 1회** 시트를 읽는다 → 10-3과 같은 방식으로 인스턴스 새로 고침 (Skip matching OFF). 시트 검증에 실패하면 새 서버가 뜨지 않고 **기존 서버가 계속 서비스**한다.

### 10-5. DB·Valkey 직접 접속

| 대상 | 방법 | 상세 |
|---|---|---|
| 앱 서버 (로그, 컨테이너) | **SSM** | 아래 A |
| RDS (SQL, GUI) | **바스티온 SSH 터널** 또는 SSM | 아래 B, A |
| Valkey | **바스티온 안에서 `valkey-cli`** | 아래 C |

전체 절차·원리·트러블슈팅: **`bastion-ssh-tunnel.md`**

**A. SSM으로 앱 서버 경유 (RDS)**

1. EC2 → 인스턴스 → `swordmaster-asg` 인스턴스 → 연결 → **Session Manager**
2. `sh-5.2$`에서 `bash` 입력 (따로 한 줄로)
3. MySQL 클라이언트를 Docker로 실행

```bash
sudo docker run -it --rm mysql:8 mysql -h {DB_HOST} -u {DB_USERNAME} -p swordmaster
```

- 서버가 교체되면 인스턴스 ID가 바뀐다.

**B. 바스티온 SSH 터널 (RDS를 내 PC GUI로)**

```bash
# 내 PC Git Bash, 창을 열어 둔 채 유지 (종료는 Ctrl+C)
ssh -i ~/.ssh/swordmaster-bastion-key.pem -N -L 3307:{RDS엔드포인트}:3306 ec2-user@{바스티온공인IP}
```

- GUI(DBeaver, HeidiSQL 등): 호스트 **`127.0.0.1`**, 포트 **`3307`** (RDS 엔드포인트를 GUI에 직접 넣으면 10060 시간 초과)
- 3307인 이유: 내 PC의 3306은 로컬 Docker MySQL이 사용 중

**C. 바스티온에서 Valkey (10/14 접속 확인)**

```bash
ssh -i ~/.ssh/swordmaster-bastion-key.pem ec2-user@{바스티온공인IP}
sudo dnf install -y valkey          # 최초 1회
valkey-cli --tls -c -h {구성엔드포인트} -p 6379
```

- `-h`에는 **주소만** (`:6379`, `{ }` 금지)
- 앱 서버의 Docker `valkey/valkey` 이미지는 CA 목록이 없어 `certificate verify failed` → 바스티온 방식 권장
- **금지**: `KEYS *`, `FLUSHALL`, `FLUSHDB`, `DEL` / 키 목록은 `SCAN`

**바스티온 운영**

| 항목 | 내용 |
|---|---|
| 평소 상태 | **중지** 권장 (켜 두면 월 약 $7, 중지 시 EBS 약 $0.7) |
| 다시 켤 때 | 공인 IP가 바뀜 → 명령의 IP 교체 |
| 다른 사람의 접근 | ① `bastion-sg` 내 IP만 ② 키 페어 ③ DB 비밀번호 — 3겹 |
| `.pem` | 내 PC `~/.ssh/`에만. Git·채팅 공유 금지, 분실 시 재발급 불가 |

- 운영 데이터를 바꾸기 전에 **스냅샷** (10-6).

### 10-6. RDS 수동 스냅샷

```bash
aws rds create-db-snapshot --db-instance-identifier swordmaster-db \
  --db-snapshot-identifier before-{작업}-{yyyyMMdd}
```

- 언제: 컬럼·테이블 삭제/변경 마이그레이션 배포 직전, 운영 DB 직접 수정 전, 통합 테스트 종료 시
- 복구는 **새 RDS 인스턴스**로 생성 → `DB_HOST` 변경 → 인스턴스 새로 고침
- 현재 수동 스냅샷 **없음**. 자동 백업은 **1일** (프리 플랜 상한).

### 10-7. 서버를 잠시 내리기 (비용 절약)

```bash
aws autoscaling update-auto-scaling-group --auto-scaling-group-name swordmaster-asg \
  --min-size 0 --desired-capacity 0
```

- 서버를 0대로 만들면 **`no-healthy-host` 알람이 울린다** (정상 동작).
- NAT·ALB·RDS·Valkey는 서버가 0대여도 계속 과금된다. 더 줄이려면 NAT 삭제를 검토 (다시 올릴 때 재생성 필요, 순서 주의: 서버 0대 → NAT 경로 삭제 → NAT 삭제).
- 다시 올리기: `--min-size 1 --desired-capacity 1`

## 11. 장애 대응

### 알람별 첫 행동

| 알람 | 확인 순서 |
|---|---|
| `no-healthy-host` | ① 대상 그룹 대상 탭 상태 사유 ② ASG 활동 탭 (교체 반복?) ③ 로그 `ERROR`, `APPLICATION FAILED` ④ 최근 배포/설정 변경 여부 |
| `target-5xx` | ① 로그에서 알람 시각 전후 `Exception` ② RDS·Valkey 상태 (콘솔) ③ 최근 배포 |
| `rds-low-storage` | ① 테이블별 용량 확인 ② 로그성 테이블(`battle_histories`, `currency_histories`) 정리 검토 |

### 상태 코드

| 코드 | 의미 | 흔한 원인 |
|---|---|---|
| 502 | 서버가 연결 거부, 응답 깨짐 | 서버 기동 중, 앱 죽음, 전부 Unhealthy일 때 fail-open |
| 503 | 등록된 대상 없음 | 서버 0대 |
| 504 | 응답 시간 초과 | 앱 처리 지연, 보안 그룹 |

### 지금까지 겪은 장애

| 장애 | 원인 | 해결 |
|---|---|---|
| 헬스체크 401 | `/actuator/health`가 인증 필요 | `permitAll` |
| 502 + 교체 반복 (10/13) | 대상 그룹 경로를 readiness로 **먼저** 바꿈 → Security가 401 | 경로 원복 → `/actuator/health/**` 허용 배포 → 200 확인 → 경로 변경 |
| 기동 실패: 시트 검증 | enum 수정이 다른 브랜치에만 있었음 | 수정 후 재배포 |
| 기동 실패: Flyway `non-empty schema` | `update`로 만든 테이블 + history 없음 | prod: DB 비우고 V1부터 / 로컬: Flyway 끄기 |
| OIDC `AssumeRoleWithWebIdentity` 거부 | `sub`에 숫자 ID 포함 | 실제 토큰 `sub` 값으로 신뢰 정책 갱신 |

> **구성 변경 원칙**: ① 새 설정이 동작할 조건을 먼저 갖추고 → ② 동작을 직접 확인한 뒤 → ③ 전환한다. 특히 헬스체크 경로는 ASG가 ELB 헬스체크를 쓰므로 **서버 생사를 결정하는 스위치**다.

## 15. 작업 규칙

### 보안
- JWT 키, DB 비밀번호, AWS Access Key, 계정 ID를 **문서·채팅·로그에 남기지 않는다.**
- SecureString은 **길이만** 확인한다.
- **루트 계정 키를 쓰지 않는다.** CloudShell과 콘솔은 IAM 사용자로.
- 사용자 데이터 스크립트에 `set -x` 금지 (비밀값이 로그에 찍힘).

### 환경
- EC2는 ARM → 이미지 `linux/arm64`
- EC2 안의 docker 명령은 `sudo`
- Git Bash에서 `/swordmaster/...` 같은 경로가 바뀌면 명령 앞에 `MSYS_NO_PATHCONV=1`
- CloudShell 출력이 `:`에서 멈추면 `q`, 미리 `export AWS_PAGER=""`
- SSM 접속 후 `bash`는 **한 줄로 따로** 입력

### 변경 순서
- 헬스체크 경로, 보안 그룹, 리스너처럼 **트래픽을 결정하는 설정**은 반드시 "준비 → 확인 → 전환"
- 스키마 변경은 엔티티 + 마이그레이션을 **같은 PR**로
- 위험한 DB 작업 전에는 **스냅샷**

## 16. 도메인과 HTTPS 적용 절차 (나중에)

### 전제와 확인된 사실

| 항목 | 내용 |
|---|---|
| **Route 53 도메인 등록** | ❌ 프리 플랜 계정은 불가 (`AccessDeniedException: Free Tier accounts are not supported for this service`, 10/14 확인) |
| 방식 | **외부 업체에서 도메인 구매 + 그 업체의 DNS 사용** (Route 53 사용 안 함) |
| 비용 | **도메인 구매비만 유료** (AWS 크레딧이 아니라 별도 결제, 연 1~2만 원대). ACM 인증서, 외부 DNS, 443 리스너는 무료 |
| 결정 필요 | 도메인 이름, 구매처, **결제자(=소유자, 매년 갱신 담당)** |
| 서버 주소 | 루트 도메인이 아니라 **`api.{도메인}`** 서브도메인 (루트는 CNAME 불가인 경우가 많음) |

```
클라이언트 ──https / wss (443)──▶ ALB (ACM 인증서로 복호화) ──http / ws (8080)──▶ EC2
```

**바뀌지 않는 것**: 서버 코드, EC2, 대상 그룹, 헬스체크, ASG, STOMP 규칙. 80 리스너도 그대로 두므로 작업 중 기존 접속이 끊기지 않는다.

### 절차

| 단계 | 위치 | 작업 | 확인 |
|---|---|---|---|
| 0 | 외부 업체 | 도메인 구매, **자동 갱신 켜기** | |
| 1 | ACM (**서울 리전**) | 퍼블릭 인증서 요청, 도메인 `api.{도메인}`, **DNS 검증** | 상태 "검증 대기 중", CNAME 이름·값 복사 |
| 2 | 외부 DNS | 검증용 CNAME 추가 (ACM이 준 이름 → ACM이 준 값) | 5~30분 뒤 ACM "발급됨" |
| 3 | 외부 DNS | `api` → CNAME → ALB DNS 이름 (`swordmaster-alb-….elb.amazonaws.com`) | |
| 4 | EC2 → 보안 그룹 `alb-sg` | 인바운드 HTTPS 443 ← `0.0.0.0/0` | |
| 5 | ALB → 리스너 및 규칙 | 리스너 추가: HTTPS:443 → 기존 swordmaster 대상 그룹, 인증서 `api.{도메인}`, 보안 정책 기본값 | |
| 6 | 클라이언트 / 브라우저 | `GET https://api.{도메인}/actuator/health/readiness` | `200 {"status":"UP"}`, 자물쇠 표시 |
| 7 | 팀 공지 | 주소 변경: `http://…elb…` → `https://api.{도메인}`, `ws://…/ws` → `wss://api.{도메인}/ws` | |
| 8 | ALB 80 리스너 | **모든 클라이언트가 7을 반영한 뒤** 기본 작업을 "URL로 리디렉션 → HTTPS 443, 301"로 변경 | |

### 순서가 중요한 이유

| 순서 | 이유 |
|---|---|
| 인증서 발급(1~2) → 리스너(5) | "발급됨" 상태여야 리스너에서 선택 가능 |
| 보안 그룹(4) → 확인(6) | 443이 막혀 있으면 타임아웃 |
| 클라이언트 변경(7) → 리다이렉트(8) | WebSocket은 리다이렉트를 따라가지 않음 → 먼저 바꾸면 `ws://` 클라이언트 연결 실패 |

### 주의

- 2단계: 업체가 이름 뒤에 도메인을 자동으로 붙이는 경우, ACM이 준 이름의 **앞부분(`_abc123…`)만** 입력 (두 번 붙으면 검증 실패)
- **검증용 CNAME은 지우지 않는다.** 인증서 자동 갱신(약 13개월마다)에도 쓰인다. 지우면 갱신 실패 → 인증서 만료 → HTTPS 중단
- Cloudflare를 쓰면 처음에는 **DNS only(회색 구름)**로 둔다. 프록시(주황 구름)를 켜면 Cloudflare 인증서가 끼어들어 구조가 달라진다
- **ALB를 다시 만들면** DNS 이름이 바뀌므로 3단계 CNAME 값을 새 이름으로 변경, 인증서는 새 리스너에 다시 연결
- 적용 후 Spring에서 원래 프로토콜(https)을 알아야 하는 기능이 생기면 `server.forward-headers-strategy=native` (ALB가 `X-Forwarded-Proto` 헤더를 붙여 줌)
