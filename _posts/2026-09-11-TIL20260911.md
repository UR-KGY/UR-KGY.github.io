## Part 1. Stream.sorted() / Comparator 개념 정리

### 1. `sorted()` 기본

```java
Stream<T> sorted()                              // 자연 순서(Comparable) 기반 정렬
Stream<T> sorted(Comparator<? super T> cmp)     // 커스텀 정렬 기준
```

- `String`, `Integer`처럼 `Comparable`을 구현한 타입은 `sorted()` 단독 호출이 가능하다.
- 직접 만든 클래스(`record` 등)는 비교 기준이 없으므로 `Comparator`를 넘겨야 한다.
- `sorted()`는 스트림 전체를 모아야 정렬 가능한 stateful 연산이라, 무한 스트림에는 `limit()`을 먼저 걸어야 한다.

### 2. `Comparator`로 오름차순/내림차순 지정

```java
// 오름차순
Comparator.comparingInt(Person::age)

// 내림차순
Comparator.comparingInt(Person::age).reversed()
```

- `reversed()`는 반드시 `comparing`으로 감싼 **Comparator 뒤**에 붙여야 합니다. 메서드 레퍼런스(`Person::age`)에는 바로 붙일 수 없다.
- 기본형 필드는 `comparingInt/Long/Double`을 쓰는 게 오토박싱을 피해 더 효율적이다.

### 3. 중첩 필드 비교 — 람다는 되지만 메서드 레퍼런스 체이닝은 안 됨

```java
// 안 됨 (컴파일 에러): 메서드 레퍼런스는 체이닝 불가
Comparator.comparing(Task::getRun::getDurationSeconds)

// 됨: 람다로 감싸면 중첩 필드도 자유롭게 접근
Comparator.comparing(t -> t.getRun().getDurationSeconds())
```

### 4. 다단계 정렬 — `thenComparing()`

```java
Comparator.comparing(Employee::dept)                                        // 1단계
          .thenComparing(Comparator.comparingInt(Employee::age).reversed()) // 2단계(내림차순)
          .thenComparing(Employee::name);                                   // 3단계
```

- 동작 원리: **비교(pair) 단위**로 동작합니다. 두 요소를 비교할 때 1번 조건이 0(동점)이 아니면 그 자리에서 끝나고, 2번 조건은 호출조차 되지 않습니다(단락 평가).
- "1번 전체 정렬 후 2번을 다시 정렬"하는 2-pass 방식이 아니라, 하나의 통합된 `compare()` 규칙입니다.
- 동점 상황에서만 다음 조건이 적용되므로, `Comparator.thenComparing(customComparator)`처럼 완전히 커스텀한 로직(예: 고정 우선순위 목록)도 동점 처리 규칙으로 넣을 수 있습니다.

-결국 전체적인 맥락은 1단계에서 정렬이 되지않은 것들을 2단계에서 다시 정렬하고 3단계에서 1,2단계에서 정렬되지 않는 것들을 정렬한다.

### 5. `Predicate` vs `Comparator`

| 구분 | `Predicate<T>` | `Comparator<T>` |
|---|---|---|
| 목적 | 필터링(조건 판별) | 정렬(순서 결정) |
| 메서드 | `boolean test(T t)` | `int compare(T o1, T o2)` |
| 조합 메서드 | `and()`, `or()`, `negate()` | `thenComparing()`, `reversed()` |

```java
Predicate<Employee> isDev = e -> e.dept().equals("개발");
Predicate<Employee> isYoung = e -> e.age() < 35;

Predicate<Employee> devAndYoung = isDev.and(isYoung);   // AND
Predicate<Employee> devOrLee = isDev.or(e -> e.name().equals("Lee"));  // OR
Predicate<Employee> notDev = isDev.negate();            // NOT
```

- `and`/`or`는 왼쪽부터 단락 평가되며, 우선순위는 괄호처럼 명시적으로 묶어줘야 한다(`a.and(b.or(c))`).

### 6. 특정 필드 기준 중복 제거

```java
// 방법 1: 정렬 후 Set으로 "처음 만난 것만" 필터링 (실무에서 가장 많이 쓰는 패턴)
Set<String> seen = new HashSet<>();
List<Item> deduped = items.stream()
        .sorted(comparator)
        .filter(item -> seen.add(item.getKey()))  // 이미 있으면 add()가 false → 걸러짐
        .toList();
```

- `filter()`는 항상 "람다가 반환한 boolean"만 보고 판단한다. `seen.add(...)`가 boolean을 반환하는 부수효과 있는 함수라는 점을 이용한 관용구이다.
- 순서 중요: **반드시 정렬 후 필터**. 순서가 바뀌면 "정렬 기준상 앞선 것"이 아니라 "원본 리스트에서 먼저 나온 것"이 남는다.
- 병렬 스트림(`parallelStream()`)에서는 사용 금지(`HashSet`이 스레드 안전하지 않음).

- 중복값이 허용되지 않는 Set을 이용하여 List 내의 정렬된 첫번째 값만 남겨 새로운 리스트로 만드는 과정이다.

### 7. 인덱스(순위) 부여 — `IntStream.range()`

```java
List<Entry> entries = IntStream.range(0, list.size())
        .mapToObj(i -> new Entry(i + 1, list.get(i).getX(), list.get(i).getY()))
        .toList();
```

- `record`는 리스트 안에서 자기 위치(인덱스)를 스스로 알 방법이 없다.(같은 값의 객체가 여러 리스트/여러 위치에 있을 수 있으므로).
- `list.indexOf(item)`으로 역산하는 것은 **값이 같은 요소가 있으면 항상 첫 번째 인덱스만 반환**하고, O(n²)로 성능도 나쁘므로 사용하면 안 된다.
- `IntStream.range(0, n)`은 `for (int i = 0; i < n; i++)`의 함수형 버전이다. `i`가 매번 새 값으로 주어진다는 점이 특징이다.

- 해당 로직 사용목적은 우선 남은 순위기록 양이 직접 처리하기엔 너무 방대했기 때문이다. 따라서 list의 size 만큼 IntStream.range() 로 for 문 처럼 동작하는 stream 환경에서 

### 8. 람다의 변수 캡처 — "effectively final" 규칙

```java
List<Record> records = getRecords();
records = filterSomehow(records);         // 재할당

final List<Record> finalRecords = records; // 람다 직전에 새 변수로 고정

IntStream.range(0, finalRecords.size())
        .mapToObj(i -> finalRecords.get(i))  // OK
        .toList();
```

- 지역 변수는 스택에 있고 람다는 나중에(다른 스레드에서) 실행될 수 있어서, 자바는 값을 복사해서 캡처합니다.
- 캡처 이후 재할당이 되면 "복사본과 원본이 달라지는" 모순이 생기므로, **재할당된 적 없는 변수(effectively final)만** 람다에서 캡처 가능합니다.
- 읽기(`list.get(i)`)는 전혀 문제없고, **재할당(`list = ...`)만** 문제가 됩니다.
- 해결책: 재할당 직후 새 변수에 한 번 담거나, 애초에 단계별로 변수명을 다르게 써서 재할당 자체를 없애는 것이 더 깔끔합니다.

## Part 2. 400 에러 디버깅 과정

### 문제 상황

`GET /rankings` 요청 시 400 Bad Request 발생. 콘솔에는 에러가 안 보이고 Hibernate 쿼리 로그만 찍힘.

### 진단 과정

| 단계 | 확인한 것 | 결과 |
|---|---|---|
| 1 | 컨트롤러에 `@RequestParam` 등 파라미터 존재 여부 | 파라미터 없음 → 요청 자체의 검증 실패는 아님 |
| 2 | 전역 예외 핸들러(`@ExceptionHandler`) 확인 | `HttpMessageNotReadableException`/`MethodArgumentTypeMismatchException`을 잡아 **로그 없이** 400으로 응답하고 있었음 |
| 3 | 핸들러에 로그 추가 후 재현 | 진짜 스택 트레이스 확보 |

### 근본 원인 1: 외부 API 응답 파싱 실패 (요청이 아니라 응답 문제였음)

```
RankingClient.fetch() → 외부 랭킹 소스 API 호출 → 응답 JSON을 RankingSource로 역직렬화
Caused by: InvalidFormatException: Cannot deserialize value of type `CardType` from String "VOID_KNIGHT"
```

- **원인**: `records[89].deck.cards[13].cardType` 값이 `"VOID_KNIGHT"`인데, `CardType` enum에 그 값이 없었음.
- 두 번째로는 `"strike"`(소문자)가 `STRIKE`와 대소문자가 달라 또 같은 예외 발생.
- **정황상 의도된 테스트 데이터로 판단**: 프로젝트 요구사항 자체가 "정상 기록과 비정상 기록을 구분해서 `excludeCount`로 세는 것"이었으므로, 이런 이상한 카드 값들은 버그가 아니라 필터링 로직을 검증하기 위한 데이터일 가능성이 큼.

### 해결책: `cardType`을 String으로 받고, 별도 검증 단계에서 대조

```java
// DTO: enum이 아니라 String으로 받아서 파싱 자체는 항상 성공하게 함
public class Card {
    private String cardType;
}

// 검증 Predicate: enum 값과 정확히(대소문자 포함) 일치하는지 확인
Predicate<Record> cardTypeOk = r -> r.getDeck().getCards().stream()
        .allMatch(card -> Arrays.stream(CardType.values())
                .anyMatch(cardType -> cardType.name().equals(card.getCardType())));

Predicate<Record> finishingCardOk = r -> r.getDeck().getCards().stream()
        .anyMatch(card -> Objects.equals(card.getCardType(), r.getBossFight().getFinishingCard()));
```

- `CardType.valueOf()` / `name().equals()`는 대소문자를 엄격히 구분하므로, 오타·대소문자 문제를 그대로 "비정상"으로 잡아냄.
- `Objects.equals()`를 사용해 `null` 값이 와도 `NullPointerException` 없이 안전하게 처리.

### 근본 원인 2: 순위가 기대와 다르게 나오는 정렬 버그

```java
// 문제의 코드 — 이름은 "Desc"인데 실제로는 오름차순으로 동작
Comparator<Record> orderByFinalHpDesc = Comparator.comparingInt(record -> record.getRun().getFinalHp());
```

- **증거**: 응답 JSON에서 `clearTimeSeconds`가 동점인 두 기록(18위 `remainingHp=1`, 19위 `remainingHp=4`)을 비교했을 때, `finalHp` 내림차순이 의도라면 HP가 높은 쪽(4)이 먼저 와야 하는데 실제론 반대로 나옴.
- **원인**: `.reversed()`가 빠져서 기본값인 오름차순으로 동작하고 있었음. 변수 이름/주석과 실제 코드가 어긋난 전형적인 논리적 버그(컴파일 에러도, 런타임 예외도 없음).

### 해결

```java
Comparator<Record> orderByFinalHpDesc =
        Comparator.comparingInt((Record record) -> record.getRun().getFinalHp()).reversed();
```

### 알아둘 것

- 전역 예외 핸들러가 실제 예외(`e`)를 로그로 남기지 않으면 원인 파악이 매우 어려워지므로, 항상 `log.error(..., e)` 형태로 원본 예외를 남겨야 한다. 
- 클라이언트의 요청이 아니라, **서버가 외부 API를 호출해서 받은 응답을 파싱하다가** 실패하는 경우도 있다는 점을 스택 트레이스에서 호출 순서(`RankingClient.fetch()` → `RestClient` → `Jackson`)로 구분해서 읽어야 한다
