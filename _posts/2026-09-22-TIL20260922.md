# 개인 프로젝트 종료
개인적으로 가장 부족한 부분은 Redis 의 구조 쪽이 아닐까 싶다. 
Redis 는 메모리 상에서 동작하며 가벼운 작업을 빠르게 처리하는 데 쓰인다고만 알고 있지
직접 많이 써보면서 어떻게 사용하는지를 알고싶었지만 이번 프로젝트에서는 아직 감이 잘 안잡힌다. 

웹소켓은 Spring에선 어떤 구조로 돌아가는 지는 흐름은 안 것 같다. 외우기보단 많이 써보면서 배워야한다..
과제에선 목표와 힌트를 미리 알려주고 들어갔지만 완전히 백지 상태에서부터 구조를 짜라고 하면 자신이 없겠다. 

최종 프로젝트 때 우선지망은 경험하면서 배우고 싶었던 클라이언트이긴 한데 솔직하게 배움이 부족해 팀원들 보기에 답답할 것 같다. 
그렇다고 서버로 하기에도 많이 부족하다 느끼기에 철면피를 깔더라도 열심히 해보고 싶다.. 
이번에 서버를 배우는 데 따라가기도 바빠서 클라이언트 공부를 많이 하지는 못했지만 AI 든 뭐든 활용해서 열심히 해보겠다.
남는 것은 결국 시간하고 경험인데 이번에도 흐지부지 하고 끝나지는 말자.

## 1부. 프로젝트 구현 기록 (README 기준, Lv 1~19)

### Lv 1. Docker DB 연결 설정
`application.properties`에 MySQL / Redis 연결 정보를 환경변수로 설정.
```properties
spring.datasource.url=jdbc:mysql://localhost:3306/webcraft
spring.data.redis.host=localhost
spring.data.redis.port=6379
```

### Lv 2. 인덱스 설정
특정 컬럼을 기준으로 미리 정렬된 별도 구조물을 만들어 전체 탐색 없이 빠르게 조회하도록 함.
```sql
CREATE INDEX idx_chat_world_created_at ON chat_messages(world_id, created_at);
```
`@Table(indexes = @Index(...))`로 엔티티에 동일한 인덱스를 선언.

### Lv 3. 요청 검증과 DTO
`@Validated` 기반 요청 검증. `@NotBlank`, `@Size(min, max)`, `@Pattern(regexp)`으로 닉네임 형식 제한. 컨트롤러는 `@PostMapping` + `@Valid @RequestBody`로 매핑하고, 서비스에서 닉네임 중복 여부를 먼저 확인한 뒤 저장(중복 시 `ConflictException`).

### Lv 4. 월드 생성 (최대 개수 제한)
`worldOperations.duringCreation(Supplier<T> action)`으로 락을 건 상태에서 월드 개수를 확인 — `worldRepository.countRootWorlds() >= MAX_WORLDS`이면 `ConflictException`, 아니면 `createPreparedWorld(request)` 실행.

### Lv 5. 채팅 저장과 내역 조회
`worldRepository.findById(worldId)`로 월드 존재 확인 → `chatMessageRepository.save(...)`로 저장 → 저장된 엔티티로 응답 DTO 생성.

```java
        .addInterceptors(nicknameInterceptor)

```

### Lv 9. 월드별 세션 관리 (SessionRegistry)
`ConcurrentHashMap<Long, ConcurrentHashMap<String, Entry>> worlds` — worldId → (nickname → Entry) 2단계 저장소.
```java
public Entry register(Long worldId, String nickname, WebSocketSession session) {
    Entry candidate = new Entry(session);
    AtomicReference<Entry> registered = new AtomicReference<>();
    worlds.compute(worldId, (ignored, current) -> {
        ConcurrentHashMap<String, Entry> sessions = current == null ? new ConcurrentHashMap<>() : current;
        Entry addResult = sessions.putIfAbsent(key(nickname), candidate);
        if (addResult == null) registered.set(candidate);
        return sessions;
    });
    return registered.get();
}
```
→ 이번 세션에서 `compute()`의 인자 전달 방식, `AtomicReference`의 역할을 상세히 분석함 (2부 참고).

### Lv 10. Redis 접속 상태 관리
```java
public void join(Long worldId, String connectionId) {
    redisTemplate.opsForZSet().add(key(worldId), connectionId, expiresAt());
    redisTemplate.expire(key(worldId), KEY_TTL);
}
public void leave(Long worldId, String connectionId) {
    redisTemplate.opsForZSet().remove(key(worldId), connectionId);
}
```
→ 실제 구현체인 `PresenceService`(join/heartbeat/leave/onlineCount)까지 이번 세션에서 전체 구조를 분석함 (2부 참고).

### Lv 18. Redis 최근 채팅 캐시
```java
public List<ChatMessageResponse> read(Long worldId, int limit) {
    String json = redis.opsForValue().get(key(worldId, limit));
    return json == null ? null : Arrays.asList(mapper.readValue(json, ChatMessageResponse[].class));
}
public void write(Long worldId, int limit, List<ChatMessageResponse> messages) {
    String json = mapper.writeValueAsString(messages);
    redis.opsForValue().set(key(worldId, limit), json, Duration.ofSeconds(5));
}
```
캐시 조회 실패는 예외를 삼키고 `null`을 반환 — DB를 보조하는 캐시이므로 캐시 장애가 서비스 전체 장애로 번지지 않도록 함.

### Lv 19. Lua Script로 원자성 확보
GET(확인) → INCR(증가)를 별도 호출로 하면 그 사이에 동시 요청이 끼어들어 제한량을 초과하는 문제를 테스트 코드로 직접 확인. 이후 하나의 Lua 스크립트로 확인+증가+최초 TTL 설정을 원자적으로 묶어 해결.
```java
private void setScript() {
    script.setScriptText("""
        local key = KEYS[1]
        local limit = tonumber(ARGV[1])
        local ttlSeconds = tonumber(ARGV[2])
        local current = tonumber(redis.call('GET', key) or '0')
        if current >= limit then return 0 end
        local updated = redis.call('INCR', key)
        if updated == 1 then redis.call('EXPIRE', key, ttlSeconds) end
        return 1
        """);
    script.setResultType(Long.class);
}
```
→ 이 스크립트가 완성되기까지의 논의(주석 문법, `setScriptText`를 생성자에서 한 번만 호출해야 하는 이유 등)는 2부에 정리.

## 2부. 헷갈리는 개념들 정리 (주제별)

### 2-1. 동시성 컬렉션 — `ConcurrentHashMap.compute()`
- `Map<K,V>.compute(key, remappingFunction)`의 `remappingFunction`은 `BiFunction<K, V, V>` 규격이라 인자가 항상 2개다.
- 첫 번째 인자는 `compute()`에 넘긴 key 자신(Lv 9 코드의 `worldId`), 두 번째 인자는 그 key에 이미 매핑된 현재 값(없으면 `null`).
- 람다가 반환한 값은 `compute()`가 자동으로 그 key의 새 매핑으로 저장한다 — 별도의 `put()` 호출이 필요 없고, "확인 + 갱신"이 하나의 원자적 연산으로 처리되어 수동 get-then-put 방식의 race condition을 피할 수 있다.
- 람다는 effectively final 변수만 캡처할 수 있어 바깥 지역변수를 직접 재할당할 수 없다. `AtomicReference<Entry>`는 "참조는 고정, 내부 값만 변경"하는 방식으로 이 제약을 우회해 람다 밖으로 결과를 꺼내는 표준적인 방법이다.
- `register()`의 두 `return`은 서로 다른 레벨: 람다의 `return sessions`는 `worlds` 맵의 값(V, 타입은 `ConcurrentHashMap<String, Entry>`)을 갱신하는 것이고, 메서드의 `return registered.get()`은 `register()` 자신의 반환 타입(`Entry`)에 맞춰 호출자에게 결과를 알려주는 것이다.
- `putIfAbsent`가 `null`을 반환하면(새로 등록됨) `registered`에 값이 설정되고, 이미 같은 nicknameKey가 그 world에 있었다면 `registered`는 초기값인 `null`로 남아 `register()`가 `null`을 반환한다. (worldId 자체가 이미 있었는지는 무관 — 판단 기준은 항상 "그 world 안의 같은 nicknameKey" 단위.)

### 2-2. Redis ZSet과 Presence 추적 설계
- ZSet은 `key → (member, score)` 쌍들의 컬렉션. Hash의 `Map<String,String>`과 유사하지만, score(숫자)로 항상 정렬 상태를 유지하고 범위 조회(`rangeByScore` 등)가 가능하다는 점이 다르다. member는 Hash의 field처럼 유일해야 한다.
- `key-value-score` 구조는 모든 Redis 자료구조의 공통점이 아니라 ZSet만의 고유한 구조다.
- score에 `expiresAt()`을 넣는 것은 단순 데이터 저장일 뿐 자동 삭제를 유발하지 않는다 — 애플리케이션이 직접 `rangeByScore`로 조회해서 지워야 한다.
- `redisTemplate.expire(key, KEY_TTL)`은 이와 별개로 Redis 서버 자체가 key 전체를 정해진 시간 뒤 자동 삭제하는 진짜 TTL이다. 두 메커니즘은 서로 보완적: score는 개별 member 단위의 세밀한 만료 판단용, `expire()`는 key 전체에 대한 안전장치(fallback)다.
- 실제 `PresenceService` 전체 분석: `join`(최초 등록 + score=expiresAt()), `heartbeat`(생존 신호 — `ZADD ... XX` 즉 `ifExists()`로 이미 존재하는 member만 score 갱신, 없는 member는 되살리지 않음), `leave`(명시적 제거), `onlineCount`(호출 시마다 `removeRangeByScore`로 만료된 member를 먼저 지운 뒤 `zCard` 반환 — 별도 스케줄러 없이 "조회하는 김에 청소"하는 lazy cleanup 패턴). `heartbeat`가 정상 종료된 connection을 재조회로 되살리지 않도록 `XX` 플래그를 쓰는 것이 이 설계의 핵심 방어 로직이다.

### 2-3. Redis vs MySQL
- **저장 위치**: MySQL(InnoDB)은 디스크 기반(WAL로 내구성 보장). Redis는 메모리 기반(RDB/AOF는 백업·복구 수단일 뿐).
- **데이터 모델**: MySQL은 관계형(테이블·JOIN·스키마 강제). Redis는 key-value 계열로 String/Hash/List/Set/ZSet 중 하나가 값이 되며 JOIN 개념이 없다.
- **쿼리 능력**: MySQL은 SQL로 임의 조건·집계·조인 가능. Redis는 각 자료구조가 지원하는 연산만 가능해, 조회 패턴에 맞는 자료구조를 미리 설계해야 한다.
- **일관성/트랜잭션**: MySQL은 ACID 트랜잭션 + `@Version` 낙관적 락으로 정합성을 보장. Redis는 단일 명령 또는 Lua 스크립트의 원자성을 이용해 동시성 문제를 해결한다(`MULTI/EXEC`는 SQL 트랜잭션 같은 롤백 개념이 아님).
- **실제 프로젝트에서의 역할**: `worldtrialsite`처럼 유실되면 안 되는 데이터는 MySQL, rate limiter 카운터나 Presence 목록처럼 유실돼도 재생성 가능한 빠른 데이터는 Redis.

### 2-4. Redis 자료구조 전반과 CLI 기초
| 타입 | 대표 명령어 | Spring Data Redis API |
|---|---|---|
| String | `SET`/`GET`/`INCR` | `opsForValue()` |
| List | `RPUSH`/`LPOP`/`LRANGE` | `opsForList()` |
| Hash | `HSET`/`HGET`/`HGETALL` | `opsForHash()` |
| Set | `SADD`/`SMEMBERS`/`SISMEMBER` | `opsForSet()` |
| ZSet | `ZADD`/`ZRANGE`/`ZSCORE` | `opsForZSet()` |

- key를 쓰기 전에 스키마를 선언할 필요가 없다 — 해당 타입의 명령어를 처음 실행하는 순간 Redis가 그 타입으로 key를 생성한다.
- 컨테이너 안 Redis에 직접 접속해 실습하는 방법: `docker exec -it <컨테이너이름> redis-cli` (예: `docker exec -it expert-redis redis-cli`). `-it`는 대화형(interactive) + 터미널(tty) 모드를 의미.
