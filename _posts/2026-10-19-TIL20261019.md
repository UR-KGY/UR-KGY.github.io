## 1. 개념 정리

### IAP란

- **IAP(In-App Purchase)**: 앱 안에서 디지털 상품(다이아 등)을 현금으로 파는 기능 **전체**
- **영수증 검증**은 IAP 중 **서버가 맡는 핵심 단계**이고, IAP 자체와 같은 말이 아님

| 단계 | 담당 |
|---|---|
| 상품 등록 (상품 ID, 가격) | Play Console |
| 상품 목록·가격 표시, 결제창 | 클라이언트 (Unity IAP 5) |
| 결제 처리, 영수증(purchaseToken) 발급 | 구글 |
| **영수증 검증 → 지급 → 소비(consume) → 환불 대응** | **서버** |

### 핵심 용어

| 용어 | 뜻 |
|---|---|
| purchaseToken | 구매 한 건의 영수증 문자열. **중복 확인 기준** |
| orderId | 구글 주문 번호 (`GPA.xxxx`). 고객 문의 대응용 |
| purchaseState | 0 결제 완료, 1 취소, 2 보류 |
| consumptionState | **이 구매 건을 소비 처리했는가** (0 아직, 1 완료) |
| acknowledgementState | 전달 확인을 했는가 (3일 자동 환불 방지) |

### consume(소비)의 의미

- **인게임에서 다이아를 썼다는 뜻이 아님.** "구매 건을 다이아로 바꿔 전달했다"고 **구글 장부에 알리는 것**
- 비유: 식권을 배식대에 내면 찢김 → 같은 식권은 재사용 불가, 새 식권은 다시 살 수 있음
- consume하지 않으면
  1. 같은 구글 계정으로 **같은 상품 재구매 불가** (ITEM_ALREADY_OWNED)
  2. **3일 후 자동 환불** (다이아는 이미 지급된 상태)
- 인게임 다이아 사용은 **우리 서버만** 관리 (`player_currencies`, `currency_histories`)
- 서버의 `CurrencyService.consume`(재화 차감)과 **이름만 같고 전혀 다른 일**

### consume vs acknowledge

| | acknowledge | consume |
|---|---|---|
| 의미 | 전달했다 | 전달했고 다 써서 없어졌다 |
| 구글 장부 보유 상태 | 계속 보유 | 보유 끝 |
| 재구매 | 불가 | 가능 |
| 자동 환불 방지 | ✅ | ✅ (acknowledge 포함) |
| 어울리는 상품 | 비소모성 (광고 제거) | **소모성 (다이아)** |

- 구글에는 "소모성/영구" 구분 칸이 없음. **개발자가 무엇을 호출하느냐**로 결정
- 현재는 다이아(소모성)만 있으므로 consume만 사용. 영구 상품이 생기면 acknowledge 추가

### 로그인과의 관계

| 구분 | 인증 주체 | 용도 |
|---|---|---|
| 구글 로그인 | 사용자 | 게임 로그인 (다른 팀원 담당) |
| 플레이 게임즈 로그인 | 사용자 | 업적, 리더보드 |
| **Google Play Developer API** | **우리 서버 (서비스 계정)** | 영수증 조회, consume, 환불 조회 |

- IAP는 구글 로그인이 아니라 **우리 userId(JWT)**에 연결됨
- 결제 계정(Play 스토어)과 게임 계정은 다를 수 있음 → 지급 기준은 항상 **우리 userId**
- 클라이언트가 결제 시작 시 `obfuscatedAccountId`에 **우리 userId(또는 해시)**를 넣고, 서버가 요청자와 비교
- 구글 로그인이 추가되어도 결과가 우리 JWT로 통일되면 **IAP 코드는 변경 없음**

### Developer API의 역할

| 호출 | 종류 | 용도 |
|---|---|---|
| `purchases.products.get` | 읽기 | 영수증 상태 조회 |
| `purchases.products.consume` | **쓰기** | 소비 처리 |
| `purchases.voidedpurchases.list` | 읽기 | 환불·취소 목록 |

- **연결(설정)은 출시 전**, **호출은 출시 후 계속** (결제마다, 스케줄러로 주기적으로)

## 2. 기존 상점 구매(ShopService)와 분리하는 이유

### 두 흐름 비교

```
[기존 상점 구매]                         [구글 결제 구매]
POST /api/shop/purchase                  POST /api/shop/iap/google
{ requestId, productCode }               { productCode, purchaseToken }
ShopController → ShopFacade              IapController
 → ShopService.purchase @Transactional    → IapService (트랜잭션 없음)
   ├─ IdempotencyService (1일)               ├─ 영수증 중복 확인 (iap_receipts)
   ├─ CASH면 거절 ← 추가할 한 줄             ├─ 구글 검증 (외부 API)
   ├─ 재화 차감                              ├─ IapGrantService.grant @Transactional
   ├─ 보상 지급 ───────────── 공유 ────────────┤   ├─ 영수증 저장 → 보상 지급 → 구매 기록
   └─ 구매 기록 ───────────── 공유 ────────────┘
                                             └─ 구글 consume (외부 API)
```

비유: 같은 매장에 **현금·포인트 계산대**와 **카드 결제 계산대**를 따로 두고, 진열대(카탈로그)·창고(보상 지급)·판매 장부(구매 기록)는 함께 씀

### 분리 이유

| 이유 | 기존 상점 구매 | 구글 결제 구매 |
|---|---|---|
| **요청 형식** | 클라이언트가 만든 `requestId` | 구글이 준 `purchaseToken` |
| **중복 방지 기간** | `idempotency_keys` **1일 보관**으로 충분 | 영수증은 며칠·몇 주 뒤에도 재전송 가능 → **영구 UNIQUE 필요** |
| **트랜잭션 경계** | 메서드 전체가 하나의 트랜잭션 | 구글 API(느리고 실패 가능)를 **트랜잭션 밖**에 둬야 함. 안에 넣으면 응답 대기 중 DB 커넥션·행 잠금을 붙잡음 |
| **실패 종류** | 재화 부족 | 위조, 보류, 구글 장애, 계정 불일치, consume 실패 |
| **후속 처리** | 없음 | consume 재시도, 환불 조회 (스케줄러) |

- 합치면 `ShopService` 안에 `if (CASH) {...} else {...}`가 커져 **두 흐름의 규칙이 얽힘**
- 분리하면 한쪽 수정이 다른 쪽에 영향을 주지 않음
- 기존 상점 테스트가 그대로 통과하는 것이 분리가 잘 됐다는 증거

### 공유하는 부품

`ShopCatalog`, `RewardService`, `CurrencyService`, `PlayerService`, `ShopPurchaseLogRepository`, `ShopProduct`/`PriceType`, 응답 `ShopPurchaseResponse`

### 기존 코드에서 바뀌는 곳 (2곳)

| 파일 | 변경 | 이유 |
|---|---|---|
| `ShopService.doPurchase` | CASH 상품이면 거절 | CASH는 재화 차감이 없어 **기존 API로 무료 획득** 가능해짐 |
| `ShopProductTable.validate` | CASH 차단 해제, 가격 규칙 정리 | 시트에 CASH 상품을 둘 수 있게 |

### `shop_purchase_logs`와 `iap_receipts`의 차이

| 항목 | `shop_purchase_logs` | `iap_receipts` |
|---|---|---|
| 대상 | 모든 상점 구매 | CASH만 |
| 기준 키 | requestId (UNIQUE 없음) | purchaseToken (**UNIQUE**) |
| 변경 | 변하지 않는 장부 | 상태가 바뀜 (GRANTED → CONSUMED / REFUNDED) |
| 용도 | 무엇을 샀고 받았나 (문의, 구매 제한) | 영수증 중복 차단, consume·환불 추적 |

- 현금 구매 1건 → **같은 트랜잭션에서 두 테이블 모두 기록**
- 한 줄 요약: **판매 장부** vs **카드 매출전표 보관함**

## 3. 전체 구조

```
IapController  POST /api/shop/iap/google
   │
IapService (트랜잭션 없음)
   ① 이미 처리한 영수증? → 저장된 상태로 응답 (재전송 대응)
   ② GooglePlayVerifier.verify (외부)
   ③ IapGrantService.grant (@Transactional): 영수증 저장 → 보상 지급 → 구매 기록
   ④ GooglePlayVerifier.consume (외부, 실패 시 스케줄러가 재시도)
   │
GooglePlayVerifier (인터페이스)
   ├─ FakeGooglePlayVerifier  (로컬: local 프로필 + google-play.fake=true)
   └─ GooglePlayApiVerifier   (운영: 서비스 계정 키가 있을 때만, 미구현)

IapScheduler
   ├─ 10분마다: GRANTED 영수증 consume 재시도 (3일 자동 환불 방지)
   └─ 1시간마다: 환불 목록 조회 → REFUNDED 표시
```

### 서버가 반드시 지킬 규칙

| 규칙 | 지키지 않으면 |
|---|---|
| 구글 API로 영수증 검증 | 가짜 영수증으로 무료 획득 |
| `purchaseState == 0`일 때만 지급 | 미입금 결제(보류)에 지급 |
| 같은 purchaseToken은 한 번만 지급 | 영수증 하나로 여러 번 지급 |
| **검증 → 지급 → consume** 순서 | consume 먼저 하고 지급 실패 시 복구 불가 |
| 3일 안에 consume | 자동 환불 |
| 클라이언트는 consume하지 않음 | 지급 전에 소비되어 보상 유실 |
| obfuscatedAccountId == 요청자 userId | 남의 영수증 도용 |

## 5. 3단계 코드 (결제 API)

### `shop/iap/IapErrorCode.java`

```java
@RequiredArgsConstructor
public enum IapErrorCode implements ErrorCode {
    NOT_CASH_PRODUCT       (HttpStatus.BAD_REQUEST,         "현금 결제 상품이 아닙니다."),

```

### `shop/iap/IapGrantService.java` (지급과 기록만 트랜잭션)

```java
@Service
@RequiredArgsConstructor
public class IapGrantService {
    private final PlayerService             playerService;
    private final ShopCatalog               shopCatalog;
    private final RewardService             rewardService;
    private final CurrencyService           currencyService;
    private final IapReceiptRepository      receiptRepository;
    private final ShopPurchaseLogRepository purchaseLogRepository;

    @Transactional
    public ShopPurchaseResponse grant(Long userId, ShopProduct product, String purchaseToken, GooglePurchase purchase) {
        Player player = playerService.getMe(userId);

        // 영수증 먼저 저장 + 즉시 INSERT → 중복이면 지급 전에 UNIQUE 위반으로 실패
        receiptRepository.saveAndFlush(new IapReceipt(
                userId, product.productCode(), purchaseToken, purchase.orderId(), purchase.purchasedAt()));

        List<Reward> rewards = shopCatalog.findRewards(product.productCode());
        List<Reward> granted = new ArrayList<>();
        for (Reward reward : rewards)
            granted.addAll(rewardService.reward(player, reward, CurrencyReason.PURCHASE));

        ShopPurchaseResponse response = new ShopPurchaseResponse(granted, currencyService.getAll(player));

        UUID requestId = UUID.nameUUIDFromBytes(purchaseToken.getBytes(StandardCharsets.UTF_8));
        purchaseLogRepository.save(new ShopPurchaseLog(userId, requestId, product, rewards, response));

        return response;
    }
}
```

- `IapService`와 분리한 이유: 같은 클래스 안에서 `@Transactional` 메서드를 호출하면 **프록시를 거치지 않아 트랜잭션이 적용되지 않음**(self-invocation)

### `shop/iap/IapService.java` (흐름 제어, 트랜잭션 없음)

```java
@Slf4j
@Service
@RequiredArgsConstructor
public class IapService {
    private final ShopCatalog                        shopCatalog;
    private final IapGrantService                    grantService;
    private final IapReceiptRepository               receiptRepository;
    private final CurrencyService                    currencyService;
    private final PlayerService                      playerService;
    private final ObjectProvider<GooglePlayVerifier> verifierProvider;
    private final Clock                              clock;

    public ShopPurchaseResponse purchaseWithGoogle(Long userId, String productCode, String purchaseToken) {
        GooglePlayVerifier verifier = verifierProvider.getIfAvailable();
        if (verifier == null) throw new BusinessException(IapErrorCode.IAP_DISABLED);

        ShopProduct product = shopCatalog.findProduct(productCode)
                .orElseThrow(() -> new BusinessException(ShopErrorCode.PRODUCT_NOT_FOUND));
        if (product.priceType() != PriceType.CASH)
            throw new BusinessException(IapErrorCode.NOT_CASH_PRODUCT);

        // ① 재전송 대응
        var existing = receiptRepository.findByPurchaseToken(purchaseToken);
        if (existing.isPresent()) return alreadyProcessed(userId, existing.get());

        // ② 구글 검증
        GooglePurchase purchase;
        try {
            purchase = verifier.verify(productCode, purchaseToken);
        } catch (GooglePlayVerifier.InvalidPurchaseException e) {
            throw new BusinessException(IapErrorCode.INVALID_RECEIPT);
        } catch (GooglePlayVerifier.GooglePlayUnavailableException e) {
            throw new BusinessException(IapErrorCode.STORE_UNAVAILABLE);
        }

        if (purchase.isPending())                              throw new BusinessException(IapErrorCode.PURCHASE_PENDING);
        if (!purchase.isPurchased() || purchase.isConsumed()) throw new BusinessException(IapErrorCode.INVALID_RECEIPT);
        if (!String.valueOf(userId).equals(purchase.obfuscatedAccountId()))
            throw new BusinessException(IapErrorCode.RECEIPT_OWNER_MISMATCH);

        // ③ 지급
        ShopPurchaseResponse response;
        try {
            response = grantService.grant(userId, product, purchaseToken, purchase);
        } catch (DataIntegrityViolationException e) {       // 같은 토큰 동시 요청
            return alreadyProcessed(userId, receiptRepository.findByPurchaseToken(purchaseToken).orElseThrow());
        }

        // ④ 구글 영수증 소비 처리
        consumeQuietly(verifier, productCode, purchaseToken);
        return response;
    }

    private ShopPurchaseResponse alreadyProcessed(Long userId, IapReceipt receipt) {
        if (!receipt.getUserId().equals(userId))
            throw new BusinessException(IapErrorCode.RECEIPT_OWNER_MISMATCH);
        return new ShopPurchaseResponse(List.of(), currencyService.getAll(playerService.getMe(userId)));
    }

    public void consumeQuietly(GooglePlayVerifier verifier, String productCode, String purchaseToken) {
        try {
            verifier.consume(productCode, purchaseToken);
            receiptRepository.findByPurchaseToken(purchaseToken).ifPresent(r -> {
                r.markConsumed(clock.instant());
                receiptRepository.save(r);
            });
        } catch (RuntimeException e) {
            log.warn("[IAP] 영수증 소비 처리 실패, 스케줄러가 재시도: product={}", productCode);  // 토큰 원문 로그 금지
        }
    }
}
```

## 6. 4단계 코드 (스케줄러)

- `@EnableScheduling`은 이미 `ConnectionNoticeScheduler`에 있어 앱 전체 적용됨

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class IapScheduler {
    private final IapReceiptRepository               receiptRepository;
    private final IapService                         iapService;
    private final ObjectProvider<GooglePlayVerifier> verifierProvider;
    private final Clock                              clock;

    private Instant lastVoidedCheck = Instant.EPOCH;    // 재시작 시 초기화 (최근 30일 재조회)

    @Scheduled(fixedDelay = 600_000)    // 10분
    public void retryConsume() {
        GooglePlayVerifier verifier = verifierProvider.getIfAvailable();
        if (verifier == null) return;

        Instant before = clock.instant().minus(Duration.ofMinutes(1));
        for (IapReceipt r : receiptRepository.findTop100ByStatusAndCreatedAtBeforeOrderByCreatedAtAsc(
                IapReceiptStatus.GRANTED, before))
            iapService.consumeQuietly(verifier, r.getProductCode(), r.getPurchaseToken());
    }

    @Scheduled(fixedDelay = 3_600_000)  // 1시간
    @Transactional
    public void syncVoided() {
        GooglePlayVerifier verifier = verifierProvider.getIfAvailable();
        if (verifier == null) return;

        Instant since = lastVoidedCheck.equals(Instant.EPOCH)
                ? clock.instant().minus(Duration.ofDays(30)) : lastVoidedCheck;

        for (String token : verifier.voidedTokensSince(since))
            receiptRepository.findByPurchaseToken(token).ifPresent(r -> {
                r.markRefunded();
                log.warn("[IAP] 환불 감지: userId={}, product={}, order={}", r.getUserId(), r.getProductCode(), r.getOrderId());
            });

        lastVoidedCheck = clock.instant();
    }
}
```

## 8. 실제 연동 시 준비 (출시 전)

1. Play Console 개발자 계정 + 판매자(결제) 프로필
2. 결제 기능이 들어간 앱을 **내부 테스트 트랙**에 업로드 (14일 조건 없음)
3. 인앱 상품 등록 (소모성, **상품 ID = 시트 productCode**)
4. 라이선스 테스터 등록 (실제 돈 없이 테스트 결제)
5. Google Cloud에서 Android Developer API 사용 설정 → **서비스 계정** + 키(JSON)
6. Play Console에서 서비스 계정 권한 부여 (반영까지 시간 걸릴 수 있음)
7. 서버
   - `build.gradle`: `google-api-services-androidpublisher`, `google-auth-library-oauth2-http` (Maven Central 최신 버전 확인 후 고정)
   - `GooglePlayApiVerifier` + `GooglePlayConfig` (키 경로가 있을 때만 Bean 등록)
   - 설정: `google-play.package-name`, `google-play.credentials-path`
8. 운영 키는 **Parameter Store(SecureString)** → 환경 변수로 주입. `jwt.secret`도 같은 방식으로 정리

### 클라이언트에 전달할 명세

| 항목 | 내용 |
|---|---|
| API | `POST /api/shop/iap/google` `{ productCode, purchaseToken }` |
| 응답 | `{ rewards, currencies }` (기존 상점과 같음) |
| 에러 | 400 영수증 오류, 202 결제 대기, 403 계정 불일치, 503 재전송 |
| 결제 시작 시 | `obfuscatedAccountId` = 합의한 형식 (userId 또는 해시) |
| consume | **클라이언트는 하지 않음** |
| 미처리 영수증 | 앱 실행 시 서버로 재전송 |

## 10. 주의 사항

- **가짜 검증기가 운영에 켜지면 누구나 무료로 다이아 획득** → 이중 잠금(`@Profile("local")` + `google-play.fake=true`) + 부팅 경고 로그
- 마이그레이션 번호는 **작성 날짜·시각**(`VyyyyMMdd_HHmm`)으로, PR 직전 develop의 마지막 번호보다 큰지 재확인
- 토큰 원문, 서비스 계정 키, 구글 응답 원문은 **로그 금지** (orderId만)
- 구글 API는 기본 **하루 20만 회** 한도 → 재전송은 DB에서 먼저 걸러짐
- 보류 결제는 지금 202 응답 후 클라이언트 재전송에 의존 → 나중에 **RTDN(Pub/Sub)**으로 개선
- 환불 시 다이아 회수·제재 여부는 **기획 결정** 필요 (현재는 REFUNDED 표시만)
- 서버가 여러 대가 되면 스케줄러 중복 실행 방지 필요 (ShedLock 등)
- 지급 중 재화 낙관적 락 충돌 시 영수증도 롤백 → 같은 영수증 재전송으로 복구 가능
