## 1. 클라이언트와 서버

클라이언트와 서버는 프론트엔드·백엔드처럼 고정된 역할이 아니라, **요청을 보내는 쪽이 클라이언트**, **요청을 받아 처리하는 쪽이 서버**라는 상대적인 관계다. 서버끼리 통신할 때도 마찬가지다.

- **A 서버 → 클라이언트**: B 서버에게 특정 데이터를 요청하는 쪽. 이 순간 A는 클라이언트 역할을 수행한다.
- **B 서버 → 서버**: A의 요청을 받아 처리하고 응답을 돌려주는 쪽. 이 순간 B는 서버 역할을 수행한다.

## 2. JSON과 XML

클라이언트와 서버가 언어·플랫폼에 상관없이 동일한 형식으로 데이터를 주고받기 위한 약속이 데이터 포맷이다. XML은 태그 구조 때문에 가독성이 떨어지고 용량이 커진다는 지적을 받았고, 이를 개선해 지금 가장 널리 쓰이는 것이 JSON이다.

### JSON — Key/Value

Value 자리에는 문자열·숫자·불리언뿐 아니라 또 다른 객체(Key-Value 묶음)가 들어갈 수 있다. 즉 중첩이 가능하다.

```json
{
  "이름": "홍길동",
  "나이": 30,
  "사는곳": {
    "시": "서울시",
    "구": "강남구",
    "동": "대치동"
  },
  "개발자인가": true
}
```

### XML — 태그 기반

```xml
<root>
  <이름>홍길동</이름>
  <나이>30</나이>
  <사는곳>
    <시>서울시</시>
    <구>강남구</구>
  </사는곳>
</root>
```

## 3. HTTP 개요

웹에서 데이터를 주고받기 위한 통신 규약. 버전은 1.1 / 2.0 / 3.0 등이 있지만, 기본 골격을 이해하기 위해 여기서는 HTTP/1.1을 기준으로 정리한다.

### 동작 순서

```
클라이언트: Request 전송 → 서버: 요청 처리 → 서버: Response 응답
```

### 무상태성 (Stateless)

서버는 클라이언트의 이전 상태를 기억하지 않는다. 예를 들어 검색엔진을 새로고침할 때마다 서버는 그 요청들을 전부 별개의 클라이언트로 취급한다.

- **장점**: 서버가 클라이언트별 데이터를 들고 있지 않으므로 수평 확장(Scale-out)이 쉽다. 요청량이 갑자기 늘어도 서버를 증설하기 수월하다.
- **단점**: 클라이언트가 매 요청마다 필요한 데이터(로그인 정보 등)를 추가로 함께 보내야 한다.

## 4. HTTP 메시지 구조

요청(Request)과 응답(Response) 메시지는 형태가 거의 같고, 첫 줄(Start Line)의 내용만 다르다.

### Request

| 구성 | 내용 |
|---|---|
| **Start Line** | `GET` /search?keyword=sparta `HTTP/1.1` — Method + Request Target(경로+쿼리스트링) + Version |
| **Header** | `Host: codingclub.kr` 처럼 Key-Value 형태. Body의 내용·크기·인증·클라이언트 정보 등 부가정보를 담는다. 임의로 추가할 수 있지만 서버가 그 값을 해석할 줄 알아야 의미가 있다. |
| **Empty Line** | 필수로 들어가는 공백 한 줄 (Header와 Body를 구분) |
| **Body** | HTML·이미지·JSON 등 byte로 표현 가능한 모든 데이터. GET 요청은 과거엔 Body를 지원하지 않는 경우가 많았다(최근엔 가능한 구현도 있음). |

### Response

| 구성 | 내용 |
|---|---|
| **Start Line** | Version + `Status Code`(성공/실패 여부) + Status Text(코드에 대한 설명 메시지) |
| **Header** | 응답 전용 Header 값이 별도로 존재한다. |
| **Empty Line** | 필수 공백 한 줄 |
| **Body** | 실제 전송 데이터. 보낼 데이터가 없으면 Body는 비워둔 채로 존재한다. |

## 5. HTTP Method

각 메서드는 CRUD와 대응되며, 세 가지 속성(안전성·멱등성·캐시가능성)으로 성격이 구분된다.

| Method | CRUD | 설명 |
|---|---|---|
| `POST` | Create | 리소스 생성. 다른 메서드로 애매할 때도 종종 쓰인다. Message Body로 요청 데이터를 전달. |
| `GET` | Read | 리소스 조회. 원칙적으로 Body를 쓰지 않는다. |
| `PUT` | Update(전체) | 리소스를 통째로 덮어쓴다. |
| `PATCH` | Update(일부) | 리소스의 일부 필드만 수정한다. |
| `DELETE` | Delete | 리소스 삭제. |
| `HEAD` | — | GET과 동일하되 Body 없이 상태줄과 Header만 반환. |
| `OPTIONS` | — | 대상 리소스가 지원하는 Method 목록을 확인한다. |

### 세 가지 속성

| Method | 안전성 (데이터 변경 없음) | 멱등성 (N번 호출 = 1번 결과) | 캐시 가능성 |
|---|---|---|---|
| `GET` | O | O | 가능 |
| `HEAD` | O | O | 가능 |
| `POST` | X | 보장 안 됨 | 스펙상 가능하나 실무에선 거의 안 씀 |
| `PUT` | X | O | 불가 |
| `PATCH` | X | 구현에 따라 다름 | 불가 |
| `DELETE` | X | O | 불가 |

멱등성은 **재시도 가능 여부**와 직결된다. 결과가 항상 같다면 실패 시 마음 놓고 재요청할 수 있지만, POST처럼 멱등성이 없으면 중복 요청이 곧 중복 결제·중복 게시글처럼 실제 부작용으로 이어진다.

## 6. HTTP 상태 코드

세부 코드는 필요할 때 찾아보되, 앞자리 숫자가 의미하는 큰 분류는 기억해두는 편이 실전에서 훨씬 유용하다.

| 대역 | 분류 | 예시 |
|---|---|---|
| `1xx` | 정보 — 요청 수신, 처리 중 (잘 안 씀) | 100 Continue |
| `2xx` | 성공 | 200 OK · 201 Created |
| `3xx` | 리다이렉션 | 301 · 302 · 304 |
| `4xx` | 클라이언트 오류 | 400 · 401 · 403 · 404 |
| `5xx` | 서버 오류 | 500 · 503 |

- **4xx**: 클라이언트 요청 자체가 잘못됨(문법 오류 등). **같은 요청을 재시도해도 계속 실패한다.**
- **5xx**: 요청은 정상인데 서버가 처리하지 못함. 서버가 일시적으로 다운되었다가 복구되면 **재시도로 성공할 수도 있다.**

서버 개발자는 상황에 맞는 상태 코드를 정확히 골라 응답하는 것이 중요하다 — 클라이언트가 그 코드만 보고 "재시도할지 말지"를 판단하기 때문이다.

## 7. API와 RESTful API

API는 프로그램끼리 대화하는 방법이며, 세부 구현이 아니라 **무엇을 할 수 있는지(명세)**가 중요하다. RESTful API는 강제 규칙은 아니지만, 협업 시 불필요한 소통 비용을 줄이기 위한 설계 관례다.

| # | 원칙 | ❌ | ✅ |
|---|---|---|---|
| 1 | 동사보단 명사를, 단수보단 복수를 | `/member/get/item/hello` | `/members/items` |
| 2 | 마지막에 `/` 넣지 않기 | `/members/` | `/members` |
| 3 | `_` 대신 `-` 사용, 대문자 지양 | `/restful_services` | `/restful-services` |
| 4 | 확장자 포함하지 않기 | `/image.svg` | `/images` |
| 5 | 계층화하기 (포함 관계를 경로 순서로) | `/items/{itemId}/members/{memberId}` | `/members/{memberId}/items/{itemId}` |

## 8. Lombok 어노테이션

어노테이션으로 반복되는 코드(Getter/Setter, 생성자 등)를 자동 생성해주는 라이브러리. 가독성과 유지보수성이 좋아져 실무에서 널리 쓰인다.

### `@Getter` / `@Setter`

클래스의 모든 필드에 대한 getter / setter 메서드를 자동 생성.

```java
@Getter @Setter
public class Member {
    private String name;
}
```


### `@ToString`

객체를 String으로 표현하는 `toString()`을 자동 생성.

```java
@ToString
public class Member { private String name; }

// System.out.println(member); 로 결과 확인
```


### `@NoArgsConstructor` / `@AllArgsConstructor` / `@RequiredArgsConstructor`

순서대로 기본 생성자 / 전체 필드 생성자 / `final` 필드만 받는 생성자를 만든다.

```java
@RequiredArgsConstructor
public class Member {
    private final String name; // final만 생성자 매개변수로 잡힘
    private int age;
}
```


### `@Slf4j`

클래스에 `log`라는 이름의 Logger 객체를 자동 생성.

```java
@Slf4j
@RestController
public class MemberController {
    // log.info("요청 도착: {}", id);
}
```

## 9. Servlet

초창기 웹은 저장된 HTML만 그대로 내려주는 정적 페이지였다. 요청마다 다른 결과를 동적으로 만들어주기 위해 자바에서 등장한 개념이 **Servlet**이다. `jakarta.servlet.http.HttpServlet`을 상속해 구현한다.

### 서블릿 컨테이너

서블릿은 스스로 실행될 수 없고, 이를 실행·관리해주는 환경이 서블릿 컨테이너다. 대표적인 예가 스프링부트 실행 시 콘솔에 뜨는 **톰캣(Tomcat)**.

```
클라이언트 요청 → 서블릿 컨테이너 수신 → 해당 서블릿 실행 → 컨테이너에 결과 반환 → 클라이언트 응답
```

스프링부트에서는 Application 클래스에 `@ServletComponentScan`을 붙여야 서블릿을 인식한다.

```java
@WebServlet("/movies/recommendation")
public class MovieRecommendationServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse res) throws IOException {
        // 1. 데이터 준비 → 2. Map 등으로 구성
        // 3. response.setContentType(...)
        // 4. ObjectMapper로 JSON 문자열 변환
        // 5. response.getWriter().print(json)
    }
}
```

## 10. MVC 패턴

Servlet 혼자 요청 처리부터 화면 구성까지 다 떠맡던 문제를 해결하기 위해, 역할을 세 갈래로 분리한 패턴이다.

- **Controller**: 요청(Request)을 받아 Model과 View를 연결해주는 중간 다리.
- **Model**: 데이터와 비즈니스 로직 담당.
- **View**: 사용자에게 보여지는 화면(UI) 담당.

```
클라이언트 요청 → Controller → Model → Controller → View → 클라이언트
```

## 11. SSR과 CSR

### SSR (Server Side Rendering)

서버가 완성된 HTML을 조립해서 내려준다. 초기 로딩이 빠르고, 내용이 HTML에 이미 포함돼 있어 검색엔진 최적화(SEO)에 유리하다.

### CSR (Client Side Rendering)

서버는 뼈대 HTML + JS만 전달, 브라우저가 JS로 데이터를 다시 요청해 화면을 조립한다. (React, Vue 등) 초기 로딩은 느리지만, 이후 화면 전환은 매끄럽고 빠르다.

## 12. DispatcherServlet과 @RestController

`DispatcherServlet`은 프론트 컨트롤러 + 어댑터 패턴 기반으로 만들어진 스프링 MVC의 진입점이다. 모든 요청이 일단 여기로 모인 뒤, 알맞은 컨트롤러로 위임된다.

| 어노테이션 | 설명 |
|---|---|
| `@ResponseBody` | 메서드의 반환값을 View 탐색에 쓰지 않고, HTTP 응답 **Body**에 그대로 작성하도록 만든다. |
| `@RestController` | `@Controller` + `@ResponseBody`가 합쳐진 것. 최근엔 View를 직접 다루지 않는 백엔드 API가 대부분이라 이 어노테이션을 주로 쓴다. |

```java
@RestController
@RequestMapping("/hello")
public class HelloController {
    // ...
}
```

## 13. 스프링 어노테이션 — HTTP 메서드 & 데이터 바인딩

컨트롤러가 "어떤 요청을 받을지"와 "요청에서 값을 어떻게 꺼낼지"를 정하는 어노테이션들. 여기가 실제 API를 짤 때 가장 자주 손이 가는 부분이다.

### HTTP 메서드 전용 어노테이션

| 어노테이션 | 대응 Method | 사용 예시 |
|---|---|---|
| `@GetMapping` | GET | `@GetMapping("/items")` |
| `@PostMapping` | POST | `@PostMapping("/items")` |
| `@PutMapping` | PUT | `@PutMapping("/items/{id}")` |
| `@PatchMapping` | PATCH | `@PatchMapping("/items/{id}")` |
| `@DeleteMapping` | DELETE | `@DeleteMapping("/items/{id}")` |


### 데이터 전달 어노테이션

#### `@PathVariable` — URL 경로 자체가 값 (필수)

리소스를 식별하는 값이 경로 자체에 박혀 있을 때. 값이 없으면 그 URL 자체가 성립하지 않으므로 항상 필수다.

```java
@GetMapping("/members/{memberId}") //D
public Member getMember(@PathVariable Long memberId) { ... }
```
.

#### `@RequestParam` — 쿼리 파라미터 (선택/조건부)

있어도 되고 없어도 되는 값. 검색·필터링처럼 "같은 API인데 조건만 다른" 상황에 주로 쓴다.

```java
@GetMapping("/search") // /search?keyword=adam&num=40      required 의 기본값은 true 다.
public List<Item> search(
    @RequestParam(required = false) String keyword ,@RequestParam() int num) { ... }
```


#### `@ModelAttribute` — 여러 값을 객체 하나로 묶기

여러 개의 쿼리 파라미터나 폼(form) 데이터를 하나의 커맨드 객체로 한 번에 받고 싶을 때. 이전에 베이스 캠프 때 DTO 객체를 만들어 요청, 응답을 하였던 것이 이것

```java
public String submit(@ModelAttribute MemberForm form) { ... }
```


#### `@RequestBody` — JSON 등 메시지 Body 전체

요청 Body에 담긴 JSON을 객체로 통째로 변환해서 받는다. 주로 POST/PUT처럼 Body가 있는 요청에 사용.

```java
@PostMapping("/members")
public Member create(@RequestBody MemberDto dto) { ... }
```


> **@PathVariable vs @RequestParam 구분 기준** — 그 값이 없으면 URL 자체가 의미 없어지는가? 그렇다면 PathVariable. 있어도 그만 없어도 그만인 부가 조건인가? 그렇다면 RequestParam.
