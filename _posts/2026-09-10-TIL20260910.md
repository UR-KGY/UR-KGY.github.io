# 랭킹 시스템 개발 과제 
요즘 잠이 부족해서 그런지 머리가 잘 안돌아가는 것 같다. (일찍 자야할 것)
랭킹 시스템은 RestClient를 사용하여 Api(JSON 데이터)를 받고
그 JSON 구조대로 객체로 만들고 그 객체를 RankingSource 라는 dto 에 담아 가져와 사용한다. 
meta 쪽은 게임의 이름 , 제작날짜 등 따로 로직 필요없이 필요한 정보를 가져오기 어렵지 않았다.
records 쪽에 여러 데이터들이 많이 담겨져있어 이쪽을 탐색하는 데 시간이 많이 들었다. (JSON 을 자세히 본적도 거의 없기도 했고 머리가 안돌아간다)
일단 리팩토링 상관없이 먼저 기능부터 만들자 하였고 기록들 중 제외해야할 대상에 대한 조건이 많아서 한 메서드에서 처리하기 곤란해졌다.
일단 Predicate<> 라는 stream 필터 에 조건으로 한번에 넣을 수 있는 기능이 있어 사용해보았고 로직은 30분 정도 고민해보다가 도저히 안될 것 같을 때
탐색 기능을 알려달라는 식으로 AI에게 물어보면서 작성하였다. 아직 Stream 기능에 대해 전부 이해는 못했지만 stream 으로 리스트나 맵 으로 자료구조를 변경하고
filter를 통해 조건에 참인 값만 새로운 리스트로 재분류, allMatch(자료구조 내에 있는 해당 요소들에 대한 조건이 모두 참), anymatch(내의 하나의 요소라도 참이면 참) ,map()에는 p -> p.getPhase() 와 동일한 표현을 람다로 BossPhase::getPhase 처럼 사용할 수 있는 것을 알았다.

오후8시 강의를 들으면서 생각해본 것이 이전 캠프에선 AI를 사용하지 않아 혼자 전전긍긍하면서 시간을 날려먹은 게 하루 이틀이 아니었다.
일단 잘은 안되지만 너무 오래 생각하면 먼저 AI든 다른 분들한테 물어보든 먼저 예시를 따라하면서 익히는 게 요즘 시대에 바람직할지도 모르겠다.
이해는 잘 안되지만 시간이 너무 촉박하니까 우선 먼저 때려맞춰보고 그 이후 리팩토링을 하든 고민해보든 하는 게 좋을 것 같다. 
가장 걱정되는 건 유니티 쪽인데 너무 많은 것을 잊어버렸다. 일찍 일어나서 과제 완성하면 바이브 코딩이든 뭐든 해서 배워놓자..

## 1. RestClient 사용법

**사용법**: RestClient는 4단계로 요청을 구성합니다. 메서드 선언 → URI 지정 → 전송 → 응답 매핑.

```java
RankingSource rankingSource = restClient.get()
        .uri(SOURCE_URL)
        .retrieve()
        .body(RankingSource.class);
```

| 단계 | 메서드 | 역할 |
|---|---|---|
| 1 | `.get()` / `.post()` / `.put()` / `.delete()` | 어떤 HTTP 메서드를 쓸지 선언, `RequestHeadersUriSpec` 반환 |
| 2 | `.uri(SOURCE_URL)` | 요청 보낼 주소 지정 |
| 3 | `.retrieve()` | 위 설정을 바탕으로 실제 요청 전송 |
| 4 | `.body(Class)` | 응답 바디를 지정한 타입으로 변환해서 반환 |

**주의 사항**: `.body(Class)`는 응답 바디만 필요할 때 쓰는 가장 단순한 방식입니다. 아래 두 메서드도 함께 알아두면 좋습니다.
- `.toEntity(Class)` — 바디뿐 아니라 상태 코드·헤더까지 함께 받고 싶을 때
- `.onStatus(predicate, handler)` — `.retrieve()` 뒤에 붙여서, 특정 상태 코드(4xx/5xx 등)일 때 커스텀 예외를 던지거나 별도 처리를 하고 싶을 때 (안 붙이면 기본적으로 4xx/5xx는 `RestClientException` 계열 예외가 발생합니다)

## 2. Stream 필터링과 Predicate 패턴

**문제 상황**: `stream().filter()`에 조건을 하나씩 추가하다 보니 메서드 하나가 계속 비대해짐.

**해결**: 조건 하나하나를 `Predicate<T>` 타입 변수로 뽑아서 이름을 붙이고, `.and()`로 조합해서 한 번에 필터에 넣기.

```java
Predicate<Record> clearTimeOk = r -> r.getRun().getDurationSeconds() >= r.getRun().getClearedFloor() * 30;
Predicate<Record> hpOk = r -> r.getRun().getFinalHp() >= 1 && r.getRun().getFinalHp() <= 99;

Predicate<Record> isValidRecord = clearTimeOk.and(hpOk); // 등등 계속 이어붙임
```

**단점**: `Predicate`는 `boolean`만 반환하므로, 조건 실패 시 "왜 실패했는지" 추적이 어렵고 단위 테스트도 애매합니다. (조건별 실패 사유까지 남기고 싶다면 `record ValidationRule(String name, Predicate<Record> check)` 형태로 규칙 리스트를 만들어 관리하는 방법이 다음 단계로 고려할 만합니다.)

## 3. 메서드 레퍼런스

`BossPhase::getPhase`는 `bossPhase -> bossPhase.getPhase()`와 완전히 같은 표현입니다.

**규칙**: `클래스명::인스턴스메서드` 형태는 "그 클래스 타입의 객체 하나를 매개변수로 받아서, 그 객체의 메서드를 호출하는" 람다와 동일합니다.

```java
// 아래 두 줄은 완전히 같은 동작
.map(BossPhase::getPhase)
.map(bossPhase -> bossPhase.getPhase())
```

## 4. 오늘 설계한 분류 로직

1. **1차 필터**: `run.status`가 `CLEARED`이고 `run.clearedFloor`가 10인 기록만 우선 추출
2. **2차 필터**: 1차로 걸러진 대상 중 "정상 기록"인지 `Predicate` 조합으로 판별
   - `clearTimeOk`: `durationSeconds >= clearedFloor × 30`
   - `hpOk`: `finalHp`가 1~99
   - `deckCardsOk`: 카드 9~20장, `deck.size`와 실제 카드 개수 일치
   - `cardTypeOk`: 모든 카드가 `CardType` enum에 존재하는 타입
   - `acquiredFloorOk`: 카드 획득 층이 0~9
   - `bossPhaseOk`: 페이즈 순서가 `THRONE → UNBOUND → ECLIPSE`, 각 페이즈 turns ≥ 1, `totalTurns` = 세 페이즈 turns 합
   - `finishingCardOk`: `finishingCard`가 실제 덱에 있는 카드 타입인지
3. **정렬**: `durationSeconds` 오름차순 → 같으면 `finalHp` 내림차순 → 같으면 `id` 오름차순

## 5. ⚠️ 현재 `RankingService` 코드에서 확인된 실제 버그

코드를 실행 로직 기준으로 검토했을 때, 의도와 다르게 동작할 부분이 두 군데 있습니다.

### 버그 1: status 대소문자 불일치

```java
.filter(record -> record.getRun().getStatus().equals("Cleared")   // ← 현재 코드
```

오늘 `rankings.json` 전체 610건을 실제로 스캔해서 확인한 결과, API가 내려주는 값은 **`"CLEARED"`(179건) / `"FAILED"`(431건)**, 전부 대문자였습니다. 지금처럼 `"Cleared"`(첫 글자만 대문자)와 비교하면 **단 한 건도 매칭되지 않습니다.**

```java
// 수정
.filter(record -> record.getRun().getStatus().equals("CLEARED")
        && record.getRun().getClearedFloor() == 10)
```

더 안전하게 가려면, 문자열 오타 위험 자체를 없애는 enum 방식도 고려해볼 만합니다.

```java
public enum RunStatus { CLEARED, FAILED }
// Run.status 필드 타입을 RunStatus로 선언하면 Jackson이 "CLEARED"를 자동으로 매핑해줍니다.
```

### 버그 2: `excludeWrongRecords`의 제외 개수 계산

```java
private ExcludeRecordDto excludeWrongRecords(List<Record> records) {
    int before = records.size();
    List<Record> result = records.stream()
            .filter(isValidRecord).toList();

    int after = records.size();   // ← 원본 records 크기를 다시 잰 것 (버그)

    return new ExcludeRecordDto(before - after, result);
}
```

`after`가 필터링 결과인 `result.size()`가 아니라 **원본 `records.size()`를 다시 재고 있어서**, `before - after`는 항상 `0`이 됩니다. 즉 `excludeCount`가 실제로 몇 건 제외됐는지와 무관하게 항상 0으로 나옵니다.

```java
// 수정
int after = result.size();
return new ExcludeRecordDto(before - after, result);
```

### 참고: `getRankings()`의 `return null`

`entry` 배열을 채우는 todo와 별개로, 메서드 맨 끝이 `return null;`로 되어 있어서 위에서 만든 `response` 객체 자체가 버려지고 있습니다. entry 배열을 채운 뒤에는 `return response;`로 바꿔야 실제 응답이 나갑니다.

## 6. JSON 구조 객체화 (DTO 설계)

API 응답은 `meta`(공통 정보)와 `records`(유저 기록, 전체의 99%)로 구성됩니다. 지금 `RankingService` 코드에서 쓰인 getter들(`getMeta()`, `getRun()`, `getDeck()` 등)을 기준으로 역추적하면 아래와 같은 클래스 구조가 나옵니다.

```java
// 최상위 응답
@Getter @NoArgsConstructor
public class RankingSource {
    private Meta meta;
    private List<Record> records;
}

@Getter @NoArgsConstructor
public class Meta {
    private Season season;
    private int totalRecords;
}

@Getter @NoArgsConstructor
public class Season {
    private String name;
}

// 유저 기록 하나
@Getter @NoArgsConstructor
public class Record {
    private String id;          // 정렬 시 tie-breaker로 쓰이므로 존재 확인 필요
    private Run run;
    private Deck deck;
    private BossFight bossFight;
}

@Getter @NoArgsConstructor
public class Run {
    private String status;      // "CLEARED" / "FAILED" — enum(RunStatus)으로 바꾸는 것도 고려
    private int clearedFloor;
    private int durationSeconds;
    private int finalHp;
}

@Getter @NoArgsConstructor
public class Deck {
    private int size;
    private List<Card> cards;
}

@Getter @NoArgsConstructor
public class Card {
    private CardType cardType;  // enum
    private int acquiredFloor;
}

@Getter @NoArgsConstructor
public class BossFight {
    private List<BossPhase> phases;
    private int totalTurns;
    private String finishingCard;   // CardType 이름과 문자열로 비교되는 값
}

@Getter @NoArgsConstructor
public class BossPhase {
    private Phase phase;        // enum
    private int turns;
}

public enum Phase { THRONE, UNBOUND, ECLIPSE }

public enum CardType {
    // TODO: 실제 API에 정의된 카드 타입 값으로 채우기
}
```

**주의 사항**:
- JSON 매핑용 클래스는 Jackson이 역직렬화할 수 있도록 기본 생성자(`@NoArgsConstructor`)가 필요합니다. 필드가 `private`이라면 Jackson 설정에 따라 세터가 필요할 수도 있으니, 역직렬화가 안 되면 `@Setter`를 추가하거나 `ObjectMapper`의 필드 가시성 설정을 확인하세요.
- 서비스 내부에서만 쓰는 응답/중간 객체(`RankingResponse`, `ExcludeRecordDto`)는 JSON에서 오는 게 아니라 서버가 직접 만드는 것이므로, 굳이 세터를 열어둘 필요 없이 생성자 기반 불변 객체로 둬도 됩니다.

```java
@Getter @AllArgsConstructor
public class RankingResponse {
    private String seasonName;
    private int totalRecords;
    private int excludeCount;
    private List<RankingEntryDto> entries; // todo: 채울 항목
}

@Getter @AllArgsConstructor
public class ExcludeRecordDto {
    private int excludeCount;
    private List<Record> validRecords;
}
```
