## 1. 오늘 반영된 변경

| 대상 | 변경 내용 | 이유 |
|---|---|---|
| `ShopPurchaseLog` | `@UniqueConstraint(name = "uk_shop_purchase_user_request", columnNames = {"user_id", "request_id"})` 추가 | 중복 저장을 막는 마지막 방어선. 같은 트랜잭션의 재화 차감까지 함께 롤백됨 |
| `ShopPurchaseLog` | `responseBody` 타입 `String` → `ShopPurchaseResponse` (+ `@JdbcTypeCode(SqlTypes.JSON)`) | String + JSON 어노테이션은 이중 인코딩 위험. `rewards` 필드와 같은 방식으로 통일 |
| `ShopService` | `ObjectMapper` 제거, 중복 시 `return found.get().getResponseBody()` | Hibernate가 JSON ↔ 객체 변환을 대신 처리 |
| `ShopPurchaseLog` | requestId 주석 "구매 요청의 UUID"로 수정 | 유저 UUID로 오해할 여지 제거 |

### 개념 정리

- **`List.copyOf`**: 수정 불가능한 방어적 복사본. 외부에서 원본 리스트를 바꾸거나 `getRewards().add()`를 해도 로그가 바뀌지 않음. null(인자·요소)이면 NPE → 잘못된 데이터를 DB 전에 차단. **유지**.
- **58줄 NPE**: `copyOf`가 아니라 `product.productCode()`(product = null)에서 먼저 발생. 데이터 미준비로 넣은 자리표시이며, 3단계 구현 후 실제 값 전달로 해결.
- **`@Column(unique = true)` vs `@UniqueConstraint`**: 전자는 단일 컬럼, 후자는 컬럼 조합. 여기서 `user_id`에 단독 unique를 걸면 유저당 평생 1회 구매가 되므로 반드시 조합으로 걸어야 함.
- **어노테이션 제약조건은 DDL 생성 시에만 효과**: 현재 `ddl-auto=update` → 기존 테이블에는 추가되지 않을 수 있음. `SHOW INDEX FROM shop_purchase_logs;`로 확인.

## 3. 현재 코드 상태

```
Controller ─▶ Facade (데드락 재시도, 트랜잭션 없음) ─▶ Service (@Transactional) ─▶ Repository
```

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 사용자 조회 + 비관적 락 | ⚠️ `userRepository.findById` (락 없음) → `playerService.lock(userId)`로 교체 예정 |
| 2 | 중복 요청 확인 (userId + requestId) → 저장된 응답 반환 | ✅ |
| 3 | 상품·보상 조회, 없으면 404 `PRODUCT_NOT_FOUND` | ⏳ 게임 데이터 담당 |
| 4 | 재화 차감·보상 지급, 부족 시 409 `NOT_ENOUGH_GOLD` / `NOT_ENOUGH_DIAMOND` | ⏳ player 담당 |
| 5 | 구매 기록 저장 + 응답 반환 | ⚠️ `new ShopPurchaseResponse(null, null)`, `new ShopPurchaseLog(..., null, null, ...)` 자리표시 |

## 4. 바로 고칠 것 (내 담당)

| 우선 | 위치 | 내용 |
|---|---|---|
| 1 | `ShopFacade` 29줄 | `log.warn("데드락 재시도 ...")`가 try 첫 줄에 있어 **모든 요청마다** 찍힘. catch 안 재시도 직전으로 옮기고 `retry + 1`을 출력 |
| 2 | `ShopService` 10줄 | `jakarta.transaction.Transactional` → `org.springframework.transaction.annotation.Transactional` |
| 3 | 로컬 DB | UNIQUE 생성 여부 확인, 없으면 테이블 DROP 후 재생성 (형식이 바뀌기 전 데이터도 정리) |
| 4 | `ShopService` 30, 55줄 | 사용하지 않는 변수 `user`, `purchaseLog` 정리 (선택) |
| 5 | 테스트 | `ShopServiceTest` (중복 시 save 미호출, 사용자 없음 404), `ShopTableTest` (중복 코드·없는 상품 참조·보상 없는 상품·빈 리스트·불변) 추가 |

```java
// ShopFacade 수정안
for (int retry = 0; ; retry++) {
    try {
        return shopService.purchase(userId, request);
    } catch (PessimisticLockingFailureException e) {
        if (retry >= MAX_RETRY || !isDeadlock(e)) {
            log.warn("상점 구매 락 충돌로 실패: userId={}, requestId={}", userId, request.requestId(), e);
            throw new BusinessException(HttpStatus.SERVICE_UNAVAILABLE, "요청이 몰려 처리하지 못했습니다. 잠시 후 다시 시도해 주세요.");
        }
        log.warn("데드락 재시도 {}/{} userId={}", retry + 1, MAX_RETRY, userId);
    }
}
```

## 7. 앞으로 고려할 사항

### 구매 로직이 완성되면

- [ ] 1단계 잠금 교체 후 **동시 요청 테스트** (스레드 2개, 같은 requestId → 결제 1회)
- [ ] 정상 구매 테스트: 잔액 감소, 보상 지급, 로그 1건
- [ ] 재화 부족 409, 없는 상품 404 테스트
- [ ] 응답 단절 수렴 검증: 구매 → 응답 무시 → 같은 requestId 재전송 → 응답·DB 동일
- [ ] null 자리표시 제거 (`product`, `rewards`, `currencies`)

### 설계 판단이 필요한 것

| 항목 | 내용 | 비고 |
|---|---|---|
| 에러 코드 형식 | `{"code", "message"}` 공용 도입 | 영향 범위가 가장 큼, 우선 협의 |
| UNIQUE 위반 처리 | 현재 `DataIntegrityViolationException` → 500. Facade에서 잡아 재조회 후 저장 응답 반환 가능 | (설계서 외), 잠금 도입 후엔 거의 발생 안 함 |
| 카탈로그 버전 | 클라이언트 비교(버전 API) vs 서버 비교(ETag/304) vs 구매 요청에 버전 포함(409 CATALOG_OUTDATED) | (설계서 외), P0-01과 함께 결정 |
| 구매 제한·품절·판매 기간 | 시트 열 + 유저별 구매 횟수 집계 + 서버 검증 필요 | 기획 확정 시 |
| 거래 ID | 응답에 `shop_purchase_logs.id` 포함 여부 | (설계서 외), 클라이언트 요청 시 |
| 로그 보관 기간 | 현재 영구 보관 | (설계서 외) |
| API 버전 표기 | `/api/v1/...` | (설계서 외), 배포 환경 구성 시 |
| Swagger | springdoc 도입 시 Boot 4 호환 버전 확인 | (설계서 외) |
| `rewardCode: null` 출력 | 키 생략 vs null 출력 클라이언트와 합의 | (설계서 외) |

### 리팩토링 예정

- `CurrencyType`, `RewardType`, `Currencies`를 공용 패키지로 이동 (현재 `shop` ↔ `gamedata` 상호 참조, player도 필요)
- `ShopPurchaseLog`가 응답 DTO(`ShopPurchaseResponse`)를 직접 들고 있음 → DTO 필드명 변경 시 과거 로그 역직렬화 실패 가능성 유의

### 설계서에 제안할 갱신

- 잠금 대상: users → **player**
- 요청 로그: 도메인별 관리, 상점은 `shop_purchase_logs`에 `request_id` + `response_body`로 통합
- users는 인증 정보만, 재화·게임 상태는 player
