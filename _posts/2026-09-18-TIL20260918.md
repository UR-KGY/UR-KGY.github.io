# 2026-09-18
과제 수행을 하면서 WebSocket 내용을 다시 복습하면서 흐름을 따라가보려고 하였다.
강의만 들었을 때 좀 생소하였는데 과제를 수행하면서 좀 따라갈 수 있는 느낌이다.
Redis 쪽과 JWT 쪽도 좀 더 복습할 기회가 있음 하면서 오늘 정리는 마무리한다.
이번에 특강으로 들었던 데이터 관리법과 테스트 코드 사용법도 유익했는데 시간이 나면 정리하고 싶다.

## WebSocketSession

서버가 클라이언트 한 명과 맺은 웹소켓 연결 하나를 표현하는 객체. `HttpServletRequest`처럼, 해당 연결에 메시지를 보내거나 연결을 끊거나 부가 정보를 저장하는 창구 역할을 한다.

| 메서드 | 설명 |
|---|---|
| `sendMessage(message)` | 이 클라이언트에게 데이터 전송 |
| `close()` | 연결 강제 종료 |
| `getId()` | 세션 고유 ID |
| `getAttributes()` | 인터셉터에서 검증한 데이터들을 담는 `Map<String, Object>` |

## 1단계 — Config

웹소켓 설정(Config)은 `WebSocketConfigurer` 인터페이스를 붙여 만든다. 인터페이스 구현 외에 `@EnableWebSocket` 어노테이션이 필요하다.

```java
@Configuration
@EnableWebSocket
public class WebSocketConfig implements WebSocketConfigurer {

    @Override
    public void registerWebSocketHandlers(WebSocketHandlerRegistry registry) {
        registry.addHandler(gameWebSocketHandler(), "/ws/game") //핸들러 연결
                .addInterceptors(new WorldAuthHandshakeInterceptor()); //인터셉터 연결
    }
}
```

"이 URL 경로(`/ws/game`)로 들어오는 웹소켓 요청은 이 Handler가 처리하고, 그 전에 이 Interceptor를 거친다"는 것을 `registerWebSocketHandlers()`에서 구현한다.

## 2단계 — HandshakeInterceptor

웹소켓 연결이 완성되기 직전(아직 일반 HTTP 요청 단계)에 끼어드는 전처리기. `HandshakeInterceptor` 인터페이스를 구현해서 만든다.

`beforeHandshake()`와 `afterHandshake()` 메서드 구현이 필요한데, 지금까지는 `beforeHandshake()`만 구현했으므로 이것만 정리한다.

- `beforeHandshake()`는 `boolean`을 반환한다. `true`를 반환하면 웹소켓 연결을 진행하고, `false`를 반환하면 웹소켓 연결을 하지 않는다(핸드셰이크 자체가 거부됨).
- `beforeHandshake()`에서 해야 할 일은 앞으로 웹소켓 연결에 필요한 데이터들의 유효성을 판별하는 것이다.
  - `String nickname = readNickname(request);`처럼 `ServerHttpRequest` 객체에서 요청 데이터를 가져오거나,
  - `private final PlayerRepository playerRepository;`처럼 DB 빈을 주입받아 `Player player = playerRepository.findByNickname(nickname).orElse(null);`처럼 조회하는 것도 가능하다.
- 데이터가 검증되면 `attributes.put(ATTR_NICKNAME, nickname);`처럼 (문자열 키, 객체 값) 형태로 매개변수의 `attributes`에 넣어둔다. (이후 웹소켓 세션에 저장될 데이터들)

**데이터 검증에 실패했을 때의 처리 방식**

웹소켓 세션에 데이터를 저장하는 것 외에 쓰이는 방법이 또 있다. 객체가 `null`일 경우 에러 코드를 attributes에 넣고 `true`를 반환하는 방식이다.

```java
String nickname = readNickname(request);
if (nickname == null || nickname.isBlank()) {
    attributes.put(ATTR_ERROR_CODE, 4000);
    return true;
}
```

이렇게 하면 여기서 바로 `false`를 반환해서 핸드셰이크 자체를 거부하는 대신, 핸드셰이크는 일단 완료시켜서 클라이언트가 이 에러 코드를 실어둔 attributes를 담은 `WebSocketSession`을 받도록 한다.

> **[추가] 이후 연결을 실제로 끊는 지점**
> 여기서 `true`를 반환하는 것은 "일단 연결은 성립시킨다"는 뜻일 뿐, 이 자체로 연결이 끊기지는 않는다. 실제로 연결을 종료하는 처리는 3~4단계로 넘어가서, **Handler의 `afterConnectionEstablished(session)` 안에서** `session.getAttributes().get(ATTR_ERROR_CODE)`를 확인하고, 값이 있다면 클라이언트에게 에러 메시지를 보낸 뒤 `session.close()`를 호출하는 방식으로 이어진다. 즉 "핸드셰이크 단계에서 에러를 표시해두고, 연결 성립 직후 Handler가 그 표시를 보고 정리한다"는 2단계 처리 흐름이다.

```java
public class WorldAuthHandshakeInterceptor implements HandshakeInterceptor {
    @Override
    public boolean beforeHandshake(ServerHttpRequest request, ServerHttpResponse response,
                                    WebSocketHandler wsHandler, Map<String, Object> attributes) {
        Long worldId = extractWorldId(request);
        String nickname = extractNickname(request);
        attributes.put("worldId", worldId);
        attributes.put("nickname", nickname);
        return true; // false 리턴 시 핸드셰이크 자체가 거부되어 연결이 성립하지 않음
    }
}
```

## Session Registry

`WebSocketSession`은 서버와 클라이언트 1명 사이의 연결이다. 사용자끼리는 서로가 무엇을 하는지 알 수 있는 방법이 없기 때문에, 서버에서 같은 방 사용자들의 연결을 모아두는 저장소가 필요하다.

```java
private final Map<Long, Map<String, WebSocketSession>> rooms = new ConcurrentHashMap<>();
```

`ConcurrentHashMap<>` 자료구조를 사용하여 `WebSocketSession`을 모으는 이유는 동시성 문제를 방지하기 위해서이다.

핸드셰이크 성공 시 서버는 내부적으로 레지스트리의 `register` 메서드를 사용하여 연결에 성공한 클라이언트의 세션을 위의 `ConcurrentHashMap<>` 속에 넣는다.

```java
// 등록 메서드
public boolean register(
        Long roomId,
        String nickname,
        WebSocketSession session
) {
    Map<String, WebSocketSession> sessionsByNickname = rooms.computeIfAbsent(roomId, id -> new ConcurrentHashMap<>());
    return sessionsByNickname.putIfAbsent(nickname, session) == null;
}
```

> **[추가] 반환값(boolean)의 의미**
> `putIfAbsent(nickname, session)`은 그 닉네임에 원래 값이 없었으면 `null`을, 이미 값이 있었으면 "원래 있던 값"을 반환한다. 따라서 `== null`은 "이 닉네임으로 등록된 세션이 원래 없어서 새로 등록에 성공했다"는 뜻이고, `false`가 반환되면 "이미 같은 닉네임으로 접속 중인 세션이 있어서 등록이 거부됐다"는 뜻이다. 즉 이 반환값 자체가 **같은 닉네임의 중복 로그인을 막는 용도**로 쓰인다.

또한 연결이 끊겼을 때는 `remove()` 메서드를 통해 자료구조 내에 있는 세션을 제거한다.

```java
// 해제 메서드
public boolean remove(
        Long roomId,
        String nickname,
        WebSocketSession session
) {
    Map<String, WebSocketSession> sessionsByNickname = rooms.get(roomId);
    return sessionsByNickname.remove(nickname, session);
}
```

## Broadcast

레지스트리의 저장소에 등록된 세션들에게 공통적으로 메시지를 보내거나, 같은 방 안의 특정 클라이언트에게 메시지를 보내는 용도의 클래스이다.

```java
@Component
@RequiredArgsConstructor
public class RoomBroadcaster {
    private final RoomSessionRegistry registry;
    private final ObjectMapper objectMapper;

    public void broadcastJson(  // 방 내의 전체 세션들에게 메시지 전송
            Long roomId,
            String jsonMessage
    ) {
        for (WebSocketSession session : registry.sessions(roomId)) {
            sendJson(session, jsonMessage);
        }
    }

    public void sendTo(
            WebSocketSession session,   // 특정 세션 하나에 메시지 전송
            Object message
    ) {
        String jsonMessage = objectMapper.writeValueAsString(message);
        sendJson(session, jsonMessage);
    }

    private void sendJson(
            WebSocketSession session,
            String jsonMessage
    ) {
        try {
            synchronized (session) {
                if (session.isOpen()) {
                    TextMessage message = new TextMessage(jsonMessage);
                    session.sendMessage(message);
                }
            }
        } catch (Exception sendFailed) {
            log.warn("전송 실패: id={}", session.getId());
        }
    }
}
```

> **[추가] `synchronized (session)`을 쓰는 이유**
> 하나의 세션(같은 클라이언트)에게 여러 스레드가 동시에 메시지를 보내려 할 수 있다 (예: 브로드캐스트 도중에 다른 이벤트가 겹쳐서 같은 세션에 또 전송을 시도하는 경우). 스프링의 `WebSocketSession` 구현체는 **동시에 여러 스레드가 같은 세션에 `sendMessage()`를 호출하는 것을 안전하게 보장하지 않는다.** 그래서 세션 객체 하나를 기준으로 `synchronized` 블록을 걸어, 이 세션에 대한 전송은 한 번에 하나씩만 이뤄지도록 순서를 강제하는 것이다. (다른 세션에 대한 전송끼리는 서로 막지 않으므로, 전체 성능에 큰 영향은 없다.)

## 라우터 (Router)

메시지 라우팅은 웹소켓에서 해당 메시지가 어떤 종류의 요청/행동인지 구분하는 것이다.

HTTP에서는 URI에 `/members`, `/chat`처럼 어느 컨트롤러로 메시지가 갈지 구분이 가능하다. 웹소켓에서는 `WebSocketConfig`에서 설정한 연결 하나(예: `/ws/game`)만을 사용하며, Config와 연결된 핸들러의 `handleTextMessage()`로만 모든 메시지가 오고 간다.

따라서 다음과 같이 `type` 필드 안에 이 메시지의 종류와 의도가 무엇인지 알 수 있도록 표시하는 것이 메시지 라우팅이다.

```json
{ "type": "ping" }
{ "type": "move", "x": 10, "y": 20 }
{ "type": "chat", "text": "안녕하세요" }
```

라우터에서는 (Config에 등록된) handler가 메시지를 받아왔을 때, 그것을 JSON으로 파싱하고 `type` 필드를 확인하여 자신이 들고 있는 커스텀 핸들러들에게 보내준다.

```java
// 타입 필드를 찾고 이 필드와 값이 같은 커스텀 핸들러를 찾는다.
JsonNode typeNode = message.get("type");
String type = typeNode != null && typeNode.isString() ? typeNode.asString() : null;
EngineMessageHandler handler = findHandler(type);
```

```java
// 커스텀 핸들러의 타입을 나타내는 메서드를 호출
private EngineMessageHandler findHandler(String type) {
    return type == null ? null : handlers.get(type);
}
```

> **[추가] 라우터와 커스텀 핸들러 간 인터페이스 일치 주의사항**

## [추가 섹션] Redis 기반 온라인 상태 관리 (PresenceService)

인메모리 `SessionRegistry`는 서버가 1대일 때는 문제없지만, 서버가 여러 대로 늘어나면(서버 A에 접속한 유저와 서버 B에 접속한 유저가 서로의 존재를 모름) 한계가 있다. 이를 여러 서버가 공유할 수 있는 저장소인 **Redis**로 옮긴 것이 `PresenceService`이다. 

```java
public class PresenceService implements com.gameexpert.api.PresenceOperations {

    private static final Duration TTL = Duration.ofSeconds(90);
    private static final Duration KEY_TTL = Duration.ofSeconds(180);

    private final StringRedisTemplate redisTemplate;
    private final Clock clock = Clock.systemUTC();

    private String key(Long worldId) {
        return "world:" + worldId + ":presence";
    }

    public long onlineCount(Long worldId) {
        String key = key(worldId);
        double now = clock.millis();
        redisTemplate.opsForZSet().removeRangeByScore(key, Double.NEGATIVE_INFINITY, now);
        Long size = redisTemplate.opsForZSet().zCard(key);
        return (size != null) ? size : 0L;
    }

    public void join(Long worldId, String connectionId) {
        String key = key(worldId);
        redisTemplate.opsForZSet().add(key, connectionId, expiresAt());
        redisTemplate.expire(key, KEY_TTL);
    }

    public void leave(Long worldId, String connectionId) {
        String key = key(worldId);
        redisTemplate.opsForZSet().remove(key, connectionId);
    }

    public void heartbeat(Long worldId, String connectionId) {
        String key = key(worldId);
        renewExisting(key, connectionId);
        redisTemplate.expire(key, KEY_TTL);
    }

    private double expiresAt() {
        return clock.millis() + TTL.toMillis();
    }
}
```

**핵심 개념**

- 인메모리 `SessionRegistry`가 "닉네임 → Entry" 맵이었다면, `PresenceService`는 **Redis의 Sorted Set(ZSet)** 하나를 그 역할로 쓴다. `connectionId`가 원소(member), **만료 예정 시각**이 점수(score)다.
- `join()`: 접속 시 ZSet에 connectionId를 추가하고, 이 키 자체에도 `KEY_TTL`(180초)을 걸어둔다.
- `heartbeat()`: 클라이언트가 주기적으로(예: ping 메시지) 보낼 때마다 해당 connectionId의 score(만료 시각)를 최신 시각으로 갱신한다. 이미 나간(등록되지 않은) 연결을 되살리지 않도록 `ZADD ... XX` 옵션(기존에 있을 때만 갱신)을 사용한다.
- `onlineCount()`: 조회 시점에 먼저 이미 만료 지난(현재 시각보다 점수가 작은) 원소들을 `removeRangeByScore`로 정리한 뒤, 남은 개수(`zCard`)를 반환한다.
- **주의:** Redis의 `EXPIRE`는 키 전체에 대한 자동 삭제지만, ZSet 안의 개별 원소는 점수를 시각으로 넣어뒀다고 자동으로 없어지지 않는다. 그래서 `onlineCount()` 안에서 직접 `removeRangeByScore`를 호출해 만료된 원소를 정리해주거나, 별도 스케줄러(`@Scheduled`)로 주기적인 정리 작업을 돌려야 한다.

**CLI로 직접 확인하는 방법**


## 트러블 슈팅
- 버그 1 — `putIfAbsent` 반환값 오해석

**문제가 된 코드**

```java
Entry addResult = sessions.putIfAbsent(nicknameKey, candidate);

if (addResult != null) {
    added = true;
}
```

**원인**

- `putIfAbsent(key, value)`의 동작을 "키와 값을 저장하고 그 값을 반환한다"로 오해석함. 실제로는 다음과 같이 동작한다.

해당 `key`가 없었다면 → `value`를 저장하고, `null`을 반환
해당 `key`가 이미 있었다면 → 아무것도 저장하지 않고, 원래 있던 값을 반환

즉 반환값은 "새로 넣은 값"이 아니라 "넣기 전에 이미 있던 값(없었으면 `null`)"이다.

**해결**
```java
Entry addResult = sessions.putIfAbsent(nicknameKey, candidate);

if (addResult == null) {
    added = true;   // null이었다는 건 원래 없어서 새로 등록됐다는 뜻
}
```
처음에는 반대로 `addResult != null`일 때 `added = true`로 잘못 작성했었고, 이번에 `== null`로 정정하면서 정상 동작함.

- 버그 2 — `get()`에서 닉네임 소문자 정규화 누락

**문제가 된 코드**

```java
// register()에서는 저장할 때 소문자로 정규화해서 저장
String nicknameKey = key(nickname);

private static String key(String nickname) {
    return nickname.toLowerCase(Locale.ROOT);
}

// get()에서는 정규화 없이 원본 nickname으로 그대로 조회
return sessions.get(nickname);

```
**원인**

`register()`에서 닉네임을 저장할 때는 `key(nickname)`으로 소문자 변환을 거쳐서 저장했는데, `get()`에서 조회할 때는 그 변환 로직을 빠뜨리고 원본 `nickname`을 그대로 키로 사용함. 그 결과 등록은 "alex"로 됐는데 조회는 "Alex", "ALEX" 같은 원본 대소문자로 시도하게 되어 저장된 키와 안 맞아 못 찾는 문제가 발생. 저장 시점의 정규화 로직을 인지하지 못한 채 다른 곳(예: 대소문자 처리 자체를 의심)에서 원인을 찾느라 시간이 걸림.

**해결**

```java
return sessions.get(key(nickname));
```
