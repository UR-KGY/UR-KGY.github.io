## 2. EC2 접속 방법과 리눅스 사용자

### 개념: 접속 방법

| 방법 | 접속 위치 | 키 필요 | 22번 필요 | 로그인 사용자 |
|---|---|---|---|---|
| **SSH + 키 페어** | 내 PC 터미널 | O | O | `ec2-user` |
| **EC2 Instance Connect** | 브라우저 | X (AWS가 임시 키 사용) | O (AWS IP 대역 허용) | `ec2-user` |
| **Session Manager (SSM)** | 브라우저 / AWS CLI | X | **X** | `ssm-user` |
| 배스천 경유 | 내 PC 터미널 | O | O | `ec2-user` |
| EC2 직렬 콘솔 | 브라우저 | X | X | 비밀번호 사용자 (긴급용) |

**Session Manager 조건**: EC2 Role에 `AmazonSSMManagedInstanceCore`, SSM Agent 실행 중 (Amazon Linux 2023 기본), EC2가 AWS로 나갈 수 있어야 함

### 개념: 리눅스 사용자와 `sudo`

| 사용자 | 정체 | 집 폴더 |
|---|---|---|
| `root` | 최고 관리자 | `/root` |
| `ec2-user` | Amazon Linux 기본 일반 사용자 (앱 파일이 여기 있음) | `/home/ec2-user` |
| `ssm-user` | Session Manager가 만든 사용자 | `/home/ssm-user` |

| 명령 | 의미 |
|---|---|
| `sudo 명령` | 관리자(root) 권한으로 명령 하나 실행 (**S**uper**u**ser **do**) |
| `su - 사용자` | 그 사용자로 전환 (`-`: 그 사용자의 집 폴더와 환경까지) |
| `sudo su - ec2-user` | 관리자 권한을 빌려 비밀번호 없이 `ec2-user`로 전환 |
| `whoami` | 현재 사용자 확인 |

> 비유: `root` = 건물 관리인, `ec2-user`/`ssm-user` = 각자 방이 있는 입주자, `sudo` = 관리인에게 일 하나를 부탁하는 것

**실행 주체 정리**

| 실행 방식 | 실행 사용자 |
|---|---|
| SSH 접속 | `ec2-user` |
| Session Manager 접속 | `ssm-user` → `sudo su - ec2-user`로 전환해서 작업 |
| **SSM Run Command (워크플로 배포)** | **`root`** → 그래서 배포 스크립트에서 `sudo -u ec2-user`로 앱을 실행 |

### 실습: Session Manager 접속

1. EC2 → 인스턴스 → 체크박스 선택 → **연결** → **Session Manager** 탭 → **연결**
2. 접속 후
   ```bash
   whoami                 # ssm-user
   sudo su - ec2-user
   whoami                 # ec2-user
   ```
3. 종료: `exit` 두 번, 또는 화면의 **종료** 버튼

### 개념: EC2 안에서 실행되는 것

| 구분 | 예시 | 멈춰도 되나 |
|---|---|---|
| 내가 실행한 앱 | `app.jar`(게임 서버), `ci-demo` | O |
| 시스템 프로그램 | `sshd`, **`amazon-ssm-agent`**, `amazon-cloudwatch-agent`, `docker` | **X** (접속, 배포, 수집이 끊김) |

- 빌드는 GitHub 러너에서 하므로 **EC2에 CI 서버는 필요 없다.** EC2는 받아서 실행만 한다.
- 앱은 배포 전에 실행 중일 필요가 없다. 배포 스크립트가 "이전 버전 종료 → 새 버전 실행"을 한다.

| 배포 방식 | EC2에서 실행 중이어야 함 | 설치만 되어 있으면 됨 |
|---|---|---|
| SSH | `sshd` | Java 21 |
| S3 + SSM | `amazon-ssm-agent` | Java 21, AWS CLI |
| ECR + SSM | `amazon-ssm-agent`, `docker` | AWS CLI |

## 3. CloudWatch

### 개념

**정의**: AWS 리소스와 앱의 상태(지표, 로그)를 모아 보여 주고, 이상이 생기면 알려 주는 모니터링 서비스

| 목적 | 대체한 것 |
|---|---|
| 로그 모아 보기 | SSH 접속 → `tail -f ~/app.log` |
| 로그 보존 | 재시작하면 덮어써지던 `app.log` |
| 자원 상태 감시 (지표) | `top`, `free -h`, `df -h` |
| 알림 (경보) | 직접 들여다봐야 알 수 있던 장애 |
| 자동 대응 | (ASG 실습에서) 경보를 신호로 서버 추가 |

| 구성 요소 | 의미 | 이번 실습의 예 |
|---|---|---|
| Logs (로그 그룹 / 스트림) | 그룹 = 앱 단위, 스트림 = 서버 단위 | `webcraft-app` / `i-0abc...` |
| Metrics (지표) | 시간에 따른 숫자 값 | `CPUUtilization`, `mem_used_percent` |
| Namespace | 지표 묶음 | `AWS/EC2`(기본), `CWAgent`(Agent가 보낸 것) |
| Dimension | 지표 구분 기준 | `InstanceId` |
| Alarm | 조건을 넘으면 동작 | CPU 80% 이상 5분 |
| Agent | 서버 안에서 로그와 지표를 보내는 프로그램 | `amazon-cloudwatch-agent` |

- **CPU는 Agent 없이도** 기본 지표로 수집된다. Agent가 필요한 이유는 **메모리, 디스크, 앱 로그**.

### 개념: "`~/app.log`에 로그를 남기는 상태"

```bash
nohup java -jar ~/app.jar --spring.profiles.active=prod > ~/app.log 2>&1 &
```
- `> ~/app.log`: 화면 대신 파일에 기록, `2>&1`: 오류 출력도 같은 파일에
- CloudWatch Agent는 **파일에 새로 추가되는 줄을 읽어** AWS로 보낸다. 그래서 로그가 **파일로 존재**해야 한다.
- 다른 방법: `application-prod.properties`에 `logging.file.name=/home/ec2-user/logs/app.log` (크기 제한 설정 가능)

### 실습 과정

**① IAM Role 연결**
- IAM → 역할 → 역할 생성 → AWS 서비스 / **EC2**
- 정책: `CloudWatchAgentServerPolicy` + `AmazonSSMManagedInstanceCore`
- 이름: `webcraft-ec2-role` → EC2 → 작업 → 보안 → **IAM 역할 수정**
- EC2에는 **Role을 하나만** 붙일 수 있다. 이미 있으면 **기존 Role에 정책을 추가**한다.
- 확인: EC2에서 `aws sts get-caller-identity` → `assumed-role/webcraft-ec2-role/...`

**② Agent 설치, 설정, 시작**
```bash
sudo dnf install -y amazon-cloudwatch-agent

sudo tee /opt/aws/amazon-cloudwatch-agent/etc/config.json > /dev/null << 'EOF'
{
  "agent": { "metrics_collection_interval": 60 },
  "metrics": {
    "append_dimensions": { "InstanceId": "${aws:InstanceId}" },
    "metrics_collected": {
      "mem":  { "measurement": ["mem_used_percent"] },
      "disk": { "measurement": ["used_percent"], "resources": ["/"] }
    }
  },
  "logs": {
    "logs_collected": {
      "files": {
        "collect_list": [
          { "file_path": "/home/ec2-user/app.log",
            "log_group_name": "webcraft-app",
            "log_stream_name": "{instance_id}",
            "retention_in_days": 7 }
        ]
      }
    }
  }
}
EOF

sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
  -a fetch-config -m ec2 -s \
  -c file:/opt/aws/amazon-cloudwatch-agent/etc/config.json

sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a status   # "running"
```

| 옵션 | 의미 |
|---|---|
| `-a fetch-config` | 설정 파일을 읽어 적용 |
| `-m ec2` | EC2 환경 (Role 자격 증명 사용) |
| `-s` | 적용 후 (재)시작 |
| `-c file:...` | 설정 파일 경로 |

**③ 확인**
- CloudWatch → 로그 → **로그 그룹** → `webcraft-app` → 인스턴스 ID 스트림
- CloudWatch → 지표 → **탐색기** → `CWAgent` → `mem_used_percent` / EC2 → `CPUUtilization`

| 지표 | 대략적인 정상 범위 | 높을 때 |
|---|---|---|
| `mem_used_percent` | Spring 실행 중 50~80% | 90% 이상 지속 → `-Xmx` 조정, 큰 인스턴스 |
| `disk_used_percent` | 8 GiB 기준 30~50% | 계속 오르면 로그 크기 제한 |
| `CPUUtilization` | 평소 10% 안팎 | 요청 없이 높으면 코드 문제 |

부하 테스트: `sudo dnf install -y stress-ng && stress-ng --cpu 2 --timeout 180`

**④ 경보(Alarm)**
- CloudWatch → 경보 → 모든 경보 → **경보 생성** → 지표 선택

| 경보 | 지표 | 조건 |
|---|---|---|
| `webcraft-cpu-high` | EC2 → `CPUUtilization` | 평균, 5분, > 80, 데이터 포인트 1/1 |
| `webcraft-mem-high` | CWAgent → `mem_used_percent` | 평균, 5분, > 90 |

- 작업: SNS **새 주제** `webcraft-alerts` + 이메일 → **메일의 Confirm subscription 클릭 필수**
- 두 번째 경보는 **기존 주제 선택**
- 테스트 (CloudShell):
  ```bash
  aws cloudwatch set-alarm-state --alarm-name webcraft-cpu-high \
    --state-value ALARM --state-reason "알림 테스트" --region ap-northeast-2
  ```

| 경보 상태 | 의미 |
|---|---|
| 정상 (OK) | 조건 미달 |
| 경보 (In alarm) | 조건 초과 → 메일 발송 |
| 데이터 부족 | 막 만들어서 데이터 수집 중 |

### 요금 기준

| 항목 | 월 무료 | 초과 요금 (공식 페이지 기준값) |
|---|---|---|
| 기본 지표 (CPU 등) | 항상 무료 | - |
| 커스텀 지표 (Agent) | 10개 | 지표당 $0.30 |
| 로그 수집 + 저장 + 조회 | 합쳐서 5 GB | 수집 GB당 $0.50, 저장 GB당 $0.03 |
| 경보 | 10개 | 경보당 $0.10 |
| 대시보드 | 3개 | 개당 $3 |

- 이번 구성(지표 2개, 경보 2개, 적은 로그)은 **월 $0**.
- 요금이 늘어나는 경우: ASG로 서버가 늘어남(지표가 인스턴스별로 셈), DEBUG 로그, 보관 기간 무기한, 수집 간격 60초 미만. 서울 리전은 조금 더 비쌀 수 있음.

## 4. CI/CD와 GitHub Actions 개념

### CI/CD

| 용어 | 의미 | 실습에서 |
|---|---|---|
| **CI** (지속적 통합) | push마다 자동 빌드, 테스트 | `./gradlew clean bootJar` |
| **CD** (지속적 배포) | 결과물을 서버에 자동 배포 | EC2에 전달하고 재시작 |

손으로 하던 **빌드 → scp → 접속 → 종료 → 교체 → 실행**을 push 한 번으로 대신한다.

### GitHub Actions 구성 요소

| 용어 | 의미 |
|---|---|
| Workflow | `.github/workflows/*.yml` 파일 하나 = 워크플로 하나 |
| Trigger (`on:`) | 언제 실행할지 |
| Job / Step | 작업 묶음 / 순서대로 실행되는 단계 (하나라도 실패하면 멈춤) |
| Runner (`runs-on:`) | GitHub가 빌려주는 **임시 서버**. 실행이 끝나면 사라짐 |
| Action (`uses:`) | 남이 만든 재사용 단계 |
| Secrets (`${{ secrets.X }}`) | 암호화된 비밀 값. 로그에서 `***`로 가려짐 |

### 워크플로 파일과 Secrets의 관계

| 구성 요소 | 역할 | 비유 |
|---|---|---|
| **워크플로 파일** | 언제, 무엇을 할지 적은 작업 지시서 | 로봇의 작업 지시서 |
| **Secrets** | 작업에 필요한 비밀 값 보관 | 맡겨 둔 열쇠와 주소 |
| **배포 대상 환경** | EC2, 보안 그룹 등 | 로봇이 찾아갈 집 |

- Secrets만 등록해서는 아무 일도 일어나지 않는다. **CI/CD를 정의하는 것은 워크플로 파일**이다.
- `.github/workflows/`에 `.yml`을 두고 **push**하면 GitHub가 자동으로 인식하고, `on:` 조건마다 실행한다.
- 인식 조건: 경로 정확, 확장자 `.yml`/`.yaml`, GitHub에 push됨, YAML 문법 정상, Actions 활성화
- Secrets는 **저장소가 비어 있든 아니든 언제든** 등록 가능. push 전에 등록하는 것은 **첫 실행 성공**을 위한 권장 순서일 뿐이다.

| `on:` 예시 | 실행 시점 |
|---|---|
| `push: branches: [main]` | main에 push |
| `pull_request:` | PR 생성, 업데이트 |
| `workflow_dispatch:` | Actions 탭의 Run workflow 버튼 (기본 브랜치에 파일이 있어야 보임) |
| `schedule: - cron:` | 정해진 시간 (UTC) |

### 요금

| 항목 | 요금 |
|---|---|
| GitHub Actions **Public** 저장소 | 무료, 제한 없음 |
| GitHub Actions Private (Free 플랜) | 월 2,000분 무료, 초과 시 Linux 분당 $0.006 |
| Larger runner | 무료 사용량과 관계없이 항상 과금 → `ubuntu-latest` 유지 |
| jar SSH/S3 배포 | AWS 추가 요금 사실상 없음 |
| ECR | 저장 GB당 월 $0.10, 같은 리전 EC2로 전송 무료 |
| OIDC, IAM, SSM Run Command | 무료 |
| AWS CodePipeline (참고) | V1 파이프라인당 월 $1, V2 액션 분당 $0.002 |

- 결제 수단이 없으면 무료 사용량 초과 시 **실행만 멈추고 청구되지 않는다.**

## 5. 실습 A: SSH 방식 자동 배포

### 흐름

```
push → 러너: checkout → Java 21 → bootJar
            → scp로 EC2에 ci-demo.jar.new 전송
            → ssh로 이전 버전 종료 → 교체 → nohup 실행
            → curl /health
```

### 실습 프로젝트 `ci-demo`

| 항목 | 값 |
|---|---|
| 구성 | Spring Boot 3.5.6, Java 21, `spring-boot-starter-web`만 |
| API | `GET /` (message, version, startedAt), `GET /health` (OK) |
| 포트 | **8081** (게임 서버 8080과 분리) |
| `version` | 배포 시 `--app.version=${{ github.sha }}`로 커밋 번호 주입 |

```gradle
bootJar { archiveFileName = 'ci-demo.jar' }   // jar 이름 고정
jar { enabled = false }                        // -plain.jar 생성 안 함
```

### 과정

**① 로컬 실행 확인**: `./gradlew bootRun` → `http://localhost:8081`

**② GitHub 저장소 생성**
- 이름 `ci-demo`, **Public**
- **Add a README file 체크 안 함**, .gitignore None, License None (빈 저장소여야 push가 거부되지 않음)

**③ Secrets 등록** (Settings → Secrets and variables → Actions)

| Name | 값 |
|---|---|
| `EC2_HOST` | EC2 퍼블릭 IP |
| `EC2_KEY` | 개인키 내용 전체 (`cat key.pem`으로 출력해서 `-----BEGIN`부터 `-----END`까지) |

**④ 보안 그룹**: 22번 `0.0.0.0/0` (**실습 중에만**, 러너 IP가 매번 바뀜), 8081 `0.0.0.0/0`

### 워크플로 핵심 (ssh-action 스크립트)

```bash
if [ -f ~/ci-demo.pid ]; then kill "$(cat ~/ci-demo.pid)" 2>/dev/null || true; sleep 3; fi
mv ~/ci-demo.jar.new ~/ci-demo.jar
nohup java -Xmx256m -jar ~/ci-demo.jar --app.version=${{ github.sha }} \
  > ~/ci-demo.log 2>&1 < /dev/null &
echo $! > ~/ci-demo.pid
```

| 설계 포인트 | 이유 |
|---|---|
| 임시 이름(`.jar.new`)으로 올린 뒤 교체 | 실행 중인 jar를 바로 덮어쓰면 앱이 죽을 수 있음 |
| **PID 파일로 종료** | `pkill -f`는 스크립트를 실행하는 셸 자신도 종료할 수 있음 |
| `> log 2>&1 < /dev/null &` | 입출력을 끊어야 SSH 세션이 앱을 기다리지 않고 끝남 |

## 6. 키(.pem) 관리

### EC2_KEY가 필요한 이유

- 러너는 매번 새로 만들어지는 **빈 컴퓨터**라서 키가 없다.
- EC2는 `~/.ssh/authorized_keys`의 공개키와 **짝이 맞는 개인키**만 받아들인다.

### 권장: CI 전용 키

```bash
ssh-keygen -t ed25519 -f ~/.ssh/webcraft-ci -C "github-actions" -N ""
cat ~/.ssh/webcraft-ci.pub | ssh -i {기존.pem} ec2-user@{IP} 'cat >> ~/.ssh/authorized_keys'
ssh -i ~/.ssh/webcraft-ci ec2-user@{IP}      # 접속 확인
cat ~/.ssh/webcraft-ci                       # → EC2_KEY 에 등록
```
- 폐기: EC2 `authorized_keys`에서 `github-actions` 줄만 삭제

### 다른 컴퓨터로 옮길 때

- **가장 좋은 방법은 옮기지 않기**: 새 컴퓨터에서 새 키를 만들고 **공개키만** EC2에 등록
- 꼭 옮겨야 하면: `7z a -p -mhe=on key.7z key.pem` (암호는 다른 경로로), 또는 `ssh-keygen -p -f key.pem`
- 전달: USB 직접(후 삭제), 같은 네트워크 `scp` / **금지**: 이메일, 메신저, 공유 링크, Git
- 옮긴 뒤: `~/.ssh/`로 이동 → `chmod 400` → 중간 복사본 삭제
- 유출 의심 시: `authorized_keys`에서 해당 공개키 줄 삭제 (파일만 지워서는 소용없음)

## 7. 실습 B: S3 + JAR + SSM 방식

### 개념

**목적**: 22번 포트와 `.pem` 키 없이 배포한다.

| 구성 요소 | 역할 | 비유 |
|---|---|---|
| **S3** | 러너가 올린 jar를 EC2가 받아 가는 중간 보관소 | 택배 보관함 |
| **SSM Run Command** | 러너가 EC2에 명령을 전달하는 통로 | 관리 사무소를 통한 지시 |
| **OIDC** | 러너가 GitHub 신분증(토큰)으로 Role의 **임시 권한**을 받는 방식 | 신분증을 보여 주고 받는 호텔 카드키 |
| **ID 제공업체 (OIDC 공급자)** | AWS가 GitHub 토큰을 믿도록 등록 | 호텔이 인정하는 신분증 목록 |
| **신뢰 정책** | 어떤 저장소, 브랜치의 토큰만 받아 줄지 | "이 사람에게만 카드키 발급" |

```
러너 ──OIDC──▶ Role(github-actions-ci-demo)
  ├─ jar → s3://ci-demo-deploy-kgy/deploy/ci-demo.jar
  └─ ssm send-command
EC2 (SSM Agent) ── aws s3 cp (webcraft-ec2-role) → sudo -u ec2-user java -jar
```

| 비교 | SSH 방식 | S3 + SSM 방식 |
|---|---|---|
| 22번 포트 | `0.0.0.0/0` 필요 | **닫아도 됨** |
| GitHub의 비밀 | `.pem` (영구) | Role ARN만 (임시 권한) |
| 실행 기록 | Actions 로그 | + Systems Manager 명령 기록 |

### 과정

**0. 전제**: EC2 Role에 `AmazonSSMManagedInstanceCore`, Session Manager 연결 가능 (CloudShell `aws ssm describe-instance-information` → `Online`)

**1. S3 버킷**: `ci-demo-deploy-kgy`, 서울, 퍼블릭 액세스 차단 유지

**2. EC2 Role에 S3 읽기** (인라인 `ci-demo-deploy-read`)

```json
      "Resource": "arn:aws:s3:::ci-demo-deploy-kgy/deploy/*" }
```

**3. 읽기 테스트**
```bash

# EC2
```

## 8. SSM과 ECR의 차이

**서로 대체하는 관계가 아니라 역할이 다르다.**

| 질문 | 선택지 |
|---|---|
| ① 결과물을 무엇으로, 어디에 두나 (**보관소**) | jar → **S3** / Docker 이미지 → **ECR** |
| ② 서버에 명령을 어떻게 전달하나 (**통로**) | **SSH** / **SSM** |

| | SSH로 전달 | SSM으로 전달 |
|---|---|---|
| jar | 실습 A | 실습 B |
| Docker 이미지 (ECR) | 가능 (22번 필요) | **실습 C** |

| 비교 | S3 + jar | ECR + 이미지 |
|---|---|---|
| 결과물 | 코드 + 라이브러리 | 코드 + 라이브러리 + **Java + OS 환경** |
| EC2에 필요한 것 | Java 21 | Docker |
| 버전 관리 | 같은 이름으로 덮어씀 | **태그**로 보관 → 되돌리기 쉬움 |
| 환경 차이 | EC2 설정에 따라 달라질 수 있음 | 어디서나 같은 환경 |
| 확장 | EC2 전용 | ECS, EKS에서 그대로 사용 |

> 비유: jar = 레시피와 재료만 보내기 (받는 주방에 조리 도구가 있어야 함), 이미지 = 조리 도구까지 든 도시락 키트

## 9. 실습 C: ECR + Docker + SSM 방식

### 개념

| 용어 | 의미 | 비유 |
|---|---|---|
| 이미지 | 앱 + Java + OS 환경 꾸러미 | 도시락 키트 |
| 컨테이너 | 이미지를 실행한 프로세스 | 데운 도시락 |
| Dockerfile | 이미지 레시피 | 조리법 |
| ECR | 이미지 저장소 | 도시락 창고 |
| 태그 | 이미지 버전 이름 (`:커밋번호`) | 라벨 |

**바뀌는 것 / 그대로인 것**

| 바뀌는 것 | 그대로인 것 |
|---|---|
| 결과물(이미지), 보관소(ECR), EC2 필요 프로그램(Docker), EC2 Role(ECR 읽기), GitHub Role(ECR 쓰기) | **OIDC 신뢰 정책, SSM 전달 방식, Health check** |

### 과정

**1. EC2에 Docker 설치** (Session Manager → `sudo su - ec2-user`)
```bash
sudo dnf install -y docker
sudo systemctl enable --now docker
sudo usermod -aG docker ec2-user
exit && sudo su - ec2-user          # 그룹 적용
docker run --rm hello-world         # "Hello from Docker!" (arm64v8 = ARM 인스턴스)
docker rmi hello-world
```

**2. ECR 저장소**
- ECR → **Private registry** → Repositories → 생성
- namespace **비움**, 이름 `ci-demo`, 태그 변경 가능성 **Mutable** (Re-run 시 같은 태그 재사용)
- URI: `{계정ID}.dkr.ecr.ap-northeast-2.amazonaws.com/ci-demo`
- **수명 주기 정책**: 우선순위 1, 태그 상태 **모두 선택**, 매치 범위 **이미지 개수**, 개수 **5**, 작업 **만료**

**3. EC2 Role에 ECR 읽기**: 관리형 정책 `AmazonEC2ContainerRegistryReadOnly`
```bash
aws ecr get-login-password --region ap-northeast-2 | \
  docker login --username AWS --password-stdin {계정ID}.dkr.ecr.ap-northeast-2.amazonaws.com
# Login Succeeded
```

**4. GitHub Role에 ECR 쓰기** (인라인 `ci-demo-ecr-push`, 기존 `ci-demo-deploy`는 유지)
```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "EcrLogin", "Effect": "Allow", "Action": "ecr:GetAuthorizationToken", "Resource": "*" },
    { "Sid": "PushCiDemoImage", "Effect": "Allow",
      "Action": [
        "ecr:BatchCheckLayerAvailability", "ecr:InitiateLayerUpload", "ecr:UploadLayerPart",
        "ecr:CompleteLayerUpload", "ecr:PutImage", "ecr:BatchGetImage",
        "ecr:GetDownloadUrlForLayer", "ecr:DescribeImages" ],
      "Resource": "arn:aws:ecr:ap-northeast-2:{계정ID}:repository/ci-demo" }
  ]
}
```

**5. Dockerfile, .dockerignore** (프로젝트 최상위)
```dockerfile
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY build/libs/ci-demo.jar app.jar
EXPOSE 8081
ENTRYPOINT ["java", "-Xmx256m", "-jar", "app.jar"]
```
```
.git
.gradle
.idea
.github
*.pem
*.log
```

| 명령 | 의미 |
|---|---|
| `FROM` | 기반 이미지 (Java 21) |
| `WORKDIR` | 작업 폴더 |
| `COPY` | 빌드된 jar를 이미지 안으로 |
| `EXPOSE` | 사용 포트 표시 |
| `ENTRYPOINT` | 시작 명령. `docker run ... 이미지 --app.version=...`의 인자가 뒤에 붙음 |

**6. 워크플로 교체**: `deploy-ssm.yml` 삭제, `deploy-ecr.yml` 추가 → push (새 Secret 없음, `DEPLOY_BUCKET`은 사용 안 함)

```yaml
name: Deploy ci-demo to EC2 (ECR)

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  id-token: write
  contents: read

env:
  AWS_REGION: ap-northeast-2
  ECR_REPOSITORY: ci-demo
  IMAGE_TAG: ${{ github.sha }}

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with: { distribution: corretto, java-version: '21', cache: gradle }

      - name: Build jar
        run: |
          chmod +x gradlew
          ./gradlew clean bootJar

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}

      - name: Login to Amazon ECR
        id: ecr
        uses: aws-actions/amazon-ecr-login@v2

      - uses: docker/setup-qemu-action@v3      # x86 러너에서 ARM 빌드
      - uses: docker/setup-buildx-action@v3

      - name: Build and push image
        uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/arm64                # t4g(ARM) 인스턴스용
          push: true
          tags: ${{ steps.ecr.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${{ env.IMAGE_TAG }}

      - name: Deploy via SSM
        run: |
          cat > remote.sh <<EOF
          set -e
          REGISTRY=${{ steps.ecr.outputs.registry }}
          IMAGE=\$REGISTRY/${{ env.ECR_REPOSITORY }}:${{ env.IMAGE_TAG }}
          aws ecr get-login-password --region ${{ env.AWS_REGION }} | docker login --username AWS --password-stdin \$REGISTRY
          docker pull \$IMAGE
          if [ -f /home/ec2-user/ci-demo.pid ]; then
            kill "\$(cat /home/ec2-user/ci-demo.pid)" 2>/dev/null || true
            rm -f /home/ec2-user/ci-demo.pid
            sleep 3
          fi
          docker rm -f ci-demo 2>/dev/null || true
          docker run -d --name ci-demo --restart unless-stopped -p 8081:8081 \$IMAGE --app.version=${{ env.IMAGE_TAG }}
          docker image prune -af --filter "until=24h" || true
          docker ps --filter name=ci-demo --format "running: {{.Image}} ({{.Status}})"
          EOF
          # 이하 jq 변환 → ssm send-command → wait → 결과 확인 (실습 B와 동일)

      - name: Health check
        run: |   # curl http://${{ secrets.EC2_HOST }}:8081/health 반복 확인 (실습 B와 동일)
```

| 새 단계 | 하는 일 |
|---|---|
| `amazon-ecr-login@v2` | 러너의 `docker login` + 레지스트리 주소 출력 |
| `setup-qemu-action` | x86 러너에서 ARM 흉내 |
| `setup-buildx-action` | 멀티 아키텍처 빌드 도구 |
| `build-push-action` | `linux/arm64` 이미지 빌드 + ECR push |

| `docker run` 옵션 | 의미 |
|---|---|
| `-d` | 백그라운드 실행 |
| `--name ci-demo` | 컨테이너 이름 (교체할 때 사용) |
| `--restart unless-stopped` | **EC2 재부팅 시 자동 재시작** (nohup 방식과 다른 점) |
| `-p 8081:8081` | EC2 8081 → 컨테이너 8081 |

**7. 확인과 되돌리기**
```bash

pgrep -af ci-demo.jar           # 아무것도 없음 (이전 jar 방식 종료)
```

```bash
  --query "sort_by(imageDetails,&imagePushedAt)[].{Tag:imageTags[0],Pushed:imagePushedAt}" --output table

REGISTRY={계정ID}.dkr.ecr.ap-northeast-2.amazonaws.com
OLD_TAG={되돌릴 태그}
aws ecr get-login-password --region ap-northeast-2 | docker login --username AWS --password-stdin $REGISTRY
docker pull $REGISTRY/ci-demo:$OLD_TAG
docker rm -f ci-demo
docker run -d --name ci-demo --restart unless-stopped -p 8081:8081 $REGISTRY/ci-demo:$OLD_TAG --app.version=$OLD_TAG
```

| 방식 | 이전 버전으로 되돌리려면 |
|---|---|
| S3 + jar | 이전 jar가 덮어써져 없음 → 코드를 되돌려 다시 빌드, 배포 |
| **ECR + 이미지** | 태그만 바꿔 `docker run` → 1분 안에 복구 |

**컨테이너 관리 명령**

## 10. 세 가지 배포 방식 비교와 권한 정리

### 방식 비교

| 항목 | A. SSH | B. S3 + SSM | C. ECR + SSM |
|---|---|---|---|
| 결과물 전달 | scp | S3 | ECR |
| 명령 전달 | ssh | SSM | SSM |
| 22번 포트 | 필요 | 불필요 | 불필요 |
| GitHub Secrets | `EC2_HOST`, `EC2_KEY` | `AWS_ROLE_ARN`, `EC2_INSTANCE_ID`, `DEPLOY_BUCKET`, `EC2_HOST` | `AWS_ROLE_ARN`, `EC2_INSTANCE_ID`, `EC2_HOST` |
| 영구 비밀 | `.pem` | 없음 | 없음 |
| EC2 실행 | `nohup java -jar` | `sudo -u ec2-user ... java -jar` | `docker run` |
| 재부팅 후 | 수동 재실행 | 수동 재실행 | **자동 재시작** |
| 되돌리기 | 재빌드 | 재빌드 | **태그 교체** |

### Role과 권한

| Role | 빌려 쓰는 주체 | 정책 | 용도 |
|---|---|---|---|
| `webcraft-ec2-role` | **EC2** | `AmazonSSMManagedInstanceCore` | SSM 명령 받기, Session Manager |
| | | `CloudWatchAgentServerPolicy` | CloudWatch 전송 |
| | | `ci-demo-deploy-read` (인라인) | S3 jar 읽기 (실습 B) |
| | | `AmazonEC2ContainerRegistryReadOnly` | ECR 이미지 받기 (실습 C) |
| `github-actions-ci-demo` | **GitHub 러너** (OIDC, `ci-demo` main만) | `ci-demo-deploy` (인라인) | S3 쓰기, **특정 EC2에만** SSM 명령, 결과 조회 |
| | | `ci-demo-ecr-push` (인라인) | ECR 로그인, `ci-demo` 저장소 push |

| 정책 종류 | 특징 | 쓰는 경우 |
|---|---|---|
| AWS 관리형 | 여러 Role에 재사용 | 흔한 공통 권한 |
| 인라인 | Role 안에 직접 작성, Role과 함께 삭제 | 이 실습 전용 권한 |

> 원칙 "서버와 자동화에는 User(Access Key) 대신 Role"이 **EC2와 러너 양쪽 모두 Role**로 구현된 구조

## 12. 트러블슈팅

### 12-1. 콘솔 화면

| 증상 | 원인 | 해결 |
|---|---|---|
| CloudWatch 지표에 "모든 지표" 메뉴가 없음 | 콘솔 버전마다 메뉴 이름이 다름 | **지표 → 탐색기** 사용, 또는 EC2 → 모니터링 탭, CloudShell `aws cloudwatch list-metrics --namespace CWAgent` |
| IAM에 "자격 증명 공급자" 메뉴가 없음 | 번역에 따라 **"ID 제공업체"**로 표시 | 같은 메뉴. 주소 `console.aws.amazon.com/iam/home#/identity_providers` 또는 CloudShell `aws iam create-open-id-connect-provider ...` |
| ID 제공업체 목록이 비어 있음 | 아직 등록 전 (정상) | **공급자 추가** |
| ECR 생성 화면에 namespace 칸이 있음 | 저장소 이름 앞 선택 접두어 | 비워 두고 이름만 `ci-demo` (넣으면 모든 ARN, 주소가 `namespace/ci-demo`로 바뀜) |
| 수명 주기 정책 선택지가 많음 | - | 태그 상태 **모두 선택**, 매치 범위 **이미지 개수**, 개수 5, 작업 **만료** |
| CloudWatch 경보 메일이 안 옴 | SNS 구독 미확인 | 메일의 **Confirm subscription** 클릭, SNS → 구독 상태 `확인됨` |
| EC2 안에서 `aws cloudwatch list-metrics` 권한 오류 | Agent 정책은 **보내기**만 허용 | 조회는 **CloudShell**에서 |

### 12-2. Git / push

| 증상 | 원인 | 해결 |
|---|---|---|
| `Reinitialized existing Git repository` + `nothing to commit` + `up to date with 'origin/master'` | 로컬에 **이전 `.git`이 남음**. GitHub 저장소를 지워도 로컬 기록과 주소는 그대로 | 비밀 파일이 기록에 없으면 `git remote set-url origin {새 주소}`, 있으면 `rm -rf .git` 후 새로 `git init` |
| push 시 `rejected (fetch first)` | 저장소 생성 시 README를 체크함 | 저장소 재생성, 또는 `git pull origin main --allow-unrelated-histories` 후 push |
| push는 됐는데 Actions가 실행 안 됨 | 브랜치가 `master` | `git branch -M main` 후 push |
| `Authentication failed` | GitHub 로그인 실패 | 브라우저 인증, 필요 시 Personal Access Token |

### 12-3. 워크플로: SSH 방식

| 실패 단계 | 로그 | 원인 | 해결 |
|---|---|---|---|
| Build jar | `Permission denied: ./gradlew` | 실행 권한 | `chmod +x gradlew` |
| Build jar | `/usr/bin/env: 'sh\r'` | `gradlew`가 CRLF | `.gitattributes`에 `gradlew text eol=lf` → `git add --renormalize .` |
| Upload jar | `i/o timeout` | 22번이 러너를 막음 | 실습 중 22번 `0.0.0.0/0` |
| Upload jar | `unable to authenticate` | `EC2_KEY` 잘림 | 전체 다시 등록 |
| Restart app | 셸이 중간에 종료 | `pkill -f`가 자기 자신을 종료 | **PID 파일 방식** |
| Restart app | 단계가 끝나지 않음 | 리다이렉트 누락 | `> log 2>&1 < /dev/null &` |
| Health check | 응답 없음 | 8081 미개방, 앱 오류 | 보안 그룹, `tail -n 50 ~/ci-demo.log` |

### 12-4. 워크플로: OIDC (Configure AWS credentials)

| 로그 | 원인 | 해결 |
|---|---|---|
| `Credentials could not be loaded` | `permissions: id-token: write` 누락, 또는 `AWS_ROLE_ARN` 이름 오타 (빈 값) | 워크플로와 Secret 이름 확인 |
| **`Request ARN is invalid`** | Secret에 **Role ARN이 아닌 값** (OIDC 공급자 ARN, 이름만, 하이픈 계정 ID, 중괄호, 공백) | `aws iam get-role --role-name github-actions-ci-demo --query Role.Arn --output text` 결과로 다시 등록 |
| **`Not authorized to perform sts:AssumeRoleWithWebIdentity`** | 신뢰 정책 조건과 토큰 값 불일치, 또는 존재하지 않는 Role | 아래 **Debug 단계**로 실제 값 확인 |

**Debug 단계** (Configure AWS credentials 바로 위에 추가, 확인 후 삭제)
```yaml
      - name: Debug OIDC (삭제 예정)
        env:
          ROLE_ARN: ${{ secrets.AWS_ROLE_ARN }}
        run: |
          echo "계정 ID : $(echo "$ROLE_ARN" | cut -d: -f5)"
          echo "Role 이름: ${ROLE_ARN##*/}"
          echo "길이     : ${#ROLE_ARN} (정상: 53)"
          TOKEN=$(curl -s -H "Authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" \
            "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=sts.amazonaws.com" | jq -r .value)
          echo "$TOKEN" | cut -d. -f2 | python3 -c \
            "import sys,base64,json;s=sys.stdin.read().strip();s+='='*(-len(s)%4);d=json.loads(base64.urlsafe_b64decode(s));print(json.dumps({k:d[k] for k in ('iss','aud','sub')},indent=2))"
```

**이번 원인: `sub`에 숫자 ID가 포함됨**
```
신뢰 정책:  repo:UR-KGY/ci-demo:ref:refs/heads/main
실제 토큰:  repo:UR-KGY@{계정숫자ID}/ci-demo@{저장소숫자ID}:ref:refs/heads/main
```
- **해결**: 신뢰 정책의 `sub`를 Debug 출력값 그대로 교체
  ```bash
  aws iam update-assume-role-policy --role-name github-actions-ci-demo --policy-document file://trust.json
  ```
- 숫자 ID는 **실행마다 바뀌지 않는 고정 번호** (주민등록번호 같은 것). 이름이 같은 다른 저장소가 Role을 빌리지 못하게 막는 보안 장치
- 저장소를 **삭제하고 다시 만들면** 저장소 ID가 바뀌므로 다시 맞춰야 함
- GitHub 주소는 대소문자를 구분하지 않지만 **토큰과 신뢰 정책은 구분**함
- 신뢰 정책 `sub` 목록에 같은 값이 두 개 있어도 결과는 같음 (목록은 "하나라도 맞으면 통과")
- 교훈: **추측으로 고치지 말고 토큰의 `iss`, `aud`, `sub`를 출력해서 그대로 맞춘다**

| 오류 | 의미 |
|---|---|
| `Request ARN is invalid` | ARN **형식**이 틀림 (권한 검사 전 단계) |
| `Not authorized ...` | 형식은 맞지만 **신뢰 조건**이 안 맞음 |

| 실패 단계 | 로그 | 원인 | 해결 |

### 12-7. EC2 / CloudWatch / Docker

| 증상 | 원인 | 해결 |
|---|---|---|
| Session Manager 연결 버튼 비활성 | Role에 SSM 정책 없음, Agent 오프라인 | 정책 확인, 5분 대기, `sudo systemctl restart amazon-ssm-agent` |
| `describe-instance-information`에 `ConnectionLost` | EC2가 AWS로 나가지 못함 | Public 서브넷, 아웃바운드 모든 트래픽 |
| Session Manager 접속 후 `~`에 파일이 없음 | `ssm-user`로 접속됨 | `sudo su - ec2-user` |
| 실수로 SSM Agent를 멈춤 (22번도 닫힘) | 접속 통로 없음 | 콘솔에서 **EC2 재부팅** (서비스 자동 시작) |
| Agent 로그에 `AccessDenied` | Role에 `CloudWatchAgentServerPolicy` 없음 | 정책 추가 |
| Agent 로그에 `no such file or directory` | `file_path` 경로 틀림 | 전체 경로 `/home/ec2-user/app.log` (`~` 사용 불가) |
| Agent 로그에 `NoCredentialProviders` | Role 미연결 | EC2 → IAM 역할 수정 |
| `aws sts get-caller-identity`에 `user/...`가 나옴 | EC2에 Access Key가 남아 Role보다 우선 사용됨 | `~/.aws/credentials`, `AWS_ACCESS_KEY_ID` 제거 |
| `docker: permission denied ... docker.sock` | docker 그룹 미적용 | `exit` 후 다시 `sudo su - ec2-user` |
| Agent 로그 확인 | - | `sudo tail -n 50 /opt/aws/amazon-cloudwatch-agent/logs/amazon-cloudwatch-agent.log` |
