# CI/CD 배포 브랜치 전환 준비: deploy-test → main

> - 목적: 운영 배포를 `main` 브랜치 push로 바꾸기 위한 **변경점과 순서**를 미리 정리
> - 바뀌는 곳은 **두 군데뿐**: ① 워크플로 파일의 트리거 브랜치 ② IAM 신뢰 정책의 `sub`
> - 둘 중 하나만 바꾸면 배포가 **실행되지 않거나**(①만) **권한 거부로 실패**(②만)한다
> - 프로젝트 파일 수정·커밋·push는 본인이 직접 진행 (아래는 변경 내용만 제시)

## 1. 지금 구조와 바뀌는 점

```
지금:   deploy-test push ─▶ Actions(OIDC) ─▶ 역할 획득(sub = …:ref:refs/heads/deploy-test) ─▶ 배포
전환 후: main push        ─▶ Actions(OIDC) ─▶ 역할 획득(sub = …:ref:refs/heads/main)        ─▶ 배포
```

| 위치 | 지금 | 전환 후 |
|---|---|---|
| `.github/workflows/deploy.yml` `on.push.branches` | `[deploy-test]` | `[main]` |
| IAM 역할 `github-actions-swordmaster-deploy` 신뢰 정책 `sub` | `…:ref:refs/heads/deploy-test` | `…:ref:refs/heads/main` |
| 워크플로 이름 | `Deploy (deploy-test)` | `Deploy (main)` |
| 인라인 권한 정책 (`swordmaster-deploy`) | - | **변경 없음** |
| GitHub Secret `AWS_DEPLOY_ROLE_ARN` | - | **변경 없음** (같은 역할) |
| AWS 리소스 (ECR, Parameter Store, ASG) | - | **변경 없음** |

> 비유하면 배포 권한은 **"deploy-test 지점 직원증"**으로 발급돼 있다. 출입 명단(신뢰 정책)과 근무지(워크플로 트리거)를 **동시에 main 지점으로** 바꿔야 한다. 하나만 바꾸면 "출근은 했는데 출입이 안 되거나", "출입증은 있는데 출근을 안 하는" 상태가 된다.

---

## 2. 전환 방식: 2단계 (안전)

한 번에 바꾸지 않고 **잠시 두 브랜치를 모두 허용**했다가 정리한다.

| 단계 | 워크플로 트리거 | 신뢰 정책 `sub` | 의미 |
|---|---|---|---|
| 지금 | `deploy-test` | `deploy-test` | |
| **1단계 (병행)** | `deploy-test`, **`main`** | `deploy-test`, **`main`** | 둘 다 배포 가능. main 첫 배포 검증 |
| **2단계 (정리)** | `main` | `main` | deploy-test 배포 권한 제거 |

- 1단계에서 main 배포가 실패해도 **deploy-test로 계속 배포할 수 있어** 안전하다
- 2단계를 빼먹으면 deploy-test에 push한 사람도 운영 배포를 할 수 있는 상태로 남는다 → **반드시 정리**

---

## 3. 사전 점검 (전환 전에)

| 확인 | 방법 | 이유 |
|---|---|---|
| **main에 최신 코드가 있나** | `git log origin/main --oneline -5`, `git diff origin/deploy-test origin/main --stat` | main이 오래된 상태면 첫 push에 **옛 코드가 운영에 배포**됨 |
| main에 **워크플로 파일**이 있나 | `git show origin/main:.github/workflows/deploy.yml` | push 트리거는 **그 브랜치에 있는 워크플로 파일**만 실행됨 |
| main에 **마이그레이션 파일**이 모두 있나 | `git diff origin/deploy-test origin/main --stat -- src/main/resources/db/migration/` | 운영 DB에 적용된 V1, V2가 main에 없으면 Flyway **기동 실패** |
| main에 `application-prod.properties`, `FilterConfig`(`/actuator/health/**`) 반영 | 위 diff로 확인 | 없으면 헬스체크 401 → 교체 반복 |
| 팀 브랜치 전략 합의 | develop → main PR 규칙 | main = 운영이 됨 |

**운영 DB에 이미 적용된 마이그레이션(V1, `V20261014_1200__…`)이 main에 없거나 내용이 다르면 서버가 뜨지 않는다.** 가장 중요한 점검이다.

---

## 4. 1단계: 병행 허용

### 4-1. IAM 신뢰 정책 수정 (콘솔)

IAM → 역할 → `github-actions-swordmaster-deploy` → **신뢰 관계** 탭 → **신뢰 정책 편집**

`sub` 조건을 **배열**로 바꿔 두 브랜치를 모두 허용한다. 숫자 ID가 포함된 기존 값을 **그대로 복사**한 뒤, 끝의 `deploy-test`만 `main`으로 바꾼 줄을 하나 더 추가한다.

**변경 전 (조건 부분만)**

```json
"Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub": "기존값…:ref:refs/heads/deploy-test"
  }
}
```

**변경 후**

```json
"Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub": [
      "기존값…:ref:refs/heads/deploy-test",
      "기존값…:ref:refs/heads/main"
    ]
  }
}
```

- `기존값…` 부분(조직·저장소 이름과 **숫자 ID**)은 지금 정책에 들어 있는 문자열을 **한 글자도 바꾸지 않고** 복사한다
- 10/12 OIDC 실패 원인이 바로 이 숫자 ID 불일치였다
- `Principal`, `Action`, `aud`는 건드리지 않는다
- 계정 ID가 포함된 ARN은 화면에 그대로 두고, 문서·채팅에 붙이지 않는다

### 4-2. 워크플로 수정 (본인이 직접)

**파일**: `.github/workflows/deploy.yml` / **위치**: 맨 위 `name`과 `on` 부분

**변경 전**

```yaml
name: Deploy (deploy-test)
on:
  push:
    branches: [deploy-test]
  workflow_dispatch:
```

**변경 후 (1단계)**

```yaml
name: Deploy (prod)
on:
  push:
    branches: [deploy-test, main]
  workflow_dispatch:
```

- `concurrency: group: deploy-prod`는 **그대로 둔다** → 두 브랜치에서 동시에 push해도 배포가 겹치지 않고 순서대로 실행됨
- 나머지 steps(빌드, ECR, IMAGE_TAG, instance refresh)는 변경 없음

### 4-3. 반영 순서

| 순서 | 작업 | 주의 |
|---|---|---|
| 1 | 4-1 신뢰 정책 수정 (AWS) | **먼저.** 워크플로가 main에서 돌 때 권한이 이미 있어야 함 |
| 2 | 4-2 워크플로 수정 커밋 → **deploy-test에 push** | deploy-test 배포로 변경된 워크플로가 정상인지 확인 |
| 3 | develop → **main** PR 머지 (워크플로·마이그레이션 포함) | 3장 점검 완료 후 |
| 4 | main push로 Actions 실행 확인 | 아래 5장 |

| 순서 | 확인 | 정상 |

## 6. 2단계: deploy-test 정리

main 배포가 1~2회 정상 동작한 뒤 진행한다.

### 6-1. 신뢰 정책

`sub` 배열에서 `…:ref:refs/heads/deploy-test` 줄을 **삭제** → main 한 줄만 남김

```json
"token.actions.githubusercontent.com:sub": "기존값…:ref:refs/heads/main"
```

### 6-2. 워크플로

```yaml
on:
  push:
    branches: [main]
  workflow_dispatch:
```

### 6-3. 브랜치

| 작업 | 선택 |
|---|---|
| deploy-test 브랜치 삭제 | 팀 합의 후. 남겨 두더라도 **배포 권한은 없음** |
| 문서 갱신 | 인수인계 문서 1장(배포 브랜치), 4장(신뢰 정책), 7장(트리거), 10-1장(배포 절차) |

## 7. 함께 권장하는 설정 (선택)

| 설정 | 위치 | 효과 |
|---|---|---|
| **main 브랜치 보호** | GitHub → Settings → Branches → `main` 규칙 | 직접 push 금지, **PR + 리뷰 1명 이상** 필수 → 실수로 운영 배포 방지 |
| 상태 검사 필수 | 같은 화면 | 빌드(컴파일) 실패한 PR은 머지 불가 → 10/13의 "컴파일 오류 커밋" 재발 방지 |
| GitHub Environment `production` | Settings → Environments | 배포 전 **승인 버튼**, 배포 이력 화면. 워크플로에 `environment: production` 추가 필요 |
| 수동 배포 | `workflow_dispatch` (이미 있음) | Actions 탭에서 브랜치를 골라 수동 실행 가능 |

**주의 (Environment를 쓸 경우)**: 잡에 `environment: production`을 넣으면 OIDC 토큰의 `sub`가 `…:environment:production`으로 **바뀐다.** 그때는 신뢰 정책의 `sub`도 그 값으로 바꿔야 한다. 처음 전환할 때는 Environment 없이 진행하고, 나중에 따로 적용하는 편이 단순하다.

## 8. 브랜치 흐름 (전환 후)

```
기능 브랜치 ──PR──▶ develop ──PR (릴리스)──▶ main ──push──▶ 자동 배포 (운영)
                     │
                     └ 통합 확인 (배포 없음)
```

| 브랜치 | 역할 | 배포 |
|---|---|---|
| 기능 브랜치 (`feat/…`, `fix/…`) | 개발 | 없음 |
| `develop` | 통합 | 없음 |
| **`main`** | **운영** | **push 시 자동** |

- 엔티티 변경은 **같은 PR에 마이그레이션 파일** (Flyway 가이드)
- main으로 가는 PR 전에 `git diff origin/main origin/develop --stat -- src/main/resources/db/migration/`로 마이그레이션 확인
- 컬럼·테이블 삭제 마이그레이션이 포함되면 **main 머지 직전에 RDS 스냅샷**

### 준비

- [ ] 팀과 브랜치 전략(main = 운영) 합의

### 1단계
- [ ] 신뢰 정책 `sub`에 main 추가 (배열)
- [ ] 워크플로 `branches: [deploy-test, main]` → deploy-test로 push해서 정상 확인
- [ ] develop → main PR 머지 → main 첫 배포 검증 (5장)

### 2단계
- [ ] 신뢰 정책에서 deploy-test 제거
- [ ] 워크플로 `branches: [main]`
- [ ] (선택) main 브랜치 보호, 상태 검사 필수
- [ ] 인수인계 문서 갱신
