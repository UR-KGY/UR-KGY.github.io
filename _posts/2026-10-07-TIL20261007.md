## 2. 단계별 변경 내용

### 3단계: 상품·보상 조회

​```java
ShopProduct product = shopCatalog.findProduct(request.productCode())
        .orElseThrow(() -> new BusinessException(HttpStatus.NOT_FOUND, "PRODUCT NOT FOUND"));

List<Reward> rewards = shopCatalog.findRewards(request.productCode());
​```

- 시트 데이터는 `ShopCatalog`가 조회 창구 역할 (`ShopProductTable` + `ShopProductRewardTable`)
- 상품이 없으면 404
- `ShopCatalog`가 부팅 시 "보상 없는 상품"을 막으므로 `rewards`는 항상 1개 이상

### 4단계: 결제 → 보상 → 잔액

​```java
CurrencyType priceType = product.priceType();

if (!currencyService.has(userId, priceType, product.price()))
    throw new BusinessException(HttpStatus.CONFLICT, "NOT_ENOUGH_" + priceType.name());

currencyService.consume(userId, priceType, product.price());

for (Reward reward : rewards) {
    rewardService.reward(userId, reward);
}

Map<CurrencyType, Long> left = currencyService.getAll(userId);
CurrenciesResponse currencies = new CurrenciesResponse(
        left.get(CurrencyType.GOLD),
        left.get(CurrencyType.DIAMOND));
​```

- 결제 재화를 하드코딩하지 않고 **상품의 `priceType`**으로 판단
- 재화 부족 시 409 `NOT_ENOUGH_GOLD` / `NOT_ENOUGH_DIAMOND`
- 보상 지급은 `RewardService`에 위임 (종류별 분기는 RewardService 한 곳에서만)
- 잔액은 차감과 지급이 **모두 반영된 뒤** 조회 (응답의 `currencies` = 변경 후 잔액)

### 5단계: 응답 생성과 기록 저장

​```java
ShopPurchaseResponse response = new ShopPurchaseResponse(rewards, currencies);
shopPurchaseLogRepository.save(new ShopPurchaseLog(userId, request.requestId(), product, rewards, response));
return response;
​```

- 응답 전체를 `response_body`에 저장 → 같은 requestId 재전송 시 그대로 반환

## 3. 오늘 발생한 오류와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| `"NOT_ENOUGH_{}"` 컴파일 에러 | `BusinessException`에 인자 3개 생성자가 없음. `{}`는 로그 전용 문법 | 문자열 연결 `"NOT_ENOUGH_" + priceType.name()` |
| 골드가 충분한데 409 | `has(...)` 조건이 반대였음 | `!currencyService.has(...)` |
| 잔액이 가격과 같을 때 구매 불가 | `price >= 잔액` 비교 | `has()`(`amount >= cost`)로 통일 |
| 중복 요청 조회 시 500 (`Unrecognized field "currenciesResponse"`) | 응답 record 필드명을 `currenciesResponse`로 바꿨을 때 저장된 기록이 남아 있음 | 필드명을 `currencies`로 되돌리고, 옛 키로 저장된 행은 SQL로 정리 |
| GOLD 보상인데 "구현되지 않은 보상" 예외 | RewardService switch에 `break`가 없어 아래 case로 흘러내림 | 화살표 switch(`case GOLD ->`) 사용 |

## 5. 남은 정리 항목

| 우선 | 내용 |
|---|---|
| 1 | `RewardService`: `case ITEM: break;` 등 미구현 종류를 **예외로 변경** (현재는 재화만 빠지고 커밋됨) |
| 2 | `jakarta.transaction.Transactional` → `org.springframework.transaction.annotation.Transactional` |
| 3 | `left.get(...)` → `left.getOrDefault(..., 0L)` (재화 행이 없을 때 NPE 방지) |
| 4 | 1단계 잠금 todo 주석 정리, `findById` → `existsById` |
| 5 | 3단계 메시지를 사용자용 문장으로 (`"상품을 찾을 수 없습니다."`), 실행되지 않는 `rewards.isEmpty()` 검사 제거 |
| 6 | 재화 부족 메시지를 `switch`로 명시 (`GOLD -> "NOT_ENOUGH_GOLD"`, `DIAMOND -> "NOT_ENOUGH_DIAMOND"`) |
| 7 | `ShopServiceTest` 작성 (중복 요청 시 결제 안 함, 재화 부족 409, 미구현 보상 예외) |

## 6. 의존 관계 (현재)

​```
ShopService
 ├ ShopPurchaseLogRepository   중복 확인, 기록 저장
 ├ UserRepository              회원 확인
 ├ ShopCatalog                 상품·보상 조회
 ├ CurrencyService             has / consume / getAll   (결제)
 └ RewardService               reward                   (지급)
      └ CurrencyService        grant
​```

- ShopService는 결제(`consume`)만 직접 하고, 지급(`grant`)은 반드시 RewardService를 거침
- 모든 호출이 ShopService의 트랜잭션 하나에 합류 → 하나라도 실패하면 전체 롤백
