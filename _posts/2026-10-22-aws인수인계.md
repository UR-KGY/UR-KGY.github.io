# swordmaster AWS 이관 인수인계 문서 (dev 계정 이전)

> - 작성일: 2026-10-22
> - 이관 방식: 개인 계정의 리소스를 **팀 dev 계정에 새로 구축**하고, 기존 개인 계정은 정리
> - 비밀값(JWT 키, DB 비밀번호, 액세스 키, 계정 ID)은 이 문서에 적지 않음 → 비밀번호 관리자로 별도 전달
> - `한글 단어`는 실제 값으로 치환

---

## 1. 개요

| 항목 | 내용 |
|---|---|
| 기존 위치 | 개인 이메일 AWS 계정 (프리 플랜), 서울 리전 `ap-northeast-2` |
| 이전 위치 | 팀 조직의 dev 계정, 서울 리전 |
| 서비스 주소 | `https://api.upgrade-29.com`, `wss://api.upgrade-29.com/ws` (**도메인 미 변경 시 변경 없음**) |
| 서비스 중단 | 컷오버 시 수 분 |
| 이전 대상 | 인프라 전체, RDS 데이터, Parameter Store 값, CI/CD 연결 |
| 이전 제외 | ECR 이미지(재빌드), Valkey 데이터(캐시), 기존 계정 크레딧(이전 불가) |

## 2. 현재 환경 (dev 계정에 동일하게 구축할 설정)

### 2-1. 네트워크

| 리소스 | 설정 |
|---|---|
| VPC | 퍼블릭 서브넷 2a·2c, 프라이빗 서브넷 2a·2c |
| 라우팅 | 퍼블릭 `0.0.0.0/0 → IGW`, 프라이빗 `0.0.0.0/0 → NAT` |
| NAT 게이트웨이 | 리전 모드 |

### 2-2. 보안그룹

| 이름 | 인바운드 | 출처 |
|---|---|---|
| `alb-sg` | 443 | `0.0.0.0/0` |
| `app-sg` | 8080 | `alb-sg` |
| `rds-sg` | 3306 | `app-sg`, `bastion-sg` |
| `valkey-sg` | 6379 | `app-sg`, `bastion-sg` |
| `bastion-sg` | 22 | 관리자 IP/32 |

> - 바스티온은 선택 사항
> - HTTP:80 리스너는 삭제됨 → `alb-sg`는 443만 허용

### 2-3. 컴퓨팅

| 리소스 | 설정 |
|---|---|
| 시작 템플릿 | ARM 인스턴스, 프라이빗 서브넷, `app-sg`, EC2 인스턴스 역할, 사용자 데이터에서 Parameter Store 조회 후 컨테이너 실행 |
| AMI | Amazon Linux 2023 (arm64) |
| 인스턴스 유형 | 확인 필요 |
| 메타데이터 | IMDSv2 필수 여부, 홉 제한: 확인 필요 (기존과 동일하게) |
| EC2 인스턴스 역할 | `EC2역할이름` (인스턴스 프로파일 동일 이름), 정책은 15장 |
| ASG `swordmaster-asg` | 최소/원하는/최대 1/1/2, ELB 헬스체크, 유예 180초 |
| 스케일링 정책 | CPU 60% 정책 **비활성 유지** (현재 채팅이 SimpleBroker 로 구현되어 있어 제약) |
| 인스턴스 새로 고침 | MinHealthy 100, MaxHealthy 200, 워밍업 180, SkipMatching false |
| 바스티온 | t4g.nano, 퍼블릭 서브넷, IAM 역할 없음 |

### 2-4. 로드 밸런서

| 항목 | 설정 |
|---|---|
| ALB `swordmaster-alb` | 퍼블릭, idle timeout 300초 |
| 리스너 | HTTPS:443 (ACM `api.upgrade-29.com`) → 대상 그룹 (HTTP:80 리스너 없음) |
| 대상 그룹 | HTTP 8080, 헬스체크 `/actuator/health/readiness`, 등록 취소 지연 30초 |

### 2-5. 데이터

| 리소스 | 설정 |
|---|---|
| RDS `swordmaster-db` | MySQL, 단일 AZ, 퍼블릭 액세스 없음, 삭제 보호 ON, `rds-sg` |
| RDS 상세 | 엔진 버전, 인스턴스 클래스, 스토리지 크기: 확인 필요 / 백업 보존 1일 / 문자셋·콜레이션: `SHOW CREATE DATABASE swordmaster;`로 확인 |
| RDS 서브넷 그룹 | 기존은 기본 서브넷 그룹 → dev 계정에서는 **프라이빗 서브넷 2a·2c 전용 그룹** 생성 |
| ElastiCache | Valkey, 클러스터 모드, 전송 중 암호화(TLS), 포트 6379, `valkey-sg` |
| ElastiCache 상세 | 노드 유형, 샤드·복제본 수: 확인 필요 / 서브넷 그룹: 프라이빗 서브넷 2a·2c |
| 스키마 | Flyway 관리, Hibernate `validate` |

### 2-6. 배포·설정

| 리소스 | 설정 |
|---|---|
| ECR `swordmaster` | 수명 주기: 태그 없는 이미지 1일 후 만료, 최대 10개 유지 |
| Parameter Store `/swordmaster/prod/` | `IMAGE_TAG`, `JWT_SECRET`, `DB_HOST`, `DB_USERNAME`, `DB_PASSWORD`, `REDIS_HOST`, `GOOGLE_WEB_CLIENT_ID` |
| 파라미터 타입 | 각 String / SecureString 여부: 기존 계정 `ssm-names.txt`로 확인 후 동일하게 |
| OIDC 공급자 | `token.actions.githubusercontent.com`, 대상 `sts.amazonaws.com` |
| 배포 역할 | `github-actions-swordmaster-deploy` (정책은 14장) |
| 신뢰 정책 조건 | `StringEquals`, `sub` = `repo:upgrade-29@조직숫자ID/swordmaster-server@저장소숫자ID:ref:refs/heads/main` (main 전용) |
| GitHub Secret | `AWS_DEPLOY_ROLE_ARN` |
| 워크플로 | `.github/workflows/deploy.yml` |

### 2-7. 모니터링

| 리소스 | 설정 |
|---|---|

## 11. 이후 추가로 적용하려던 사항
- cloudfront + s3 (cdn) 을 적용하여 서버와 클라이언트 모두 같은 시트 데이터를 사용할 수 있도록 설정, 어드레서블도 이곳에서 관리.
cdn용 도메인은 cdn.upgrade-29.com 과 같이 
- cdn 적용사항을 서버의 CICD 과정에 포함시켜 서버 배포 중 최신화가 자동화되도록 설정
- simplebroker 방식을 바꾼다면 ec2를 다중 az 에 두어서 부하를 줄이는 설정이 필요하다. (ags 스케쥴링 참조)
- 만약 ssh 방식으로 rds , elasticashe 에 접근하는 바스티온이 보안상으로 문제가 된다면 ssm 으로만 접근하도록 변경
- 이번에 배포하기 전에 느낀 점은 테스트 용 ec2 를 하나 더 두는 것이 좋아보인다. 도메인을 하나 더 구매해서 테스트용으로 구축하는 것도 좋아보임. (도메인 구매 시 프리티어는 route53 을 이용못하니 가비아 추천)
- 이번에 급하게 배우고 하다보니 root 계정만을 사용하였는데 iam 권한의 사용자 계정으로 여러 팀원들이 aws를 관리하는 것이 좋아보인다.
- 루트 계정에 MFA 설정, 일상 작업은 IAM 사용자 또는 IAM Identity Center로 진행
- 이관 후 `JWT_SECRET` 교체 (전원 재로그인 공지와 함께)

## 13. 시작 템플릿의 사용자 데이터

```bash
#!/bin/bash
# swordmaster 시작 템플릿 dev 계정 버전 1 - 사용자 데이터 (기존 계정 v5에서 이관)
set -euo pipefail
exec >> /var/log/swordmaster-init.log 2>&1
echo "[init] start $(date -u)"

REGION=ap-northeast-2
P=/swordmaster/prod
REPO=swordmaster

# 실패하면 10초 간격으로 최대 5번 다시 시도
retry() {
  local n=0
  until "$@"; do
    n=$((n+1))
    if [ "$n" -ge 5 ]; then echo "[init] FAILED: $*" >&2; return 1; fi
    echo "[init] retry $n: $1" >&2
    sleep 10
  done
}

# 1) Docker 설치 및 시작
retry dnf install -y docker
systemctl enable --now docker

# 2) Parameter Store에서 설정값 읽기
getp() { aws ssm get-parameter --name "$P/$1" --with-decryption --region "$REGION" --query Parameter.Value --output text; }
TAG=$(retry getp IMAGE_TAG)
JWT_SECRET=$(retry getp JWT_SECRET)
DB_HOST=$(retry getp DB_HOST)
DB_USERNAME=$(retry getp DB_USERNAME)
DB_PASSWORD=$(retry getp DB_PASSWORD)
REDIS_HOST=$(retry getp REDIS_HOST)
GOOGLE_WEB_CLIENT_ID=$(retry getp GOOGLE_WEB_CLIENT_ID)
echo "[init] tag=$TAG len: JWT=${#JWT_SECRET} DBU=${#DB_USERNAME} DBP=${#DB_PASSWORD} REDIS=${#REDIS_HOST} GOOGLE=${#GOOGLE_WEB_CLIENT_ID}"

# 3) ECR 로그인 및 이미지 받기 (계정 ID는 실행 중인 계정에서 자동 조회)
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
REGISTRY="$ACCOUNT_ID.dkr.ecr.$REGION.amazonaws.com"
retry bash -c "aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin $REGISTRY"
retry docker pull "$REGISTRY/$REPO:$TAG"

# 3-1) 인스턴스 ID 조회 (로그 스트림 이름으로 사용)
IMDS_TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
INSTANCE_ID=$(curl -s -H "X-aws-ec2-metadata-token: $IMDS_TOKEN" http://169.254.169.254/latest/meta-data/instance-id)
echo "[init] instance=$INSTANCE_ID"

# 4) 컨테이너 실행
docker rm -f swordmaster 2>/dev/null || true
docker run -d --name swordmaster \
  -p 8080:8080 \
  --restart unless-stopped \
  --log-driver awslogs \
  --log-opt awslogs-region="$REGION" \
  --log-opt awslogs-group=/swordmaster/prod/app \
  --log-opt awslogs-stream="$INSTANCE_ID" \
  --log-opt mode=non-blocking \
  --log-opt max-buffer-size=4m \
  -e SPRING_PROFILES_ACTIVE=prod \
  -e JWT_SECRET="$JWT_SECRET" \
  -e DB_HOST="$DB_HOST" \
  -e DB_USERNAME="$DB_USERNAME" \
  -e DB_PASSWORD="$DB_PASSWORD" \
  -e REDIS_HOST="$REDIS_HOST" \
  -e GOOGLE_WEB_CLIENT_ID="$GOOGLE_WEB_CLIENT_ID" \
  "$REGISTRY/$REPO:$TAG"

echo "[init] done tag=$TAG $(date -u)"
```
