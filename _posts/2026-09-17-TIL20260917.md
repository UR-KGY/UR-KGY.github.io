## 1. 인덱스 정리 

인덱스는 특정 컬럼(들)을 기준으로 조회 성능을 높이기 위한 자료구조다. `WHERE`, `JOIN`, `ORDER BY`에 자주 쓰이는 컬럼에 인덱스를 걸어두면, 전체 테이블을 훑지 않고 바로 해당 데이터 위치를 찾아갈 수 있다.

### 풀 테이블 스캔 문제

```sql
SELECT * FROM member WHERE email = 'a@naver.com'
```

이렇게 실행하면 DB는 이 행이 테이블 어디에 있는지 미리 알 방법이 없어, 첫 번째부터 마지막 행까지 다 읽으며 조건이 되는 `email` 값을 비교한다. 데이터가 적다면 괜찮지만 100만 건이면 100만 번 비교하듯, 데이터가 많을수록 느려진다. 이걸 **풀 테이블 스캔**이라고 한다.

### 인덱스의 구조

인덱스는 책에서 특정 키워드를 기준으로 내용을 찾는 색인처럼, 특정 컬럼을 정렬된 트리 구조로 **별도 저장**한다.

```
[원본 테이블 chat] — 그대로, 정렬 안 됨
┌────┬──────────┬────────────┬─────────┐
│ id │ world_id │ created_at │ message │
├────┼──────────┼────────────┼─────────┤
│ 1  │    3     │   10:00    │  ...    │
│ 2  │    1     │   09:00    │  ...    │
│ 3  │    2     │   08:30    │  ...    │
│ 4  │    1     │   09:10    │  ...    │
└────┴──────────┴────────────┴─────────┘

[별도로 저장되는 인덱스 구조물] — 여기만 정렬됨
┌──────────┬────────────┬──────────────────┐
│ world_id │ created_at │ 원본 위치(포인터)  │
├──────────┼────────────┼──────────────────┤
│    1     │   09:00    │  → id=2 위치       │
│    1     │   09:10    │  → id=4 위치       │
│    2     │   08:30    │  → id=3 위치       │
│    3     │   10:00    │  → id=1 위치       │
└──────────┴────────────┴──────────────────┘
```

### SQL 문법

```sql
CREATE INDEX idx_member_email ON member (email);
```

- `CREATE INDEX` : 인덱스를 새로 만들겠다
- `idx_member_email` : 새로 만들 인덱스에 붙이는 명칭
- `ON` : 어느 테이블에 대해 만들 것인가
- `member` : 인덱스를 걸 대상인 테이블 이름
- `(email)` : 인덱스로 만들 컬럼(들). 여러 개면 `(email, age)`처럼 콤마로 나열

### JPA에서의 인덱스 선언

```java
@Table(name = "member",
       indexes = @Index(name = "idx_member_email", columnList = "email"))
```

기준이 되는 컬럼이 두 개인 복합 인덱스도 같은 방식이다.

```sql
CREATE INDEX idx_chat_world_created_at ON chat_messages(world_id, created_at);
```

```java
@Table(name = "chat_messages",
       indexes = @Index(name = "idx_chat_world_created_at", columnList = "world_id,created_at"))
```

## 2. 트러블슈팅 노트

### 오류 1 — 빈 JSON 요청인데 400이 아니라 201이 나옴

**증상**

```java
@Test
void rejectsMissingNicknameBeforeCallingService() throws Exception {
    mockMvc.perform(post("/players")
                    .contentType(MediaType.APPLICATION_JSON)
                    .content("{}"))
            .andExpect(status().isBadRequest());

    verifyNoInteractions(playerService);
}
```

테스트 코드가 기대하는 상태코드는 `400`인데, 실제로는 `201`이 나왔다.

**원인**

다른 테스트 코드들과 비교해봤을 때, 아예 빈 JSON 구조(`{}`)인 경우 — 즉 완전히 아무것도 안 넣었을 때의 처리가 되지 않은 상태였다. 요청 DTO 필드에 검증 어노테이션이 없어서, 값이 없어도 그냥 통과되어 서비스 로직까지 실행되어 버린 것.

**해결**

요청 DTO 필드에 `@NotBlank` 어노테이션을 붙여서 해결.

```java
@NotBlank
private String nickname;
```

`@Valid`와 함께 검증을 강제하면, 빈 값이 들어왔을 때 컨트롤러 진입 전에 `400 Bad Request`로 걸러지고, `playerService`까지 호출이 가지 않는다(`verifyNoInteractions` 통과).

### 오류 2 — null 참조 (NullPointerException)

**배경**

이번 과제의 핸드셰이크 인터셉터에서는, 검증에 실패한 경우에도 `return false`가 아니라 `return true`로 하되, `attributes`에 에러가 발생했다는 정보를 담아서 넘기는 패턴을 쓰고 있다.

**원인**

```java
String nickname = readNickname(request);
if (nickname == null || nickname.isBlank()) {
    attributes.put(ATTR_ERROR_CODE, 4000);
    return true;
}

Player player = playerRepository.findByNickname(nickname).orElse(null);
if (player == null) {
    attributes.put(ATTR_ERROR_CODE, 4000);
    return true;
}
```

`nickname`의 데이터는 정상적으로 들어있으나 `player`는 `null`인 상태에서 `player` 안의 `nickname`을 꺼내려고 하여 발생한 문제였다.

```java
attributes.put(ATTR_NICKNAME, player.getNickname());  // player가 null인데 접근함
```

즉 "null인 경우를 배제하는 조건문(`if (player == null) { ...; return true; }`)"이 먼저 있었어야 하는데, 그 분기 처리 없이 `player`를 바로 참조해버린 것이 문제.


`null` 체크와 실제 사용(`player.getNickname()`) 사이에 다른 로직이 끼어들면서 체크가 누락되는 것을 주의할 것


### 오류3. 스트림 정렬 실수 

```java
List<ChatMessage> latest = recent.stream()
        .sorted(Comparator.comparing(ChatMessage::getCreatedAt))
        .sorted(Comparator.comparing(ChatMessage::getId))   // 앞의 정렬을 덮어씀
        .toList();

return recent.stream()   // ← latest가 아니라 recent를 반환 (버그)
        .map(chat -> new ChatMessageResponse(...))
        .toList();
```

- `.sorted()`를 두 번 연달아 호출하면 두 번째 호출이 첫 번째 정렬을 덮어씀 → 여러 기준으로 정렬하려면 `thenComparing` 사용.
- **가장 핵심적인 버그**: 정렬 결과(`latest`)를 계산해놓고 `return`문에서는 원본(`recent`)을 그대로 반환 → 실제로는 최신순 그대로 응답됨

## 3. 기타 개념 정리

### Mock

가짜 객체를 만들어 테스트하는 용도. 실제 DB/외부 의존성 없이 원하는 상황을 인위적으로 재현할 수 있다.

### `Supplier<T> action`이 매개변수로 올 때

메서드 시그니처가 `Supplier<T>`를 파라미터로 받는다면, 그 메서드를 호출하는 쪽(구현부)에서는 **람다식을 인자로 넣어주어야** 한다.

```java
public <T> T duringCreation(Supplier<T> action) { ... }

// 호출하는 쪽
duringCreation(() -> playerRepository.save(new Player(...)));
```

### 채팅 메시지는 최신순으로 가져오되, 왜 오래된 순으로 다시 정렬하는가

- DB에서 오래된 순으로 가져오면(ASC + LIMIT), 정작 필요한 **최신 메시지가 잘려서 빠질 위험**이 있다.
- 그래서 DB 조회 자체는 **최신순(DESC) + LIMIT**으로 "최근 N개"를 정확히 잘라내고, 화면에 보여줄 때는 다시 오래된 순으로 정렬한다.
- 카카오톡을 생각해보면, 오래된 메시지는 위에 남고 최신 메시지가 아래에 쌓이는 것을 알 수 있다 — 이 UI 순서를 맞추기 위한 재정렬이다.

### 왜 `HandshakeInterceptor`에서 `return false` 대신 `return true` + `attributes.put(ATTR_ERROR_CODE, ...)`를 쓰는가

- `return false`를 하면 핸드셰이크 자체가 불가능해진다(웹소켓 연결 자체가 성립 안 됨). 이 경우 클라이언트 쪽에서는 왜 실패했는지 오류 파악이 힘들다(정보가 전달되지 않음).
- 그래서 `return true`로 일단 핸드셰이크를 통과시킨 뒤, 클라이언트에게 오류 정보(에러코드)를 넘겨주고 나서 연결을 끊는 패턴을 쓰는 것으로 이해했다.

### `onclose`란 무엇인가

핸드셰이크가 아예 실패하면, `onclose` 같은 이벤트 핸들러조차 의미 있는 정보를 담지 못한 채로 그냥 닫혀버린다.

`onclose`는 브라우저의 `WebSocket` 객체가 기본으로 제공하는 이벤트 핸들러 중 하나다. 웹소켓은 보통 다음 네 가지 이벤트를 통해 상태를 알려준다.

| 이벤트 | 발생 시점 |
|---|---|
| `onopen` | 연결이 성공적으로 수립됐을 때 |
| `onmessage` | 서버로부터 메시지를 받았을 때 |
| `onerror` | 오류가 발생했을 때 (정보가 거의 없음) |
| `onclose` | 연결이 종료됐을 때 (`code`, `reason` 포함) |

`return true` + 명시적 `close()` 패턴을 쓰는 이유가 바로 여기 있다: 핸드셰이크 단계에서 거부하면 `onclose`가 사유를 담지 못하지만, 연결을 성립시킨 뒤 정식 Close 프레임으로 닫으면 `onclose`의 
`code`/`reason`에 정확한 사유가 담겨 클라이언트에 전달된다.


## 4. 다시 복습

### 1. 페이징 / 파라미터
- 이전에 학습했던 페이징을 처음으로 사용하는 예제가 나왔다. 

`PageRequest`

```java
PageRequest.of(0, capped)   // 0번째 페이지(0부터 시작), 최대 capped개
```

- 리포지토리 메서드 이름으로 정렬 조건을 정하고, `Pageable`로 "몇 개까지만 가져올지"(LIMIT)를 지정.
- 반환 타입이 `List`면 전체 개수 등 메타데이터 없이 결과 목록만 반환(가벼움), `Page`면 전체 개수/페이지 수 등을 함께 제공(추가 COUNT 쿼리 발생).


### 2. `@RequestParam` vs `@PathVariable`

| | PathVariable | RequestParam |
|---|---|---|
| 위치 | URL 경로 | 쿼리스트링 |
| 용도 | 자원 식별(필수) | 검색조건/옵션 |
| 기본값 | 개념 없음(경로 자체가 안 맞으면 매핑 안 됨) | `defaultValue` 속성으로 지정 가능 |

```java
@RequestParam(defaultValue = "0") int page
@RequestParam(required = false) String nickname
```


### 3. WebSocket 흐름
- 전체 구조

```
[레지스트리]  ← 서버 시작 시 1회, "이 URL엔 이 핸들러+인터셉터"를 배선(설정 단계, 런타임 흐름 아님)
      ↓
[인터셉터]    ← 연결 시도마다 1회, HTTP 단계에서 검증(토큰, DB 조회 등)
      ↓ (통과 시 핸드셰이크 성공)
[핸들러]      ← 연결 유지 동안 반복 실행(연결됨/메시지옴/끊김)
      ↓
[서비스]      ← 핸들러가 받은 메시지의 실제 비즈니스 로직 처리
```
