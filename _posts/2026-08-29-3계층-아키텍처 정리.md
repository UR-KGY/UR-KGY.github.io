# 3계층 아키텍처(3-Layer Architecture) 정리

Book API 과제에서 잠깐 언급했던 "Controller - Service - Repository" 구조를 따로 떼어서 더 자세히 정리한다. 스프링 백엔드 프로젝트 대부분이 이 구조를 기본 골격으로 삼는다.

## 1. 3계층이란

애플리케이션의 책임을 **세 개의 층(layer)**으로 나누는 설계 방식이다. 각 층은 "자기 일"만 하고, 다른 층의 일에는 관여하지 않는다.

| 계층 | 역할 | 스프링에서의 이름 |
|---|---|---|
| 프레젠테이션 계층 | 클라이언트의 요청을 받고, 응답을 돌려준다 | Controller |
| 비즈니스 계층 | 실제 로직(검증, 가공, 처리 순서 결정)을 수행한다 | Service |
| 퍼시스턴스(영속) 계층 | 데이터 저장소에 실제로 접근한다 | Repository |

```
클라이언트
   ↓ HTTP 요청
Controller   ← 요청을 받고 응답을 반환 (창구 역할)
   ↓
Service      ← 비즈니스 로직 수행 (판단·검증·가공)
   ↓
Repository   ← 저장소(DB, Map 등)에 실제 접근
   ↓
데이터 저장소(DB / Map / 파일 등)
```

## 2. 각 계층이 절대 하지 말아야 할 일

계층을 나누는 진짜 의미는 "무엇을 하는가"보다 **"무엇을 안 하는가"**에 있다.

- **Controller는 비즈니스 로직을 담지 않는다.** "이 이름이 2자 이상인가?" 같은 판단을 Controller가 직접 하면 안 된다. Controller가 하는 일은 딱 두 가지뿐이다 — 요청(DTO)을 받아서 Service에 넘기고, Service가 돌려준 결과를 응답(DTO)으로 포장해서 반환하는 것.
- **Service는 HTTP나 DB의 구체적인 기술을 몰라야 한다.** Service 코드 안에 `HttpServletRequest`나 SQL 문자열이 직접 등장하면 계층이 섞인 것이다. Service는 "무엇을 해야 하는가"(도메인 로직)만 알고, "어떻게 저장하는가"는 Repository에 위임한다.
- **Repository는 판단을 하지 않는다.** "이 책이 이미 등록됐으면 거부한다" 같은 판단은 Repository의 일이 아니다. Repository는 그냥 "저장해라", "찾아와라" 같은 지시를 받아 데이터 저장소에 접근만 한다.

```java
// Controller: 요청/응답 창구
@RestController
@RequiredArgsConstructor
public class BookController {
    private final BookService bookService;

    @PostMapping("/register")
    public BookResponseDto registerBook(@RequestBody BookRequestDto requestDto) {
        return bookService.register(requestDto); // 판단은 Service에 전부 위임
    }
}

// Service: 비즈니스 로직 (검증 + 처리 순서 결정)
@Service
@RequiredArgsConstructor
public class BookService {
    private final BookRepository bookRepository;

    public BookResponseDto register(BookRequestDto requestDto) {
        if (bookRepository.existsByTitle(requestDto.getTitle())) {
            throw new IllegalStateException("이미 등록된 책입니다."); // 판단은 여기서
        }
        Book book = new Book(requestDto.getTitle(), requestDto.getComment());
        Book saved = bookRepository.save(book); // 저장은 Repository에 위임
        return new BookResponseDto(saved.getId(), saved.getTitle(), saved.getComment());
    }
}

// Repository: 저장소 접근만
@Repository
public class BookRepository {
    private final Map<Long, Book> store = new HashMap<>();

    public Book save(Book book) { store.put(book.getId(), book); return book; }
    public boolean existsByTitle(String title) {
        return store.values().stream().anyMatch(b -> b.getTitle().equals(title));
    }
}
```

## 3. 의존 방향은 한 방향으로만 흐른다

Controller는 Service를 알고, Service는 Repository를 알지만, **그 반대는 절대 안 된다.** Repository가 Service를 호출하거나, Service가 Controller를 호출하는 일은 없다.

```
Controller → Service → Repository   (O, 이 방향으로만 의존)
Repository → Service                (X, 거꾸로는 안 됨)
```

이게 가능한 이유가 지난번에 정리했던 `@RequiredArgsConstructor` + 생성자 주입이다. Controller는 Service를, Service는 Repository를 필드로 갖고 있고(`private final`), 스프링이 이 의존관계를 자동으로 엮어(주입해)준다.

## 4. 왜 굳이 나누는가

- **역할이 명확해져서 코드를 어디서 찾을지 헷갈리지 않는다.** "이 API가 어떤 순서로 처리되지?"는 Service만 보면 되고, "DB 쿼리가 어떻게 됐지?"는 Repository만 보면 된다.
- **저장소를 바꿔도 Service/Controller는 안 바뀐다.** 지금은 `Map`으로 저장하지만 나중에 MySQL로 바꿔도, Repository 내부 구현만 JdbcTemplate 등으로 교체하면 되고 Service의 비즈니스 로직 코드는 그대로 재사용된다.
- **테스트하기 쉬워진다.** Service의 로직만 테스트하고 싶으면 Repository를 가짜(mock)로 바꿔치기해서, 실제 DB 없이도 "이미 등록된 책이면 거부하는지"를 검증할 수 있다.

## 5. 예외: 작은 과제에서는 Service를 생략해도 된다

Map 하나로 데이터를 다루고, 별다른 검증·가공 로직이 없는 아주 작은 과제라면 Controller가 Repository(Map)를 직접 다뤄도 기능적으로는 문제없다. 다만 "이미 등록된 책이면 거부한다"처럼 판단 로직이 하나라도 생기는 순간, 그걸 Controller에 두면 위에서 말한 "역할 분리"가 깨지기 시작한다. 그래서 처음부터 Service를 만들어두는 습관을 들이는 게 나중에 로직이 복잡해졌을 때 코드를 다시 갈아엎지 않아도 되는 지름길이다.

## 한 줄 정리

- 3계층은 Controller(요청·응답 창구) - Service(비즈니스 로직·판단) - Repository(저장소 접근)로 책임을 나누는 구조다.
- 각 계층은 "자기 일만 하고 남의 일에 관여하지 않는다"는 게 핵심이다 — Controller에 판단 로직이, Repository에 검증 로직이 들어가면 계층이 섞인 것이다.
- 의존은 Controller → Service → Repository 한 방향으로만 흐르고, 이 연결은 생성자 주입(`@RequiredArgsConstructor`)으로 스프링이 자동으로 엮어준다.
- 계층을 나누면 저장소 교체·테스트가 쉬워지지만, 로직이 거의 없는 아주 작은 과제에서는 Service를 생략해도 기능상 문제는 없다.
