## 1. 개념 정리

| 용어 | 설명 |
|---|---|
| **AWS** | 서버를 클라우드 형식으로 지원해 주는 서비스. 전 세계에 데이터 센터를 두고 있음 |
| **Account** | AWS 서비스를 사용하기 위한 기본 단위. 결제와 보안, 리소스 관리의 경계 |
| **Region** | 지리적 영역 (서울은 `ap-northeast-2`) |
| **Availability Zone (AZ)** | 리전 안에 있는 개별 데이터 센터(들)의 묶음 |
| **루트 사용자** | 해당 Account의 모든 권한을 가진 사용자 (가입할 때 쓴 이메일로 로그인) |
| **IAM** | 누가 어떤 AWS 리소스에 무엇을 할 수 있는지 정하는 권한 관리 서비스 |
| **IAM 사용자** | IAM으로 만든 사용자. 허가된 기능에만 접근 가능 |
| **Key Pair** | EC2에 SSH로 접속할 때 쓰는 공개키/개인키 한 쌍 (`.pem` 파일이 개인키) |

### Account

- 1인 1계정 또는 회사에서 여러 계정을 운용한다.
- 콘솔은 **한 번에 하나의 Account**(그리고 하나의 리전)만 조작한다.

> **보완**: Account는 로그인하는 "사람"이 아니라 리소스와 결제를 담는 **공간(12자리 계정 ID)** 이다.
> 그 공간 안에 로그인하는 주체가 **루트 사용자**와 **IAM 사용자**다. 하나의 Account 안에 로그인할 수 있는 사용자가 여러 명 있을 수 있다.

### Region

- 리전마다 독립적이다.
- 서울에서 만든 EC2는 버지니아 같은 다른 리전에서는 보이지 않고, 데이터도 서울 리전 안에만 저장된다.
- 콘솔에서 인스턴스가 안 보이면 **오른쪽 위 리전 선택**을 먼저 확인한다.

### Availability Zone (AZ)

- 데이터 센터를 물리적으로 여러 곳에 분산시킨 이유는 **고가용성** 때문이다.
- 하나의 데이터 센터에 장애가 생겨도 다른 데이터 센터에서 서비스를 이어서 유지할 수 있다.

### Key Pair

- **공개키**는 EC2 안의 `~/.ssh/authorized_keys`에 저장된다. (자물쇠)
- **개인키(`.pem`)** 는 내 PC에 보관한다. (열쇠)
- AWS는 개인키를 보관하지 않으므로 **생성할 때 한 번만 다운로드**할 수 있다.

> **보완**: `.pem` 파일은 특정 컴퓨터에 묶여 있지 않다. 다른 PC로 복사해도 사용할 수 있다.
> 단, USB(FAT32/exFAT)에서 바로 쓰면 권한 문제로 실패하므로 PC로 복사한 뒤 `chmod 400`을 해야 한다.
> 키를 잃어버려도 인스턴스는 그대로 남아 있으며, EC2 Instance Connect 등으로 접속해 새 공개키를 추가하면 된다.

## 2. AWS 공동 책임 모델

AWS는 보안 책임을 **고객 책임**과 **AWS 책임**으로 나눈다.
사용자가 설정한 것은 사용자 책임이고, AWS가 관리하는 영역은 AWS 책임이다.

| 구분 | 범위 | 예시 |
|---|---|---|
| **고객 책임** | 클라우드 **"안에서"** 내가 만든 것의 보안 | 데이터 암호화 및 보호, IAM 사용자/권한 관리, 보안 그룹 설정, 운영체제 패치, 애플리케이션 보안 |
| **AWS 책임** | 클라우드 **"자체"** 인프라의 보안 | 데이터 센터 물리적 보안, 네트워크 인프라, 관리형 서비스 기본 보안 |

### 서비스 유형별 책임 범위

| 유형 | 빌리는 범위 | 책임 |
|---|---|---|
| **IaaS** | 인프라만 | 거의 모든 것이 사용자 책임 (**우리가 사용할 것**, 예: EC2) |
| **PaaS** | 플랫폼까지 | IaaS보다 AWS 책임이 늘어남 (예: RDS, ElastiCache) |
| **SaaS** | 소프트웨어까지 | 거의 모든 것을 AWS가 책임 |

## 3. 예산 관리 (Budget)

요금 폭탄을 방지하기 위해 반드시 설정한다.

### 알림 설정 방법

1. AWS 콘솔 → **Billing** → **Budgets**
2. **Create a budget** 클릭
3. **Cost budget** 선택
4. 월 예산: `$30` (필요할 때마다 늘리면 된다)
5. 알림 임계값: `80%`, `100%`
6. 알림을 받을 이메일 주소 입력
7. 생성 완료

### 무료 플랜

- 최대 6개월간 제공된 크레딧으로 요금을 대체할 수 있다. (기본 100, 미션 달성 시 추가)
- 무료 플랜은 **동시에 만들 수 있는 인스턴스 수가 제한**된다.

> **보완**: `You reached the maximum number of instances available with free plan accounts.` 오류가 나면
> 안 쓰는 인스턴스(중지 상태 포함)를 **종료(Terminate)** 해서 정리한다. 다른 리전에 남은 리소스도 확인한다.
> 유료 플랜으로 업그레이드하면 무료 플랜으로 되돌릴 수 없다.

## 4. IAM

**정의**: 누가 어떤 AWS 리소스에 무엇을 할 수 있는지를 정하고 통제하는 접근 제어 시스템

### 권한 판단 기준

| 기준 | 질문 |
|---|---|
| 누가 (Who) | 이 요청은 인증되었는가? |
| 무엇을 (What) | 어떤 작업을 하려고 하는가? |
| 할 수 있는가 (Can) | 그 작업을 할 권한이 있는가? |

### 4-1. User

**사람**이 AWS에 접근할 때 사용하는 계정

**사용 예**
- 개발자가 콘솔에 로그인하는 경우
- 관리자가 CLI로 AWS를 관리하는 경우
- 사람이 직접 AWS를 조작하는 경우

**핵심 특징**: 영구적인 자격 증명을 가진다.

#### 자격 증명

본인임을 증명하는 정보(비밀번호, 키 등)

| 종류 | 용도 |
|---|---|
| 비밀번호 | AWS 콘솔 로그인 |
| Access Key | API/CLI 접근 (`Access Key ID` = 아이디, `Secret Access Key` = 비밀번호) |

**특징**
- 한 번 생성하면 삭제하기 전까지 유효하다. (만료 없음, `AKIA`로 시작)
- 1인 1계정 원칙을 권장한다.

| 예시 사용자 | 권한 |
|---|---|
| 개발자1 | 개발 관련 권한 |
| 관리자2 | 관리자 권한 |
| 프론트 개발자3 | 백엔드 내용 읽기 권한만 (실무에서는 백엔드가 프론트까지 배포하는 경우가 많음) |

**Access Key의 문제**
- 비밀번호와 같은데 영구적이라 **유출되면 큰 사고**로 이어진다.
- 관리가 어렵다.
- 그래서 **서버와 자동화에서는 User 대신 Role 사용을 권장**한다.

#### User 생성 과정 (S3 접근 권한 예시)

**① IAM Policy 생성** (IAM → 정책 → 정책 생성)

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": ["s3:PutObject", "s3:GetObject"],
            "Resource": "arn:aws:s3:::{버킷이름}/{버킷 내 폴더 경로}/*"
        }
    ]
}
```

- 마지막 `*`는 해당 폴더 아래 **모든 파일**을 뜻하는 와일드카드다. (하위 폴더 포함)
- 폴더 경로 뒤의 `/`를 빼먹으면(`uploads*`) `uploads-old/` 같은 다른 경로까지 허용되니 주의한다.

**② IAM User 생성** (IAM → 사용자 → 사용자 생성)
- 사용자 이름 설정
- **직접 정책 연결** 선택 후 ①에서 만든 정책 선택
- 사용자와 권한 확인 후 생성

**③ Access Key 발급**
- ②에서 만든 사용자 클릭 → **액세스 키 만들기**
- 사용 사례는 용도에 맞게 선택 (강의에서는 **로컬 코드**)

**④ Access Key 저장**
- 액세스 키와 비밀 액세스 키를 따로 저장한다.
- 이 화면을 벗어나면 **다시는 볼 수 없으니** 복사하거나 `.csv`로 다운로드한다.

**⑤ Spring Boot에서 사용**

```properties
# application-local.properties
spring.cloud.aws.credentials.access-key=AKIA...
spring.cloud.aws.credentials.secret-key=+JIr...
```

- 민감한 정보이므로 `-local` 파일은 **`.gitignore`로 제외**해서 로컬에서만 쓰거나, 하드코딩 대신 Parameter Store를 사용한다.

> **보완**: 더 안전한 방법은 키를 파일에 적지 않는 것이다.
> `aws configure`로 `~/.aws/credentials`에 저장하면 properties에서 키 두 줄을 지워도 SDK가 자동으로 찾는다.
> SDK가 자격 증명을 찾는 순서: properties → 환경변수 → `~/.aws/credentials` → **EC2 IAM Role**
> 그래서 **로컬은 Access Key, EC2는 Role**을 쓰는 것이 표준 패턴이다.

### 4-2. Role

**서버/서비스**에 권한을 부여할 때 사용한다. 서버나 서비스가 다른 AWS 서비스에 접근할 때 쓰는 권한이다.

**사용 예**
- EC2 서버가 S3에 파일을 업로드할 때
- GitHub Actions가 AWS에 배포할 때
- 서버/자동화 시스템이 AWS를 사용하는 모든 경우

**핵심**: 임시로 빌려 쓰는 권한 세트

#### User와 Role 비교

| User | Role |
|---|---|
| 사람용 | 서버/서비스용 |
| 영구 자격 증명 보유 (비밀번호, Access Key) | 자격 증명 없음 (필요할 때 임시 발급, `ASIA`로 시작) |
| 직접 로그인 가능 | 직접 로그인 불가 (권한을 빌려서 사용) |
| 만료 없음 | 자동 만료 |
| 비유: **집 열쇠** | 비유: **호텔 카드키** (반납) |

### 4-3. Policy

어떤 작업을 허용/거부할지 정의한다.
단독으로 쓰이지 않고 **User나 Role에 연결**하는 형태다.

- `AWS XXX 서비스 읽기` Policy를 `kim-dev` User에 연결 → kim-dev가 XXX 서비스 읽기 가능
- `AWS XXX 서비스 읽기` Policy를 Role에 연결 → 그 Role을 가진 서버가 XXX 서비스 읽기 가능

#### 구조

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}
```

| 항목 | 의미 |
|---|---|
| `Version` | 정책 문법 버전 (고정값) |
| `Effect` | 허용(`Allow`)인가 거부(`Deny`)인가. Deny가 Allow보다 우선 |
| `Action` | 어떤 동작을 (AWS **API 작업 이름**, 예: `s3:PutObject`) |
| `Resource` | 어떤 대상에 (**ARN**) |
| `Condition` | (선택) 어떤 조건일 때 |

#### ARN (Amazon Resource Name)

AWS 리소스의 고유 식별자 (사람으로 치면 주민등록번호). 보통 콘솔에서 복사해서 쓰므로 외울 필요는 없다.

```
arn : aws : s3 : (리전) : (계정ID) : camp-health-kgy-files/uploads/*
                   └ S3는 버킷 이름이 전 세계에서 유일하므로 리전, 계정 ID를 비움 (:::)
```

| 서비스 | ARN 예시 |
|---|---|
| S3 버킷 | `arn:aws:s3:::my-bucket` |
| S3 파일 | `arn:aws:s3:::my-bucket/uploads/*` |
| EC2 | `arn:aws:ec2:ap-northeast-2:123456789012:instance/i-0abc1234` |
| Parameter Store | `arn:aws:ssm:ap-northeast-2:123456789012:parameter/myapp/prod/*` |

> **보완**: 버킷 자체와 버킷 안 파일의 ARN은 다르다.
> `s3:ListBucket`은 버킷 ARN(`/*` 없음), `s3:GetObject`/`PutObject`는 파일 ARN(`/*` 있음)에 걸어야 한다.
> ARN 안의 하이픈(`-`)은 구분자가 아니라 이름의 일부다. 구분자는 `:`과 `/`뿐이다.

#### AWS 관리형 Policy

| Policy 이름 | 설명 | 위험도 |
|---|---|---|
| `AdministratorAccess` | 모든 권한 | 🔴 매우 높음 |
| `AmazonS3FullAccess` | S3 전체 권한 | 🟠 중간 |
| `AmazonS3ReadOnlyAccess` | S3 읽기만 | 🟢 낮음 |
| `AmazonEC2FullAccess` | EC2 전체 권한 | 🟠 중간 |

미리 만들어진 Policy나 직접 만든 Policy를 User나 Role에 연결해서 사용한다.

### 4-4. 보안 원칙

**1. 최소 권한 원칙**: 꼭 필요한 권한만 부여하고, 그 외에는 모두 거부한다.
- `AdministratorAccess` 같은 광범위한 Policy 부여를 피한다.
- 처음에는 아무 권한도 주지 않고, 필요에 따라 하나씩 추가한다.
- **IAM Access Analyzer**로 사용하지 않는 과도한 권한을 찾아서 제거한다.

**2. 루트 사용자 보호**: 모든 권한을 가졌으므로 조심해서 사용한다.
- 루트 사용자의 **Access Key는 만들지 않거나 삭제**한다.
- 계정 생성, 결제 정보 수정 등 특수한 경우 외에는 **일상 업무에 사용하지 않는다.**
- **MFA**를 설정한다.

> **보완**: "root"라는 이름은 세 곳에서 쓰이며 서로 관계가 없다.
> - **AWS 루트 사용자**: AWS 계정의 주인
> - **리눅스 root**: EC2 안의 최고 관리자 (`sudo`로 권한을 빌림)
> - **ec2-user**: SSH로 로그인할 때 쓰는 기본 리눅스 사용자

## 5. 보안 그룹

**정의**: AWS 리소스에 대한 네트워크 트래픽을 제어하는 가상 방화벽

- **리소스마다 개별로** 적용한다. (EC2, RDS, ElastiCache 각각에 붙임)
- 보안 그룹은 VPC에 소속되며, **같은 VPC 안에서만** 사용할 수 있다.
- VPC 하나에 여러 개를 만들고, 하나의 보안 그룹을 여러 리소스가 공유할 수도 있다.

### 규칙

**1. Whitelist 방식**
- 규칙이 하나도 없으면 **모두 차단**이 기본값이다.
- 허용한 포트 외의 접근은 모두 차단된다.

**2. Stateful (상태 저장)**
- 인바운드로 허용된 요청에 대한 **응답**은 아웃바운드 규칙과 관계없이 자동으로 나간다.
- 그래서 보통 **인바운드만 엄격하게** 관리하고, 아웃바운드는 기본값(모든 트래픽 허용)으로 둔다.

| 방향 | 의미 | 예시 |
|---|---|---|
| 인바운드 | 밖 → 리소스로 **들어오는** 새 요청 | 내 PC가 SSH 접속, 사용자가 API 호출 |
| 아웃바운드 | 리소스 → 밖으로 **나가는** 새 요청 | EC2가 RDS 조회, S3 업로드, 패키지 설치 |

> **보완**: 아웃바운드를 `SSH 22`만 허용으로 바꾸면 EC2 → RDS(3306), Redis(6379), S3(443) 요청이 모두 막힌다.
> 아웃바운드는 **모든 트래픽 → 0.0.0.0/0** 을 유지한다.

### CIDR 읽는 법

| CIDR | 의미 |
|---|---|
| `211.10.20.30/32` | IP **딱 1개** (내 IP) |
| `10.0.0.0/16` | `10.0.x.x` 65,536개 (VPC 내부) |
| `0.0.0.0/0` | **모든 IPv4 주소** (보안 그룹에서는 "모두 허용") |

### 실습 구성 예시

```
인터넷(누구나) ──8080──▶ [webcraft-app]  EC2 (Spring 서버)
내 PC(내 IP)  ──22────▶      │
                             │ 3306 (MySQL), 6379 (Redis)
                             ▼
                        [webcraft-data]  RDS + ElastiCache
```

| 보안 그룹 | 붙일 곳 | 인바운드 규칙 |
|---|---|---|
| `webcraft-app` | EC2 | SSH 22 ← **내 IP** / TCP 8080 ← `0.0.0.0/0` |
| `webcraft-data` | RDS, ElastiCache | 3306 ← `webcraft-app` / 6379 ← `webcraft-app` |

- 소스를 IP가 아닌 **다른 보안 그룹**으로 지정하면, EC2의 IP가 바뀌어도 규칙을 고칠 필요가 없다.
- 보안 그룹은 **요청을 받는 쪽**에 붙인다. EC2에 `webcraft-data`를 붙일 필요는 없다.
- RDS, ElastiCache는 SSH로 접속하는 서비스가 아니므로 22번 규칙이 필요 없다.
- SSH를 내 IP로 제한하는 이유: 키가 유출되더라도 허용한 장소가 아니면 접속할 수 없게 하는 **이중 잠금**. (AWS 루트 사용자와는 무관)

## 6. VPC (Virtual Private Cloud)

**정의**: AWS 클라우드 안에 만드는 사설 네트워크. 다른 AWS 계정의 네트워크와 격리되어 있다.

```
AWS 클라우드
└── 리전 (서울)
    └── VPC (여러 개 생성 가능)
        └── 서브넷 (여러 개, 각각 하나의 AZ에 속함)
```

### IP 주소 설정

- **사설 IP 대역**: VPC 내부는 외부 인터넷과 직접 연결되지 않는 IP를 쓴다. (주로 `10.x.x.x`)
- **IP 크기 설정**: VPC를 만들 때 사용할 IP 개수를 정한다.
- 실습 표준값: **`10.0.0.0/16`** (약 65,000개의 IP)

### 6-1. Subnet

**정의**: VPC 네트워크를 관리하기 편하게 작게 쪼갠 구역

**규칙 1. 서브넷 = 1 가용 영역(AZ)**
- 하나의 서브넷이 여러 AZ에 걸칠 수 없다. (예: Subnet-A는 서울 A존에만 존재)
- 반대로 **AZ 하나에는 서브넷이 여러 개** 있을 수 있다.
- 리전에 AZ를 여러 개 두는 이유처럼, 서브넷을 여러 AZ에 나눠 두는 것도 **가용성 확보**를 위해서다.

**규칙 2. IP 쪼개기**
- VPC 전체 IP를 서브넷들이 나눠 가진다.
- 개수만큼 균일하게 나누지 않고 **지정한 CIDR 범위만큼만** 가져간다. 남는 공간은 비워 둘 수 있다.

```
VPC 10.0.0.0/16
├── public-a    10.0.1.0/24    256개
├── private-a   10.0.16.0/20   4,096개
├── db-a        10.0.100.0/28  16개
└── (나머지는 미할당)
```

> **보완**
> - 서브넷은 기본적으로 **사용자가 직접** 만든다. (기본 VPC와 "VPC 등" 마법사는 자동으로 만들어 줌)
> - 서브넷끼리 CIDR이 겹치면 안 되고, 만든 뒤에는 크기를 바꿀 수 없다.
> - 크기는 `/16`(최대) ~ `/28`(최소, 16개)이며, AWS가 서브넷마다 **5개 IP를 예약**한다. (`/24` = 실제 251개)

### 6-2. 라우팅 테이블 (Route Table)

**정의**: 네트워크 트래픽이 어디로 가야 하는지 알려 주는 표지판(규칙)
모든 서브넷은 반드시 하나의 라우팅 테이블과 연결되어야 한다.

| 경로 | 의미 |
|---|---|
| **Local** (내부 통신) | 목적지가 VPC 내부(`10.0.x.x`)라면 VPC 안에서 찾아서 보낸다. 삭제할 수 없으며, 같은 VPC 안에서는 서브넷이 달라도 통신할 수 있다. |
| **External** (외부 통신) | 목적지가 모르는 주소(`0.0.0.0/0`, 즉 인터넷)라면 인터넷 게이트웨이로 보낸다. **이 규칙의 유무가 Public/Private을 결정한다.** |

> **보완**: "별도 설정 없이 통신 가능"은 **라우팅** 관점이다. 실제로 연결되려면 받는 쪽 **보안 그룹**에서도 허용해야 한다.

### 6-3. 인터넷 게이트웨이 (IGW)

- VPC와 외부 인터넷 사이를 연결하는 관문
- VPC는 고립된 환경이므로 IGW를 통해서만 인터넷과 통신할 수 있다.
- IGW는 **사설 IP ↔ 공인 IP를 1:1로 변환**한다. (EC2 안에서 `ip addr`로는 사설 IP만 보임)

인터넷과 통신하려면 아래 세 가지가 **모두** 필요하다.
1. VPC에 IGW 연결
2. 서브넷 라우팅 테이블에 `0.0.0.0/0 → igw-xxxx`
3. 인스턴스에 Public IP 또는 Elastic IP

### 6-4. Public Subnet vs Private Subnet

Private 서브넷을 만드는 버튼은 따로 없다. **라우팅 테이블 설정의 차이**로만 구분된다.

| 구분 | Public Subnet | Private Subnet |
|---|---|---|
| IGW 경로 | 있음 | 없음 |
| 통신 | VPC 내부 + 인터넷 | VPC 내부만 |
| 라우팅 예시 | `10.0.0.0/16 → local`<br>`0.0.0.0/0 → igw-xxxxxxxx` | `10.0.0.0/16 → local` |

> **보완**: 기본 VPC는 `172.31.0.0/16`, 실습에서 만든 VPC는 `10.0.0.0/16`이다. local 경로의 CIDR은 VPC의 CIDR과 같다.
> 서브넷 이름에 `public`이 들어가도, **라우팅 테이블에 igw 경로가 없으면 Private**이다.

#### VPC 생성 과정

1. AWS 콘솔 → **VPC** → **VPC 생성**
2. **VPC 등** 선택 → 이름 태그 자동 생성 및 이름 입력
3. AZ 개수, 퍼블릭/프라이빗 서브넷 개수 선택 (CIDR은 자동 계산)
4. NAT 게이트웨이 설정 (강의에서는 설정하지 않음)

#### NAT 게이트웨이

- **Private 서브넷의 리소스가 인터넷으로 나갈 때** 쓰는 관문 (예: 패키지 설치, 외부 API 호출)
- 밖으로 나가는 것만 허용하고, 외부에서 Private 서브넷으로 직접 들어오는 것은 막는다.
- EC2 같은 서비스를 Private 서브넷에 두고 인터넷을 써야 한다면 설정해야 한다.

| 종류 | 설명 |
|---|---|
| **Zonal NAT Gateway** | Public 서브넷 안에 두는 방식. 서브넷이 AZ마다 있으므로 AZ마다 설정해야 함 |
| **Regional NAT Gateway** | 리전 전체를 커버. 하나만 만들면 AWS가 AZ별로 알아서 확장 (최종 프로젝트에서 사용 예정) |

### 6-5. 서브넷 그룹

**정의**: RDS, ElastiCache처럼 **AWS가 직접 배치하고 관리하는 서비스**가 사용할 수 있는 서브넷들의 목록

- EC2는 서브넷 하나를 직접 고르지만, RDS는 AWS가 이 목록 안에서 배치할 곳을 정한다.

**생성 목적**
1. **고가용성**: 서브넷은 AZ 하나에만 속하므로, **서로 다른 AZ의 서브넷을 2개 이상** 묶어서 DB가 다른 AZ로 옮겨 갈 자리를 마련한다. **Multi-AZ**를 켜면 한 AZ가 다운되어도 다른 AZ의 예비 DB가 자동으로 서비스를 이어받는다.
2. **보안**: 그룹에 **Private 서브넷만** 넣어서 DB가 인터넷에 노출되지 않게 한다.

**주의**
- Multi-AZ를 쓰지 않아도 **AZ 2개 이상**이 생성 조건이다.
- 그룹의 모든 서브넷에 DB가 생기는 것이 아니다. 그중 한 곳(Multi-AZ는 두 곳)에만 배치된다.
- 모든 서브넷은 **같은 VPC**에 있어야 한다.
- EC2와 DB가 같은 서브넷에 있을 필요는 없다. **같은 VPC**에만 있으면 Local 경로로 통신한다.

## 7. AWS 서비스

수백 가지 서비스가 있으며, 필요할 때 검색해서 적재적소에 사용한다.

| 위치 | 대표 서비스 |
|---|---|
| **VPC 서브넷 안** | EC2, RDS, ElastiCache, ALB, NAT 게이트웨이 |
| **선택적으로 VPC에 연결** | Lambda, API Gateway(프라이빗) |
| **VPC 밖** (리전/글로벌) | S3, DynamoDB, SQS, SNS, IAM, Route 53, CloudFront |

**서비스 사용 전 확인**
- 콘솔 오른쪽 위의 **리전**을 먼저 설정한다.
- **예산 설정**이 되어 있는지 확인한다.

### 7-1. EC2

**정의**: AWS에서 제공하는 클라우드 컴퓨팅 서비스 (마음대로 세팅할 수 있는 AWS 컴퓨터)

- 로컬에서 실행하던 서버를 EC2에서 실행할 수 있다.
- 물리 컴퓨터 한 대를 통째로 쓰는 것이 아니라, 컴퓨터 안의 공간을 쪼개서 만든 가상 서버를 사용한다.
- **서브넷 하나**를 지정해서 그 서브넷 안에 만들어진다.

#### 7-1-1. 인스턴스 상태

| 상태 | 설명 | EC2 비용 | 퍼블릭 IP | 데이터 |
|---|---|---|---|---|
| Pending | 시작 중 | - | - | 유지 |
| Running | 실행 중 | 과금 | 과금 | 유지 |
| Stopped | 중지됨 (재시작 가능) | 무료 | 해제 (재시작 시 새 IP) | 유지 |
| Terminated | 삭제됨 (복구 불가) | 무료 | 해제 | 삭제 |

**주의**
1. Public IP는 인스턴스를 **중지 후 재시작하면 바뀐다.**
2. 실습 후 종료하지 않으면 **계속 과금**된다.

> **보완**: 중지 상태에서도 **EBS 디스크(스토리지) 요금과 Elastic IP 요금**은 계속 나간다.

**중지 vs 종료**

| 구분 | 중지 (Stop) | 종료 (Terminate) |
|---|---|---|
| 의미 | 서버 전원 끄기 | 서버 반납 (삭제) |
| 데이터 | 유지 | 삭제됨 (기본) |
| 재사용 | 다시 시작 가능 | 복구 불가 |
| 퍼블릭 IP | 해제됨 | 해제됨 |

#### 7-1-2. EC2 인스턴스 IP 주소 종류

EC2에는 **Private IP 1개가 항상** 있고, 여기에 **공인 IP(Public IP 또는 Elastic IP) 중 하나**가 붙는다.
Elastic IP를 연결하면 기존 Public IP는 반납되고 Elastic IP로 교체된다.

| 종류 | 특징 |
|---|---|
| **Private IP** | VPC 내부 통신용. 생성 시 자동 할당. 중지/시작해도 유지. 인터넷에서 접근 불가 |
| **Public IP** | 인터넷 통신용. 시작 시 자동 할당(설정으로 끌 수 있음). 중지 → 시작 시 변경. Public Subnet에서만 의미 있음 |
| **Elastic IP** | 고정된 공인 IP. 직접 할당해서 연결. 인스턴스를 삭제해도 계정에 남아 **계속 과금** |

| 구분 | Public IP (자동 할당) | Elastic IP |
|---|---|---|
| IP 변경 | 재시작 시 변경 | 고정 |
| 비용 | $0.005/h | $0.005/h |
| 다른 EC2로 이동 | 불가 | 가능 |

- 2024년부터 모든 공인 IPv4에 동일하게 과금되므로, 고정 IP가 필요하면 Elastic IP를 쓰면 된다.
- Elastic IP를 다 쓰면 **연결 해제 → 릴리스**까지 해야 과금이 멈춘다.

#### 7-1-3. 인스턴스 생성 방법

**1. 이름 및 태그 설정**: EC2 이름 설정

**2. AMI 선택**
- AMI는 EC2를 시작할 때 쓰는 설치 이미지 (Docker 이미지처럼 어떻게 구성할지 정의)
- 운영체제, 기본 패키지/도구, 초기 설정 등이 포함
- 강의: Quick Start → **Amazon Linux 2023 AMI**, 64비트

**3. 인스턴스 유형 설정** (예: `t4g.small`)

| 구성 요소 | 의미 |
|---|---|
| family (`t`) | 용도 (깊게 알 필요 없음) |
| generation (`4`) | 세대 (대체로 높을수록 좋음) |
| additional capability (`g`) | `g`가 있으면 **Graviton**(Arm/arm64), 없으면 보통 x86_64 |
| instance size (`small`) | 사양 (nano < micro < small < medium < large < …) |

- Spring은 다른 프레임워크보다 무거워서 micro는 버겁고, **small 이상**을 권장한다.
- `g`가 붙은 유형을 고르는 이유는 성능과 가성비. **`t4g.small`** (2026년 12월까지 무료)

**4. 키 페어 설정**
- **새 키 페어 생성** → 이름 설정
- 유형: **RSA**, 파일 형식: **.pem**
- 키 페어는 **이때만 다운로드**할 수 있으므로 잃어버리면 안 된다.

**5. 네트워크 설정**
- VPC 선택
- 서브넷: **퍼블릭 서브넷** 선택 (강의에서는 퍼블릭, 실제 환경에서는 프라이빗 권장)
- 퍼블릭 IP 자동 할당: **활성화**
- 보안 그룹 설정 (SSH 소스는 **내 IP**)

**6. 스토리지 구성**: 기본값 (8 GiB gp3)

**7. 인스턴스 시작**
- EC2 대시보드 → 인스턴스 목록
- 인스턴스 상태 **"실행 중"**, 상태 검사 **"검사 통과"** 확인

> **보완**: 인스턴스의 서브넷은 **만든 뒤에 바꿀 수 없다.** Private 서브넷에 잘못 만들었다면 Public 서브넷에 다시 만들어야 한다.

#### 7-1-4. 접속 방법

**1. 키 파일 권한 설정** (최초 1회)

```bash
chmod 400 {pem 키 파일 경로}
```

- `400` = 소유자만 읽기 가능, 쓰기/실행 금지
- SSH는 다른 사람도 읽을 수 있는 키 파일을 **사용 거부**하므로 이 설정이 필요하다.
- 파일을 다른 PC로 복사하거나 다시 다운로드하면 다시 해야 한다.

> **보완**: `chmod`는 접속 명령이 아니라 **내 PC의 파일 권한을 잠그는 준비 작업**이다.
> 여기서 "소유자"는 내 PC에 로그인한 OS 사용자이며, AWS 계정과는 관계없다.
> Windows PowerShell에서는 `chmod` 대신 `icacls`를 쓴다.

**2. SSH 접속**

```bash
ssh -i {.pem 파일 경로} ec2-user@{Public IP 또는 Elastic IP}
```

- 접속에 성공하면 그 터미널은 **로컬이 아니라 EC2 내부**를 조작한다.
- 파일 전송(`scp`)도 같은 22번 포트와 같은 키를 사용한다.

**SSH 접속이 통과하는 단계**

```
[1] 내 PC        chmod 400 → 키 파일이 잠겨 있어야 ssh가 키를 사용
[2] 보안 그룹    이 IP가 인바운드 22번에 허용되어 있나?
[3] EC2 (sshd)   이 키가 authorized_keys에 등록되어 있나? 사용자명이 맞나?
```

#### 7-1-5. IAM Role 설정

- 경로: EC2 → 인스턴스 선택 → **작업 → 보안 → IAM 역할 수정**
- 처음에는 연결된 Role이 없다.
- S3, Parameter Store처럼 **IAM 권한이 필요한 AWS 서비스**에 접근하려면 Role이 있어야 한다.

> **보완**: RDS, ElastiCache 연결은 IAM Role이 아니라 **보안 그룹 + DB 사용자명/비밀번호**로 제어된다.

#### 7-1-8. JAR 빌드와 배포

**1. JAR 빌드** (IntelliJ 프로젝트 폴더에서)

```bash
./gradlew clean bootJar
ls -la build/libs/
```

- 또는 Gradle 탭 → Tasks → build → **bootJar** 더블 클릭
- `bootJar`: JAR만 생성 / `build`: 테스트 실행 후 JAR 생성
- `-plain.jar`는 실행할 수 없는 파일이다. 이름에 `plain`이 없는 jar를 사용한다.

**2. 보안 그룹**: Spring 앱이 8080 포트로 실행되므로 인바운드에 **8080** 추가

**3. Java 설치** (EC2에 SSH 접속 후)

```bash
sudo dnf install java-21-amazon-corretto -y

```

| 용어 | 의미 |
|---|---|
| `sudo` | 관리자 권한으로 실행 |
| `dnf` | 패키지 관리자 (소프트웨어 설치/삭제 도구) |
| `-y` | 설치 확인 질문에 자동으로 "yes" |

**4. JAR 업로드** (로컬 → EC2)

```bash
# 기본 형식
scp -i {키 페어 경로} {로컬 파일} ec2-user@{EC2-IP}:~/app.jar

# 예시
scp -i ~/.ssh/my-key.pem build/libs/app-0.0.1-SNAPSHOT.jar ec2-user@{EC2-IP}:~/app.jar
```

**5. 실행**

| 방식 | 특징 |
|---|---|
| 포그라운드 | 로그가 화면에 출력. 터미널을 닫거나 `Ctrl+C`를 누르면 종료 |
| 백그라운드 | 터미널을 닫아도 계속 실행. 직접 프로세스를 종료해야 함 |

```bash
# 포그라운드 (application.properties만 있을 때)
java -jar ~/app.jar

# 포그라운드 (application-prod.properties도 있을 때)
java -jar ~/app.jar --spring.profiles.active=prod

# 백그라운드 (application.properties만 있을 때)
nohup java -jar ~/app.jar > ~/app.log 2>&1 &

# 백그라운드 (application-prod.properties도 있을 때)
nohup java -jar ~/app.jar --spring.profiles.active=prod > ~/app.log 2>&1 &
```

- `nohup` (No Hang Up): SSH가 끊어져도 앱이 계속 실행된다.
- `> ~/app.log 2>&1`: 일반 출력과 오류 출력을 모두 `app.log` 파일에 저장한다.
- 끝의 `&`: 백그라운드로 실행한다.
- **처음에는 포그라운드로 실행해서 오류를 확인**하고, 문제없으면 백그라운드로 실행한다.

**6. 상태 확인과 종료**

```bash
pgrep -af java           # 실행 중인 앱 확인 (아무것도 안 나오면 종료된 상태)
ps aux | grep java       # 같은 용도
tail -f ~/app.log        # 실시간 로그 (Ctrl+C는 로그 보기만 종료)
curl localhost:8080      # EC2 안에서 응답 확인

pkill -f app.jar         # 일반 종료
kill -9 {PID}            # 종료되지 않을 때만 강제 종료
```

> **보완**
> - 포그라운드 앱은 반드시 **`Ctrl+C`**로 종료한다. `Ctrl+Z`는 **일시정지**라서 앱이 DB 연결을 붙잡은 채 남는다.
>   실수로 눌렀다면 `fg` → `Ctrl+C`, 또는 `kill -9 {PID}`로 정리한다.
> - `kill -9`는 앱이 정리 작업을 할 틈 없이 끝내므로, 평소에는 일반 종료를 먼저 쓴다.
> - 명령어 목록을 **통째로 붙여 넣지 않는다.** `pkill` 같은 종료 명령까지 함께 실행된다.
> - 로그는 `vi`로 열지 않는다. `tail -f`(나가기 `Ctrl+C`) 또는 `less`(나가기 `q`)를 쓴다.

**7. 재배포 (파일 교체)**

```bash
# 내 PC: 다시 빌드 후 임시 이름으로 업로드
./gradlew clean bootJar
scp -i {키 경로} build/libs/{jar 파일} ec2-user@{EC2-IP}:~/app.jar.new

# EC2: 앱 종료 → 교체 → 재실행
pkill -f app.jar
mv ~/app.jar ~/app.jar.bak
mv ~/app.jar.new ~/app.jar
nohup java -jar ~/app.jar --spring.profiles.active=prod > ~/app.log 2>&1 &
```

### 7-2. Parameter Store

**정의**: AWS Systems Manager Parameter Store. 설정값을 안전하게 저장하고 관리하는 서비스

- Spring Boot에서는 `application.properties`(주로 prod)의 값을 **하드코딩하지 않기 위해** 사용한다.

| 장점 | 설명 |
|---|---|
| 버전 관리 | 변경 이력 자동 기록 |
| IAM 권한 제어 | 누가 읽을 수 있는지 세밀하게 제어 |
| 재부팅 영향 없음 | AWS가 관리하므로 서버 재부팅과 무관 |

- 보안을 강화한 **AWS Secrets Manager**도 있지만 유료다. (DB 비밀번호 자동 교체 기능 제공)

#### 7-2-1. 사용 방법

AWS 콘솔 → **Parameter Store** → **파라미터 생성**

| 항목 | 값 | 설명 |
|---|---|---|
| Name | `/{앱이름}/{프로필}/{키}` | 계층 구조로 이름 지정 (권한 제어가 쉬움) |
| Type | `String`, `StringList`, `SecureString` | 값 타입 |
| Value | 값 | 설정값 |

| Type | 설명 |
|---|---|
| `String` | 문자열 |
| `StringList` | 콤마(`,`)로 구분된 문자열 리스트 |
| `SecureString` | **암호화된** 문자열 (비밀번호 등 민감한 값) |

**Spring Boot 설정**

```gradle
implementation 'io.awspring.cloud:spring-cloud-aws-starter-parameter-store:4.1.1'
```

```properties
# application-prod.properties
# Parameter Store에서 설정한 파라미터의 공통 경로
spring.config.import=aws-parameterstore:/camp-health-app/prod/

# 위 경로에 이어진 파라미터 이름을 ${ }로 대입
spring.datasource.url=jdbc:mysql://${DB_HOST}:${DB_PORT}/${DB_NAME}
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}
```

**대응하는 Parameter Store 파라미터**

| 파라미터 이름 | Type | 용도 |
|---|---|---|
| `/{앱이름}/prod/DB_HOST` | String | DB 엔드포인트 |
| `/{앱이름}/prod/DB_PORT` | String | 3306 (MySQL 포트) |
| `/{앱이름}/prod/DB_NAME` | String | 데이터베이스명 |
| `/{앱이름}/prod/DB_USERNAME` | String | 사용자명 |
| `/{앱이름}/prod/DB_PASSWORD` | **SecureString** | 비밀번호 |

> **보완**
> - 비밀번호는 `String`이 아니라 **`SecureString`**으로 저장해야 암호화된다.
> - `spring.config.import`를 공통 `application.properties`에 넣으면 로컬에서도 Parameter Store에 접근하려다 실패한다. **prod 파일에만** 넣거나 앞에 `optional:`을 붙인다.

#### 7-2-2. EC2 권한 설정

EC2가 Parameter Store를 읽으려면 IAM 권한이 필요하다.

**IAM 정책 생성**

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "ssm:GetParameter",
                "ssm:GetParameters",
                "ssm:GetParametersByPath"
            ],
            "Resource": "arn:aws:ssm:ap-northeast-2:*:parameter/{properties에 입력한 경로}/*"
        }
    ]
}
```

- `SecureString`을 쓰면 `kms:Decrypt` 권한도 필요할 수 있다.

**EC2 Role에 정책 연결**
1. AWS 콘솔 → IAM → **역할(Roles)**
2. EC2에 연결된 Role 선택
3. **권한 추가 → 정책 연결**
4. 위에서 만든 정책 연결

### 7-3. S3

**정의**: 모든 파일을 담을 수 있는 저장소

- S3 버킷에는 범용 버킷, 디렉터리 버킷 등이 있는데 **범용 버킷** 외에는 거의 사용하지 않는다.
- 경로: AWS 콘솔 → S3
- 버킷 이름은 **전 세계에서 유일**해야 한다. (`S3Template`도 버킷 이름으로 찾음)
- 버킷 이름에는 소문자, 숫자, 하이픈(`-`), 점(`.`)만 쓸 수 있다. (3~63자)

| 용어 | 설명 | 비유 |
|---|---|---|
| 버킷 (Bucket) | 파일을 담는 저장소 | 폴더 |
| 오브젝트 (Object) | 저장된 파일 자체 | 파일 |
| 키 (Key) | 오브젝트의 고유 경로/이름 | 파일 경로 |

```
s3://my-app-bucket/
    ├── uploads/
    │   ├── profile/user1.jpg
    │   └── docs/report.pdf
    └── static/
        └── logo.png
```

- `uploads/profile/user1.jpg` **전체가 하나의 키**다. S3에는 실제 폴더가 없고, 슬래시로 묶어서 보여 줄 뿐이다. (이 앞부분을 **접두어, prefix**라고 부름)
- 코드에서 키 앞에 `/`를 붙이지 않는다. (`uploads/a.png` O, `/uploads/a.png` X)

#### 7-3-1. 보안

| 원칙 | 설명 |
|---|---|
| 퍼블릭 액세스 차단 | 기본적으로 모든 퍼블릭 접근 차단 (버킷 생성 시 기본값) |
| 최소 권한 | 필요한 권한만 부여 |

- **ACL**(Access Control List)은 버킷/오브젝트별 접근 권한 설정 기능이지만 레거시 방식이라 잘 쓰지 않는다. 현재는 **IAM 정책**을 권장한다.

#### 7-3-2. 연동 및 사용 방법

**의존성 추가**

```gradle
implementation platform('io.awspring.cloud:spring-cloud-aws-dependencies:4.0.0-RC1') // BOM으로 버전 관리
implementation 'io.awspring.cloud:spring-cloud-aws-starter-s3'
```

**application.properties**

```properties
# AWS Region
spring.cloud.aws.region.static=ap-northeast-2

# 파일 업로드 크기 제한
spring.servlet.multipart.max-file-size=10MB

# @Value로 주입하기 위해 직접 정한 키 (Spring Cloud AWS 공식 설정 키는 아님)
spring.cloud.aws.s3.bucket={S3 버킷 이름}
```

**S3Template 사용**

```java
@RequiredArgsConstructor
public class XxxClass {
    private final S3Template s3Template; // DI
}

// 파일 업로드
s3Template.upload("버킷 이름", "S3 내에 지정할 경로(key)", inputStream);

// 파일 다운로드용 Presigned URL 생성
s3Template.createSignedGetURL(bucket, key, PRESIGNED_URL_EXPIRATION);
```

**Presigned URL**
- 버킷은 퍼블릭 액세스가 차단된 **프라이빗** 상태라 URL로 직접 접근할 수 없다.
- Presigned URL은 **임시로 접근을 허용하는 서명된 URL**이다.
- 유효 시간을 설정할 수 있고, 유효 시간 안에는 URL을 가진 **누구나** 파일에 접근할 수 있다.

**응답 DTO**

```java
// 업로드 응답: 이후 다운로드할 때 필요한 key를 반환
@Getter
public class FileUploadResponse {
    private final String key;

    public FileUploadResponse(String key) {
        this.key = key;
    }
}

// 다운로드 응답: Presigned URL을 반환
@Getter
public class FileDownloadUrlResponse {
    private final String url;

    public FileDownloadUrlResponse(String url) {
        this.url = url;
    }
}
```

**Service**

```java
// UUID를 쓰는 이유: 생성 비용이 O(1)이고 중복 가능성이 매우 낮음
@Service
@RequiredArgsConstructor
public class S3Service {

    private static final Duration PRESIGNED_URL_EXPIRATION = Duration.ofMinutes(10);

    private final S3Template s3Template;

    @Value("${spring.cloud.aws.s3.bucket}")
    private String bucket;

    public String upload(MultipartFile file) {
        try {
            String key = "uploads/" + UUID.randomUUID() + "_" + file.getOriginalFilename();
            s3Template.upload(bucket, key, file.getInputStream());
            return key;
        } catch (IOException e) {
            // 커스텀 예외로 바꾸고 GlobalExceptionHandler에서 처리 필요
            throw new RuntimeException("파일 업로드 실패", e);
        }
    }

    public URL getDownloadUrl(String key) {
        return s3Template.createSignedGetURL(bucket, key, PRESIGNED_URL_EXPIRATION);
    }
}
```

**Controller**

```java
@RestController
@RequiredArgsConstructor
public class FileController {

    private final S3Service s3Service;

    @PostMapping("/files/upload")
    public ResponseEntity<FileUploadResponse> upload(@RequestParam("file") MultipartFile file) {
        String key = s3Service.upload(file);
        return ResponseEntity.ok(new FileUploadResponse(key));
    }

    @GetMapping("/files/download-url")
    public ResponseEntity<FileDownloadUrlResponse> getDownloadUrl(@RequestParam String key) {
        URL url = s3Service.getDownloadUrl(key);
        return ResponseEntity.ok(new FileDownloadUrlResponse(url.toString()));
    }
}
```

> **보완**
> - 코드의 키 경로(`uploads/`)와 IAM 정책의 Resource 경로(`uploads/*`)가 **일치**해야 한다.
> - 정책에 `s3:ListBucket`이 없으면 없는 파일을 요청할 때 `404`가 아니라 **`403 Access Denied`**가 나온다.
> - Private 서브넷의 EC2가 S3에 접근하려면 NAT 게이트웨이나 **S3 게이트웨이 엔드포인트**(무료)가 필요하다.

### 7-4. RDS

**정의**: AWS에서 제공하는 관리형 DB 서비스

**사용 목적**: EC2에 상태(데이터)를 두지 않는다.
- EC2에 직접 DB를 설치하면 서버가 다운될 때 데이터가 날아갈 수 있고 유지보수가 힘들다.
- RDS를 쓰면 AWS가 **백업, 패치, 장애 조치**를 해 준다. (인건비 절약)

#### 7-4-1. 생성 방법

경로: AWS 콘솔 → **Aurora and RDS**

**1. 서브넷 그룹 생성**
- DB가 여러 서브넷(AZ)에 배치될 수 있도록 먼저 설정한다. (6-5 참고)
- 강의에서는 Public 서브넷으로 구성했지만 **Private 서브넷**으로 구성하는 것이 좋다.

**2. 데이터베이스 생성** (전체 구성, MySQL)

| 항목 | 설명 |
|---|---|
| DB 인스턴스 식별자 | 콘솔에 표시되는 RDS 이름 |
| 마스터 사용자 이름 | DB username |
| 마스터 암호 | DB password |
| VPC | 지금 EC2가 사용하는 VPC |
| 서브넷 그룹 | 1단계에서 만든 그룹 |
| 퍼블릭 액세스 | 강의에서는 로컬 접속용으로 "예", **실무에서는 "아니요"** |
| 기존 VPC 보안 그룹 | 강의에서는 default → **`webcraft-data`로 변경** |
| 추가 구성 → 초기 데이터베이스 이름 | 사용할 데이터베이스 이름 |

> **보완**: 초기 데이터베이스 이름을 비워 두면 앱용 DB가 만들어지지 않는다.
> 콘솔에 "데이터베이스 이름: `mysql`"로 표시되는데, 이것은 **시스템 데이터베이스**라서 앱이 쓸 수 없다.
> 이 경우 EC2에서 직접 만든다.
> ```bash
> mysql -h {RDS 엔드포인트} -u admin -p
> ```
> ```sql
> CREATE DATABASE webcraft CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
> ```
> URL에 `?createDatabaseIfNotExist=true`를 붙이는 방법도 있다.

#### 7-4-2. 보안 그룹

- RDS 보안 그룹 인바운드에 **유형: MySQL/Aurora, 포트 3306**, 소스: **EC2의 보안 그룹(`webcraft-app`)**

#### 7-4-3. 연결

호스트는 **RDS 엔드포인트**를 사용한다. (failover가 일어나도 엔드포인트는 새 DB를 가리킴)

```gradle
implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
runtimeOnly 'com.mysql:mysql-connector-j'
```

```properties
spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver
spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.MySQLDialect

spring.datasource.url=jdbc:mysql://{RDS 엔드포인트}:3306/{데이터베이스명}
spring.datasource.username={유저네임}
spring.datasource.password={비밀번호}

# 운영(prod)에서 create나 update는 데이터/테이블을 덮어쓸 수 있으므로 주의
spring.jpa.hibernate.ddl-auto=validate
```

- 그 외에는 기존 MySQL과 사용 방식이 같다.
- 엔드포인트를 복사할 때 **`:3306` 같은 포트는 빼고** 호스트만 넣는다.

#### 7-4-4. 보안 그룹 변경

RDS → 데이터베이스 → DB 선택 → **수정** → 연결 → VPC 보안 그룹 변경 → **즉시 적용**

### 7-5. ElastiCache

**정의**: AWS에서 제공하는 관리형 인메모리 캐시 서비스 (Redis와 같은 기능)

#### 7-5-1. 생성

**1. 서브넷 그룹 생성**
- RDS와 다르게 **퍼블릭 접근을 지원하지 않는다.** Private 서브넷으로 구성한다.

**2. Valkey 캐시 생성** (Redis가 아닌 Valkey 선택)
- Valkey는 Redis와 **호환**되고, 성능과 가격도 더 낫다.
- 노드 기반 캐시 → **간편한 생성** → 구성: **데모** (비용 측면)
- 클러스터 이름: 클러스터를 쓰지 않더라도 이름은 지어야 한다.
- 서브넷 그룹: 1단계에서 만든 그룹

#### 7-5-2. 엔드포인트와 연결 설정

캐시 종류에 따라 사용할 엔드포인트가 다르다.

| 캐시 종류 | 사용할 엔드포인트 |
|---|---|
| Serverless | 엔드포인트 (TLS 항상 필수) |
| 노드 기반 + **클러스터 모드 활성화** (간편 생성 기본값) | **구성 엔드포인트** (`clustercfg.`로 시작) |
| 노드 기반 + 클러스터 모드 비활성화 | 기본 엔드포인트 |

```gradle
implementation 'org.springframework.boot:spring-boot-starter-data-redis'
```

```properties
# 클러스터 모드 활성화 + 전송 중 암호화 필수인 경우 (실습 캐시)
spring.data.redis.cluster.nodes={구성 엔드포인트 호스트}:6379
spring.data.redis.ssl.enabled=true
spring.data.redis.lettuce.cluster.refresh.adaptive=true
```

> **보완**
> - "기본 엔드포인트"가 `-`로 비어 있다면 클러스터 모드가 켜진 것이다. 구성 엔드포인트를 쓴다.
> - **전송 중 암호화: 필수**라면 `ssl.enabled=true`가 없을 때 연결이 멈추거나 끊긴다.
> - 호스트 값에 `:6379`를 넣으면 `Host has a port` 오류가 난다. 기본값 문법 `${REDIS_HOST:호스트}`에서도 호스트만 넣는다.
> - EC2에서 테스트: `redis6-cli -h {호스트} -p 6379 --tls -c ping` → `PONG`

#### 7-5-3. 보안 그룹 수정

ElastiCache → Valkey 캐시(또는 Redis OSS 캐시) → 캐시 선택 → **수정** → 보안 그룹 변경 → **즉시 적용**

## 8. 부록: 실습 중 만난 오류 정리

### SSH 접속

| 오류 메시지 | 원인 | 해결 |
|---|---|---|
| `bad permissions` / `UNPROTECTED PRIVATE KEY FILE` | 키 파일 권한이 너무 열려 있음 | `chmod 400` (Windows는 `icacls`) |
| `Connection timed out` | 서버에 도달하지 못함 | 보안 그룹 22번 소스(내 IP), 현재 퍼블릭 IP, **Public 서브넷 여부**, 와이파이 차단 확인 |
| `Connection refused` | 서버에는 도착했지만 22번 포트가 닫힘 | sshd 동작 여부 확인 |
| `Permission denied (publickey)` | 키 또는 사용자명이 틀림 | 키 페어 확인, `ec2-user`/`ubuntu` 확인 |

### 앱 실행

| 오류 메시지 | 원인 | 해결 |
|---|---|---|
| `no main manifest attribute` | `-plain.jar`를 실행함 | plain이 없는 jar 사용 |
| `UnsupportedClassVersionError` | EC2의 Java 버전이 낮음 | 빌드 버전과 같은 Java 설치 |
| `Could not resolve placeholder 'XXX'` | 환경변수 없이 실행함 | 환경변수 설정 또는 기본값 지정 |
| `Port 8080 was already in use` | 이전 앱이 실행 중 | `pgrep -af java` 후 종료 |
| `Access denied for user 'admin'@'%' to database 'mysql'` | 시스템 DB(`mysql`)를 사용하려 함 | 앱 전용 데이터베이스 생성 후 URL 변경 |
| `Unknown database 'xxx'` | 데이터베이스가 없음 | `CREATE DATABASE` |
| `Communications link failure` | RDS 네트워크 문제 | 보안 그룹, 엔드포인트 확인 |
| `Host has a port: ...:6379` | Redis 호스트 값에 포트가 포함됨 | 호스트에서 `:6379` 제거 |
| `Another server is already running on this database` | 이전 앱이 DB 잠금을 쥐고 있음 (`Ctrl+Z`로 일시정지된 프로세스 등) | `kill -9 {PID}` 후 재실행 |

### 셸 사용

| 상황 | 원인 | 해결 |
|---|---|---|
| `set +a nohup java ...` 가 실행되지 않음 | `;` 누락으로 뒤 명령이 `set`의 인자가 됨 | `;` 또는 `&&`로 구분 |
| `syntax error near unexpected token 'newline'` | `<PID>` 같은 자리표시를 그대로 입력 | 실제 값으로 바꿔서 입력 |
| 화면에 `~`가 가득하고 입력창이 안 보임 | `vi` 편집기 안 | `Esc` → `:q!` → `Enter` |
| 화면 아래 `(END)` | `less` 화면 | `q` |
| `Exit 143` | `kill`/`pkill`로 종료됨 (128 + 15) | 오류 아님, 필요하면 재실행 |
| `Exit 137` | `kill -9` 또는 메모리 부족 | 메모리 부족이면 `-Xmx512m` 또는 큰 인스턴스 |

### 셸 명령 구분 기호

| 기호 | 의미 |
|---|---|
| `;` | 앞 명령이 끝나면 무조건 다음 명령 실행 |
| `&&` | 앞 명령이 **성공했을 때만** 다음 명령 실행 |
| `&` (맨 끝) | 백그라운드로 실행 |
