## 1. 전역 예외처리 (`@RestControllerAdvice` + `@ExceptionHandler`)

**용도**
여러 컨트롤러에서 흩어져 발생하는 예외를 한 곳에서 모아 처리하기 위해 사용된다. 매 컨트롤러마다 try-catch를 반복하지 않아도 된다.

**사용법**
1. 클래스에 `@RestControllerAdvice`를 붙인다 (JSON 응답 자동 직렬화 포함).
2. 그 안에 `@ExceptionHandler(예외타입.class)` 메서드를 정의하고, `ResponseEntity<T>`로 상태코드+본문을 함께 반환한다.

**주의사항**
- `@RestControllerAdvice`가 여러 개면 `@Order`로 우선순위를 정해야 한다.
- 부모/자식 예외 타입 핸들러가 동시에 있으면 **자식(더 구체적인 타입)이 우선** 적용된다.
- 같은 예외 타입에 핸들러가 중복되면 앱 시작 시 오류가 난다.
- `@ResponseStatus`와 `ResponseEntity` 반환을 같이 쓰면 **`ResponseEntity`가 우선**한다.

**예시 코드**
```java
// 1. 커스텀 예외 정의 (예외가 너무 광범위하거나 구체적 상황이 필요할 때 상속해서 사용)
public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(String message) { super(message); }
}

// 2. 전역 예외 처리
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleUserNotFound(UserNotFoundException e) {
        ErrorResponse error = new ErrorResponse("USER_NOT_FOUND", e.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error);
    }

    // 처리 안 된 예외 fallback
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleException(Exception e) {
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(new ErrorResponse("INTERNAL_ERROR", "서버 오류가 발생했습니다."));
    }
}
```

## 2. N+1 문제

**발생 상황(용도가 아니라 "왜 문제인지")**
부모 목록 1번 조회 + 부모마다 자식을 따로 조회 → 총 N+1번의 쿼리가 나가는 성능 문제.

**원인**
연관 엔티티가 **Lazy Loading**일 때, 실제로 접근하는 시점마다 개별 쿼리가 발생하기 때문이다.

**해결 방법**
PK-FK 관계를 이용해 **JOIN**으로 한 번에 가져오면 방지된다.

## 3. 오류 로그 분석 — DeckCount 집계 쿼리


###  오류 로그 
```
No argument for named parameter :games
```
- **문제가 된 코드**
  ```java
  @Query("select new com.gamebasic.runcard.dto.projection.DeckCount(g.id,count(r.game))" +
          "from RunCard r join Game g where g = :games" +
          " group by r.game")
  List<DeckCount> countByGames(List<Game> games);
  ```
- **원인**: 두 가지가 겹쳐 있다.
  1. `where g = :games` → `List`를 `=`로 비교할 수 없다. (문법 오류)
  2. 메서드 파라미터에 `@Param("games")`가 없어서 JPQL이 `:games`를 어떤 파라미터와 연결할지 못 찾는다.
- **해결**
  - `=` → `in`으로 변경
  - 파라미터에 `@Param("games")` 추가
  ```java
  List<DeckCount> countByGames(@Param("games") List<Game> games);
  ```

###  오류 로그 
```
Entity join did not specify a join condition
[SqmEntityJoin(com.gamebasic.game.entity.Game(g))]
(specify a join condition with 'on' or use 'cross join')
```
- **문제가 된 코드**: `from RunCard r join Game g where g in :games`
- **원인**: `join Game g`처럼 **테이블(엔티티) 자체**를 조인 대상으로 쓰면, JPQL이 어떤 컬럼끼리 연결할지 알 수 없다. JOIN은 반드시 `FROM`에 선언한 테이블이 가진 **FK 필드**를 통해서 해야 한다.
- **해결**: `join Game g` → `join r.game g` (RunCard가 가진 FK 필드로 조인)

### ✅ 최종 완성 쿼리
```java
@Query("select new com.gamebasic.runcard.dto.projection.DeckCount(g.id, count(r)) " +
       "from RunCard r join r.game g where g in :games " +
       "group by g.id")
List<DeckCount> countByGames(@Param("games") List<Game> games);
```
> `count(r.game)` / `group by r.game` 대신 `count(r)` / `group by g.id`로 바꾼 이유: PK-FK로 연결되어 값은 같지만, "game의 id로 묶어 덱 개수를 센다"는 의도를 더 직관적으로 드러내기 위함.


1. JOIN은 테이블명이 아니라 FROM에서 선언한 엔티티의 **FK 필드**로 한다.
2. 파라미터를 바인딩하려면 반드시 `@Param`이 필요하다.
3. 집계 함수 외의 컬럼을 SELECT하려면 그 컬럼은 GROUP BY에도 있어야 한다.

##  SQL 실행 순서

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
```

| 절 | 역할 |
|---|---|
| FROM | 어느 테이블(들)을 합쳐 데이터 집합을 만들지 결정 (JOIN 포함) |
| WHERE | 그룹으로 묶기 전, 행 단위로 필터링 |
| GROUP BY | 같은 값끼리 묶어서 그룹 단위로 집계 함수(COUNT 등) 계산 |

- GROUP BY 없이 COUNT: 전체가 하나의 그룹 → 결과 1행
- GROUP BY 있으면: 그룹 수만큼 결과 행 생성

## 4. JPQL의 JOIN이 SQL과 다른 점

- **SQL**: `JOIN game g ON r.game_id = g.id` — 상대 테이블 이름 + ON 조건 필요
- **JPQL**: `from RunCard r join r.game g` — 엔티티의 **연관관계 필드**로 바로 조인 가능

이게 가능한 이유는 엔티티에 이미 매핑이 되어 있기 때문이다.
```java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "game_id", nullable = false)
private Game game;
```
→ `@JoinColumn`이 자동으로 `r.game_id = g.id` 조건을 성립시켜 준다.

## 6. 외부 API 응답 → DTO 매핑

**용도**: JSON 배열은 `List<Type>`으로 받는다 (Array보다 List가 더 흔히 쓰임). JSON 내부 배열의 필드명 = List 변수명.

**예시 코드**
```java
@Getter
public class RankingResponse {
    private String season;
    private int totalRecords;
    private int excludedCount;
    private List<Entry> entries; // JSON 배열 데이터를 받는 리스트
}

public class Entry {
    private int rank;
    private String playerName;
    private int clearTimeSeconds;
    private int remainingHp;
    private int bossTurns;
    private int deckSize;
}
```

> 참고: 여기서 "Response"는 내가 응답하는 게 아니라 **외부 API가 보내주는 응답**을 받는 DTO라는 뜻이다.
