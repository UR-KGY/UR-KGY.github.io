## 1. 빈 생명주기 (Bean Lifecycle)

### @PostConstruct

빈의 생성과 의존성 주입이 완료된 직후, 초기화 로직을 실행하기 위해 사용한다.

**왜 생성자에서 하지 않는가?**
생성자 실행 시점에는 아직 다른 빈들의 의존성 주입이 끝나지 않았을 수 있다. 생성자 안에서 그런 빈을 건드리면 불완전한 상태의 객체를 사용하게 될 위험이 있어 불안정하다. 그래서 초기화 로직의 우선순위는 다음과 같이 생각하면 된다.

1. 생성자 — 단순히 값을 필드에 대입하는 정도의 초기화
2. `@PostConstruct` — 다른 빈에 의존하거나, 주입이 전부 끝난 뒤에만 안전하게 할 수 있는 초기화

실무에서 자주 쓰이는 편은 아니지만, 필요할 때는 이 우선순위를 기준으로 판단하면 된다.

### @PreDestroy

빈이 컨테이너에서 제거되기 직전에 실행할 자원 정리 로직에 사용한다.

애플리케이션이 완전히 종료되면 JVM이 메모리를 전부 회수하긴 하지만, 그렇다고 이 애노테이션을 쓸 일이 없는 건 아니다. DB 커넥션 풀, 스레드 풀, 외부 시스템에 등록해둔 상태(서비스 디스커버리 등록 해제) 처럼 **JVM 메모리 회수만으로는 정리되지 않는 외부 자원**을 우아하게 종료(graceful shutdown)하려면 이 콜백이 필요하다. 다만 `HikariCP`, `ThreadPoolTaskExecutor` 같은 스프링 제공 빈들은 이미 내부적으로 이런 정리 로직을 갖고 있어서, 직접 자원을 다루는 커스텀 빈이 아니라면 직접 작성할 일은 상대적으로 적다.

## 2. IoC와 DI

객체를 생성하고 관리하는 책임을 원래는 개발자가 직접 코드로 처리해야 했지만, 스프링이 이를 대신 맡아서 처리하는 것을 **IoC(Inversion of Control, 제어의 역전)**라고 한다.

이렇게 생성된 빈 객체들이 관리되는 공간을 **IoC 컨테이너**라고 부른다. 그리고 개발자가 컨테이너에서 빈을 직접 찾아 꺼내오는 게 아니라, **컨테이너가 필요한 의존 객체를 각 빈에게 알아서 주입해주는 것**을 **DI(Dependency Injection, 의존성 주입)**라고 한다. 즉 DI의 핵심은 "누가 의존 객체를 찾아오는가"가 개발자에서 컨테이너로 뒤바뀌었다는 것이다.

## 3. 빈 스코프

빈이 몇 개나 만들어지고, 얼마나 오래 재사용되는지를 결정하는 설정이다.

| 스코프 | 설명 |
|---|---|
| **singleton** (기본값) | 컨테이너 안에 인스턴스가 단 하나. `@Service`, `@Repository`, `@Component`, `@RestController` 등 대부분의 빈이 여기 해당하며, 실무에서 쓰는 빈의 99%가 싱글톤이다. |
| **prototype** | 빈을 요청할 때마다 새 인스턴스를 생성 |
| **request** | HTTP 요청 하나마다 새로 생성되며, 그 요청 처리 안에서는 재사용됨 |
| **session** | HTTP 세션마다 생성되며, 같은 세션이 유지되는 동안 계속 재사용됨 |

## 4. 순환 참조

서로가 서로를 필요로 해서 어느 쪽도 먼저 완성될 수 없는 상황을 순환 참조라고 한다.

```java
@Service
@RequiredArgsConstructor
public class MemberService {
    private final PostService postService;
}

@Service
@RequiredArgsConstructor
public class PostService {
    private final MemberService memberService;
}
```

### 올바른 해결 방법 — 공통 로직을 제3의 클래스로 분리

```java
@Service
@RequiredArgsConstructor
public class MemberReader {
    private final MemberRepository memberRepository;
    // 두 서비스가 공통으로 필요로 하던 로직
}

@Service
@RequiredArgsConstructor
public class PostService {
    private final MemberReader memberReader;
}

@Service
@RequiredArgsConstructor
public class MemberService {
    private final MemberReader memberReader;
}
```

### 권장하지 않는 임시방편들

- **`spring.main.allow-circular-references=true`**: 필드/세터 주입 방식의 순환만 허용해준다. 생성자 주입 순환은 이 옵션으로도 해결되지 않으므로, 이 옵션을 쓰려면 생성자 주입 자체를 포기해야 한다.
- **필드 주입(`@Autowired`)으로 바꿔서 에러만 없애기**: 에러가 사라질 뿐 구조적 문제는 그대로 남는 방식이라 지양한다.
- **`@Lazy`로 한쪽 주입을 지연시키기**: 임시방편일 뿐 정상적인 해결책은 아니다.

## 5. AOP (Aspect Oriented Programming)

여러 곳에 반복되는 공통 기능을 핵심 비즈니스 로직과 분리해서 적용하는 프로그래밍 방식이다.

**AOP가 필요한 이유**를 보여주는 전형적인 예:
```java
public List<PostResponse> findRecent(int limit) {
    long start = System.nanoTime();       // 1. 이 두 줄이
    try {
        return postRepository.findRecent(limit).stream().map(PostResponse::from).toList(); // 본문
    } finally {
        log.warn("{}ms", (System.nanoTime() - start) / 1_000_000); // 2. 메서드마다 반복됨
    }
}
```
메서드 실행 시간을 재는 코드가 본래 하려던 일(본문)보다 더 많은 자리를 차지하면서 가독성을 해치고, 이런 부가 기능이 여러 메서드에 똑같이 필요할 때마다 중복된다. AOP는 이런 "메서드의 본래 역할이 아닌 처리"를 코드 밖으로 빼내기 위해 사용한다.

**의존성 추가**:
```
implementation 'org.springframework.boot:spring-boot-starter-aspectj'
```

**용어**
- **JoinPoint**: 부가 기능을 끼워 넣을 수 있는 지점. Pointcut으로 지정한 메서드가 실행되는 부분.
- **Advice**: 그 지점에서 실제로 할 일. `@Before`(전), `@After`(후), `@Around`(전후 모두) 등이 있다.
- **Pointcut**: 여러 JoinPoint 중 어디에 적용할지 고르는 식 (`execution(...)`).

전역 예외 처리와 비슷한 감각으로 쓰이지만, 패키지 경로를 지정해서 적용 범위를 좁힐 수 있다는 점이 다르다.

```java
@Slf4j
@Aspect
@Component
public class ExecutionTimeAspect {

    // Pointcut: 어떤 메서드에 적용할지 (패키지 경로)
    @Around("execution(public * com.example.board..service..*.*(..))")
    public Object measure(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.nanoTime();
        try {
            return joinPoint.proceed(); // 실제 대상 메서드 실행
        } finally {
            long tookMs = (System.nanoTime() - start) / 1_000_000;
            if (tookMs >= 100) {
                log.warn("느린 호출 {} — {}ms", joinPoint.getSignature().toShortString(), tookMs);
            }
        }
    }
}
```

## 6. 프로퍼티 바인딩

소스 코드에 값을 하드코딩하지 않고, `application.properties`나 `.yml` 같은 외부 설정 파일에 값을 분리해두고 필요한 곳에서 읽고 쓰기 위한 기능이다.

### `@Value`

설정값을 필드에 직접 주입시키는 애노테이션이다.

- 기본형: `${설정 경로}`
- 기본값 지정: `${설정 경로:기본값}`

기본값은 **없어도 안전하게 동작하는 값에만** 둔다. 반드시 입력받아야 하는 비밀번호나 외부 주소 등에는 기본값을 두지 않아, 값이 빠졌을 때 기동 시점에 바로 발견되도록 한다.

```properties
# application.properties
app.post.recent-limit=10
app.name=my-service
```
```java
// 필드 주입
@Component
public class PostService {
    @Value("${app.post.recent-limit}")
    private int recentLimit;

    @Value("${app.name:default-service}") // 콜론 뒤가 기본값
    private String appName;
}
```
```java
// 생성자 매개변수 주입
@Component
public class PostService {
    private final int recentLimit;

    public PostService(@Value("${app.post.recent-limit:5}") int recentLimit) {
        this.recentLimit = recentLimit;
    }
}
```

### `@ConfigurationProperties`

같은 주제의 설정값 여러 개를 `@Value`로 하나씩 나열하지 않고 한 번에 묶어서 관리할 수 있다.

```properties
# board.post까지가 동일 주제
board.post.max-count=3
board.post.default-page-size=50
board.post.max-page-size=100
```
```java
@ConfigurationProperties(prefix = "board.post")
@Validated
@Getter
public class PostProperties {

    @Min(1)
    private final int maxCount;
    @Min(1)
    private final int defaultPageSize;
    @Min(1)
    private final int maxPageSize;

    // 생성자 바인딩 — final 필드를 유지할 수 있다
    public PostProperties(int maxCount, int defaultPageSize, int maxPageSize) {
        this.maxCount = maxCount;
        this.defaultPageSize = defaultPageSize;
        this.maxPageSize = maxPageSize;
    }
}
```
`@ConfigurationProperties`를 쓰려면 `@Configuration` 클래스에서 `@EnableConfigurationProperties(대상클래스.class)`로 빈 등록을 해줘야 한다.
```java
@Configuration
@EnableConfigurationProperties(PostProperties.class)
public class BoardConfig {
}
```
```java
@Service
@RequiredArgsConstructor
public class TestService {
    private final PostProperties postProperties; // DI 받아서 사용
}
```

### 프로필별 설정

지금까지는 공통 설정 파일인 `application.properties`만 써왔다. 프로필을 활성화하면, 같은 위치의 `application-{프로필명}.properties`가 공통 파일보다 우선 적용된다. **파일을 만드는 것만으로는 프로필이 선택되지 않고**, 반드시 별도로 활성화해줘야 한다.

```bash
# 커맨드라인 인자로
java -jar app.jar --spring.profiles.active=local

# 환경변수로
SPRING_PROFILES_ACTIVE=local java -jar app.jar
```
```yaml
# application.yml에 기본값으로 지정
spring:
  profiles:
    active: local
```
```properties
# application.properties (공통)
spring.jpa.hibernate.ddl-auto=validate
logging.level.root=INFO

# application-local.properties (로컬 전용)
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
logging.level.com.example.board=DEBUG

# application-test.properties (테스트 전용)
spring.datasource.url=jdbc:h2:mem:test;MODE=MySQL
spring.jpa.hibernate.ddl-auto=create-drop
```

프로필로 빈 등록 여부도 정할 수 있다. `@Component`와 `@Profile("local")`을 함께 붙이면, `local` 프로필이 활성화되었을 때만 그 클래스의 빈이 등록된다.

> Git Bash에서 `cd`를 하려면 리눅스 경로 형식이 필요한데, 이동할 폴더를 Git Bash 창에 드래그해서 놓으면 자동으로 경로가 입력된다.

## 7. Filter

`DispatcherServlet`으로 HTTP 요청이 들어오기 전에 수행할 로직과, 요청을 처리한 후 응답할 때 수행할 로직을 넣는 용도로 사용한다.

`OncePerRequestFilter`를 상속받아 사용하는 게 일반적이다. 기존의 `Filter` 인터페이스는 하나의 클라이언트 요청이 서버 내부에서 forward/에러 페이지 전환/비동기 처리 등으로 여러 번 디스패치될 경우 필터 로직이 중복 실행될 수 있는 문제가 있는데, `OncePerRequestFilter`는 이 문제를 해결한 클래스다(내부적으로 `Filter`를 구현).

사용하는 메서드 이름도 다르다.
```java
// 기존 Filter
void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)

// OncePerRequestFilter
protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain)
```

핵심은 메서드 안에서 `chain.doFilter(...)`를 기준으로, **그 위가 전처리, 아래가 후처리**로 나뉜다는 것이다.

```
HTTP 요청
   │
   ▼
[Filter.doFilter 진입] ── 전처리 코드 실행
   │
   ▼
chain.doFilter(request, response)  ← 이 호출로 다음 단계로 넘어감
   │
   ▼
DispatcherServlet → HandlerMapping → Controller 실행 → 응답 생성
   │
   ▼ (실행 결과를 들고 되돌아옴)
chain.doFilter() 호출 지점으로 리턴
   │
   ▼
[chain.doFilter() "다음 줄"] ── 후처리 코드 실행
   │
   ▼
클라이언트에게 응답 전송
```

```java
@Slf4j
public class RequestLoggingFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain chain
    ) throws ServletException, IOException {
        long start = System.nanoTime();
        log.info("BEFORE {} {}", request.getMethod(), request.getRequestURI());
        try {
            chain.doFilter(request, response);
        } finally {
            long tookMs = (System.nanoTime() - start) / 1_000_000;
            log.info("AFTER {} {} -> {} ({}ms)", request.getMethod(),
                    request.getRequestURI(), response.getStatus(), tookMs);
        }
    }
}
```

### Config 등록 방식

필터를 만들었다고 바로 적용되는 게 아니다. Config 클래스에서 어떤 요청에 필터가 작동할지 정해주고 빈으로 등록해야 한다.

```java
@Configuration
public class FilterConfig {
    @Bean // 반환하는 객체를 빈으로 등록
    public FilterRegistrationBean<RequestLoggingFilter> requestLoggingFilter() {
        FilterRegistrationBean<RequestLoggingFilter> registration = new FilterRegistrationBean<>();
        registration.setFilter(new RequestLoggingFilter());     // 필터 인스턴스 생성
        registration.addUrlPatterns("/posts", "/posts/*");      // 적용할 URL 패턴 (*은 와일드카드)
        registration.setOrder(1);                               // 필터 적용 우선순위
        return registration;
    }
}
```

### `@Component`로 등록하는 방식

Config 클래스 없이 `@Component`로 등록하고 `@Order`로 우선순위를 정하는 방법도 있다. 앞의 방식보다 간단해 보이지만, `addUrlPatterns()`처럼 세부 설정을 하기는 더 복잡하다는 단점이 있다.

```java
@Slf4j
@Component
@Order(1)
public class RequestLoggingFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain chain
    ) throws ServletException, IOException {
        long start = System.nanoTime();
        log.info("BEFORE {} {}", request.getMethod(), request.getRequestURI());
        try {
            chain.doFilter(request, response);
        } finally {
            long tookMs = (System.nanoTime() - start) / 1_000_000;
            log.info("AFTER {} {} -> {} ({}ms)", request.getMethod(),
                    request.getRequestURI(), response.getStatus(), tookMs);
        }
    }
}
```

## 8. Interceptor

컨트롤러 실행 전후에 공통 처리를 넣는 스프링 MVC의 인터페이스다.

`DispatcherServlet`은 요청을 받으면 처리할 핸들러(컨트롤러 메서드)를 먼저 선택하고, 인터셉터는 그 핸들러가 선택된 **이후**에 실행되므로 컨트롤러 메서드의 정보를 확인할 수 있다.

- `preHandle`: 컨트롤러 실행 전
- `postHandle`: 컨트롤러 실행 후
- `afterCompletion`: 요청 처리가 완전히 끝난 후

### 사용 방법

`HandlerInterceptor` 인터페이스를 구현해서 각 핸들러 메서드를 오버라이드하고, 클래스에 `@Component`를 붙여 빈으로 등록한다.

```java
@Slf4j
@Component
public class RequestLoggingInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler
    ) {
        log.info("preHandle: {}", request.getRequestURI());
        return true; // true면 다음 인터셉터/컨트롤러로 진행, false면 여기서 중단
    }

    @Override
    public void postHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            ModelAndView modelAndView
    ) {
        log.info("postHandle: {} -> {}", request.getRequestURI(), response.getStatus());
    }

    @Override
    public void afterCompletion(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            Exception ex
    ) {
        log.info("afterCompletion: {} -> {}", request.getRequestURI(), response.getStatus());
    }
}
```

### Config 클래스에 등록

`WebMvcConfigurer` 인터페이스를 구현한 Config 클래스에서 설정한다. 위에서 만든 인터셉터 빈을, Config 빈이 생성되는 시점에 주입받고, 그 빈을 대상으로 `addInterceptors` 메서드에서 등록한다.

- `addPathPatterns("/posts/**")`: 이 경로로 들어오는 요청에 인터셉터를 적용
- `excludePathPatterns("/posts/public/**")`: `addPathPatterns`로 지정한 범위 중 이 경로는 제외

```java
@Configuration
@RequiredArgsConstructor
public class WebConfig implements WebMvcConfigurer {
    private final RequestLoggingInterceptor requestLoggingInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(requestLoggingInterceptor)
                .addPathPatterns("/posts/**")
                .excludePathPatterns("/posts/public/**");
    }
}
```

인터셉터는 여러 개를 만들고 같은 메서드 안에서 함께 등록할 수 있다.
```java
@Configuration
@RequiredArgsConstructor
public class WebConfig implements WebMvcConfigurer {

    private final RequestLoggingInterceptor requestLoggingInterceptor;
    private final AuthCheckInterceptor authCheckInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(requestLoggingInterceptor)
                .addPathPatterns("/**");

        registry.addInterceptor(authCheckInterceptor) // 같은 메서드 안에서 한 번 더
                .addPathPatterns("/admin/**");
    }
}
```

## 9. 스케줄링

정해진 간격이나 시각에 자동으로 로직을 실행하는 기능이다.

```java
@Configuration
@EnableScheduling
public class SchedulingConfig {
}
```
어느 `@Configuration` 클래스에 붙이든 애플리케이션 컨텍스트 전역에서 스케줄링을 쓸 수 있게 된다. 그래도 역할 분리를 위해, 내용이 비어있는 클래스라도 `SchedulingConfig`처럼 따로 두는 게 낫다.

```java
// 매 5초마다
@Scheduled(cron = "*/5 * * * * *")
public void task() { }

// 매일 오전 9시
@Scheduled(cron = "0 0 9 * * *")
public void task() { }

// 평일 오전 9시
@Scheduled(cron = "0 0 9 * * MON-FRI")
public void task() { }
```
cron 표현식의 규칙은 외워야 하는 게 아니라 필요할 때 찾아서 쓰면 된다. 다만 스케줄링은 코드만 볼 게 아니라 **배포 상황까지 고려**해서 신중히 써야 한다. 예를 들어 서버가 3대라면, 같은 스케줄링 코드가 각 서버에서 동시에 실행되어 같은 작업이 3번 발생하는 문제가 생길 수 있다.

## 10. RestClient

클라이언트의 입장이 되어 다른 서버에게 HTTP 요청을 보내는 도구다.

**의존성 추가**
```
implementation 'org.springframework.boot:spring-boot-starter-restclient'
```

**사용 방법**: `RestClient` 객체에서 메서드를 차례로 호출하는 방식이다.
1. HTTP 요청 종류 선택 — 보낼 요청에 맞게 `.get()`, `.post()` 등을 선택
2. URI 입력 — 요청을 보낼 URI 지정
3. 실제 요청 — 위 설정을 바탕으로 HTTP 요청 전송
4. 응답 저장 — 응답받은 내용을 준비해둔 객체에 담기

```java
@Slf4j
@Service
public class ExchangeRateClient {
    private final RestClient restClient;

    public ExchangeRateClient(
            RestClient.Builder builder,
            @Value("${rates.base-url}") String baseUrl
    ) {
        this.restClient = builder.baseUrl(baseUrl).build();
    }

    public ExchangeRateResponse fetch(String code) {
        log.info("환율 API 호출: {}", code);
        return restClient.get()
                .uri("/rates/{code}.json", code)
                .retrieve()
                .body(ExchangeRateResponse.class);
    }
}
```

### HTTP 에러 처리

RestClient로 요청을 보낼 때 자주 발생하는 예외:

| 외부 응답 | 발생하는 예외 |
|---|---|
| 4xx — 요청한 자원이 없거나 요청이 잘못됨 | `HttpClientErrorException` |
| 5xx — 외부 서버가 요청을 처리하지 못함 | `HttpServerErrorException` |

### 타임아웃

요청을 보낸 뒤 언제까지 기다릴지를 설정한다.
```properties
# 연결 대기 최대 2초
spring.http.clients.connect-timeout=2s
# 연결 후 응답 대기 최대 2초
spring.http.clients.read-timeout=2s
```

### 재시도 (실패 시 재호출)

재시도를 활성화하려면 `@EnableResilientMethods`가 붙은 Config가 있어야 한다.
```java
@Configuration
@EnableResilientMethods
public class ResilienceConfig {
}
```

`@Retryable` 애노테이션으로 요청 메서드에 재시도를 설정할 수 있다.
- `includes`: 재시도를 트리거할 예외 클래스들
- `maxRetries`: 재시도 횟수
- `delay`: 재시도 간 대기 시간(밀리초)

```java
@Slf4j
@Service
public class ExchangeRateClient {
    private final RestClient restClient;

    public ExchangeRateClient(
            RestClient.Builder builder,
            @Value("${rates.base-url}") String baseUrl
    ) {
        this.restClient = builder.baseUrl(baseUrl).build();
    }

    @Retryable(
            includes = {HttpServerErrorException.class, ResourceAccessException.class},
            maxRetries = 3,
            delay = 200)
    public ExchangeRateResponse fetch(String code) {
        log.info("환율 API 호출: {}", code);
        return restClient.get()
                .uri("/rates/{code}.json", code)
                .retrieve()
                .body(ExchangeRateResponse.class);
    }
}
```

## 11. 세션

**인증(Authentication)**: 누구인지 확인하는 절차 → 로그인. 실패 시 `401 Unauthorized`
**인가(Authorization)**: 특정 행위를 할 수 있는지 확인하는 절차 → 권한. 실패 시 `403 Forbidden`

**세션(Session)**: 사용자의 로그인 정보를 서버가 보관하는 저장 공간(방식). 세션이 유지되는 동안은 서버가 사용자를 계속 기억해서 로그인 상태가 유지된다.

스프링(톰캣)에서는 `JSESSIONID`라는 이름의 세션 키를 발급해서, 이를 쿠키에 담아 응답한다.

**전체 흐름**:
1. 서버가 세션을 만들고, 그 세션을 가리키는 키(`JSESSIONID`)를 쿠키에 담아 응답한다. 이때 응답 헤더 이름이 `Set-Cookie`인 이유는, 서버가 클라이언트(브라우저)에게 "이 값을 쿠키로 저장해라"라고 자동으로 지시하기 때문이다. `JSESSIONID`의 값 자체는 무작위 문자열이다.
2. 이후 같은 도메인으로 보내는 모든 요청에, 브라우저는 저장해둔 이 쿠키를 자동으로 실어 보낸다. 이때는 헤더 이름이 `Cookie`다(`Set-Cookie`로 저장해둔 값이 그대로 실려 나가는 것).
3. 서버는 `HttpServletRequest`를 통해 이 `Cookie` 헤더에서 세션 ID를 꺼내고, 그 ID로 서버의 세션 저장소를 조회해서 로그인 상태를 확인한다.

### 예시 코드 전체 흐름

```java
// 세션 attribute의 키를 상수로 관리하는 클래스 (직접 객체로 생성되지 않도록 abstract로 선언)
public abstract class SessionConst {
    public static final String LOGIN_MEMBER_ID = "LOGIN_MEMBER_ID";
}
```

**회원가입** — 그동안 다뤄온 것과 같은, 단순히 DB에 저장하는 흐름이다.
```java
@PostMapping("/signup")
public ResponseEntity<MemberResponse> signup(
        @RequestBody SignupRequest body
) {
    return ResponseEntity.status(HttpStatus.CREATED).body(authService.signup(body));
}
```

**로그인** — 받은 요청과 가입 시 저장된 정보를 대조한다(정보가 틀리면 예외 발생으로 흐름이 중단됨).
- `HttpServletRequest`는 매개변수로 선언해두면 요청마다 자동으로 할당된다. 클라이언트가 보낸 정보를 그대로 담고 있을 뿐 아니라, 그 정보(세션 ID 등)를 열쇠로 서버의 다른 저장소(세션 저장소 등)에서 데이터를 찾아오는 통로 역할도 한다.
- `request.getSession()`은 세션 저장소에 이미 세션이 있으면 그걸 반환하고, 없으면 새로 생성하거나 `null`을 반환한다. 생성 여부는 인자 `true`(생성)/`false`(없으면 `null`)로 결정되며, 인자를 생략하면 기본값은 `true`다.
- `request.changeSessionId()`는 세션 안의 데이터는 그대로 두고, 클라이언트에게 노출되는 세션 ID만 새로 바꾼다(세션 고정 공격 방지 목적). 세션이 없는 상태에서 호출하면 예외가 발생하므로, 반드시 `getSession()`으로 세션을 확보한 뒤에 호출해야 한다.
- `session.setAttribute(...)`는 세션 안에 데이터를 저장한다(매개변수의 상수를 키로, 인증에 성공한 회원의 id를 값으로). 그 키로 저장된 값이 없었다면 새로 추가되고, 이미 있었다면 덮어써진다.
- `cacheControl(CacheControl.noStore())`는 응답 헤더에 "이 응답을 저장해도 되는지"에 대한 지시를 담는 메서드다. `noStore`라면 브라우저(및 중간 캐시)에게 이 응답을 저장하지 말라고 지시한다.

```java
@PostMapping("/login")
public ResponseEntity<MemberResponse> login(
        @RequestBody LoginRequest body,
        HttpServletRequest request
) {
    MemberResponse member = authService.authenticate(body);
    HttpSession session = request.getSession();
    request.changeSessionId();
    session.setAttribute(SessionConst.LOGIN_MEMBER_ID, member.getId());
    return ResponseEntity.ok().cacheControl(CacheControl.noStore()).body(member);
}
```

**마이페이지** — 클라이언트가 보낸 쿠키를 통해 세션을 조회하고, 그 세션에 저장된 회원 ID로 DB에서 정보를 가져온다.
```java
@GetMapping("/me")
public ResponseEntity<MemberResponse> me(
        @SessionAttribute(name = SessionConst.LOGIN_MEMBER_ID, required = false) Long memberId
) {
    return ResponseEntity.ok().cacheControl(CacheControl.noStore())
            .body(authService.requireMember(memberId));
}
```

**로그아웃** — `HttpServletRequest`에서 `getSession`으로 세션을 가져와 폐기한다.
`getSession`으로 가져온 값이 null이 아니라면 `session.invalidate()` 로 폐기.
```java
@PostMapping("/logout")
public ResponseEntity<Void> logout(
        HttpServletRequest request
) {
    HttpSession session = request.getSession(false);
    if (session != null) {
        session.invalidate();
    }
    return ResponseEntity.noContent().build();
}
```

**세션 만료 설정** - 환경 변수로 설정하여 세션만료 시간을 정할 수 있다. (application.properties 등) 
```
//설정 전에는 세션은 시간이 지나도 만료되지 않는다.

server.servlet.session.timeout=30m //30분 후 만료

server.servlet.session.timeout=30s //30초 후 만료

```
