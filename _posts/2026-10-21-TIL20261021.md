## 1. 랭킹 상위 목록 미표시 · 집계 시각 16일 고정

### 증상

| 환경 | 상태 |
| --- | --- |
| 로컬 | 정상 |
| AWS | 상위 랭킹이 표시되지 않음, 집계 시각이 **10/16**에서 멈춤 |

### 랭킹 구조

```
실시간 랭킹   ranking:{TYPE}                       ← 기록 시마다 갱신 (내 순위 계산)
집계본       ranking:{TYPE}:snapshot              ← 주기적으로 실시간 랭킹을 COPY (상위 100명 표시)
집계 시각     ranking:{TYPE}:snapshot:updated-at
```

상위 목록은 **집계본만** 조회하므로, 집계(COPY)가 실패하면 마지막 성공 시점에 멈춘다.

### 문제 로그

```
ERROR [MessageBroker-2] c.s.ranking.redis.RankingSnapshotJob : 랭킹 집계 실패: type=SWORD_LEVEL
Caused by: io.lettuce.core.RedisCommandExecutionException: CROSSSLOT Keys in request don't hash to the same slot
```

- SWORD_LEVEL, STAGE_CLEARED, COMBAT_POWER **3개 타입 모두** 실패

### 원인

- AWS ElastiCache(Valkey)는 **클러스터 모드** → 키 이름에 따라 데이터를 여러 슬롯에 분산 저장
- 집계 코드의 `COPY`는 **키 2개를 함께 다루는 명령**
- `ranking:SWORD_LEVEL`과 `ranking:SWORD_LEVEL:snapshot`이 **다른 슬롯**에 배치 → `CROSSSLOT`으로 거부
- 로컬 Redis는 단일 서버라 슬롯 구분이 없어 문제가 드러나지 않음

```java
// RankingRedisStore.snapshot()
if (count(key(type)) == 0) redis.delete(snapshotKey(type));
else redis.copy(key(type), snapshotKey(type), true);     // ← CROSSSLOT 발생
redis.opsForValue().set(updatedAtKey(type), ...);         // 예외로 도달하지 못함
```

### 16일에 멈춘 이유

1. 10/16 최초 기동 시 실시간 랭킹이 **비어 있음** → `COPY` 대신 `delete` 경로 → 성공 → 집계 시각 16일 기록
2. 이후 실시간 랭킹에 데이터가 생기자 `COPY` 실행 → **매번 CROSSSLOT 실패**
3. 재시작 시 복구 로직(`RankingRedisRestorer`)은 **집계 시각이 없을 때만** 집계 → 16일 값이 남아 재시도 안 함
4. 상위 목록은 16일의 **빈 집계본**을 계속 표시

### 해결

**해시 태그**로 관련 키를 같은 슬롯에 배치 (PR #24 `dev_JH/Ranking-Fix`)

```java
// 변경 전
private String key(RankingType type) { return "ranking:" + type.name(); }

// 변경 후 — {} 안의 값으로만 슬롯 계산 → 세 키가 항상 같은 슬롯
private String key(RankingType type) { return "ranking:{" + type.name() + "}"; }
```

```
ranking:{SWORD_LEVEL}
ranking:{SWORD_LEVEL}:snapshot
ranking:{SWORD_LEVEL}:snapshot:updated-at
```

- 새 키는 비어 있으므로 부팅 시 DB에서 실시간 랭킹 복구 + 즉시 1회 집계
- 다른 Redis 사용처 점검 결과: `BattleLock` Lua 스크립트는 **키 1개**라 영향 없음 → 수정은 이곳 하나로 충분

### 확인

| 시각 (UTC) | 내용 |
| --- | --- |
| 03:52 | main 배포 (`e0ae99a`, PR #25) |
| 03:55 | `Started SwordmasterApplication`, Flyway 검증 7건 통과 |
| 03:56 ~ | 매 분 집계 중 `랭킹 집계 실패` **로그 없음** → 해결 |

### 분석 과정

1. CloudWatch에서 `랭킹` 검색 → 매 분 3건씩 `랭킹 집계 실패` 확인
2. 요약 줄만 보여 원인 불명 → `CROSSSLOT` / `Caused by`로 재검색 (스택 트레이스는 별도 로그 이벤트로 저장됨)
3. CROSSSLOT 확인 → 클러스터 모드의 다중 키 명령 문제로 확정
4. 코드 전체에서 다중 키 Redis 명령 점검

## 2. DB 데이터 초기화와 후속 영향

### 작업

- 수동 스냅샷 생성 후 운영 DB 11개 테이블 `TRUNCATE` (테이블 구조 유지)
- **`flyway_schema_history`는 제외** (비우면 다음 배포 시 Flyway 검증 실패)

```sql
SET FOREIGN_KEY_CHECKS = 0;
TRUNCATE TABLE `battle_histories`;

TRUNCATE TABLE `idempotency_keys`;
TRUNCATE TABLE `player_artifacts`;

TRUNCATE TABLE `player_rankings`;
TRUNCATE TABLE `players`;
TRUNCATE TABLE `refresh_tokens`;
TRUNCATE TABLE `shop_purchase_logs`;
TRUNCATE TABLE `user_identities`;
TRUNCATE TABLE `users`;
SET FOREIGN_KEY_CHECKS = 1;
```

### 후속 영향

| 현상 | 원인 | 조치 |
| --- | --- | --- |
| `BusinessException: 플레이어 정보가 없습니다.` | 기존 토큰을 가진 클라이언트가 요청했지만 플레이어 데이터가 삭제됨 | 정상 동작. **재가입 필요** 공지 |
| 랭킹에 "알 수 없음" 플레이어 표시 가능 | DB는 비었지만 Redis의 옛 랭킹 키는 남음 | 해시 태그 적용으로 새 키 사용 → 옛 데이터 미조회. 옛 키는 개별 `DEL`로 정리 예정 |

## 3. 기타 로그에서 발견된 사항

| 로그 | 의미 | 조치 |
| --- | --- | --- |
| `Using generated security password: ...` | Spring Security가 기본 테스트 계정을 자동 생성 (JWT 구조라 실제 사용 안 됨) | `UserDetailsServiceAutoConfiguration` 제외 검토 (보안 담당과 상의) |
| 스케줄 작업이 `MessageBroker-*` 스레드에서 실행 | 집계 작업이 STOMP 브로커 스케줄러 스레드 풀을 공유 | 당장 문제 없음. 채팅 부하 증가 시 전용 스케줄러 검토 |
