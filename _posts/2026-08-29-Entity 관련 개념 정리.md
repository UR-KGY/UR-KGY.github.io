# JPA / Entity / 영속성 컨텍스트 학습 노트



---

## 1. 큰 그림 - 왜 JPA를 쓰는가

자바 객체와 데이터베이스(DB)는 생긴 모양이 다릅니다. 자바는 객체, DB는 테이블(표)입니다.
원래는 이 둘을 연결하려면 `INSERT INTO player (name, level) VALUES (...)` 같은 SQL을 직접 작성해야 했습니다.

**ORM (Object-Relational Mapping)**은 "자바 객체 ↔ DB 테이블"을 자동으로 연결해주는 방식입니다.
SQL을 직접 안 쓰고, 자바 코드만으로 저장/조회/수정/삭제를 할 수 있게 해줍니다.

**JPA (Java Persistence API)**는 이 ORM을 하는 방법에 대한 **표준 규격**입니다. JPA 자체는 동작하지 않고,
실제로 동작하는 건 **Hibernate** 같은 구현체입니다. (JPA = 규격, Hibernate = 그 규격을 구현한 제품)

---

## 2. Entity - DB 테이블과 짝지어진 자바 클래스

`@Entity`가 붙은 클래스는 DB의 특정 테이블과 1:1로 대응됩니다.

```java
@Entity
public class Player {

    @Id                                          // 고유 식별자(기본 키) 표시
    @GeneratedValue(strategy = GenerationType.IDENTITY) // DB가 자동으로 번호 채움
    private Long id;

    private String name;
    private int level;
    private int exp;
}
```

| 어노테이션 | 의미 |
|---|---|
| `@Entity` | 이 클래스는 DB 테이블과 연결되어 있다 |
| `@Id` | 이 필드가 각 데이터를 구분하는 고유 값(기본 키)이다 |
| `@GeneratedValue` | 고유 값을 DB가 자동으로 채워준다 (직접 안 정함) |

---

## 3. EntityManager - DB를 다루는 창구

`EntityManager`는 Entity 객체를 실제로 저장·조회·수정·삭제하는 역할을 대신 해주는 객체입니다.
SQL을 직접 만드는 건 엄밀히는 Hibernate(구현체)가 하고, `EntityManager`는 그 요청을 받는 창구입니다.

```java
entityManager.persist(player);              // 새로 저장
Player p = entityManager.find(Player.class, 1L); // ID로 조회
entityManager.remove(p);                     // 삭제 예정으로 표시
```

**수정(Update)은 별도 메서드가 없습니다.** 조회해온 객체의 값을 그냥 바꾸면,
영속성 컨텍스트가 알아서 변경을 감지해서 반영합니다 (→ 더티 체킹, 아래 참고).

### 3-1. 자바 코드 ↔ 실제 SQL 대응표

자바 코드로는 SQL을 안 쓰지만, 뒤에서 Hibernate가 실제로 이런 SQL을 만들어서 DB로 보냅니다.
(콘솔 로그를 켜두면 실제로 이 SQL이 출력되는 걸 볼 수 있습니다.)

**조회 (SELECT) - `find()`**

```java
Player p = entityManager.find(Player.class, 1L);
```

```sql
SELECT id, name, level, exp
FROM player
WHERE id = 1;
```

**저장 (INSERT) - `persist()`**

```java
Player player = new Player();
player.setName("용사");
player.setLevel(1);
entityManager.persist(player);
```

```sql
INSERT INTO player (id, name, level, exp)
VALUES (1, '용사', 1, 0);
```

**수정 (UPDATE) - 값만 변경 (더티 체킹)**

```java
Player p = entityManager.find(Player.class, 1L);
p.setLevel(10);   // update() 같은 메서드를 따로 호출하지 않음
```

```sql
UPDATE player
SET name = '용사', level = 10, exp = 0
WHERE id = 1;
```

> 참고: 더티 체킹은 기본적으로 **바뀐 필드만이 아니라 엔티티 전체 컬럼**을 UPDATE 문에 담아 보냅니다.
> (필요하면 `@DynamicUpdate` 같은 옵션으로 바뀐 컬럼만 보내게 바꿀 수 있습니다.)

**삭제 (DELETE) - `remove()`**

```java
Player p = entityManager.find(Player.class, 1L);
entityManager.remove(p);
```

```sql
DELETE FROM player
WHERE id = 1;
```

> 위 4개의 SQL은 모두 **즉시** 실행되는 게 아니라, `commit()`(정확히는 그 안의 flush 시점)에
> 한꺼번에 DB로 전송됩니다. 자세한 순서는 아래 5-3절 참고.

---

## 4. 트랜잭션 - 전부 성공 아니면 전부 무효

여러 작업을 하나의 묶음으로 처리해서, **묶음 전체가 성공해야 commit으로 확정 반영**되고,
하나라도 실패하면 지금까지 한 작업을 전부 되돌리는(rollback) 안전장치입니다. ("All or Nothing")

```java
try {
    player.setGold(player.getGold() - 100);  // 1. 골드 차감
    inventory.addItem(sword);                 // 2. 아이템 지급

    entityManager.getTransaction().commit();  // 둘 다 성공 → 확정
} catch (Exception e) {
    entityManager.getTransaction().rollback(); // 하나라도 실패 → 전부 취소
}
```

골드만 깎이고 아이템은 안 들어오는 버그를 막아주는 게 트랜잭션의 역할입니다.

## 5. 영속성 컨텍스트 (Persistence Context) - 오늘의 핵심

`EntityManager`가 관리하는 Entity 객체들이 머무는 **메모리 상의 보관 공간**입니다.
(비유: 던전에 들어갈 때 캐릭터를 담아두는 "파티 창")

### 5-1. 주요 기능 3가지

| 기능 | 설명 |
|---|---|
| **1차 캐시** | 같은 ID로 두 번 조회해도 DB에 다시 안 가고, 이미 갖고 있는 객체를 바로 반환 |
| **동일성 보장** | 같은 영속성 컨텍스트 안에서 같은 ID를 조회하면 **완전히 같은 객체(주소)**가 나옴 (`p1 == p2` → `true`) |
| **더티 체킹** | 관리 중인 객체의 필드 값을 바꾸기만 해도, flush/commit 시점에 자동으로 UPDATE SQL 생성 |
| **쓰기 지연** | `persist()`해도 즉시 SQL이 안 나감. 대기 목록에 쌓아뒀다가 flush 시점에 한꺼번에 전송 |

```java
Player p1 = entityManager.find(Player.class, 1L);
Player p2 = entityManager.find(Player.class, 1L);
System.out.println(p1 == p2); // true - 완전히 동일한 객체

p1.setLevel(10); // save() 안 불러도 됨 → 더티 체킹으로 자동 UPDATE
```

> ⚠️ 동일성 보장은 **같은 EntityManager(같은 영속성 컨텍스트) 안에서만** 성립합니다.
> 다른 EntityManager로 같은 ID를 조회하면 값은 같아도 객체(주소)는 다릅니다.

### 5-2. Entity의 4가지 상태

| 상태 | 설명 |
|---|---|
| 비영속 (new/transient) | `new Player()`만 한 상태. 영속성 컨텍스트와 무관 |
| 영속 (managed) | `persist()` 또는 `find()`로 영속성 컨텍스트에 들어온 상태. 캐싱/더티체킹 적용됨 |
| 준영속 (detached) | 한때 영속 상태였다가 컨텍스트에서 빠져나옴. 더티체킹 안 됨 (`merge()`로 재등록 가능) |
| 삭제 (removed) | `remove()` 호출로 삭제 예정 표시된 상태 |

### 5-3. 저장/삭제가 실제로 반영되는 순서

```
persist(memo) 또는 remove(memo)
  → 영속성 컨텍스트에 상태만 기록 (entityKeys에 추가/삭제 표시)
  → 실제 SQL은 아직 DB로 안 감 (쓰기 지연 SQL 저장소에 대기)

commit() 호출
  → 1단계: flush 발생 → 대기 중이던 SQL들이 실제 DB로 전송됨
  → 2단계: DB 트랜잭션이 최종 확정(commit)됨
```

즉 `persist()`나 필드 값 변경은 "메모만 남기는 것"이고, 실제 DB 반영은
**flush(SQL 전송) → commit(최종 확정)** 두 단계를 거쳐 일어납니다.

예를 들어 캐릭터 하나를 새로 만들고, 다른 캐릭터를 하나 지우고, 레벨을 하나 수정한 뒤 commit 하면:

```java
entityManager.persist(newPlayer);   // INSERT 대기
entityManager.remove(oldPlayer);    // DELETE 대기
existingPlayer.setLevel(20);        // UPDATE 대기 (더티 체킹)

entityManager.getTransaction().commit(); // 여기서 flush → 아래 SQL 3개가 순서대로 DB에 전송됨
```

```sql
INSERT INTO player (id, name, level, exp) VALUES (3, '신규용사', 1, 0);
DELETE FROM player WHERE id = 2;
UPDATE player SET name = '기존용사', level = 20, exp = 0 WHERE id = 1;
```

## 6. 한 줄 정리

- **JPA**: 자바 객체와 DB를 SQL 없이 연결하는 표준 규격
- **Entity**: DB 테이블과 짝지어진 자바 클래스 (`@Entity`, `@Id`)
- **EntityManager**: Entity를 저장·조회·삭제하는 창구 (SQL은 Hibernate가 대신 만듦)
- **트랜잭션**: 묶인 작업이 전부 성공해야 commit, 하나라도 실패하면 rollback
- **영속성 컨텍스트**: EntityManager가 관리하는 객체들의 보관 공간. 1차 캐시, 동일성 보장, 더티 체킹, 쓰기 지연이 여기서 일어남
