## 영속성 컨텍스트 (Persistence Context)

어플리케이션과 DB 사이에서 임시로 객체(Entity)를 보관하는 역할을 한다.

**하는 일**
1. 엔티티를 임시로 보관
2. 변경사항을 추적(더티 체킹)
3. DB와 동기화

### 엔티티 생명주기

엔티티 객체가 생성되어 소멸되기까지 거치는 여러 상태 변화 과정.

- **비영속**: 영속성 컨텍스트와 아무런 관계가 없는 상태. DB에 한 번도 갔다오지 않은 상태.
- **영속**: 영속성 컨텍스트에 의해 관리되고 있는 상태. DB를 갔다 온 상태.
- **준영속** 트랜잭션 종료 후 영속성 컨텍스트를 벗어난 상태.

### 트랜잭션과의 관계

작업이 모두 성공하거나 하나라도 실패하면 모두 실패하는 것을 말한다 (원자성).
영속성 컨텍스트가 동작하려면 트랜잭션의 경계 안에 있어야만 한다.

## JPA에서의 트랜잭션 적용

어플리케이션에서 트랜잭션이라는 것은 하나의 작업 단위를 뜻한다.
이 작업 단위는 여러 개의 DB 연산으로 이루어지는 경우가 많다.

예시 (계좌 이체):
1. 사용자가 사용자의 계정에서 10000원을 차감
2. 사용자의 상대방 계정에 10000원을 추가
3. 송금 내역을 장부에 기록

이 중 하나라도 제대로 되지 않는다면 송금이 제대로 이루어졌다고 할 수 없다.
이 세 가지 작업을 한 단위로 묶어 하나라도 실패하면 롤백시키는 것이 트랜잭션이다.

```java
@Service // 비즈니스 로직이니 서비스 계층에서 작성
@RequiredArgsConstructor
public class AccountService {

    @Transactional
    public void paymentTransaction() {
        // 1. 사용자 A의 계좌에서 10,000원을 차감하는 로직
        // 2. 사용자 B의 계좌에 10,000원을 추가하는 로직
        // 3. 송금 내역을 장부에 기록하는 로직
    }
}
```

### @Transactional

JPA에선 트랜잭션을 사용할 때 `@Transactional` 어노테이션을 메서드에 붙인다.
메서드 자체가 트랜잭션의 한 단위 개념이 되는 것이다.

속성 (예: `@Transactional(readOnly = true)`처럼 사용):

- **readOnly**: 기본값은 false. 읽기 전용으로 설정하여 성능을 최적화할 것인지를 정한다. 데이터 조회 전용이라고 선언하는 셈.
- **propagation**: 트랜잭션 전파 규칙을 정의한다. (아직 자세히는 모름)
- **isolation**: 트랜잭션의 격리 수준을 설정하여 동시성 문제를 제어한다. (아직 자세히는 모름)
- **rollbackFor**: 특정 예외가 발생했을 때 강제로 롤백하도록 지정한다. (아직 자세히는 모름)

## JpaRepository 활용

`JpaRepository<>`는 인터페이스이다. 제네릭에 각각 대응할 'Entity 타입', 'Entity의 Id 타입'을 넣고 상속시켜 사용한다.
레포지토리는 DB에서 데이터를 관리하는 메서드를 만들기만 하고 이것을 사용하는 쪽은 서비스이다.

```java
@Service
@RequiredArgsConstructor // 아래의 생성자 내용을 생략할 수 있는 Lombok 어노테이션
public class UserService {
    private final UserRepository userRepository; // 생성자를 기반으로 Repository 빈을 주입받음

    public UserService(UserRepository userRepository) { // @RequiredArgsConstructor로 생략 가능
        this.userRepository = userRepository;
    }
}
```

## CRUD 작업

### CREATE

Entity 객체를 새로 만들어 repository의 `save()` 메서드 안에 넣어 저장한다.

```java
// 컨트롤러 부분
@PostMapping("/memos") // 무언가 새로 만드는 것이기 때문에 POST 매핑
public ResponseEntity<MemoCreateResponse> create(@RequestBody MemoCreateRequest request) {
    return ResponseEntity.ok(service.save(request));
}
```

```java
// 서비스 부분
@Transactional
public MemoCreateResponse save(MemoCreateRequest request) {
    Memo memo = new Memo(request.getName(), request.getComment());
    Memo saveMemo = repository.save(memo);
    return new MemoCreateResponse(
            saveMemo.getId(),
            saveMemo.getName(),
            saveMemo.getComment(),
            saveMemo.getCreatedAt(),
            saveMemo.getModifiedAt()
    );
}
```

### READ

READ 용도로 메서드를 사용할 땐 `@Transactional`의 `readOnly`를 true로 사용한다 (가져오기만 하니까).

이 때 단건 조회는 조건에 해당하는 데이터가 없을 시 null을 반환할 수 있기 때문에 Optional 타입에 묶여서 객체가 반환된다.
Optional 타입에서 객체를 빼오는 방법은 `orElse` 계열 메서드를 사용하는데, `orElseThrow`는 데이터가 없을 시에 예외를 던지고 데이터가 있다면 객체를 반환해준다.

```java
// 컨트롤러 부분
@GetMapping("/memos")
public ResponseEntity<List<MemoGetResponse>> getAll() {
    return ResponseEntity.ok(service.findAll());
}

@GetMapping("/memos/{memoId}")
public ResponseEntity<MemoGetResponse> getOne(@PathVariable Long memoId) {
    return ResponseEntity.ok(service.findOne(memoId));
}
```

```java
// 서비스 부분
@Transactional(readOnly = true)
public List<MemoGetResponse> findAll() {
    List<Memo> memos = repository.findAll();
    List<MemoGetResponse> dtos = new ArrayList<>();
    for (Memo memo : memos) {
        MemoGetResponse dto = new MemoGetResponse(
                memo.getId(),
                memo.getName(),
                memo.getComment(),
                memo.getCreatedAt(),
                memo.getModifiedAt()
        );
        dtos.add(dto);
    }
    return dtos;
}

@Transactional(readOnly = true)
public MemoGetResponse findOne(Long memoId) {
    Memo memo = findById(memoId);
    return new MemoGetResponse(
            memo.getId(),
            memo.getName(),
            memo.getComment(),
            memo.getCreatedAt(),
            memo.getModifiedAt()
    );
}

private Memo findById(Long memoId) {
    return repository.findById(memoId).orElseThrow(
            () -> new IllegalStateException("해당하는 메모가 존재하지 않습니다.")
    );
}
```

### DELETE

우선 삭제할 데이터가 존재하는지 여부를 먼저 확인한다.

```java
// 컨트롤러 부분
@DeleteMapping("/memos/{memoId}")
public void delete(@PathVariable Long memoId) {
    service.delete(memoId);
}
```

```java
// 서비스 부분
@Transactional
public void delete(Long memoId) {
    if (!repository.existsById(memoId)) {
        throw new IllegalStateException("삭제하려는 해당 메모가 존재하지 않음");
    }
    repository.deleteById(memoId);
}
```

### UPDATE

업데이트 메서드는 레포지토리에서 따로 만들어주진 않는다. (레포지토리에서 자동으로 만들어주는 것은 제네릭으로 Id를 기반으로 한 메서드뿐이다.)
Entity 객체의 클래스에 `update()` 메서드를 따로 만들어준다.

```java
@Id @GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

@Column(length = 50, nullable = false)
private String name;

private String comment;

public Memo(String name, String comment) {
    this.name = name;
    this.comment = comment;
}

public void update(String name, String comment) {
    this.name = name;
    this.comment = comment;
}
```

```java
// 컨트롤러 부분
@PutMapping("/memos/{memoId}")
public ResponseEntity<MemoUpdateResponse> update(
        @PathVariable Long memoId,
        @RequestBody MemoUpdateRequest request
) {
    return ResponseEntity.ok(service.update(memoId, request));
}
```

업데이트 또한 단건 조회로 데이터를 가져온 후 해당 객체의 `update()`를 사용하여 데이터를 바꾸게 된다.
이때 더티 체킹이라는 용어가 나왔는데, 변경사항의 유무를 판별한다고 보면 된다.
트랜잭션 안에서 변경사항이 일어났을 경우 이것이 원본 데이터를 덮어씌운다고 보면 될 것 같다.

```java
@Transactional
public void update() {
    User user = userRepository.findById(1L).orElseThrow(
            () -> new IllegalStateException("존재하지 않는 유저입니다.")
    );
    user.update("새로운 이름", "new-email@naver.com", "경기도");
}

@Transactional
public MemoUpdateResponse update(Long memoId, MemoUpdateRequest request) {
    Memo memo = findById(memoId);
    memo.update(
            request.getName(), request.getComment()
    );
    return new MemoUpdateResponse(
            memo.getId(),
            memo.getName(),
            memo.getComment(),
            memo.getCreatedAt(),
            memo.getModifiedAt()
    );
}
```

## 커스텀 쿼리 메서드

repository의 `save()`, `findById()`, `existsById()` 등은 자동으로 생성되어 있다. (제네릭으로 만들어진 메서드가 미리 선언되어 있기 때문)
자동 생성된 메서드는 Id를 조건으로 하거나 조건이 필요없는 메서드들뿐이다.
만약 다른 조건을 가진 메서드가 필요하다면 직접 선언을 해야 한다.

```java
// 커스텀 쿼리 메서드
// Select * From User Where email = email
Optional<User> findByEmail(String email);
```

## DTO

원본 entity 객체 대신 데이터를 담아 요청, 응답에 쓰이는 객체를 말한다.

- **Request(요청) DTO**: 클라이언트가 보낸 요청이 실수로 변형되는 것을 방지하기 위해 필드에 `final`을 붙이는 경우가 많은 것 같다.
- **Response(응답) DTO**: 클라이언트에게 보내는 응답이며, return 시 `ResponseEntity<>` 클래스를 사용해 감싸 보낼 수 있다.

## Auditing

생성, 수정 시점의 시간을 기록하기 위해 사용한 기능이다.
최신 Jpa 버전에선 `@Temporal`을 생략하고 필드 타입으로 제어하는 듯하다. 예) `LocalTime`, `LocalDateTime`

```java
@Getter
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {

    @CreatedDate
    @Column(updatable = false)
    // @Temporal(TemporalType.TIMESTAMP) 최신 버전에서는 사용되지 않음
    private LocalDateTime createdAt;

    @LastModifiedDate
    // @Temporal(TemporalType.TIMESTAMP) 최신 버전에서는 사용되지 않음
    private LocalDateTime modifiedAt;
}
```

해당 기능을 사용하기 위해선 `@EnableJpaAuditing`을 어플리케이션에 붙여주어야 한다.

```java
@EnableJpaAuditing
@SpringBootApplication
public class MemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(MemoApplication.class, args);
    }
}
```

## IoC (제어의 역전)

스프링이 개발자 대신 객체를 생성(new를 선언할 필요 없이)하여 관리하는 것.
Bean을 관리하는 감독관을 IoC Container라고 부른다. 싱글톤 패턴이 적용되어 있는 듯하다.

## DI (의존성 주입)

IoC에서 사용자가 지정한 객체에 자동으로 의존성을 주입, 관리하는 것을 말한다.

## Bean

스프링에서 자동관리해주는 싱글톤 객체.
빈으로 설정할 객체는 자주 재사용되거나 교체가 가능한 비즈니스 로직이고 (Service, Repository, Controller 등도 빈 객체), 매번 새로운 상태를 가지는 객체일 경우엔 빈으로 등록하면 안 된다.

### 빈 설정 어노테이션

`@Component`가 붙은 클래스(`@Controller`, `@Service`, `@Repository` 등)는 Bean으로 등록된다.
`@ComponentScan`은 IoC Container에게 어디서 빈을 필요로 하는지 알려주는 역할을 한다.
`@SpringBootApplication`에 포함이 되어 있어 알게 모르게 사용 중이었다.

### @Bean 수동 등록

**@Configuration**: 클래스에 붙이는 어노테이션이며, 이 어노테이션이 붙은 클래스는 설정 클래스로 인식된다. 내부의 `@Bean` 메서드들이 컨테이너의 Bean으로 등록된다.

**@Bean**: 메서드에 붙이는 어노테이션. 이 메서드가 반환하는 객체를 Spring 컨테이너에 Bean으로 등록한다. Bean 이름은 기본적으로 메서드명으로 지어진다. (`@Bean(name="이름")`처럼 커스텀 가능)

```java
@Configuration
public class AppConfig {

    @Bean
    public MemberRepository memberRepository() {
        return new MemoryMemberRepository();
    }
}
```

빈을 자동으로 등록하는 경우는 `@Repository`, `@Controller`, `@Service`를 활용한 자동 등록이 사용 빈도가 높다.
수동 등록은 외부 라이브러리를 Bean으로 등록하고 싶을 때 활용한다.

### DI 비교 방식

**1. 필드 직접 선언 주입**

`@Autowired`를 필드에 붙여 빈 객체를 주입받는 방식이다. 이 방식은 `final`을 사용할 수 없어 중간에 객체가 바뀔 위험성이 있어 지금은 사용하지 않는다.

```java
@Service
public class MemberService {
    @Autowired
    private MemberRepository memberRepository;
}
```

**2. Setter 주입 방식**

이 방식 또한 객체 변경 위험으로 사용하지 않는다.

```java
@Service
public class MemberService {
    private MemberRepository memberRepository;

    @Autowired
    public void setMemberRepository(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }
}
```

**3. 생성자 주입 방식**

`final`로 필드를 선언하고 생성자로 객체를 주입하는 방식이다. `final`로 인해 중간에 객체를 다시 초기화하는 일이 일어나지 않아 가장 안전한 방식이다.

```java
@Service
public class MemberService {
    private final MemberRepository memberRepository;

    @Autowired // 생성자가 1개만 있으면 @Autowired 생략 가능
    public MemberService(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }
}
```

### Bean 우선순위

같은 타입의 빈이 두 개 이상 존재한다면 해당 타입의 주입 대상이 생겼을 때 에러가 발생한다. 따라서 그런 상황이 올 경우엔 우선순위를 지정해주어야 한다.

**@Primary**: 별다른 설정이 없다면 같은 타입의 여러 빈들 중 가장 우선적(default)으로 주입된다.

```java
@Component
public class KakaoPayService implements PayService { ... }

@Primary // PayService 타입의 빈이 여러 개일 때, 우선권을 갖는다!
@Component
public class NaverPayService implements PayService { ... }

@RestController
@RequiredArgsConstructor
public class PayController {
    private final PayService payService; // NaverPayService가 자동으로 주입됨
    // ...
}
```

**@Qualifier**: 직접 지정한 빈으로 대상을 주입하는 방법이다. `@Primary`보다 우선적으로 주입된다. `@Primary`는 보편적인 상황에 쓰이고 `@Qualifier`는 그 외 지정이 필요한 대상에게 쓰인다.

```java
@Component("kakaoPay") // "kakaoPay"라는 별명을 붙여줌
public class KakaoPayService implements PayService { ... }

@Component("naverPay")
public class NaverPayService implements PayService { ... }

@Service
public class OrderService {
    private final PayService payService;

    // "kakaoPay"라는 이름을 가진 빈을 주입해줘!
    public OrderService(@Qualifier("kakaoPay") PayService payService) {
        this.payService = payService;
    }
}
```
