## Validation

클라이언트 요청에 제한 조건을 거는 기능이다.

```
implementation 'org.springframework.boot:spring-boot-starter-validation'
```

```java
@Getter
public class UserSaveRequest {
    private long id;

    @Size(min = 4, max = 20)
    private String name;

    @Email
    private String email;
}
```

```java
@PostMapping("/users")
public ResponseEntity<UserSaveResponse> saved(
        @Valid @RequestBody UserSaveRequest request
) {
    return ResponseEntity.status(HttpStatus.CREATED).body(userService.save(request));
}
```

**주요 어노테이션**

- `@NotBlank`: 공백이 아닌 문자 1개 이상 (null, "", " " 모두 거부)
- `@Email`: 이메일 형식
- `@Size`: 문자열 길이/컬렉션 크기 제한
- `@Min` / `@Max`: 숫자 최소/최대값
- `@Pattern`: 정규표현식 강제
- `@Valid`: 컨트롤러의 `@RequestBody` 앞에 붙여 검증을 활성화

정규식은 직접 외우기보다 상황에 맞게 AI나 검색으로 만들어 쓰면 된다.

         message = "올바른 생년월일 형식이 아닙니다 (YYMMDD)")

## 예외처리

서버 예외가 클라이언트 잘못이어도 500으로 뭉뚱그려지는 걸 막기 위해, 상태 코드를 명확히 구분해서 응답할 의무가 있다.

**처리 전략 (우선순위 순)**

1. `@ExceptionHandler` — 컨트롤러 클래스마다 개별 선언. 컨트롤러가 많아질수록 중복 코드가 늘어남.
2. `@RestControllerAdvice` — 모든 컨트롤러의 예외를 한 곳에서 처리. 사실상 표준.
3. Spring 기본 예외 처리

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(IllegalStateException.class)
    public ResponseEntity<String> handleIllegalStateException(IllegalStateException e) {
        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body("요청 오류: " + e.getMessage());
    }
}
```

## 영속성 컨텍스트

불필요한 쿼리를 중간에 날리지 않고 최종 결과만 반영하려는 의도로 동작한다.

- **1차 캐시 & 동일성 보장**: ID를 키로 하는 캐시(Map). 같은 트랜잭션에서 같은 ID로 조회하면 DB를 다시 조회하지 않고 캐시된 엔티티를 반환하며, `==` 비교 시 항상 동일 인스턴스임을 보장한다.
- **더티 체킹**: 1차 캐시의 엔티티는 최초 상태와 현재 상태를 비교한다. flush 시점(보통 트랜잭션 커밋 직전)에 변경을 감지해 자동으로 UPDATE SQL을 생성한다.
- **쓰기 지연**: `save()` 호출 시 INSERT SQL을 바로 보내지 않고 모아뒀다가 커밋 시점에 한 번에 전송해, 네트워크 비용과 DB 상호작용 횟수를 줄인다.

**Flush**: 영속성 컨텍스트의 변경 내용을 DB에 동기화하는 것. 커밋과 달리 트랜잭션을 확정하지는 않으므로, 이후 롤백되면 flush로 반영된 내용도 함께 롤백된다.

## Entity Manager

내부에 영속성 컨텍스트를 가진 JPA 핵심 인터페이스. Spring Data JPA를 쓰는 지금은 내부적으로 관리된다는 정도만 알면 된다.

| 구성요소 | 역할 |
|---|---|
| Persistence Unit | DB 연결 정보, 관리할 Entity 목록, JPA 구현체 설정을 담은 설정 파일 |
| EntityManagerFactory | Persistence Unit으로 EntityManager를 생성. 앱당 하나만 존재, 스레드 안전 |
| EntityManager | 엔티티 저장/수정/삭제/조회 실행. 생명주기는 트랜잭션과 같음, 스레드 안전하지 않음 |

## 트랜잭션 전파

`@Transactional(propagation = ...)`로 설정하며, 기본값은 `REQUIRED`다.

| 옵션 | 동작 | 사용 예 |
|---|---|---|
| REQUIRED (default) | 부모 트랜잭션 있으면 참여, 없으면 새로 생성 | 서비스 핵심 로직 대부분 |
| REQUIRES_NEW | 부모와 무관하게 항상 새 트랜잭션 생성 | 메인 작업이 롤백돼도 남아야 하는 로그·통계 기록 |
| NESTED | 부모 있으면 그 안에 savepoint 생성(부모 롤백 시 함께 롤백), 없으면 REQUIRED와 동일. REQUIRES_NEW와 달리 부모에 종속적 | 큰 작업 중 일부만 실패 처리하고 싶을 때 (예: 쿠폰 적용 실패) |
| SUPPORTS | 부모 있으면 참여, 없으면 트랜잭션 없이 실행 | 읽기 전용 조회 |
| NOT_SUPPORTED | 항상 트랜잭션 없이 실행 | 이메일 발송, 외부 API 호출 |
| MANDATORY | 부모 트랜잭션 필수, 없으면 예외 | 반드시 트랜잭션 안에서만 호출돼야 하는 메서드 |
| NEVER | 트랜잭션 없을 때만 실행 가능, 있으면 예외 | 트랜잭션과 섞이면 안 되는 메서드 |

실무에서는 거의 기본값(REQUIRED)만 쓰고, 나머지는 필요할 때 찾아본다.

## 트랜잭션 격리 수준

동시 트랜잭션들이 서로 얼마나 격리될지 정하는 설정. 낮은 순서대로 READ UNCOMMITTED → READ COMMITTED → REPEATABLE READ → SERIALIZABLE.

| 격리 수준 | 설명 | 발생 현상 |
|---|---|---|
| READ UNCOMMITTED | 커밋 여부와 상관없이 다른 트랜잭션의 변경을 읽음. 정합성 문제로 사용 비권장 | DIRTY READ |
| READ COMMITTED | 커밋된 데이터만 읽음. RDB 기본값으로 흔함 | NON-REPEATABLE READ |
| REPEATABLE READ | 자신의 트랜잭션 시작 이전에 커밋된 데이터만 읽음. MySQL 기본값 | PHANTOM READ |
| SERIALIZABLE | 항상 Lock을 걸고 조회. 가장 엄격하나 성능 문제로 거의 안 씀 | - |

**용어**

- DIRTY READ: 커밋 안 된 변경을 다른 트랜잭션이 읽는 현상
- NON-REPEATABLE READ: 같은 트랜잭션에서 같은 쿼리를 두 번 실행했는데, 중간에 다른 트랜잭션의 커밋으로 결과가 달라지는 현상
- PHANTOM READ: 같은 범위 쿼리를 두 번 실행했는데, 중간에 다른 트랜잭션이 INSERT/DELETE해서 행 개수가 달라지는 현상 (NON-REPEATABLE READ는 "값 변경", PHANTOM READ는 "행 추가/삭제" 문제)

지금 단계에서 전파/격리 수준을 깊이 알 필요는 없고, 필요할 때(예: 면접) 찾아보면 된다.

## 연관관계

Entity(테이블) 간의 관계를 말한다.

### PK와 FK

- **PK**: 각 행을 유일하게 식별하는 값. 한 테이블에 PK 제약은 하나만 존재하지만, 열 하나로 구성될 수도 여러 열의 조합(복합키)일 수도 있다. 중복·NULL이 불가능해서 행을 유일하게 식별하는 데 쓰일 수 있다.
- **FK**: 다른 테이블의 PK를 참조하는 열. 중복과 NULL이 허용된다 (예: 한 팀에 여러 멤버가 속할 수 있고, 아직 팀이 없는 멤버도 있을 수 있음).

### 단방향 / 양방향 관계

**단방향**: 한쪽만 상대방의 PK를 FK로 참조.

```java
@Entity
public class Member {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String username;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "team_id")
    private Team team;
}

@Entity
public class Team {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
}
```

**양방향**: 서로 상대방의 PK를 참조. Team 쪽에 컬렉션을 추가한다 (한 팀에 여러 멤버가 속하므로 List).

```java
@Entity
public class Team {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;

    @OneToMany(mappedBy = "team")
    private List<Member> members = new ArrayList<>();
}
```

### 연관관계의 주인

- 단방향은 FK를 가진 쪽이 곧 주인 (다른 경우의 수가 없음).
- 양방향은 FK를 가진(즉 `@ManyToOne`이 붙은) 쪽이 주인. 주인이 아닌 쪽은 `mappedBy`로 주인의 필드를 명시하며, 이쪽 설정은 DB에 반영되지 않고 조회만 가능하다.

### 매핑 종류

- **@OneToOne (1:1)**: 예) 멤버-프로필. 사실상 멤버 엔티티에 프로필 필드를 합치면 되는 경우가 많아 실무에서 자주 쓰이진 않지만, 대용량 컬럼이나 민감 정보를 분리하고 싶을 때는 쓰인다.
- **@ManyToOne (N:1)**: 위 단방향 예시가 바로 이 매핑. 다수가 하나를 참조하며, 실무에서 사실상 이것만 쓴다고 봐도 될 정도로 기본이 되는 형태다.
- **@OneToMany (1:N)**: 위 양방향 예시가 바로 이 매핑. `@ManyToOne`이 있는 상대 테이블에만 붙일 수 있다. 문제가 많이 발생해 실무에선 잘 안 쓰는 방향으로 개발한다.
- **@ManyToMany**: 다대다 관계. 매핑 시 엔티티로 관리되지 않는 숨은 조인 테이블이 생겨 컬럼 추가나 조회가 어려워 잘 사용하지 않는다. 대신 중간 테이블을 직접 엔티티로 만들어 양쪽을 각각 `@ManyToOne`으로 연결하는 방식을 쓴다.

```java
@Entity
public class BookAuthor {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne @JoinColumn(name = "book_id")
    private Book book;

    @ManyToOne @JoinColumn(name = "author_id")
    private Author author;
}
```

### 조회 전략 (Fetch)

- `EAGER`: 조회 시 연관 엔티티도 즉시 함께 조회
- `LAZY`: 필요한 시점에만 연관 엔티티 조회 (주로 사용)

**@ManyToOne 옵션**: `fetch`(로딩 방식), `optional`(null 허용 여부, 기본 true)

**@JoinColumn 옵션**: `name`(FK 컬럼명), `unique`(사실상 1:1 제약화), `nullable`(FK NULL 허용 여부, `optional`과 짝을 맞춤), `foreignKey`(DB FK 제약 생성 여부/이름)

### 영속성 전이 (Cascade)

부모의 영속성 상태 변화를 자식에 전파. 실무에선 아예 안 쓰거나 `ALL`만 쓰는 경우가 대부분이다.

| 옵션 | 설명 |
|---|---|
| ALL | PERSIST+REMOVE+MERGE+REFRESH+DETACH 전체 적용. 부모·자식 생명주기가 완전히 일치할 때 |
| PERSIST | 부모 저장 시 자식도 함께 저장 |
| REMOVE | 부모 삭제 시 자식도 함께 삭제 |
| MERGE | 준영속 부모 병합 시 변경사항을 자식에도 적용 |
| REFRESH | 부모 재조회 시 자식도 함께 재조회 |
| DETACH | 부모 준영속화 시 자식도 함께 준영속화 |

**Orphan Removal**: 부모-자식 연관이 끊기면(컬렉션에서 제거/교체, 부모 삭제) 남은 자식을 자동 정리. `orphanRemoval = true`로 설정하며 역시 잘 안 쓴다.

## JPQL

| 구분 | 설명 | 예시 |
|---|---|---|
| SQL | 테이블/컬럼 기준으로 조회 | `SELECT * FROM members WHERE team_id = 1` |
| JPQL | 엔티티 객체/필드 기준으로 조회 | `SELECT m.username FROM Member m WHERE m.team = ?` |

차이: 대소문자 구분, 테이블명 대신 엔티티명 사용, 별칭(alias) 필수.

```java
@Query("SELECT m FROM Member m WHERE m.age > :age")
List<Member> findByAgeGreaterThan(@Param("age") int age);

@Query("SELECT m FROM Member m JOIN m.team t WHERE t.name = :teamName")
List<Member> findMembersInTeam(@Param("teamName") String teamName);

@Query("SELECT m FROM Member m LEFT JOIN m.team t")
List<Member> findAllMembersWithTeam();
```

## JPA 프로젝션

엔티티 전체가 아닌 원하는 필드만 골라 받는 기술.

**인터페이스 기반**: Getter만 선언하면 실행 시점에 구현체를 자동 생성.

```java
public interface NicknameOnlyDto {
    String getNickname();
}
List<NicknameOnlyDto> findByNickname(String nickname);
```

**클래스(DTO) 기반**: JPQL의 `new` 키워드로 DTO 생성자를 직접 호출.

```java
@Query("SELECT new com.member.dto.projection.MemberDto(m.nickname, t.name) " +
       "FROM Member m JOIN m.team t WHERE m.nickname = :nickname")
Optional<MemberDto> findMemberDtoByNickname(@Param("nickname") String nickname);
```

클래스 기반 프로젝션이 추천받은 방식이며, 직접 써보면서 익힐 필요가 있다.
