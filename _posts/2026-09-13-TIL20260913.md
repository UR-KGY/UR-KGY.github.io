## 1. Git 형상관리

### 1-1. .gitignore — 개인 설정 vs 팀 공용 설정

**용도** — Unity 프로젝트는 "팀 전체가 공유해야 하는 설정"과 "나만의 에디터 취향"이 폴더로 분리되어 있다. 이를 구분하지 않으면 개인 레이아웃이나 IDE 캐시가 실수로 저장소에 올라간다.

| 폴더/파일 | 커밋 여부 | 이유 |
|---|---|---|
| `ProjectSettings/` (AudioManager.asset, TagManager.asset 등) | O | 팀 전체가 공유해야 하는 게임 설정 |
| `UserSettings/` | X | 개인 에디터 레이아웃, 최근 연 씬 |
| `Library/`, `Temp/`, `Obj/` | X | 로컬 캐시, 자동 재생성됨 |
| `.vs/`, `.idea/`, `.vscode/` | X | IDE가 자동 생성하는 개인 설정 |
| `*.meta` | O (예외) | 에셋 GUID 매핑 — 절대 무시 금지 |

**예시 — 기본 .gitignore 핵심 라인**
```gitignore
[Ll]ibrary/
[Tt]emp/
[Oo]bj/
[Bb]uild/
[Ll]ogs/
[Uu]ser[Ss]ettings/

# IDE (에디터에 맞게 선택)
.vs/
.idea/
.vscode/
*.csproj
*.sln
*.user
*.userprefs
```

**주의사항**
- 이미 실수로 커밋된 폴더는 `.gitignore`에 추가하는 것만으로는 안 지워진다. `git rm -r --cached <폴더명>` 으로 추적을 끊어야 한다.
- `ProjectSettings/` 전체를 무시 대상으로 착각하지 않도록 주의한다 — 이건 반드시 커밋해야 하는 공용 설정이다.

### 1-2. 협업 시 설정 파일 관리

**사용법**
1. **텍스트 직렬화 고정** — `Edit > Project Settings > Editor`에서 Asset Serialization을 Force Text로 설정
2. **UnityYAMLMerge를 git mergetool로 등록**해서 충돌 시 자동 병합
3. 설정 변경은 코드와 분리해서 **작은 단위로, 자주** 커밋 + `pull` 먼저 하고 작업
4. Tag/Layer는 항상 **리스트 맨 뒤에만 추가** (중간 삽입 시 인덱스가 밀려 LayerMask 참조가 깨짐)

```bash
git config --global merge.tool unityyamlmerge
git config --global mergetool.unityyamlmerge.trustExitCode false
git config --global mergetool.unityyamlmerge.cmd \
  '"C:/Program Files/Unity/Hub/Editor/<버전>/Editor/Data/Tools/UnityYAMLMerge.exe" merge -p "$BASE" "$REMOTE" "$LOCAL" "$MERGED"'
```

## 2. VS Code ↔ Unity 연동

**용도** — Visual Studio에서 VS Code로 전환할 때, Unity가 프로젝트 구조(csproj/sln)를 VS Code에게 알려주고, 디버거를 붙일 수 있게 연결하는 작업.

**사용법**
1. Unity 에디터: `Edit > Preferences > External Tools > External Script Editor`를 **Visual Studio Code**로 지정 → 저장하면 `.vscode/settings.json`, `extensions.json`, `launch.json`이 자동 생성됨
2. VS Code에서 프로젝트 폴더를 열고, 추천 확장 설치:
   - `Unity` (`visualstudiotoolsforunity.vstuc`)
   - `C# Dev Kit` (`ms-dotnettools.csdevkit`) — 무료 개인용 로그인 필요
   - `C#` (`ms-dotnettools.csharp`)
3. Unity에서 ▶ Play 상태에서 VS Code 좌측 실행 탭 → "Attach to Unity" → F5로 디버깅 테스트

**주의사항**
- `.vscode/launch.json`에 `"type": "vstuc"` 설정이 있다면 이미 External Editor가 VS Code로 지정된 상태라는 뜻이다.
- C# Dev Kit은 로그인하지 않으면 자동완성/정의로 이동 기능이 계속 안 먹는다.
- 로그에 `Canonical.csproj` 관련 경고나 한글 깨짐이 보여도, 실제 프로젝트 csproj들이 "loaded by C# Dev Kit"으로 뜨면 정상 작동 중인 것이다.

**전체 테마 변경**: `Ctrl+K` → `Ctrl+T`로 색 테마 선택 (`settings.json`에 `"workbench.colorTheme"`로 저장됨)

## 3. ScriptableObject 기초

**사용 목적** — MonoBehaviour는 씬의 GameObject에 묶여야 하지만, ScriptableObject는 독립된 에셋 파일이라 씬과 무관하게 데이터를 저장하고 여러 오브젝트가 공유할 수 있다. "로직과 데이터의 분리"가 핵심이다.

**사용처** — 무기/몬스터/아이템 스탯 테이블, 전역 설정값, 이벤트 채널, 대화/퀘스트 데이터

**사용법**
```csharp
// 1. 데이터 정의
[CreateAssetMenu(fileName = "NewWeapon", menuName = "Data/Weapon")]
public class WeaponData : ScriptableObject
{
    public string weaponName;
    public int damage;
    public float attackSpeed;
}
```
```csharp
// 2. 사용하는 쪽
public class Player : MonoBehaviour
{
    [SerializeField] private WeaponData currentWeapon;
    void Attack() => Debug.Log($"{currentWeapon.weaponName}로 {currentWeapon.damage} 데미지!");
}
```

**응용 — 이벤트 채널 패턴**
```csharp
[CreateAssetMenu(menuName = "Events/GameEvent")]
public class GameEvent : ScriptableObject
{
    private event Action listeners;
    public void Raise() => listeners?.Invoke();
    public void Register(Action listener) => listeners += listener;
    public void Unregister(Action listener) => listeners -= listener;
}
```

**주의사항**
- 런타임에 SO 필드를 직접 수정하면 **에디터 원본 에셋 값이 영구히 바뀐다.** 개인별로 달라지는 값은 `Instantiate(originalSO)`로 복제해서 쓴다.
- 씬의 특정 GameObject를 SO 필드에 직접 참조로 저장할 수 없다 (씬 전환 시 참조가 깨짐).
- 클래스만 정의해두고 아직 어디서도 참조하지 않은 상태는 정상이다 — 스키마를 먼저 설계하고 나중에 연결하는 흔한 작업 순서다.

> SO를 값이 수정되면 영구히 바뀌는 특성 때문에 보통 "읽기 전용"으로만 쓴다고 생각하기 쉽지만, 실제로는 그 외에도 여러 활용 패턴이 있다 → 4장에서 심화로 다룬다.

## 4. ScriptableObject 심화 — 읽기 전용 필드 설계

### 4-1. 람다(식 본문) 문법과 정규 문법의 관계

`=>` 문법은 "식 본문 멤버(Expression-bodied member)"라는 C# 축약 문법으로, 아래 두 코드는 완전히 동일하게 동작한다.

```csharp
// 람다(축약형)
public int Damage => damage;

// 정규 문법 (완전히 동일한 의미)
public int Damage
{
    get { return damage; }
}
```

### 4-2. 자주 하는 실수 두 가지

| 코드 | 문제 |
|---|---|
| `public int attackSpeed => attackSpeed;` | 필드와 프로퍼티 이름이 같으면 **자기 자신을 호출하는 무한 재귀** → `StackOverflowException` |
| `public int damage { get; }` | 값을 넣어줄 생성자가 없어서 **항상 0으로 고정**됨 (죽은 필드) |

**해결** — 필드와 프로퍼티는 반드시 이름이 달라야 한다.
```csharp
[SerializeField] private int attackSpeed;   // 필드
public int AttackSpeed => attackSpeed;       // 프로퍼티 (이름 다르게)
```

### 4-3. 네 가지 필드 작성 방식 비교

| 작성 방식 | 인스펙터 노출 | 외부 읽기 | 외부 쓰기 |
|---|---|---|---|
| `public int damage;` | O | O | O (위험 — 아무나 수정 가능) |
| `public int damage { get; }` | X | O (항상 기본값) | X |
| `[SerializeField] private int damage;` + `public int Damage => damage;` | O | O | X (안전) |
| `[field: SerializeField] public int Damage { get; private set; }` | O | O | X (안전, 더 간결) |

**`[field: SerializeField]` 문법** — 자동 구현 프로퍼티 뒤에 컴파일러가 몰래 만드는 백킹 필드에 직접 `[SerializeField]`를 붙이는 문법(C# 7.3+). 단, **식 본문 프로퍼티(`=>`)에는 백킹 필드가 없어서 이 문법이 적용되지 않는다** — 그런 경우엔 직접 private 필드를 만들어야 한다.

### 4-4. SO는 읽기 전용 데이터만을 위한 게 아니다 — 4가지 활용 패턴

| 패턴 | 목적 | 값 변경 |
|---|---|---|
| 정적 데이터 | 디자이너용 설정값 (무기 스탯 등) | 읽기 전용이 정석 |
| 런타임 변수 (Runtime Variable) | 서로 무관한 시스템끼리 값 공유 (체력바 ↔ 데미지 시스템) | 의도적으로 쓰기 허용 — 단, 플레이 종료 후 값이 에디터에 영구히 남는 위험 있음 |
| 이벤트 채널 (Event Channel) | 신호 전파 (Raise/Register) | 값이 아니라 호출 |
| Runtime Set | 활성 오브젝트 목록 공유 (씬에 남은 적 수 등) | 등록/해제 (`OnEnable`/`OnDisable`에서 Add/Remove) |
| **전략 패턴 (Strategy)** | 교체 가능한 로직 자체를 에셋으로 | 메서드가 핵심 (아래 9장) |

## 5. Physics 기반 이동 (Rigidbody)

**사용 목적** — `transform.position`으로 직접 이동시키는 대신, 물리 엔진에게 이동/충돌 계산을 맡긴다.

**최종 코드 (Input System + Rigidbody 이동)**
```csharp
[RequireComponent(typeof(Rigidbody))]
public class PlayerMove : MonoBehaviour
{
    private PlayerController controller;
    private Rigidbody rb;
    private Vector2 moveInut;
    [SerializeField] private float speed = 3;

    private void Awake()
    {
        rb = GetComponent<Rigidbody>();
        controller = new PlayerController();
        rb.constraints = RigidbodyConstraints.FreezeRotationX | RigidbodyConstraints.FreezeRotationZ;
    }

    private void OnEnable()
    {
        controller.Player.Move.Enable();
        controller.Player.Move.performed += Move;
        controller.Player.Move.canceled += Move;
    }

    private void OnDisable()
    {
        controller.Player.Move.Disable();
        controller.Player.Move.performed -= Move;
        controller.Player.Move.canceled -= Move;
    }

    private void FixedUpdate() => Move();

    private void Move()
    {
        Vector3 moveVector = new Vector3(moveInut.x, 0, moveInut.y);
        // FixedUpdate 안에서는 반드시 fixedDeltaTime 사용
        rb.MovePosition(rb.position + moveVector * speed * Time.fixedDeltaTime);
    }

    private void Move(InputAction.CallbackContext callbackContext)
    {
        moveInut = callbackContext.ReadValue<Vector2>();
    }
}
```

**주의사항**
- 물리 이동은 반드시 `FixedUpdate()` + `Time.fixedDeltaTime` 조합으로 처리 (`Update()` + `Time.deltaTime` 조합과 섞이면 안 됨).
- `transform.position`으로 직접 이동시키면 충돌이 깨지므로 반드시 `rb.MovePosition` 사용.

## 6. Raycast / OverlapSphere 활용 (+ 점프 구현)

**사용 목적** — "지금 이 위치·방향에 뭐가 있는지" 즉석에서 물어보는 물리 쿼리. 점프 가능 여부 외에도 활용처가 다양하다.

| 용도 | 함수 | 비고 |
|---|---|---|
| 바닥 체크 (점프) | `Physics.Raycast` (아래 방향, 짧은 거리) | 아래 6-1 참고 |
| 총알 명중 판정 | `Physics.Raycast` (전방, 사거리) | 즉발형 무기 전용 |
| 상호작용 감지 | `Physics.Raycast` (시야 방향) | 아래 8장 참고 |
| 적 시야(FOV) 판정 | 각도 계산 + `Physics.Raycast` | 시야각+장애물까지 확인 |
| 범위 감지 (폭발/어그로) | `Physics.OverlapSphere` | 한 점이 아니라 반경 전체 검사 |

**예시 — 총알 명중 판정**
```csharp
void Shoot()
{
    if (Physics.Raycast(muzzle.position, muzzle.forward, out RaycastHit hit, attackRange, enemyLayer))
        hit.collider.GetComponent<Health>()?.TakeDamage(damage);
}
```

**예시 — 적 시야 판정(FOV)**
```csharp
bool CanSeePlayer()
{
    Vector3 dirToPlayer = (player.position - transform.position).normalized;
    float angle = Vector3.Angle(transform.forward, dirToPlayer);
    if (angle < viewAngle * 0.5f && Vector3.Distance(transform.position, player.position) < viewRadius)
    {
        if (!Physics.Raycast(transform.position, dirToPlayer, out RaycastHit hit, viewRadius, obstacleLayer))
            return true;
    }
    return false;
}
```

**예시 — 폭발 범위 피해**
```csharp
void Explode()
{
    Collider[] hits = Physics.OverlapSphere(transform.position, explosionRadius, damageableLayer);
    foreach (var hit in hits)
        hit.GetComponent<Health>()?.TakeDamage(explosionDamage);
}
```

**주의사항 — `OverlapSphere`/`Raycast`가 아무것도 못 찾을 때 체크리스트**
1. **LayerMask가 `Nothing`으로 비어있는지** — 인스펙터에서 필터용 LayerMask를 안 만지면 기본값이 `Nothing`이라 무조건 빈 배열/미검출
2. **대상 오브젝트 자체의 Layer가 안 바뀌었는지** — 필터는 맞게 설정했는데 정작 대상 오브젝트의 Layer가 `Default`인 경우
3. **거리(range/radius)가 너무 작은지**
4. **Collider와 로직 컴포넌트가 다른 GameObject(부모-자식)에 있는지** — 11장 참고

### 6-1. 점프 구현 (Raycast 바닥 체크 + Rigidbody)

```csharp
[Header("Jump")]
[SerializeField] private float jumpForce = 5f;
[SerializeField] private Transform groundCheck;
[SerializeField] private float groundCheckDistance = 0.2f;
[SerializeField] private LayerMask groundLayer;

private bool isGrounded;
private bool wantsToJump;

private void OnEnable()
{
    controller.Player.Jump.Enable();
    controller.Player.Jump.performed += OnJump;
}

private void FixedUpdate()
{
    isGrounded = Physics.Raycast(groundCheck.position, Vector3.down, groundCheckDistance, groundLayer);
    Move();

    if (wantsToJump && isGrounded)
        rb.AddForce(Vector3.up * jumpForce, ForceMode.Impulse);
    wantsToJump = false;
}

private void OnJump(InputAction.CallbackContext callbackContext) => wantsToJump = true;
```

**주의사항**
- 입력 콜백에서 바로 힘을 주지 않고 `wantsToJump` 플래그만 세운 뒤 `FixedUpdate`에서 소비 — 물리 스텝과 입력 타이밍을 맞추기 위함.
- `groundCheck`는 캐릭터 발밑 위치에 빈 자식 오브젝트로 만들어 연결.
- 추가 개선 아이디어: **Coyote Time**(바닥에서 떨어진 직후 잠깐 점프 허용) — 게임 감(Game Feel)을 다듬을 때 적용.

## 7. Animator 연동

**사용 목적** — if문으로 애니메이션을 직접 관리하는 대신, 상태 전환 규칙을 시각적 그래프로 분리하고 코드는 조건 값만 넘겨준다.

```csharp
[SerializeField] private Animator animator;

private void FixedUpdate()
{
    isGrounded = Physics.Raycast(groundCheck.position, Vector3.down, groundCheckDistance, groundLayer);
    Move();

    if (wantsToJump && isGrounded)
    {
        rb.AddForce(Vector3.up * jumpForce, ForceMode.Impulse);
        animator.SetTrigger("Jump"); // 점프 "순간"에만 호출
    }
    wantsToJump = false;

    animator.SetFloat("Speed", moveInut.magnitude);
    animator.SetBool("IsGrounded", isGrounded);
}
```

| 전환 | 조건 |
|---|---|
| Idle → Run | `Speed > 0.1` |
| Run → Idle | `Speed < 0.1` |
| Any State → Jump | `Jump` 트리거 |
| Jump → Idle/Run | `IsGrounded == true` |

**주의사항** — `bool`/`float`은 매 프레임 갱신해도 되지만, `trigger`는 발동 순간에만 호출해야 한다 (매 프레임 호출 시 애니메이션이 계속 끊김). 전환에 "Exit Time"이 켜져 있으면 즉각 반응하지 않으니 이동/점프 전환에는 꺼두는 것을 권장한다.

## 8. 상호작용 시스템 (IInteractable)

**사용 목적** — 문/아이템/NPC처럼 서로 다른 동작을 공통 인터페이스로 묶어, 감지 스크립트가 대상의 구체적인 타입을 몰라도 되게 설계.

```csharp
// 공통 규격
public interface IInteractable
{
    string PromptText { get; }
    void Interact(GameObject interactor);
}
```
```csharp
// 구현 예시
public class Door : MonoBehaviour, IInteractable
{
    public string PromptText => "문 열기";
    private bool isOpen;
    public void Interact(GameObject interactor) => isOpen = !isOpen;
}
```
```csharp
// 감지 + 실행
public class PlayerInteractor : MonoBehaviour
{
    private PlayerController controller;
    [SerializeField] private Transform interactionOrigin;   // 보통 메인 카메라
    [SerializeField] private float interactRange = 3f;
    [SerializeField] private LayerMask interactableLayer;
    [SerializeField] private GameObject promptUI;            // 상호작용 UI 패널
    [SerializeField] private TMPro.TextMeshProUGUI promptText;
    private IInteractable currentTarget;

    private void Awake() => controller = new PlayerController();

    private void OnEnable()
    {
        controller.Player.Interact.Enable();
        controller.Player.Interact.performed += OnInteractInput;
    }

    private void Update()
    {
        if (Physics.Raycast(interactionOrigin.position, interactionOrigin.forward,
                out RaycastHit hit, interactRange, interactableLayer)
            && hit.collider.TryGetComponent(out IInteractable interactable))
        {
            currentTarget = interactable;
            promptUI.SetActive(true);
            promptText.text = interactable.PromptText;
        }
        else
        {
            currentTarget = null;
            promptUI.SetActive(false);
        }
    }

    private void OnInteractInput(InputAction.CallbackContext ctx) => currentTarget?.Interact(gameObject);
}
```

**필드 설명**

| 필드 | 설명 |
|---|---|
| `interactionOrigin` | Raycast 시작 위치/방향 (메인 카메라 Transform 권장) |
| `interactRange` | 상호작용 가능 최대 거리 |
| `interactableLayer` | 상호작용 대상 레이어만 필터링 |
| `promptUI` / `promptText` | 프롬프트 UI 패널 / 실제 텍스트 컴포넌트 |
| `currentTarget` | 현재 바라보는 대상 캐시. 입력 시점엔 새로 Raycast 안 쏘고 이 값만 사용 |

**Input Actions 설정**
1. `.inputactions` 에셋 → `Player` 맵 → `+`로 `Interact` 액션 추가 (Button 타입)
2. 바인딩 추가 → `E [Keyboard]` 검색해서 연결
3. 반드시 **Save Asset**해야 생성된 코드에 `controller.Player.Interact`가 반영됨

**UI 생성 팁**
1. Canvas 자식으로 빈 오브젝트(`InteractPrompt`) 생성 → `promptUI`에 연결
2. 그 자식으로 TextMeshPro 텍스트 생성 → `promptText`에 연결 (최초 사용 시 `Import TMP Essential Resources` 필요)
3. `InteractPrompt`는 기본 비활성화 상태로 시작

## 9. 전략 패턴 (Strategy Pattern) + Context Object 패턴

### 9-1. 기본 형태 — 이동 전략 (Chase / Flee)

```csharp
public abstract class MoveStrategy : ScriptableObject
{
    public abstract Vector3 GetMoveDirection(Transform self, Transform target);
}

[CreateAssetMenu(menuName = "AI/Strategy/Chase")]
public class ChaseStrategy : MoveStrategy
{
    public override Vector3 GetMoveDirection(Transform self, Transform target)
        => (target.position - self.position).normalized;
}
```
호출자(`Enemy`)는 어떤 전략이 꽂혀있든 항상 같은 코드로 호출한다.
```csharp
Vector3 dir = strategy.GetMoveDirection(transform, player);
transform.position += dir * speed * Time.deltaTime;
```

### 9-2. 한계 발견 — 전략마다 필요한 매개변수가 다르면?

Patrol(순찰)은 `target` 하나가 아니라 **여러 웨이포인트 + 현재 진행 인덱스**가 필요하다. 매개변수를 늘리려면 전략 종류에 따라 다른 시그니처가 필요해지고, 결국 호출자 쪽에서 `if (strategy is PatrolStrategy) ...` 같은 타입 분기가 생겨버린다 — 전략 패턴을 쓰는 이유 자체가 무너지는 상황이다.

### 9-3. 해결 — Context(매개변수 객체) 패턴

메서드에 필요한 값을 하나하나 넘기는 대신, **모든 전략이 필요로 할 수 있는 데이터를 담은 상자 하나**를 넘긴다. 각 전략은 자기가 필요한 필드만 꺼내 쓰고 나머지는 무시한다.

```csharp
public class MoveContext   // SO가 아닌 순수 C# 클래스
{
    public Transform Self;
    public Transform Target;
    public Transform[] Waypoints;
    public int CurrentWaypointIndex;   // 상태(state)는 여기 — SO 안에 두지 않음!
}

public abstract class MoveStrategy : ScriptableObject
{
    public abstract Vector3 GetMoveDirection(MoveContext context);
}
```

```csharp
[CreateAssetMenu(menuName = "AI/Strategy/Patrol")]
public class PatrolStrategy : MoveStrategy
{
    [SerializeField] private float arriveThreshold = 0.2f;

    public override Vector3 GetMoveDirection(MoveContext context)
    {
        Transform point = context.Waypoints[context.CurrentWaypointIndex];
        Vector3 dir = point.position - context.Self.position;

        if (dir.magnitude < arriveThreshold)
            context.CurrentWaypointIndex = (context.CurrentWaypointIndex + 1) % context.Waypoints.Length;

        return dir.normalized;
    }
}
```

**핵심 — 왜 인덱스를 Context에 두는가**: `PatrolStrategy` 에셋 하나를 여러 적이 공유해서 쓰는데, 만약 "지금 몇 번째 웨이포인트로 가는 중인지"를 `PatrolStrategy` 안에 저장하면, 그 값을 공유하는 모든 적이 서로 인덱스를 덮어써서 꼬인다. `MoveContext`는 `Enemy.Awake()`에서 **각자 새로 `new`로 만드는** 순수 C# 클래스라, 상태를 여기 두면 적마다 완전히 분리된다.

### 9-4. `%`(나머지 연산자)로 순환시키는 관용구

```csharp
context.CurrentWaypointIndex = (context.CurrentWaypointIndex + 1) % context.Waypoints.Length;
```
웨이포인트가 3개일 때: `0→1`, `1→2`, `2→(2+1)%3=0`(다시 처음으로). `if (index >= length) index = 0;` 같은 분기 없이 배열 순환을 표현하는 흔한 방법이다.

### 9-5. 필드 기본값 관련 — SO와 일반 클래스의 차이

`MoveContext`는 `new`로 만드는 평범한 C# 클래스라서, 명시적으로 값을 안 넣은 `int` 필드는 자동으로 `0`이 된다. **이건 ScriptableObject의 "도메인 리로드 시 기본값이 안 먹히는" 문제와는 무관하다** — SO는 Unity의 특수 직렬화 시스템을 거치지만, 순수 C# 클래스는 평범한 C# 규칙 그대로 동작하기 때문이다.

## 10. 아이템 사용 효과 실습 — Context 패턴 두 번째 사례

### 10-1. 왜 "반환값 + 통일된 적용"이 안 통하는가

Move 전략은 방향(Vector3)을 반환하면 호출자가 항상 같은 방식(`위치 += 방향`)으로 적용했지만, 아이템 효과는 다르다.
- 힐 → 회복량(int) 반환 후 `target.Heal(amount)` 호출 필요
- 텔레포트 → 목적지(Vector3) 반환 후 `transform.position = pos` 필요
- 폭탄 → 심지어 호출자가 아니라 **폭탄이라는 별개의 오브젝트**가 자기 몫을 수행해야 함

**결론 — 적용 방식이 전략마다 다르면, 그 적용까지 전략 내부에서 끝내야 한다.**

```csharp
public abstract class ItemEffect : ScriptableObject
{
    public abstract void UseItem(ItemUseContext context);   // 반환값 없음
}
```

각 효과는 반환하지 않고 직접 행동을 완료한다.
```csharp
// 힐 — 직접 회복시켜버림
public override void UseItem(ItemUseContext context)
    => context.target.GetComponent<IHealAble>()?.Heal(context.healAmount);

// 텔레포트 — 직접 위치를 옮겨버림
public override void UseItem(ItemUseContext context)
    => context.self.position = context.target.position;

// 폭탄 — "폭탄을 소환하는 것"까지만 책임짐, 폭발 로직은 Bomb 오브젝트가 소유
public override void UseItem(ItemUseContext context)
{
    GameObject obj = Instantiate(bombObject, context.target.position, Quaternion.identity);
    if (obj.TryGetComponent<Bomb>(out Bomb bomb))
        bomb.Ignite(context.explosionTime, context.damage, context.explosionDistance, context.targetLayer);
}
```

이 원칙은 OOP의 **"Tell, Don't Ask"** — 값을 물어봐서 내가 처리하는 게 아니라, 상대에게 시켜서 알아서 처리하게 하는 것과 같은 맥락이다.

### 10-2. 실습에서 나온 실제 버그들

| 버그 | 원인 | 해결 |
|---|---|---|
| `Destroy(this)` | `this`는 컴포넌트 자신만 가리켜서, GameObject(모델·이펙트)는 씬에 그대로 남음 | `Destroy(gameObject)`로 변경 |
| `obj.TryGetComponent<Bomb>(out Bomb bomb);` 다음 줄에서 바로 `bomb.Ignite(...)` | 반환값(bool)을 검사 안 해서, 프리팹에 `Bomb` 컴포넌트가 없으면 `NullReferenceException` | `if (obj.TryGetComponent<Bomb>(out var bomb)) { bomb.Ignite(...); }` |
| `quaternion.identity` (소문자) | `Unity.Mathematics.quaternion`이라는 별개 타입 — `Instantiate`가 요구하는 `UnityEngine.Quaternion`과 다름 | `Quaternion.identity`(대문자)로 수정 |
| `if(time > explosionTime)`가 `isTrigger`와 무관하게 매 프레임 계산됨 | 당장은 초기값(0>0=false)이라 문제없지만 의도가 불명확 | `if (isTrigger && time > explosionTime)`로 묶기 — `&&`는 단락 평가라 왼쪽이 false면 오른쪽은 계산 자체를 안 함 |
| `new ItemUseContext(a, b, c, ...)` (생성자 방식) | `ItemUseContext`엔 그런 생성자가 없어서(필드만 있음) 컴파일 에러 가능 | 객체 초기화 구문(`new ItemUseContext { target = t, healAmount = 10 }`)으로 변경 — 이름이 명시되어 순서 실수도 방지됨 |
| `OnUseItem(InputAction.CallbackContext context)`에서 매개변수 이름이 필드(`context`)와 같음 | 매개변수가 필드를 가림(shadowing) — `this.context`로만 필드 접근 가능 | 매개변수 이름을 `ctx` 등으로 바꿔서 혼동 방지 |

> `OverlapSphere`가 아무것도 못 찾는 문제의 체크리스트는 6장에 통합되어 있다 (LayerMask/Layer/거리/부모-자식 구조).

## 11. Unity 오브젝트 계층 구조 — 부모(로직) / 자식(모델·콜라이더) 분리

### 11-1. 왜 이렇게 나누는가

```
Enemy_Goblin (빈 오브젝트, 부모)
 ├─ EnemyAI.cs, Health.cs, Rigidbody   ← 로직
 ├─ Model (임포트된 FBX)                ← 시각적인 것
 └─ Hitbox (Collider)                  ← 충돌 판정
```

- 임포트된 모델의 내부 구조(본, 메쉬)를 건드리지 않고 로직을 분리
- 모델 교체가 쉬워짐 (자식만 갈아끼우면 됨)
- 모델의 이상한 피벗 문제를 부모의 깨끗한 Transform으로 회피
- 콜라이더 형태(단순 캡슐/박스)를 실제 메쉬와 다르게 자유롭게 배치 가능

### 11-2. 콜라이더가 자식에 있을 때 컴포넌트 찾는 법

`collider.TryGetComponent<T>()`는 **그 콜라이더가 붙은 오브젝트 자기 자신만** 검사한다. 로직이 부모에 있다면 못 찾는다.

```csharp
// ❌ 자식과 부모가 다른 오브젝트라 못 찾음
collider.TryGetComponent<IDamageable>(out var damageable);

// ✅ 부모 방향으로 계속 올라가며 찾음
IDamageable damageable = collider.GetComponentInParent<IDamageable>();
```

### 11-3. 조상이 여러 단계이거나, 같은 타입이 여러 개 있을 때

| 상황 | 설명 | 해결 |
|---|---|---|
| 부모가 여러 단계로 깊음 | `GetComponentInParent`는 찾을 때까지 계속 위로 올라감 — 문제없음 | 그대로 사용 |
| 조상 중 같은 타입(`IDamageable` 등)이 여러 개 있음 (예: Squad와 Enemy 둘 다 구현) | `GetComponentInParent`는 **가장 가까운 것 하나만** 반환 — 원하는 게 아닐 수도 있음 | `GetComponentsInParent<T>()`(복수형)로 전부 받아 직접 선택, 또는 Hitbox에 소유자 참조를 인스펙터에서 명시적으로 연결(더 견고함) |

### 11-4. 중복 데미지 주의사항

적 하나에 콜라이더가 여러 개(머리/몸통 등) 있으면, 폭발 한 번에 같은 적이 `hits` 배열에 중복으로 걸려 데미지가 여러 번 들어갈 수 있다.
```csharp
var alreadyDamaged = new HashSet<IDamageable>();
foreach (Collider collider in hits)
{
    IDamageable damageable = collider.GetComponentInParent<IDamageable>();
    if (damageable != null && alreadyDamaged.Add(damageable))
        damageable.GetDamage(damage);
}
```
